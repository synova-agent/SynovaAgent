## 一、Synova 是什么

一个**驻扎在企业内部的 AI 诊断 Agent**。

不是 ChatBot。区别：
- ChatBot：你问一句，它答一句。答完就结束了。
- Synova：7×24 运行。自己发现信号，自己启动诊断，自己出报告。**它主动替企业干活。**

核心问题：**这家企业的增长卡在哪里？现在该做什么？**

## 二、谁在用

- **直接用户** = GA（Growth Advisor，增长顾问）。他们有行业经验、有客户资源，但缺系统诊断工具。Synova 帮他们从"靠感觉"变成"靠数据"。1 个 GA 服务 10-20 个客户，就能活得比打工好。
- **最终受益者** = 企业主。部署之后，企业主自己看信号和报告。GA 从日常翻译变成定期深度诊断。

## 三、Synova 怎么工作

**两套系统并行**：

1. **GA 按需诊断**：GA 采访企业主（八维框架）→ 上传文档 → 8 专家并行分析 → HTML 诊断报告
2. **哨兵定时巡检**：25 个哨兵 7×24 自动跑 → 发现异常 → 对比基线 → 信号路由给专家 → 严重信号自动建工单

**8 个专家**（同时看企业的 8 种视角）：
- 战略（方向对吗？）| 组织（人能执行吗？）| 财务（钱够吗？）| 营销（市场对吗？）
- 技术（软件→AI 怎么转？）| 行动（分析完了到底干什么？）
- 商业模式（赚钱机器的结构对吗？）| 知识管理（经验怎么沉淀？）

**7 个监测维度**（25 个哨兵分布在 7 个维度下）：
D1 增长动力 | D2 组织能力 | D3 人+Agent | D4 软件生态 | D5 软件-Agent 适配 | D6 战略健康 | D7 风险预警

## 四、技术骨架

- **五层架构**：L1 交互 → L2 编排 → L3 洞察 → L4 本体 → L5 存储。只能向下依赖相邻层。
- **文件优先**：专家知识在 `.md` 文件里，改文件就改行为，不需要改代码。`POST /api/reload` 5 秒生效。
- **无限扩展**：加新哨兵 = 创建 `xxx-sentinel.ts`（自动注册）。加新专家 = 写 5 个 `.md` 文件 + `registry.register()`。不需要改核心代码。
- **本体层**：17 种节点 + 14 种边 = 企业的"数字孪生"。数据存在图里，专家查询图。

## 六、还没做的（按真实优先级，不是按列表长度）

**P0 — 没有这些不能给 GA 用**：
- 哨兵真实数据流：表建了但空着。需要 GA 实际使用 → 数据自然产生
- 诊断报告质量验证：GA 用过吗？报告准吗？需要真实反馈

**P1 — 演示时有很好，没有也能演示**：
- D5 软件-Agent 适配哨兵（缺 1 个安全边界）
- D6 战略健康哨兵（缺 3 个）
- 一对多对话 + RBAC（多用户的前提）

**P2 — 现在做是过度开发**：
- Docker 部署自动化（等有 3+ GA）
- 18 字段记忆结构（需要真实使用数据）
- 语义缓存（没用户就没流量）

**伪需求 — 听起来重要，实际不是**：
- 完美覆盖 34 个哨兵：没用户的时候，哨兵再多也是空转
- 专家知识自动进化：没真实纠错数据，自动进化 = 自动退化
- 前端 UI：GA 操作台用 API 就行。企业主看板等有企业主用户再说

## 七、我犯过的错

1. **跳过 task-start**：Week 1-2 没跑 task-start.sh。原因：它是人工步骤，没有物理阻断。修复：pre-commit 第 7 项强制检查。
2. **信号路由表硬编码**：Week 2 加了 25 条硬编码路由。应该从哨兵 config 读。修复：Week 4 重构。
3. **看到跨层违规不修**：遗留了 l1/qa-router.ts 直接 import L4。原因：Agent 自检没有架构问。修复：第 6 问 + pre-commit 第 8 项。
4. **增强哨兵 finding 但不检查数据源**：Week 3-4 增强了 8 个哨兵的 finding 提取，但 D3 数据源根本没接。修复：建表 + 接线。

**这些错的共同根源**：我在"写代码"模式下工作，不是在"做产品"模式下工作。

## 八、Loop Engineering 需要成为什么

当前的 v3.0 是**代码质量系统**。它检查：
- 语法（as any、空 catch）
- 安全（secrets）
- 接线（有调用方）
- 架构（不跨层）

但**不检查产品对齐**。我可以在 pre-commit 全通过的情况下做出完全偏离产品目标的东西。

**v3.2 需要加的**：

1. **产品对齐检查**（task-start 后、写代码前）：
   - 这个任务在产品的哪一块？
   - 做完了用户能看到什么？
   - 有什么是可以不做的？
   - 上一个类似任务犯过什么错？

2. **全局状态感知**（每次任务启动时自动注入）：
   - 我们现在在 Phase 0。当前分支 feat/prompt-architecture。
   - 已完成的：全链路通、D1/D3 增强、架构可扩展。
   - 还没做的：D5/D6 哨兵、真实数据流、RBAC。
   - 最近犯的错：[动态从 memory/ 读取]

3. **决策建议**（decide-next.sh 升级）：
   - 不是永远显示"工作区干净"
   - 而是读取 全量对齐手册 + 代码实际 + memory/ → 给出具体的下一步建议

这不是大工程。三个文件：
- `.claude/PRODUCT-BRIEF.md`（本文档 — 每次任务前重读）
- `scripts/workflow/scope-check.sh`（产品对齐 4 问 — task-start 后自动触发）
- `scripts/workflow/decide-next.sh`（升级 — 接实际数据）
