# api-and-interface-design — 好接口让对的事容易、错的事困难

> 来源：addyosmani/agent-skills（MIT）· `skills/api-and-interface-design/SKILL.md` @ 1401c8b8。
> 本文件是中文改写版（结构保留、按 Synova 语境收敛），许可与原文以上游仓库为准。

## 何时用
设计新端点；定义模块边界或跨团队契约；定义组件 props；设计会决定 API 形状的数据库 schema；**修改既有公开接口**。

## 两条底层规律

**Hyrum 定律**：只要有足够多的使用者，你系统里**所有可观测行为**都会被某人依赖——不管契约里写没写。
⇒ ① 有意识地决定暴露什么（每个可观测行为都是潜在承诺）；② 不泄露实现细节；③ **设计时就规划弃用**；④ 契约测试也不够——"安全"的改动照样可能弄坏依赖未文档化行为的真实用户。

**单版本规则**：不要让消费者在同一 API/依赖的多个版本之间做选择（菱形依赖）。**扩展，而不是分叉**。

## 六条原则

1. **契约优先**：先定义接口再实现，契约即规格。
   ```ts
   interface TaskAPI {
     createTask(input: CreateTaskInput): Promise<Task>;   // 返回服务端生成字段
     listTasks(params: ListTasksParams): Promise<PaginatedResult<Task>>;
     getTask(id: TaskId): Promise<Task>;                  // 找不到抛 NotFoundError
     updateTask(id: TaskId, input: UpdateTaskInput): Promise<Task>; // 局部更新
     deleteTask(id: TaskId): Promise<void>;               // 幂等：已删也算成功
   }
   ```
2. **错误语义统一**：全站一种错误策略，形状一致 `{ error: { code, message, details? } }`；状态码语义固定 400 数据非法 / 401 未认证 / 403 无授权 / 404 不存在 / 409 冲突 / 422 语义校验失败 / 500 服务端（**绝不外泄内部细节**）。**不许混用**：有的抛异常、有的返回 null、有的返回 `{error}`。
3. **只在边界校验**：内部代码信任类型；外部输入进入系统处校验（路由处理器、表单、**第三方响应——永远当不可信**、环境变量加载）。**不该校验的地方**：共享类型契约的内部函数之间、已被校验数据调用的工具函数、刚从自己数据库取出的数据。
4. **只增不改**：新字段用可选方式加（`priority?: 'low'|'medium'|'high'`）；**不改既有字段类型、不删字段**。
5. **命名可预测**：REST 用复数名词、无动词（`GET /api/tasks`）；query 参数 camelCase；响应字段 camelCase；布尔字段 `is/has/can` 前缀；枚举 UPPER_SNAKE。
6. **接受 `Idempotency-Key` 只是契约，兑现它才是实现**——服务器接受却处理不当，比不接受更糟（客户端会误以为重试安全）。四条硬细则：
   - **键从"意图"派生，不从"尝试"派生**：`randomUUID()` ✗（每次重试都是新键＝重复扣款）；`${userId}:${amount}` ✗（两笔合法的 50 元被合并成一笔）；`${orderId}:${Date.now()}` ✗（时间戳＝戴帽子的 UUID）。✓ 客户端生成一次并在重试中复用，或 `charge:v1:${orderId}` 这类由不可变标识派生的键。**键来自客户端或发起事件，绝不来自做重试的那一层。**
   - **原子认领，"先查后写"是竞态**：`if (!await db.exists(key)) { charge(); insert(); }` ✗（两个并发重试都读到"没见过"）。✓ 靠唯一约束裁决：`insert({key, state:'in_progress', requestHash})` 撞唯一键 → 重放或拒绝；**唯一约束就是机制本身**，无法在一次操作里保证唯一性的存储不配承载它。
   - **守 payload**：同键不同 body 是客户端 bug，必须**响亮失败**（422），不许把第一次的响应当第二次的答案返回。
   - **in-flight 重复要有明确策略**：拒绝 409 / 有界等待 / 返回 202 + 状态 URL —— 三选一，且是主动选择。**绝不能因为"第一个看起来卡住了"就放第二个进来**。
   - **每次调用有三种结局：成功、失败、未知**。超时不告诉你效果是否已发生 ⇒ 调出去**之前**先记录意图，崩溃后才有"待解决"的证据，而不是被静默重试的扣款。
   - **保留期按最长重试链设置**，不是按磁盘成本：键必须活过所有可能重复投递同一意图的路径（含一周后才重放的死信队列、供应商争议窗口）。**24 小时的键 TTL 配 7 天的 DLQ ＝ 等待发生的重复。**

## REST 模式速查
`GET/POST /api/tasks`、`GET/PATCH/DELETE /api/tasks/:id`、子资源 `/api/tasks/:id/comments`；列表**必须分页**（`?page&pageSize&sortBy&sortOrder` → `{ data, pagination:{ page,pageSize,totalItems,totalPages } }`）；筛选用 query 参数；局部更新用 PATCH（只改传入字段）。

## TypeScript 模式速查
- **可辨识联合表达变体**：`{type:'completed'; completedAt: Date; completedBy: string}` → 消费者可类型收敛。
- **输入/输出分离**：Input＝调用方给的；Output＝系统返回的（含服务端生成字段）。
- **品牌类型防串用 ID**：`type TaskId = string & { readonly __brand: 'TaskId' }`。

## 反合理化对照表

| 借口 | 现实 |
|---|---|
| "文档以后再补" | 类型**就是**文档，先定义 |
| "暂时不需要分页" | 有人到 100+ 条的那一刻就需要，一开始就加 |
| "PATCH 麻烦，用 PUT 吧" | PUT 每次都要求完整对象；PATCH 才是客户端真正想要的 |
| "需要时再做版本" | 没有版本机制的破坏性变更直接弄坏消费者，一开始就为扩展设计 |
| "没人用那个没文档的行为" | Hyrum 定律：可观测即被依赖，每个公开行为都是承诺 |
| "维护两个版本就行" | 多版本＝维护成本翻倍 + 菱形依赖，优先单版本 |
| "内部 API 不需要契约" | 内部消费者也是消费者；契约防止耦合、支持并行开工 |
| "接受 Idempotency-Key 头就够了" | 头是契约，把键和结果一起存下来才是实现 |
| "我们的队列保证恰好一次" | 跨消费者崩溃没有恰好一次：broker 的 ack 与你的副作用不在一个事务里。按"至少一次 + 幂等处理"设计 |
| "重复请求很少见" | 重复是**相关**的：依赖降级时重试激增——正是重复最可能也最贵的时刻 |

## 红旗
- 端点随条件返回不同形状；错误格式不统一
- 校验散落在内部代码而非边界
- 对既有字段做破坏性变更（改类型、删字段）
- 列表端点没有分页；REST URL 里出现动词（`/api/createTask`）
- 第三方响应未校验就使用
- 幂等键"先 SELECT 再 INSERT"——那是竞态不是守卫
- 幂等键由 UUID / 时间戳 / 每次尝试重新生成的东西派生
- 同键不同 body 被静默返回第一次的响应
- 键保留期短于最长的重投递路径

## 验收清单
- [ ] 每个端点都有类型化的输入/输出 schema
- [ ] 错误响应全站单一格式
- [ ] 校验只发生在系统边界
- [ ] 列表端点支持分页
- [ ] 新字段是追加且可选（向后兼容）
- [ ] 命名约定在所有端点一致
- [ ] API 文档/类型与实现同批提交
- [ ] 改状态的端点要么兑现幂等键，要么显式标注"重试不安全"
- [ ] 键在**一次原子操作**里认领，由唯一约束守护
- [ ] 同键不同 payload **响亮失败**，不重放错误响应
- [ ] in-flight 重复的响应是主动选择（409 / 等待 / 202）
- [ ] 键保留期长过最长重试路径（含死信重放）
