# code-simplification — 行为不变地降复杂度

> 来源：addyosmani/agent-skills（MIT）· `skills/code-simplification/SKILL.md` @ 1401c8b8。
> 本文件是中文改写版（结构保留、按 Synova 语境收敛），许可与原文以上游仓库为准。

## 目标

在**精确保留行为**的前提下降低复杂度。目标不是行数更少，而是**更容易读、改、调**。
每一次简化都要过一道检验："新人理解这版，会比原版更快吗？"

## 何时用 / 何时不用

**用**：功能已跑通、测试通过，但实现明显比需要的重；评审被指出可读性/复杂度问题；遇到深嵌套、超长函数、含糊命名；重构赶工代码；合并后出现重复与不一致。

**不用**：代码本来就清楚（别为简化而简化）；**你还没搞懂它在干什么**（先理解再简化）；性能关键路径且"更简单"的版本实测更慢；这个模块马上要整体重写（简化一次性代码＝浪费）。

## 五原则

1. **精确保留行为**：输入输出、副作用、顺序、错误行为、边界全部不变。每次改动前自问：所有输入下输出一致吗？错误路径一致吗？副作用与顺序一致吗？**现有测试不改一行还全绿吗？**
2. **跟随项目约定**：简化是让代码更贴合本仓库，不是推行你的偏好。先读 `CLAUDE.md`/项目规范，再看邻近代码怎么写（import 顺序、函数风格、命名、错误处理、类型标注深度）。**破坏项目一致性的"简化"是 churn，不是简化。**
3. **清晰优先于聪明**：需要停顿一下才能解析的紧凑写法，不如显式写法。嵌套三元 → if/else 或映射表；链式 reduce 内联逻辑 → 具名中间步骤。
4. **保持平衡（防过度简化）**：过度内联（把有名字的概念抹掉，调用点更难读）；把不相关逻辑合并成一个复杂函数；删掉为扩展性/可测性存在的抽象；**按行数优化**——行数不是目标。
5. **限定改动范围**：默认只简化本次改动涉及的代码；不做"顺手"式无关重构（除非明确被要求扩大范围）。无范围的简化＝噪声 diff + 无意回归。

## 四步流程

### 第 1 步 · 先理解再动手（Chesterton's Fence）
动手前必须能回答：这段代码的职责是什么？谁调用它、它调用谁？边界与错误路径有哪些？有测试定义它的预期行为吗？**它当初为什么这么写**（性能？平台限制？历史原因？）——查 `git blame`。
答不上来＝还没准备好简化，继续读上下文。

### 第 2 步 · 找简化机会（具体信号，不是模糊"坏味道"）

| 结构类 | 信号 | 动作 |
|---|---|---|
| 深嵌套（≥3 层） | 控制流难跟 | 提取守卫子句或辅助函数 |
| 超长函数（≥50 行） | 多重职责 | 拆成有描述性名字的聚焦函数 |
| 嵌套三元 | 需要心智栈 | 改 if/else、switch 或查表 |
| 布尔参数开关 | `doThing(true,false,true)` | 改 options 对象或拆函数 |
| 重复条件 | 同一 if 出现在多处 | 提取成命名谓词 |

| 命名/可读性 | 信号 | 动作 |
|---|---|---|
| 泛化名 | `data` `result` `temp` `val` | 改成描述内容的名字 |
| 缩写 | `usr` `cfg` `btn` | 用完整词（`id`/`url`/`api` 这类通用缩写除外） |
| 误导名 | `get` 却在改状态 | 改名反映真实行为 |
| 解释"是什么"的注释 | `// 计数加一` | 删（代码已够清楚） |
| 解释"为什么"的注释 | `// 这里重试是因为上游在负载下会抖` | **保留**（承载代码表达不了的意图） |

| 冗余 | 信号 | 动作 |
|---|---|---|
| 重复逻辑 | 同样 5+ 行出现在多处 | 提取共享函数 |
| 死代码 | 不可达分支、未用变量、注释掉的块 | 确认真死之后删除（铁律 37） |
| 无价值包装 | 只做转发的 wrapper | 内联，直接调底层 |
| 过度设计 | 工厂的工厂、只有一个策略的策略 | 换成直接写法 |
| 冗余类型断言 | 断言到已推断出的类型 | 删 |

### 第 3 步 · 增量落地
一次只做一处，每处之后跑测试：通过 → 提交/继续；失败 → 回退重想。
**重构与功能/修 bug 必须分开提交**：一个 PR 里既重构又加功能＝两个 PR，拆开。
**500 行规则**：一次重构超过 500 行 → 上自动化（codemod / sed / AST 转换），别手改；这个量级手改易错且难评审。

### 第 4 步 · 验收（退一步看整体）
前后对比：真的更容易懂了吗？引入了与仓库不一致的新模式吗？diff 干净可评审吗？同事会批准吗？**如果"简化"后更难懂或更难评审 → 回退**。不是每次简化尝试都会成功。

## 反合理化对照表

| 借口 | 现实 |
|---|---|
| "能跑，别动它" | 难读的代码在坏掉时同样难修；现在简化＝为以后每次改动省时间 |
| "行数少就是简单" | 一行嵌套三元不比五行 if/else 简单；简单＝理解速度 |
| "顺手把无关代码也简化了" | 无范围简化＝噪声 diff + 意外回归 |
| "类型本身就是文档" | 类型描述结构，不描述意图；好名字比签名更能说明为什么 |
| "这个抽象以后可能有用" | 不要保留投机性抽象：现在没用＝纯复杂度。删掉，需要时再加 |
| "原作者一定有理由" | 也许——查 blame 用 Chesterton's Fence；但累积的复杂度往往没有理由，只是赶工残留 |
| "加功能时顺便重构" | 重构与功能分离；混在一起的改动更难评审、回滚与追溯 |

## 红旗

- 为了让测试通过而改测试（多半是改了行为）
- "简化"后更长、更难跟
- 按自己偏好改名而非项目约定
- **以"代码更干净"为由删掉错误处理**
- 简化自己没完全读懂的代码
- 把多处简化塞进一个巨大难评审的提交
- 未经要求重构本任务范围外的代码

## 验收清单

- [ ] 现有测试**不改一行**全部通过
- [ ] 构建通过且无新增 warning
- [ ] lint/格式化通过（无风格回归）
- [ ] 每处简化都是可评审的增量改动
- [ ] diff 干净，无无关改动
- [ ] 符合项目约定（对照 `CLAUDE.md` 等）
- [ ] 没有删弱任何错误处理
- [ ] 未留下死代码（未用 import、不可达分支）
- [ ] 同事或评审 agent 会认为这是净改进
