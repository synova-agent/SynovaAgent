# north-star-guard — 北星对齐裁决

## 使用时机
① 收到任何 dev doc / 实现方案 / 设计提案时——**先判它对不对齐北星，再谈技术**。
② 自己写完 dev doc 后——提交前自裁决一遍，把偏离扼杀在分发前。

## 输入
- 候选文档（dev doc / 方案，必须带北星 front-matter）
- `PRODUCT-BRIEF.md`（"我们在做什么"的唯一事实源，131 行，先读）

## 四问裁决（逐问，缺一即偏离 —— 问 4 于 2026-09-26 加）

**问 1：服务真实用户场景吗？**
- 文档锚定块的"服务用户"是 PRODUCT-BRIEF 里的真实用户（GA / 企业主）吗？
- 还是凭空造了一个没人要的功能？对不上的 → 偏离。

**问 2：让模块更接近终态吗？**
- 文档的"模块终态"与 PRODUCT-BRIEF 里该模块的定位一致吗？
- 这个改动是"朝终态走一步"还是"横向加一个无关的东西"？横向的 → 偏离。

**问 3：会不会让产品"变成另外的样子"？**
- 做完这个，Synova 还是"驻扎企业、主动诊断、为增长服务"的 Agent 吗？
- 还是悄悄变成了 ChatBot / 报表工具 / 别的产品？变味 → 偏离（最高优先级）。


**问 4：这条约束会拦截哪条既有工作流？**（2026-09-26 加，来源 K3 文档契约审计 P0-1）
- **凡"约束类条款"**（白名单 / 禁令 / 必须 / 阻断 / 门禁），必须**列出它会拦截的现有工作流，并逐条确认**。
- 实测教训：文档契约的「入库白名单」本意是挡"过程文档"，
  却**同时挡住了「加目录就能加专家/技能」这个产品核心机制**（CLAUDE.md「文件驱动扩展」）。
  ⇒ **规范类文档不能只看它想挡什么，还要看它会误伤什么。**
- 答不出"会拦截谁" ⇒ **不得生效**（先补这条再放行）。

## 输出

- **对齐**：四问全过 → 放行，写明"对齐北星 §X + 终态推进点"。
- **偏离**：任一问不过 → 打回，附理由 + PRODUCT-BRIEF 引用行号 + 改哪里。
- 裁决是**物理判断**（对照文档原文），不是感觉；引用必须给到具体章节。

## 红线
- 这是方向裁决，不是技术 review——技术问题走 D333 决策模式，不在这里判。
- 若文档没有北星 front-matter → 直接打回（锚定块是硬前提，缺了无法裁决）。
- 拿不准方向 = 升级创始人（产品方向是创始人拥有的领域）。
