## Q0: 定位 — 项目拼图 + 文件审计
### a) 项目拼图
本任务在 **`scripts`/CI 控制塔层**（非 L1–L5 产品代码）。改的是 CI 触发与并发控制：`.github/workflows/ci.yml` 的 `on:` 与顶层 `concurrency`。
### b) 文件审计
- `grep -n 'concurrency' .github/workflows/*.yml` → **零命中**（全仓 5 个 workflow 都没有并发控制）
- `.github/workflows/ci.yml:3-7` → `on.push.branches: [main, feat/*]`；`on.pull_request.branches: [main]`
- 实测放大器：同分支反复 push 无取消 ⇒ `feat/d962-2a-merge` 独占 18 条 run；全队列一度 38 queued 不消费（CTO 2026-09-26 定位 N12）
### c) 决策
复用 GitHub Actions 原生 `concurrency`（不新建机制、不加脚本）；`on.push.branches` 收窄为 `[main]`（feature 分支的验证由 `pull_request` 面覆盖）。

## Q1: 调研 — 业界最佳实践 / Anthropic 决策链 / memory 历史教训
- **GitHub 官方**：`concurrency.group` + `cancel-in-progress: true` 是"同 ref 只保留最新 run"的标准做法；官方文档明确其用途正是"避免同一分支的排队堆积"。
- **Anthropic 工程基线**：CI 反馈应"快且唯一"——同一变更的过期 run 无信息价值，取消它是减少等待而非减少保护。
- **memory 历史教训**：本项目 M 模式里 **M5（环境依赖门禁）/ M4（执行证据链断裂）** 同族；N12 的教训是"**门禁/CI 自身成为阻塞源**"，与蓝图 §Q7 伪减负第 9 型（双入口）同源。
- **决策参考系**：第一性原理（同一 ref 的多条 run 互为冗余）+ GitHub 官方范式 + 本项目实测（38 queued 不消费）→ **结论：加 concurrency；push 触发收窄**。

## Q3: 验收 — 入口 → 交互 → 结果
入口：向本分支 push / 开或更新 PR。
处理：GitHub Actions 按 `concurrency.group` 归组；同 ref 新 run 到达时取消旧的 in-progress/queued run。
结果：① 同分支连推 3 次 ⇒ 前两次 `cancelled`、只留最新；② push feature 分支 ⇒ **不触发** CI；③ 开/更新 PR ⇒ 触发。
