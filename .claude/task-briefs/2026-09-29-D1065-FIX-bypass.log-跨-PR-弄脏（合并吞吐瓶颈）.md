## Q1: 调研 — 实测证据（D1061 批次，2026-09-29）
1. **GitHub 的合并后端尊重 `merge=union`**：main 上该文件 1881 行 → 1895 行（= 并入两侧各自新增都在），
   实测于 #875/#867 连续合并后（`git show <sha>:.claude/bypass.log | wc -l`）。
2. **GitHub 的可合并性计算不尊重 `merge=union`**：
   - 同一 PR 在 main 前移后变 `mergeable=False / state=dirty`（#880 实测：main 前移 → dirty）；
   - `PUT /repos/.../pulls/880/update-branch` 直接报 `merge conflict between base and head`（422）；
   - 本机 `git merge-tree --write-tree origin/main <branch>`（honors union）对同一组合报 **clean**；
     关掉 union（临时 `.git/info/attributes` 里 `.claude/bypass.log -merge`）后**唯一冲突文件就是它**。
3. **代价**：每个 PR 必须在合并前「贴最新 main 再推一次」；一轮 CI ≈ 40 分钟
   （Control Tower Gate Tests (windows) 单跑 37 分钟，timeout 基线 106 分钟）。
   ⇒ 串行合并 N 个 PR 的墙钟 ≈ N × 40 分钟，是当前**合并吞吐的真正瓶颈**。
参考系：第一性原理（同一份事实不应有两条写入路径）+ 开源实证（GitHub merge driver 支持边界）。
