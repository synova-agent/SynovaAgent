## Q1: 调研 — 业界最佳实践 / Anthropic 决策链 / memory 历史教训

- **铁律 0-2**：`spec → test → impl → wire → review → merge`；新 export 必须在生产入口有调用方。
- **铁律 4/5**：后端能力 ≠ 可用功能；本卡的「结果」必须是**真 HTTP 入口观测到的 403**，不是"写了守卫"。
- **铁律 12**：集成测试 cover 真实路由，**不 mock 管线**（真 `express()` + `app.listen(0)` + 真 `jwtAuthMiddleware`）。
- **铁律 24/31**：拒绝路径必须 `log.warn` + 明确 code（照抄 `rbac.ts:247-252` 的 `RBAC_DENIED` 先例）。
- **铁律 39**：`routes/`(L1) → `middleware/`(L2) 相邻层，合法；**不得**让路由直触 L4。
- **D947 先例**（`2ea4df105`，PR #896）：fail-closed 姿态 = 未认证上下文一律拒绝，**先于任何角色分支（含 admin）**。
- **D947 R6**：`department-workspace.ts` 身份通道退役「另立卡」⇒ 本卡不得顺手改。
- **D333 决策四步**：① 第一性原理 —— 授权必须在**进入数据之前**判定，不能事后过滤；
  ② Anthropic 工程基线 —— 授权是横切关注点，应走单一规则真源、在边界处一次判定；
  ③ 开源实证 —— Express 生态惯例为路由级守卫消费上下文（`req.rbac`），不在路由内重算身份；
  ④ 收敛检查 —— 与 `workspaces-api.ts` 既有 5 处 `canModifyWorkspace` 同构。
  ⇒ 结论：**逐路由消费 `req.rbac` + 复用 `canAccessWorkspace`，不新增第二份规则**。

   - `ctx.authenticated !== true` ⇒ `403 FORBIDDEN` + `log.warn({code:'RBAC_DENIED'})`（照 `rbac.ts:247-252` 先例）
   - 能定位到具体工作区对象的端点（`goals/:goalId`、`proposals/:proposalId`、`alerts/:id`）⇒
     再叠 `canModifyWorkspace` / `canAccessWorkspace`，与 `workspaces-api.ts` 同构

3. `tests/security/rbac-all-routes.test.ts` — **新建**，枚举**所有**工作区数据路由（含 `workspaces-api.ts` 作对照），
   真 HTTP（`express()` + `app.listen(0)` + `jwtAuthMiddleware` + 真签 JWT）：
   - 未认证 rbac 上下文（无 `req.auth`）⇒ **403**
   - 已认证且有权 ⇒ **非 403**（防"一刀切全拒"的假绿）
