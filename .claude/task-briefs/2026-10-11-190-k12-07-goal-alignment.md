## Q0: 定位 — 项目拼图 + 文件审计

### a) 项目拼图
宪章 §2.7 五层一致性的**第④层「目标一致」**：岗位目标与公司目标的关系**可追溯**。
本卡在架构上的位置 = **② 本体层**（GOAL 节点 ＋ 目标分解边）：①循环管动力学、③哨兵管观测、
⑤导航管目标生命周期 —— 本卡给 ⑤ 提供"目标从公司哪条分解下来的"这一**结构关系**。
该层此前**零载体**：登记件搜"目标一致" 0 命中；本体有 GOAL 节点但**没有"分解"这条边**
⇒ 目标之间是孤岛（宪章 §2.7 原文痛点：同一个目标被拆成互相打架的子目标）。

### b) 文件审计（逐条实测，命令即证据）
- `ls extensions/ontology/edge-types/*.json | wc -l` ⇒ **55**（既有边类型；全 ontology 97 件 JSON）⇒ **无目标分解边**。
- `grep -rn "allowedFrom\|allowedTo" src/l4/ontology-loader.ts` ⇒ 端点矩阵由 `loadOntology()` 从
  `extensions/ontology/edge-types/*.json` **动态构建**（`ontology-loader.ts:100-106`），校验入口
  `validateEdgeEndpoints(label, from, to)`（`:137-142`）—— 即卡面§⑥「端点矩阵校验」的**唯一执行体**。
  ⇒ 边类型文件必须落在 `edge-types/` 子目录，否则矩阵拿不到（故落点与卡面字面 `<goal-edges>.json` 不同，见例外 E1）。
- GOAL 节点有**两个生产写入字面量**：`src/growth/goal-store.ts:169` 写 `'GOAL'`；
  `src/agent/conversation-engine.ts:543-551`（建档 Phase 0 访谈摘要）写 `'Goal'`。
  SQLite `type = ?` **大小写敏感** ⇒ 只读 'GOAL' 会让**建档产出的节点在链路上不可见**（V5 的机器判据）。
- 复用面（不新造模型）：GOAL 节点（`src/growth/goal-store.ts`）、图原语
  `queryNodes/queryEdges/createEdge/deleteEdge`（`src/adapters/sqlite-graph-store.ts`）、
  层级词表 `props.level || props.scope`（既有消费点 `src/sentinel/adapters/goal-alignment-sentinel.ts:38`，
  已 `@deprecated` 但词表是可复用的既有口径）。
- 消费者候选审计（架构边界，实测 `bash scripts/check-architecture.sh` 规则）：L2（`src/agent/**`）
  **禁触 L4**（白名单 8 件，`loop-handlers.ts` 不在内）⇒ L2 不可作消费方；
  L3→L4 合法（`grep -rn "from '\.\./l4/" src/l3/` 既有 9 处）⇒ 真调用落 `src/l3/briefing-generator.ts`
  （其 store 类型**本就声明了 `queryEdges`**，`src/deploy/bootstrap.ts:1148-1151` 是真生产入口）。

### c) 决策
复用本体（**加边类型**，不新造目标模型）；分解边类型**走共享契约包**
（`packages/ontology/src/edge-types.ts` 的 `EdgeType`，卡面 Q1 memory 教训：内容面规范 §3.3「类型走契约包」）；
「公司级/岗位级」判定**显式标记驱动**（`props.goalLevel ?? level ?? scope`），无标记 ⇒ `unknown` ⇒ **不追认为公司级**
（fail-closed：否则"断开分解边"会变成假绿，直接废掉 V4）。

## Q1: 调研

### a) 业界最佳实践
OKR/目标树的标准做法是**父子分解关系 + 双向可追溯**（员工 O 必须能上溯到公司 O；公司 O 必须能枚举下级 O）。
本卡只取"关系与可追溯"这一层，不做评分/对齐度（那属 ⑤导航 与考核，另卡）。

### b) 顶级团队怎么做（DSH 借鉴 · 诚实标注：弱）
DSH 是**运行时/插件宿主**，不涉及"企业目标分解"这种领域语义 ⇒ 本卡主要依据是我们自己的本体设计。
唯一可借并在本卡落地的一条：

| 采纳 | 依据 | 落地形态 |
|---|---|---|
| ✅ 类型也走**注册表 + 自带端点校验**（不生效就报错） | `@deepseek-ai/dsh-invariants/lib/index.js:6-13`（package-owned 注册 + 机器可读失败） | `EdgeType.GOAL_DECOMPOSITION` 登记进 `packages/ontology` ＋ 端点矩阵由 JSON 自带 `allowedFrom/allowedTo`；矩阵不含该边 ⇒ 逐跳校验恒 false ⇒ **fail-closed 落红** |

### c) memory 历史教训 / 铁律
- **铁律 47/48**：先定契约（`@input/@output/@degraded`）再实现；测试必须有真 `expect()`，
  覆盖正常/降级/边界三路径（本件 20 例，含 4 条降级 + 5 条边界）。
- **铁律 11/24/31（降级不静默）**：`catch` 一律 `log.warn/log.error` + `degraded:true` + 原因进 `errors[]`。
- **铁律 24 的反面（本卡显式区分）**：**数据不完整 ≠ 模块故障**。追不到公司目标 ⇒ `satisfied:false` +
  原因，但 `degraded` 仍 `false`；只有能力/环境失败（无 `queryEdges` / 读图抛错 / 端点矩阵缺边）才 `degraded:true`。
  两者混同会把"未接入链路"读成"系统坏了"。
- **卡面 Q1 教训（类型走契约包）**：见 Q0 c)。
- **实测教训（新，非教条，写进测试注释）**：`tests/l4/*.test.ts` 用真 `SqliteGraphStore` 会触发
  better-sqlite3 析构器在 **vitest worker 关闭期 GC** 里 `node::RemoveEnvironmentCleanupHook`
  断言失败 ⇒ **原生 abort（`Worker exited unexpectedly`，整文件 20 例全丢）**。实测 3/6 崩
  （补 `db.close()` 仍崩；改共享句柄 7/8 崩）⇒ 单元件改用**内存 GraphStore 实现**（铁律 33：
  `*.test.ts` = 纯函数/无 I/O；真库形态属 `.integration.test.ts`），存储层真实性下沉到探针。
  内存实现实测 **0/8 崩**。

### d) 决策参考系
参考：第一性原理（"可追溯"的最小充分条件 = 显式关系边 + 逐跳校验）+ DSH invariants（包自声明、
宿主保证不生效即报错）+ 本仓实测（端点矩阵执行体只有 `validateEdgeEndpoints` 一处）
⇒ 结论：**边类型落 `edge-types/` ＋ 逐跳过矩阵 ＋ 无标记不认公司级**。
