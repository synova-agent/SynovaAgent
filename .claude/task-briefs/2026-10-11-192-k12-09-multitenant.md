## Q1: 调研

### a) 业界最佳实践 + 顶级团队怎么做
- **多租户隔离的判据是「声明 vs 身份」不一致即拒**（不是「日志提醒」）：声明的目标租户必须是
  验签身份的一部分，任何第三方声明的租户标识都不可信（OWASP API1:2023 BOLA / API5:2023
  BFLA 同源口径 —— 越权访问的根因是「对象归属未与身份比对」）。
- **fail-closed 优先**：判据不可用（身份缺失/判据配置不可读）时拒绝，绝不放宽。
- **拒绝必须机器可读**：稳定 `code` + 归属（本卡采纳 DSH `InvariantError{code,packageName}`
  的**唯一**可借点 —— 诚实标注：DSH 是单用户桌面运行时，**无多租户对应物**，多租户是我们的
  产品约束；可借的只有「拒绝带稳定 code + 归属」这一条，见 `@deepseek-ai/dsh-invariants/lib/index.js:11-13`）。

## Q3: 验收

入口（从哪触发）：**生产入口** —— `src/server.ts:396` `app.use(jwtAuthMiddleware)`（全仓唯一全局
认证挂载点）。请求带 A 租户验签身份 + 显式声明 B 租户目标。

处理（中间步骤）：
1. 请求属性 `X-Org-Id` / `X-Tenant-Id` 头声明**目标组织**；
2. 内核 `jwtAuthMiddleware` 在认证路径与 DevMode 路径**共用同一判定函数**比对
   「声明组织 vs 验签身份组织」；
3. 不一致 ⇒ 403 + `code` + `log.warn` 留痕；一致/未声明 ⇒ 原语义不变（放行）。

结果（最终展示）：
- V1 `npx tsx scripts/control-tower/probe-rbac-multitenant.ts --case cross-org` ⇒ **exit 0**
- V2 **穿生产入口**（真 `jwtAuthMiddleware` + 真 HTTP）：跨租户读声明 ⇒ **403 被拒**（非 200）
- V3 **DevMode 姿态**：`DEV_MODE=true` 且无 `JWT_SECRET` 时，跨 orgId 读**仍必须被拒**
  （DevMode 只提升单租户内权限）—— **两态各跑一次**
- V4 反例：让 DevMode 路径绕过隔离判定 ⇒ V2/V3 **必红**；改回 ⇒ 全绿
- V5 留痕：每次拒绝带 `code`（`CROSS_ORG_FORBIDDEN`）+ 归属（声明组织、身份组织、path）
