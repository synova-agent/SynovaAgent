# Task Brief: #202 → K12-19（原 RB-05）— 人在环审批（approval seam · 无人应答 ⇒ 拒）

## 〇、为什么要做这个（通俗版 · 先读这一节）

**① 一句话**：**高风险动作要人点头**；**没人应答就拒绝**（不是"没人管就放行"）。

**② 解决什么问题**：任何自动化系统都有一个诱惑——**超时放行**（省事）。但那等于「**只要没人看，什么都能干**」。
 院方《02》与我们的四层结构都把这一层单列：它是权限体系的**最后一道纵深**。

**③ 做完对项目的推动**：这是**四层结构（预设/解析/执行/人在环）的第 4 层**；
 也是"企业级"三个字里**最像企业**的一块（企业要的不是"全自动"，是"**我批准了我认**"）。

**④ 不做行不行**：**不行**。缺这一层 ⇒ 四层只剩三层，且**风险最高的动作没有兜底**；
 结构判据也失效（"拆掉人在环 ⇒ 高风险动作**直接拒**"这条要求一个真实存在的层）。

**⑤ 现在有什么基础**：
 · ✅ 运行时侧已含"审批"（宪章 §4.2 运行时七件之一）
 · ✅ 拒绝留痕有先例：`auth.ts` 的 `AUTH_DEV_MODE_GRANT`（带 code 的告警风格）
 · ❌ `src/runtime/approval-seam.ts` **不存在**；`probe-approval-seam.ts` 不存在
 · ⚠️ 「什么算高风险动作」**是我的产品判断**，不是从 DSH 借的（本卡需明写清单）

**⑥ 还需要做什么**：审批缝（按名注入）＋ **无人应答 ⇒ 拒**＋ 拒绝留痕 ＋ **策略声明缺失即报错** ＋ 测试 ＋ 探针

**⑦ DSH 借鉴方式**：**参考自研**
 · ✅ 可借：**按名声明 + 宿主满足**（`packages/compaction/compaction-basic/src/index.ts:114`）—— 审批缝按名注入
 · ✅ 可借（同型实测）：**sandbox 与 approval 分离**（`packages/interaction/permission-presets/README.md`：
   "bundles sandbox mode with an approval policy"）⇒ 权限判定与审批**分开管**
 · ⚠️ DSH **无"企业高风险动作"语义** —— 那张清单是我们定的
