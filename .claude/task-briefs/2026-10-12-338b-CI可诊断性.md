# Task Brief: #338 前置 — 补 CI 可诊断性（step ③ 在 `set -e` 下吞掉全部失败输出）

> 来源：K12 第 5 批【1】#335 CI failure 诊断 与【2】#338 诊断的共同前置
> 批次：第 5–6 批交界 ｜ 坐标系：总闸 不适用｜承重件 不适用｜命名空间 不适用

## 〇、为什么要做这个（通俗版 · 先读这一节）

**① 一句话**：让 CI 的**失败**能说清"哪条测试挂了、断言是什么"，而不是只给一句 `exit status 1`。

**② 解决什么问题（实测钉死，非推断）**：
```
PR #335 的 CI 在 ③ 增量测试 步失败，但其**真实日志**（Gitea 本地落盘 `data/actions_log/.../421.log.zst`）逐字如下：
    增量基线 = origin/local-main
    本次变更集: 5 文件（代码面 4 个，其中 vitest 可收集 2 个；不可测面 2 个）
      ❌  Failure - Main ③ 增量测试（vitest --changed；只测改动面，避免全量摩擦）
    exit status 1
⇒ **vitest 的输出一行都没有** ⇒ 红因不可诊断。
根因：Gitea runner 对**每一步**注入 `set -e`（同一 job 日志 step0 的 `Wrote command` 明示 `set -e\n…`），
  而本步写成 `VITEST_OUT="$(npx vitest … 2>&1)"; VITEST_RC=$?`
  ⇒ `set -e` 下**子命令非 0 ⇒ 赋值语句即失败 ⇒ shell 当场退出** ⇒ 紧随的 `printf | tail -20` **永不执行**。
```

**③ 🔴 这是回退（如实记录）**：旧写法 `npx vitest … 2>&1 | tail -20 || { echo "::error::…"; exit 1; }`
**反而会打印**尾部输出。是我在 #345（PR #371）重构该步时把「打印」改成了「先捕获到变量」而引入的。

**④ 做完对项目的推动**：
- 直接解 **#335 的红因不可诊断**（本件落地后，同一步会打出断言文本与失败文件名）
- 同时解 **#338 的第一个任务**（卡面：先补 CI 可诊断性 ⇒ 再判是否代码缺陷）

**⑤ 判据（可复跑）**：
```
bash scripts/control-tower/ci-emptygreen-sim.sh      ⇒ rc=0，8 场景全 PASS
  其中 丁 场景判据已**收紧为「摘要:」** —— 只有新实现（set +e 捕获 + ::error 带摘要）才有此行
改坏即红（实测）: 把 `set +e` 拿掉（恢复旧实现）⇒ harness rc=**2**，丁 判 **HARNESS-BROKEN**
  （整步在 set -e 下静默死掉，连桩哨兵都打不出来）⇒ 该类缺陷**无处藏身**
```

**⑥ 附带（与 CI 同构，纪律 8）**：harness 原来用 `bash -c` 跑 step 正文（**不带** `set -e`）
⇒ **结构上抓不到本类缺陷**。已改为 **`bash -e -c`**，与 Gitea runner 的注入保持一致。

**⑦ 涉及文件**：`.gitea/workflows/local-gates.yml`（仅 step ③）｜`scripts/control-tower/ci-emptygreen-sim.sh`

## Q1: 调研
a) 业界：CI 步骤必须让**失败自带诊断**（断言文本 + 用例名），否则红灯只是"某处坏了"。
b) 顶级团队：`set -e` 环境下取子命令退出码的标准写法是 `set +e; out=$(cmd); rc=$?; set -e`，
   或 `out=$(cmd) || rc=$?`（**不得**依赖赋值后再读 `$?`）。
c) memory 教训：**纪律 8**（判据自证"跑的是自己"）；本批「幻影可跑性」；#338 卡面「`::error` 行不含 message ⇒ 不可诊断」。
