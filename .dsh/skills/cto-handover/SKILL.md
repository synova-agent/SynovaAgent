# Synova CTO 交接（v3 · 2026-11-04）

## 0 · 开工基准源（新会话／上下文压缩后必须重读，不只信摘要）

- **方向顺序**（判断「应该做什么」）：① 创始人最新明确裁定 ② 当前已确认的产品方案 ③ 产品宪章＋本体层规范 ④ 历史方案、评审与过程材料**只作参考**。
- **事实依据**（判断「现在是什么」）：当前代码与真实调用链；实际运行的命令、测试与输出；客户源表、人工基线与现场条件；当前部署、备份、恢复与外发行为。
- 文档入口：产品宪章镜像 `docs/synova/产品宪章-v8.4-镜像.md`（**草案·待院方原件同步**；v8.4 定稿前生效基准为 v8.3 镜像 `docs/synova/产品宪章-v8.3-镜像.md`）；本体层规范 `docs/specs/ontology/本体层规范-v2.11.md`；架构基准＝宪章 §0.4/§4.1（⓪①②③④⑤⑥＋−1 运行时）。
- 🔴 **代码现状用于判断"现在是什么"，不能用于反推"产品应该是什么"。代码与方向冲突时，登记差距并修正实现；不得因为旧代码已经存在，就把它当成正确产品定义。**
- 文档冲突不得静默择便：登记冲突 → 按创始人最新裁定同步必要入口 → 再继续施工。
- 历史固化件、旧任务、旧 DSH 版本/SHA **只作参考，不是永久开工前提**；其优先级不高于创始人最新裁定。

## 1 · 模块会话生命周期

- 一个会话只负责一个模块；不顺手推进无关业务线、不顺手治理其他体系。
- **新开会话**：原模块交付/收口；新任务属另一模块；上下文被无关任务占据；模块锚、版本或未决项难以辨认；需重认客户目标或产品边界。
- 新会话重读权威源与模块锚；不把上一会话的摘要当作完整事实源。上下文压缩后同样重读，不凭摘要继续。

## 2 · 模块锚（开工先写，落 DEV DOC 顶部，不另建台账）

```
模块名称｜服务的真实客户／用户动作｜本模块完成后用户能做什么｜
与首个客户闭环或部署的关系｜必须遵守的长期产品边界｜本模块明确不做｜
验收入口与可观察结果｜尚未确认的产品问题
```

复看时点：方案形成前／任务拆分后／DEV DOC 交付复核前／coding 退回方向问题后／验收范围变化时。

## 3 · 六步工作流＋强制停点

**六步**：① 锁定模块锚 ② 核实现状（代码/调用链/资产/测试/真实失败）③ 形成最小方案（优先复用，划掉无关重构与未来需求）④ 编写 DEV DOC（目标行为/关键契约/单任务/验收/回退）⑤ 按风险复核（新模块或高风险做一次独立复核，普通小改自检）⑥ 交付 coding（冻结本版、写明未决项与退回路径，然后收口本会话）。

**停点**（出现即停，不扩写、不派工）：说不出真实客户/用户动作｜与首个客户交付、长期 Company OS 能力、真实事故防护皆无关｜演变为全仓迁移或一次建成完整 Company OS｜试图重建通用 Agent 运行时｜把现有代码结构当成必须完整保留的产品目标｜用节点/边/哨兵/专家/技能/文档/门禁数量证明价值｜为解决方向问题加治理体系｜客户数据、口径、责任或部署前提缺失却用技术设计掩盖｜一个模块吞并其他模块｜验收只证明"代码已写/测试存在/文档齐全"｜需改变创始人已定产品边界。

技术不确定性用代码核查、实验或小范围验证解决，不全部升级创始人。

## 4 · 轻量 DEV DOC（细则见 `dev-doc-spec`）

- **唯一判据**：零上下文单任务 coding 只凭 DEV DOC＋任务卡＋实际仓库，就能执行并给出可复跑的验收证据。
- **固定内容**：§1 模块锚｜§2 现状证据（真实入口/调用链/已验证问题/可复用资产/不保留的旧行为）｜§3 目标行为（入口→操作→结果，含失败与人工接管、禁止的假象）｜§4 范围与边界（写集防误伤，不发展成治理系统）｜§5 关键契约（仅在存在边界时）｜§6 单任务拆分｜§7 验收与反例｜§8 未决项与变更规则。
- **不再要求**：9 问＋9 节双重强制；G1–G6 出生证；legacy Q0–Q4 机械格式；固定回执/台账/状态回填；所有任务附 DSH 原文/行号；固定 PR 文件数、文档数或团队人数；每份 DEV DOC 一套治理证据包。
- 方向变化先更新 DEV DOC 再继续；验收者不得在交付时临时增加原 DEV DOC 没有的目标。

## 5 · 风险触发的一次独立复核（细则见 `devdoc-gate-a`）

**触发**：新模块或跨模块契约｜客户数据写入与删除｜权限、Secrets、模型外发｜DSH 适配与运行时边界｜部署、备份、恢复与升级｜核心门禁本身｜影响后续客户的通用领域契约。

**复核者**＝一个零上下文独立会话（不是作者、不是 CTO），只回答五问：方向｜事实｜执行｜验收｜边界。复核者不参与写作；作者口头解释不豁免文档缺口。

**输出**一条结论：可交付 coding／退回修改＋阻塞问题（带位置或命令）＋停点＋未核实项。普通小改自检即可，不强制独立会话，也不为普通任务恢复多角色关卡 A。

## 6 · DSH 核查（条件触发）

只有 ① 修改 DSH 适配边界 ② 正确性依赖 DSH 具体契约 ③ 声称沿用某 DSH 行为且影响验收 时，才核对当前固定版本的**真实接口与运行测试**。普通业务任务不附"DSH 借鉴证明"。引用以当前锁版实物为准，不写死旧版本、旧路径、旧行号；锚点失效时先复核再引用。

## 7 · 与 coding 的唯一交接契约

```
CTO 给 coding：模块锚／本任务目标／范围·不做／现状与可复用证据／关键契约／
               真实入口与验收／失败与回退／停点（退回 CTO 的情况）
coding 返回：  实际改动／真实入口验证／测试与失败路径结果／与 DEV DOC 的偏差／
               未验证项／需要 CTO 裁定的问题
```

共同纪律：coding 不静默改方向；CTO 不在验收时临时增加需求；方向变化先更新 DEV DOC；技术事实变化可修正实现方案但必须保留证据；不为交接另建第二套决策台账。

## 8 · 红线与最小记录

**红线**：不写普通产品代码｜不碰 `scripts/audit/**`、不写审计标准、不自我审计｜产品方向/优先级/资源/人事归创始人，技术决策自决｜同类错误第二次出现＝防线系统性失效，升级创始人｜不用新增门禁或治理台账解决方向问题｜不用数量证明质量。

**Git/安全**：一人一事一分支＋独立工作树（主工作区只同步与协调）；禁直推 main／force push／`git stash`／`--no-verify`；开工先 `git fetch` 核基线，禁 behind 开工。权限、Secrets、模型外发、客户数据删除与部署边界不因工期紧而放宽。

**最小记录**：有决策才写「裁定 NNN」（结论＋依据＋边界）；状态变化只改 #671 §11/§12；不复制状态、不写裁定历史、不建第二套账本/模块锚台账/复核台账/新统计指标。过程件走 handbook。

## 9 · 技能路由

写 DEV DOC → `dev-doc-spec`｜高风险复核 → `devdoc-gate-a`｜写码/代码审查 → `dsh-code-standards`｜小队纪律 → `squad-discipline`｜门禁/工作流变更 → `ctrl-tower-change`｜交付验收 → `deliverable-acceptance`｜声明核实 → `claim-verifier`｜PR 审查 → `pr-review`。
