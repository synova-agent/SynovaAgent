# pre-plan-thinking — L1 开工前的 9 问

## 何时用

**L1（包负责人）接到一个批次、动笔写 plan / dev doc 之前**。
也用于 CTO 判"这张卡该不该派"（9 问答不出 ⇒ 卡本身没想清 ⇒ 退回）。

## 为什么存在（2026-10-18 创始人令）

> 「之前 dev doc 有十多个章节，目的就是**编码之前一定要先想清楚再动手**。
>   但现在写作模式变了，编码不需要去想那么多。**但是各线负责人写 dev doc、做 plan 之前需要想清楚**。」

```
 旧模型：dev doc 13 章 = **边写边想**（论证留在文档里，给 K3 看）
 新模型：dev doc 8 节  = **想完再写**（论证在 L1 的调研里，文档只留结论）
 ⇒ 🔴 **"想"没有减少，它前移了** —— 必须固化成开工前流程，否则 8 节模板会变成"填空题"
```

🔴 **判据**：**9 问每问都能拿出证据 ⇒ 才许动笔；有任何一问答不出 ⇒ 先补调研或缩小范围。**

---

## 9 问（顺序不可跳；每问必须留证据，证据格式见括号）

### 第一段 · 搞清现状（3 问）

**① 问题**：谁在什么场景下遇到什么？不做会怎样？
- 证据：用户/线负责人的**原话**、日志、报错、现状数据（`- <原话/日志> | <来源>`）
- 反例：「这是个明显的 bug」而不说谁受影响 ⇒ **不算想清**
- ⇒ 落到 dev doc **§1 目标**

**② 现状**：这块现在是怎么跑的？谁调用它？改它会波及谁？
- 证据：`grep` 出的**调用链** ＋ **跑一遍的原始输出** ＋ 关键 `file:line`
- 反例：只看文件名就断定"改这里就行" ⇒ **不算想清**
- ⇒ 落到 **§3 凭什么做（现状证据）**

**③ 有没有现成的**：这个能力是不是已经存在？
- 证据：`<能力> | grep 命令 | 命中 N | 结论：复用/扩展/确需新建(为何不能复用)`
- 必须查：`scripts/control-tower/`（136 件）／`doc-system`·`workflow`·`integration`／相关 skill／既有约定
- 反例：「应该没有」⇒ **不算想清**
- ⇒ 落到 **§6 有什么基础**

### 第二段 · 定范围（2 问）

**④ 最小改动**：最少改哪里能达成目标？
- 证据：列两份清单 —— **「必须改」** vs **「想改但不必要」**；**后者全部划掉**（YAGNI）
- 反例：把"顺手重构"写进同一批 ⇒ **越界风险**
- ⇒ 落到 **§2 在哪做（file:line ＋ 写集）**

**⑤ 最危险的假设**：如果我错了，最可能是**哪个假设**错？
- 证据：列出 1–3 个最危险假设，**并先实测它们**（命令 ＋ 输出）
- 反例：「我觉得这个函数没人调用」⇒ **必须 grep 过**
- ⇒ 落到 **§3（前提已实测）＋ §7 前置（未满足则停）**

### 第三段 · 定验收与边界（4 问）

**⑥ 失败路径**：失败会怎样？静默错还是报错？降级会不会掩盖问题？
- 证据：**先写反例** —— `改坏 <X> ⇒ 必红`，附命令与期望输出
- 反例：只写"正常路径" ⇒ **没有反例＝没判据**
- ⇒ 落到 **§4 怎么算做完（反例）**

**⑦ 边界**：我明确**不做什么**？谁负责那些？
- 证据：逐条列**路径**（禁碰）；必含 `scripts/audit/**`（K3 专属）
- 反例：只写"不做什么"的抽象表述 ⇒ **不算边界**
- ⇒ 落到 **§1 非目标**

**⑧ 可观测**：做完后**哪一个命令／哪一个数字**能证明它对？
- 证据：命令 ＋ 期望输出；🔴 **禁"应该没问题"**
- 反例：判据是"看代码觉得对" ⇒ **不可观测**
- ⇒ 落到 **§4 怎么算做完（正常路径）**

**⑨ 拆步**：能不能拆成 2–3 个可独立验证的步骤？每步失败能回滚吗？
- 证据：步骤清单 ＋ 每步验证点 ＋ 回滚方式
- 反例：一次性做完 500 行 ⇒ **不可回滚**
- ⇒ 落到 **封面（批次划分）＋ §8 交什么**

## 9 问 → dev doc 八节（**同一份思考，两个视图**）

| 思考 | → | dev doc 节 |
|---|---|---|
| ① 问题 ② 现状 | → | §3 凭什么做 |
| ③ 有没有现成 | → | §6 有什么基础 |
| ④ 最小改动 ⑤ 危险假设 | → | §1 做什么 ＋ §2 在哪做（file:line） |
| ⑥ 失败路径 ⑧ 可观测 | → | **§4 怎么算做完（反例必红）** |
| ⑦ 边界 | → | §1 非目标（禁碰路径） |
| ⑨ 拆步 | → | 封面（批次划分）＋ §8 交什么 |

🔴 **所以：dev doc 八节不是"模板填空"，是 9 问的**产物**。9 问没做完就写八节 ＝ 抄格式。**

---

## 反例：什么不算"想清楚"

- ❌ **"我觉得应该是这样"**（无证据）
- ❌ **"参照 XX 模块做"**（没查现状 —— XX 可能也是错的）
- ❌ **"先做起来再看"**（没定反例 ＝ 做完了也不知道对不对）
- ❌ **只列"要做什么"，不列"不做什么"**（边界 = 无限膨胀）
- ❌ **判据是"看代码觉得对"**（不可观测）
- ❌ **一次性 500 行**（不可回滚、不可独立验证）

## 输出（9 问的产物放哪）

```
 ① 不另写文档 —— 9 问的结论**直接填进 dev doc 的对应节**（见上表）
 ② 证据原始输出放 `<路径>`（**不放 /tmp**）；dev doc 里引路径 ＋ 摘要
 ③ 若某问"答不出" ⇒ **在 dev doc 的 §7 前置里写「未决：<问题>，需 <谁> 回答」**，不许默默跳过
```

## 与 DSH 决策镜头的关系

- **`dsh-decision-lens`**：**遇到取舍**时怎么判（六原则 ＋ file:line 证据）
- **本件**：**开工前**想什么（9 问）
- ⇒ **互补**：9 问里若出现取舍（如"最小改动 vs 完整设计"、"先修 reare 例 vs 先补覆盖"）⇒ **用 decision-lens 判**
