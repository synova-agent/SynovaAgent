# research-acceptance — 研究/审计类交付验收

> 一句话：**验收 = 交付是否满足了"委托"，不是报告是否自洽。**
> 触发过的事故：报告内部一致＋独立复核通过，但**委托项少一维（件质量）**、结论"件在装配点缺"被直接采纳，另查发现"件几乎不合格"。

## 0. 用在哪 / 不用在哪
| 用 | 不用 |
|---|---|
| 院方/第三方研究报告、对照研究、审计报告、评估报告 | 代码 PR（用 `pr-review`／四条件） |
| 任何"别人出的、你要据此决策"的文档类交付 | dev doc（用 `devdoc-gate-a`） |

## 1. 五步（顺序不可跳）
**第 0 步：先写验收计划（读报告之前）**
```
把委托书逐条抄成清单：委托项｜要求产出｜可核判据｜验收方法
清单没写完 ⇒ 不许打开报告（防被作者框架锚定）
```

**第 1 步：委托项 → 交付章节 100% 对照**
```
每项：交付里哪一节回答？证据是什么？→ 标 覆盖 / 部分 / 缺
任何"缺"或"部分" ⇒ 直接进 blocking（不许用"整体不错"抵消）
```

**第 2 步：抽样自核（≥10%，高风险项全查）**
```
 · 抽出的每条结论：自己跑命令/读代码/查源码，不采信报告转述
 · 高风险＝安全/数据/钱/交付闸门，一律全查
 · 每条记：我的命令＋原始输出＋结论（与报告一致/不一致）
```

**第 3 步：单列「件质量」验收（最易漏）**
```
对交付涉及的每个"件"（模块/文件/脚本/文档）单独判：
 合格 / 部分合格 / 不合格 ＋ 证据（file:line 或命令）
禁止用"缺装配/没接线"替代"件本身是否合格"——两回事
```

**第 4 步：独立复核的范围核对**
```
复核者是否独立（非作者）？其 range 是否覆盖委托项（不是只核报告内部一致）？
复核回执必须有：不一致处/无法核实处/跑不通处/能否据此决策
```

**第 5 步：判定（三态）**
```
 通过：委托项 100% 覆盖＋抽样自核一致＋件质量无不合格＋复核范围覆盖
 有条件：= 不通过（照创始人令），列必修项
 退回：缺维度/结论无据/件不合格
每条 blocking 必须带 file:line 或命令＋改法
```

## 2. 反模式（见到即判流程失败）
```
 ❌ 把"报告内部一致＋独立复核通过"当"委托达成"
 ❌ 采信结论层（"不是缺件是装配缺"这类框架句，本身就预设了件合格）
 ❌ 抽样自核=0（一条都没跑）
 ❌ 用"整体/方向性"掩盖缺项
 ❌ 复核者只核报告、不核委托
```

## 3. 记录模板（贴 Issue／台账）
```
| 委托项 | 交付落点 | 覆盖 | 我的自核（命令/输出） | 件质量 | 判定 |
（抽样≥10%；高风险全查；不合格件单列）
结论：通过/有条件(不通过)/退回 ＋ blocking 清单 ＋ 是否可据此决策
```

## 4. 与其它 skill 的关系
- `claim-verifier`：单条"声明是否成立"的核实口径（本 skill 第 2 步用它）
- `devdoc-gate-a`：dev doc 的六镜头评审（对象不同）
- `pr-review`：代码 PR 的合并前审查（对象不同）
