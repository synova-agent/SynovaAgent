# security-and-hardening — 安全是约束，不是阶段

> 来源：addyosmani/agent-skills（MIT）· `skills/security-and-hardening/SKILL.md` @ 1401c8b8。
> 本文件是中文改写版（结构保留、按 Synova 语境收敛）；上游引用的 `references/hardening-patterns.md`、`security-checklist.md` 未随附。

## 先威胁建模，再谈加固

没有威胁模型的控制措施都是猜。动手前花五分钟像攻击者一样想：

1. **画信任边界**：HTTP 请求、表单、文件上传、webhook、第三方 API、消息队列、**LLM 输出**——以及那些"看起来是内部的"值：**其它进程的命令行、环境变量、共享盘上的文件名、任务负载里的路径**。**信任跟"谁写的这个值"走，不跟"哪个通道送来的"走。** 每一条边界都是攻击面。
2. **点名资产**：凭证、PII、支付数据、管理动作、资金流。
3. **对每条边界跑 STRIDE**（是镜头，不是仪式）：

| 威胁 | 自问 | 典型缓解 |
|---|---|---|
| **S**poofing 冒充 | 有人能冒充用户/服务吗？ | 认证、签名校验 |
| **T**ampering 篡改 | 传输中/静态数据能被改吗？ | 完整性校验、参数化查询、HTTPS |
| **R**epudiation 抵赖 | 事后能否认做过吗？ | 安全事件审计日志 |
| **I**nfo disclosure 泄露 | 数据会漏吗？ | 加密、字段白名单、通用错误信息 |
| **D**oS 拒绝服务 | 能被压垮吗？ | 限流、输入大小上限、超时 |
| **E**levation 提权 | 能拿到不该有的权限吗？ | 鉴权检查、最小权限 |

4. **在用例旁边写滥用用例**："我会怎么滥用这个功能？"——把它变成你的第一个测试。
5. 说不出一个功能的信任边界＝还没准备好保护它。这就是 OWASP **A04 Insecure Design**：多数事故起于设计，不起于代码。

## 三层边界

**永远做（无例外）**：边界处校验所有外部输入；**参数化所有数据库查询**（绝不拼接用户输入）；输出编码防 XSS（用框架自动转义，不绕过）；外部通信一律 HTTPS；密码用 bcrypt/scrypt/argon2 哈希（绝不存明文）；设置安全响应头（CSP/HSTS/X-Frame-Options/X-Content-Type-Options）；会话 cookie 用 `httpOnly + secure + sameSite`；发布前对**已提交的 lockfile** 跑本仓包管理器原生审计。

**先问人（需人类批准）**：新增认证流程或改认证逻辑；存储新类别敏感数据（PII、支付）；新增外部服务集成；改 CORS 配置；新增文件上传处理；改限流/节流；授予提权或新角色。

**绝不做**：把密钥提交进版本库；记录敏感数据（密码、token、完整卡号）；把客户端校验当安全边界；为方便关掉安全响应头；对用户数据用 `eval()` 或 `innerHTML`；把会话/认证 token 放客户端可读存储（localStorage）；把 stack trace 或内部错误细节暴露给用户。

## 加固控制（按代码位置取用）

- **注入 / XSS / 访问控制**：所有查询参数化，SQL/NoSQL/shell 命令都不许由输入字符串拼成；输出走框架自动转义，必须原样渲染 HTML 时先用白名单 sanitizer；**认证之后还要鉴权**——已登录用户必须拥有或被授权访问**那一个具体资源**（A01 / IDOR）。
- **认证与会话**：密码哈希 bcrypt（≥12 轮）/scrypt/argon2；会话密钥来自环境变量，绝不写死在代码里；cookie `httpOnly + secure + sameSite:'lax'|'strict'`（`'none'` 会在跨站请求带上 cookie），`maxAge` 有界。
- **响应头 / CORS / 响应体**：每个响应都带安全头（helmet 或等价物），CSP 从 `default-src 'self'` 起步、只能收紧不能放松；CORS 用配置里的显式来源清单，**带凭证时绝不 `*`**；响应前剥离敏感字段（`passwordHash`、重置 token），错误体保持通用，内部细节只进服务端日志。
- **输入校验与上传**：边界用 schema 白名单校验（形状、长度、枚举、格式），失败回 422 + 结构化详情，下游只用解析后的类型化值；上传走 MIME 白名单、大小上限、必要时验 magic bytes——**扩展名不能证明任何事**。
- **服务端取 URL（SSRF）**：任何用户可影响的 URL（webhook、按 URL 导入、图片代理、链接预览）都能被打向内网。白名单 scheme + host，解析**全部** DNS 记录并拒绝任何私有/保留地址（loopback、link-local `169.254.169.254`、private、unique-local，IPv4 与 IPv6 都要），禁止重定向。该检查仍有 DNS rebinding 的 TOCTOU 缝隙：高风险面要固定解析后的 IP 或前置过滤代理。
- **派生路径上的破坏性操作**（删除/移动/覆盖）：安全性取决于"谁写了这个路径值"——**另一个进程的命令行和表单字段一样可被攻击者控制**；形状检查只证明格式合法，不证明授权。执行前三条同时满足：解析后（symlink 已解析）的目标**在允许根之下**、**至少低于该根一层**、**带有操作前读到的归属证据**。拒绝时记录被拒目标并停止，**绝不回退到更宽泛的默认路径**。
- **限流**：API 普遍限流，认证端点严格限流（约 15 分钟 10 次）。一旦有一个以上进程在服务流量，内存计数器会静默变成 `上限 × 实例数`，或在 serverless 上永不触发——限流器要接共享存储。
- **密钥**：密钥来自环境；`.env.example` 提交占位符，真实 `.env*` 与密钥材料 gitignore；提交前 grep 暂存 diff（Synova 对应 pre-commit 组 3）。**密钥一旦到达远端即视为已泄露：先轮换，再清历史。**
- **依赖与供应链**：① 先确定安装边界与包管理器（以拥有 lockfile 的工作区根为准），用 `packageManager`、lockfile、CI 三方互证，出现分歧或多个竞争 lockfile 就停；② **首次执行前先阻断依赖脚本**——用禁用脚本的方式引导或在策略里显式 fail-closed，审查待执行脚本源码，只批准最小集合，把策略提交进仓库，再用干净的 frozen/immutable 安装验证，**绝不整批批准**；③ 每次发布前对已提交 lockfile 跑原生审计，按**可达性**（运行时/构建/测试/部署路径）分级 critical/high 并看是否有修复版本，**绝不自动**跑强制修复（`npm audit fix --force` 及等价物会跨越声明的依赖范围），先预览、读 changelog、逐个升级测试，每一条延期都要写原因与复核日期；④ 审计只能匹配**已知**公告，抓不到新出现的恶意包或仿冒包名——把新依赖、lockfile diff、脚本策略变更放在一起评审（归属、维护活跃度、发布年龄、来源、传递依赖图），支持时校验注册表签名（`npm audit signatures`/`pnpm audit signatures`），签名缺失是"要查"的信号而非自动证明被投毒（A06、LLM03）。
- **个人数据与隐私**：加固问"攻击者能读到吗"，隐私问"我们**该不该**持有、持有多久"。最便宜的数据是从未收集的数据。
  给字段**边加边分类**（非个人 / PII / 敏感）；只在**声明的目的**下收集（"以后可能有用"是潜在泄露面，不是目的）；**PII 不进遥测**；先定保留期再真的删——每个个人数据存储都要有 TTL 与可用的删除路径，**包括备份、缓存、搜索索引、分析副本**；支持辖区要求的数据主体权利（GDPR/CCPA：导出、更正、删除），schema 要能让某个用户的数据**找得到、删得掉**；同意书是收集与第三方共享的前置且可审计，把 PII 发给分析/广告/LLM 供应商＝共享，供应商需要数据处理协议；地区/合规做成可配置策略，不写死假设。
- **AI / LLM 功能**（对照 OWASP Top 10 for LLM Applications 2025）：**模型输出是不可信输入**（LLM05）——绝不进 `eval`、SQL、shell、`innerHTML`、文件路径，先按 schema 防御式解析再编码；**提示可被劫持**（LLM01）——上下文里的不可信文本（用户消息、抓取的网页、PDF）可以夹带指令，**系统提示不是安全边界，权限必须在代码里强制**；密钥、其它租户数据、完整系统提示都不进上下文窗口（LLM02/LLM07）；限制工具权限、校验每个工具参数、破坏性动作要确认（LLM06）；限制 token、请求速率、递归深度（LLM10）；RAG 向量按租户隔离、入库前校验文档（LLM08）。

## 反合理化对照表

| 借口 | 现实 |
|---|---|
| "内部工具，安全无所谓" | 内部工具一样会沦陷，攻击者专挑最弱环节 |
| "以后再补安全" | 事后补比一开始做难 10 倍，现在就做 |
| "没人会来打这个" | 自动化扫描器会找到；靠隐蔽不是安全 |
| "框架会处理安全" | 框架给的是工具不是保证，用错照样出事 |
| "这只是原型" | 原型会变生产，从第一天养成习惯 |
| "这里做威胁建模太重了" | 五分钟的"我会怎么打它"能挡住事后任何控制都补不上的设计缺陷 |
| "只是 LLM 输出，就是段文本" | 这段"文本"可以是 SQL、script 标签或 shell 命令，按不可信输入对待 |
| "审计过了，依赖是安全的" | 审计只匹配已知公告，抓不到新恶意包，也不能让未审查的安装脚本变安全 |
| "先收集，以后可能用得上" | 不持有的数据不会被泄露、被调取、被误删；"可能用得上"是泄露面不是目的 |
| "删除请求我们手工处理" | 手工删除会漏掉备份、缓存、分析副本；schema 找不到用户数据就兑现不了请求 |
| "合规是法务的事" | 导出、删除、保留、同意都是 schema 与代码，PII 撒到十个系统之后法务补不上 |

## 红旗
- 用户输入直接进数据库查询、shell 命令或 HTML 渲染
- 删除/移动/覆盖的目标来自负载、配置值或**其它进程的命令行**，且只有路径形状检查
- 源码或提交历史里有密钥
- 端点没有认证或鉴权
- 缺 CORS 配置或通配来源；认证端点无限流，或限流器是内存态而实例多于一个
- 把 stack trace / 内部错误暴露给用户
- 依赖有已知 critical 漏洞、同一安装边界存在竞争 lockfile、安装不可复现、脚本被整批批准
- 服务端取用户给的 URL 而无白名单（SSRF）
- LLM 输出直接进查询、DOM、shell 或 `eval`
- 密钥、PII 或完整系统提示被放进 LLM 上下文
- 个人数据无声明目的、无保留期、无删除路径
- PII 发给分析/广告/LLM 供应商而无同意与数据处理协议
- "注销账号"只翻了个标志位，个人数据还留在各存储与备份里

## 验收清单
- [ ] 原生审计无未缓解的**可达** critical/high；CI 保留权威 lockfile 并阻断未审查的依赖脚本
- [ ] 源码与 git 历史无密钥
- [ ] 所有用户输入在系统边界校验
- [ ] 破坏性文件操作先解析 symlink，再验允许根、最小深度、归属后才执行
- [ ] 每个受保护端点都做了认证**与**鉴权
- [ ] 响应含安全头（浏览器 DevTools 可验）
- [ ] 错误响应不暴露内部细节
- [ ] 认证端点有限流；多实例时接共享存储
- [ ] 服务端 URL 抓取走白名单（无 SSRF）
- [ ] LLM/模型输出经校验与编码后才使用（有 AI 功能时）
- [ ] 个人数据已分类、按声明目的最小化、有保留期
- [ ] 删除与导出请求端到端可用（含备份、缓存、分析副本）

## 与 Synova 的对应关系
- **项目侧已有**：`security/`（PIIScrubber、DataBoundary）+ 数据安全分层（L0 公开摘要 / L1 聚合信号 / L2 脱敏证据 / L3 原始数据仅客户内 Agent 可见）——本技能是**工程侧**补位，不替代它们。
- **门禁侧已有**：pre-commit 组 3（Secrets 扫描）。本技能负责"组 3 抓不到的那部分"：设计期威胁建模、越权、SSRF、幂等、供应链。
- **LLM 输出**：本项目 LLM 调用集中在 `providers/`，其返回值一律按不可信输入处理。
