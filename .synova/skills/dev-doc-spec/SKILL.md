# dev-doc-spec — 模块 DEV DOC 撰写（v4）

> **唯一判据**：**一个零上下文 coding 小队，只凭 DEV DOC、任务卡和实际仓库，就能执行单任务并给出可复跑的验收证据。**
> 「零上下文可执行」依靠关键信息完整，不依靠章节数量和格式复杂。

## 0 · 动笔前先回答（答不出就补调研或缩范围；仍答不出 ⇒ 写进 §8 未决项并标明谁回答）

① 本模块服务哪个真实客户／用户动作？② 现在实际怎么跑（入口/调用链/真实输出）？③ 有什么可复用资产？④ 最小改动是什么、划掉什么？⑤ 最危险的假设是哪个（先实测）？⑥ 失败路径与回退是什么？⑦ 验收从哪个真实入口跑、期望值哪来？⑧ 哪些问题当前未确认？

## 1 · §1 模块锚

客户／用户动作；模块目标；与当前产品阶段的关系；非目标；长期边界。
（与 `cto-handover` 的模块锚卡同源，粘贴即可，不另建台账。）

## 2 · §2 现状证据

当前真实入口与调用链；已验证的问题；可复用资产；关键代码或运行证据（`path:line@sha` 或命令＋原始输出）；哪些旧行为明确不保留。
只核查与本模块有关的对象，不为形式列举全仓目录。

## 3 · §3 目标行为

用「入口→操作→结果」描述客户或用户可观察行为，同时写明：正常结果；数据缺失或外部依赖失败时的表现；人需要确认或接管的位置；不允许出现的假象（假绿、静默降级、伪造成功）。

## 4 · §4 范围与边界

准备修改的模块或文件范围；明确不改的范围；不做的未来能力；数据、安全、运行时和部署红线；与其他在飞工作的依赖或冲突。
写集用于防误伤和冲突，不发展成独立治理系统。

## 5 · §5 关键契约（只在存在相应边界时写）

输入与输出；数据来源、期间、口径和缺失；接口与数据结构；错误、降级与调用方表现；幂等、权限、外发或恢复要求；DSH 实际接口与锁版行为。
纯内部小实现不强迫填写无意义的全套契约。

## 6 · §6 单任务拆分

每个 coding session 只获得**一个**明确任务：目标；范围与不做；前置依赖；验收；失败和回退；需要退回 CTO 的停点。
按用户可验证行为与依赖关系拆分，不为凑团队编制而拆任务。
任务卡字段＝`cto-handover` §7 的「CTO 给 coding」八字段。

## 7 · §7 验收与反例

至少覆盖：正常路径；一个真实失败或边界路径；从真实入口运行的方式；期望值来自哪里；如何防止零对象、跳过或同源数据造成假绿；涉及部署或写入时的回退与恢复。
高风险验收必须有能证明"改坏会失败"的反例；普通任务不机械要求所有测试同一种形式。

## 8 · §8 未决项与变更规则

哪些问题尚未确认；谁负责回答；coding 遇到哪些情况必须停止；方向变化时先更新 DEV DOC 再继续执行；验收者不得在交付时临时增加原 DEV DOC 没有的目标。

## 9 · 交付与复核

- 交付物：DEV DOC（本八节）＋单任务卡。需要落盘时落 `docs/synova/coordination/编码指令-<任务>-<YYYYMMDD>.md`，内容＝任务卡＋停点，不另造治理包。
- 新模块或高风险（触发范围见 `devdoc-gate-a`）⇒ 交付 coding 前做**一次**零上下文独立复核；普通小改由 CTO 自检。
- 写完自检（逐条答）：零上下文能答出目标/范围/真实入口/验收/停点？每条现状有证据？每条验收可复跑？高风险有反例？未决项有负责人？
- 撰写者不得实现本规格；复审只验上轮 blocking ＋抽验 3 条，不重跑整套多角色流程。

## 10 · 已删除的默认要求（不再作为所有模块的固定内容）

9 问前置与 9 节格式的双重强制；G1–G6 出生证；legacy Q0–Q4 与机械解析格式；固定数量的回执、台账和状态回填；所有任务必须附 DSH 原文/行号/不变量；固定 PR 文件数、文档数或团队人数；为每份 DEV DOC 另建一套治理证据包。
（保留的有效思想：零上下文、现状证据、最小改动、真实失败路径、边界、验收、停点。）
