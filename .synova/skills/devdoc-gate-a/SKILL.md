# devdoc-gate-a — 关卡 A：新模块／高风险的独立复核

> **一句话**：判断「一个零上下文的单任务 coding，只凭这份 DEV DOC＋任务卡＋实际仓库，能否独立完成并交出可复跑验收证据」，以及方向是否正确。
> 本关不评文字好坏、不重写 DEV DOC、不参与写作。**普通小改不强制走本关。**

## 0 · 何时用 / 不用

| 用（触发范围，任一命中） | 不用 |
|---|---|
| 新模块或跨模块契约 | 普通小改（由 CTO 自检） |
| 客户数据写入与删除 | 已在跑的批次中途纠偏（按原 DEV DOC 对账） |
| 权限、Secrets、模型外发 | 单卡实现细节 review（`pr-review`） |
| DSH 适配与运行时边界 | 纯文档镜像存档 |
| 部署、备份、恢复与升级 | |
| 核心门禁本身 | |
| 影响后续客户的通用领域契约 | |

## 1 · 复核者身份与纪律（缺一即不合规）

- 复核者＝**一个零上下文独立会话**：不得是 DEV DOC 作者，不得是 CTO；不因作者口头解释而豁免文档缺口。
- 输入：DEV DOC＋单任务卡＋实际仓库（只读，钉 SHA）＋既有证据原件；不看作者/CTO 的结论。
- 每条判断带**位置（`path:line`）或命令**；无法核实 ⇒ 单列「未核实」，**不得冒充通过**。
- 只读：不改任何文件、不重写 DEV DOC、不新建台账/报告文件；结论落一条交接记录或 Issue 评论。

## 2 · 五个问题（逐问给结论；任一 blocking ⇒ 退回）

### 问 1 · 方向
是否符合模块锚与当前产品阶段：真实客户/用户动作说得清？与首个客户闭环或长期 Company OS 的关系成立？是否演变为全仓迁移、重建通用 Agent 运行时、一次性建成完整 Company OS？是否用节点/边/哨兵/专家/技能/文档/门禁数量证明价值？是否改变创始人已确定的产品边界？（方向依据顺序见 `cto-handover` §0；架构基准＝产品宪章 §0.4/§4.1。）

### 问 2 · 事实
关键现状声明是否有实际证据：入口/调用链实读过（`path:line@sha` 或命令＋原始输出）？"已验证的问题"可复现？可复用资产核过（grep/命令输出）？"旧行为不保留"说明理由？`as_of` 是否落后、差集是否涉本面？

### 问 3 · 执行
零上下文 coding 能否完成：取树/依赖/环境能否走通？每个判据能答"跑什么命令、期望值哪来、怎么证明真的跑了"？单任务卡字段（模块锚/目标/范围·不做/现状证据/契约/真实入口与验收/失败回退/停点）是否齐？不清时的停工规则写明？

### 问 4 · 验收
是否可能假绿、或只证明内部函数：恒真断言（`>=0`、`ok===true`、0 failed 但 0 条执行）？期望值与被测对象同源派生？只测 mock/只测既有函数而没打在新代码被消费的缝上？零对象/跳过能否满足验收？部署或写入是否有回退与恢复？高风险是否有"改坏必红"反例？

### 问 5 · 边界
是否越界、失败能否停止回退恢复：写集是否闭合且与在飞工作不冲突（给命令/输出，不是声明）？红线路径是否排除（`scripts/audit/**`、权限/Secrets/外发、DSH 适配边界）？数据/安全/部署前提是否成立？停点是否明确（哪些 coding 不得自行决定）？

## 3 · DSH 核查（条件触发，不默认全查）

只有：① 修改 DSH 适配边界；② 正确性依赖 DSH 具体契约；③ 声称沿用某个 DSH 行为且该行为影响验收。
核查以**当前固定版本的真实接口与运行测试**为准（给包名/路径/命令或运行测试结果），不写死旧版本、旧路径、旧行号。普通业务任务不要求"DSH 借鉴证明"。

## 4 · 输出（一条结论，不默认多份角色报告）

```text
结论：可交付 coding／退回修改
阻塞问题：逐条给位置、理由、修正方向
停点：哪些问题 coding 不得自行决定
未核实项：明确列出（禁"基本通过""应该没问题"）
```

判据：退回时每条必修都能让作者直接改（有位置/改法/验收方式）；通过时写明"复审抽验哪 3 条"。
复审：只验上轮 blocking＋抽验 3 条，不重跑整套流程。

## 5 · 反模式（见到即判流程失败）

❌ 用多角色/多会话数量冒充评审质量｜❌ 作者在场解释后放行｜❌ 复核者参与写作｜❌ 只审文字不跑命令｜❌ 抽样通过当全量通过｜❌ 用"多数票"压过单个致命缺口｜❌ 退回意见没有位置/改法｜❌ 拿"实现期再对齐"给方向或契约缺口打折｜❌ 为普通小改强制走本关（重流程回潮）。
✅ 本关只是交付前的一次独立复核：技术取舍由 CTO 裁定，验收按已批准的 DEV DOC 执行，验收者不得临时增加目标。

## 6 · 历史

- 原名「关卡 A：北星对齐＋七镜头评审」：要求所有派单强制、5–9 个评审会话、G1–G6/9 节固定判据。
- **2026-11-04 按 CTO 方案 v1.0 §10.5 收缩**：从所有任务强制改为新模块/高风险触发；从 5–9 个会话改为一个独立复核者；从七镜头固定 blocking 改为五个核心问题；DSH 源码核查按实际依赖触发；保留不得自审、证据可核、未核实不得冒充通过。
