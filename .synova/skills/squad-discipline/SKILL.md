# squad-discipline — 小队行为纪律（门禁之外的部分）

## 为什么只有这些条款

门禁能拦的（架构边界、`as any`、空壳测试、分支命名、全量测试）由 pre-commit 与 CI 硬执行；重复它们只会产生噪音和「写了就当做了」的错觉。
**本技能只收「无人能拦、只能靠自持」的条款**，门禁已覆盖的一律以脚本与 CI 为单一事实源。

## 一、真实用户场景与 Done

1. **开工先锚定**：① 本任务服务哪个客户／用户动作？② Done 是什么，从哪个真实入口验证？③ 最小改动是什么，明确不做什么？④ 正常、失败和回退分别怎么证明？
2. **锚定不清 ⇒ 停下问**；带着模糊锚定开工是返工第一来源。
3. **不假设共识**：先复述理解并确认 Done、范围与停点；歧义先问，禁「我以为」。

## 二、声称与证据对应

4. **汇报 ＝ 声称与证据逐条对应**：每条「改了什么／接了什么」都要挂物理证据（grep 命中、测试原始输出、`git diff --stat`），无自报项。
5. **数字来自命令原始输出**，禁手写；关键输出不 `head` 截断。
6. **如实报告四态**：通过／失败／跳过／未验证，各给依据；把「没跑」说成「跑了」＝事故。

## 三、自验与高风险独立验收分层

7. **实现者必须完成自验，并可以明确报告哪些测试实际通过；但不得把自验冒充高风险任务要求的独立验收。**
8. 普通任务不默认叠加「队内独立自验 ＋ 队外独立复核 ＋ 多层收件」；只在新模块、高风险变更或 DEV DOC 明确要求时，做一次有针对性的独立复核。
9. 复核者不参与写作，也不因作者口头解释豁免文档缺口。

## 四、DEV DOC 有错：带证据退回，不静默改方向

10. 发现任务书前提不成立或与代码冲突，不得静默修正方向，必须退回并给齐四件：
    - 哪条前提不成立；
    - 实际代码或运行证据；
    - 继续执行会破坏什么；
    - 需要 CTO 改哪条 DEV DOC。
11. 小范围技术修正自己做完并留证据；产品方向变化才升级 CTO／创始人。CTO 更新任务书后再继续。

## 五、独立工作树与基本 Git 安全

12. **一人一事一分支 ＋ 独立工作树**：`git worktree add .synova-wt-<任务>`，不复用他人工作树；主工作区只做同步与协调。
13. **开工前 `git fetch`**；禁在 `[behind N]` 状态开工或 push；**禁 `git stash`**——要停就 commit 或换工作树。
14. **main 唯一真相**：合并只走 PR，禁直推 main、禁 force push、禁 `--no-verify`；提交被拒先读原因修复。
15. **不绕过安全纪律**：权限、Secrets、外发、删除与部署边界不因工期紧而放宽。

## 六、越范围停止

16. 只做任务卡范围内的最小实现；要写范围外文件或改验收标准 ⇒ 停，退回。
17. 优先复用现有能力；用「顺手重构」扩大改动 ＝ 越范围。

## 七、同类严重错误：修机制，不修人

18. 同类错误第二次出现 ＝ 防线系统性失效：先查是否已有同类机制，同类则强化既有防线，不同类才加新机制（一类一机制，防臃肿）；不靠个人检讨或掩饰收场。
19. 错误归属分清：DSH 行为差异 → 补事实与测试；工程约定 → 补测试或脚本；审计脚本与审计标准 → 只转达独立审计，绝不改 `scripts/audit/`。

## 用法

- 队长与编码 session **开工时加载**；派单写「按 squad-discipline 执行」即可，不复制条款正文。
- **本技能不含**门禁已覆盖条款——以脚本与 CI 为单一事实源。
- 修改本技能按治理变更处理（走 PR 与独立复核），改纪律的人不得自判通过。
