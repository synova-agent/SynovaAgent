# 决策: 三分工定稿 —— 谁出结论、谁出代码、谁出门禁、谁出方向

状态: implemented
日期: 2026-10-02

## 一句话

**四类产出各有其主**：出结论归基座线、出代码归产品线、出门禁归治理线、出方向归 CTO；**判据一句话，遇争议照此判。**

## 问题

三级制落地后，"谁该做什么"散在院方研究件、CTO 岗位件、各线锚里，**没有一份可引用的定稿**。后果在实际中已出现：

- CTO 陷入**线内操作**（逐 PR 解冲突、补声明、改号）——**上下文被任务级内容灌满**，正是三级制要治的病；
- 治理线**改了自己的门禁却等外部裁定**（判断链不清）；
- 产品线与基座线在"**照范式自研**"上**边界模糊**（谁出结论、谁出代码）；
- Win 侧派单**来源不明**（"X30 工程落地 session 给的"），授权链断裂。

## 决定

### 一、四角色职责（定稿）

| 角色 | 负责 | **不负责** |
|---|---|---|
| **创始人** | 方向／钱／风险承受（放保护、生产数据出库、不可逆操作）／**红线与定价**／ruleset 转换时点／撤豁免 | 不派单、不逐 PR 操作、不判技术通过 |
| **CTO** | ① **方向锚＋边界声明**（每线每窗一件）② **跨线裁决**（当日）③ **治理三件事**（每日 K3 处置／周 bypass 对账／方向复盘）④ **线级周对账** | 线内拆解／派单／写集／验收命令；逐 PR 操作；`scripts/audit/**`；**判自己派出去的工作通过**（终审归 K3） |
| **治理线** | **门禁与控制塔演进**／**散落门禁归一**／**迁移 M0-M6**／**文档治理（含 HTML）**／**门禁语义变更送审**／治理:产品比监测 | `scripts/audit/**`；产品 `src/**` 的逻辑；**不判自己改的门禁通过** |
| **基座线** | **DSH 契约与边界**（读上游源码、核条款、出结论、守 G1）／"照范式自研"的**范式面** | 不改 `src/**`（出结论交产品线执行）；不改门禁 |
| **产品线** | **领域能力面**（本体／计算库／专家／哨兵／报告／导航／记忆）＋**照范式自研的运行时代码**＋每能力面一份 `AGENTS.md` | 不改 `scripts/control-tower/**`、`.github/**`、门禁脚本 |
| **Win 侧** | **CTO 直配模块的执行**（一次一个模块，WIP=1） | 无方向权／无合并权／无独立派单权 |

### 二、分界判据（一句话，遇争议照此判）

```
出【结论】（对账/登记/建议/范式）  ⇒ 基座线
出【代码/功能】（领域能力面）       ⇒ 产品线
出【规则/门禁/CI/迁移/文档治理】    ⇒ 治理线
出【方向/跨线裁决/线级对账】        ⇒ CTO
出【钱/风险/不可逆/红线】           ⇒ 创始人
```

**配套**：改"哪条检查阻断合并" ⇒ **治理线提案 → K3 过审 → CTO 裁**（**不许线下自定**）｜
`ci.yml`／`ownership.yaml`＝**单写者热点文件**（改动须并入治理线窗）｜跨线写集冲突 ⇒ CTO **当日裁**。

### 三、CTO 输出形态（**守住这条，CTO 就不会再陷进去**）

| CTO 发出去的 | CTO **不**发的 |
|---|---|
| ① 方向锚＋边界声明（A1–A8）② 收件闸回执（收 R1–R5）③ 跨线裁决（当日，带 `file:line` 证据） | ❌ 任务清单／优先级排序／写集／验收命令／分档处置表 |

**判据**：**CTO 发出的件里出现"任务级内容" ＝ 违例**（自查可核：全文应无 `做什么：` 任务清单段）。

### 四、失效条件（便于外部抓 CTO）

| 条件 | 后果 |
|---|---|
| CTO **连续两个窗**在做线内操作（改门禁／排优先级／写实现） | **CTO 违例**，请创始人当场指出 |
| 治理线**两个窗**内无 R 收口 | 院方 R-7 信号：**建制失败**，升创始人（逐兼治理块并重议编制） |
| 产品线**连续两周**并行小队 ≥2 或周派单 ≥6 卡 | 按院方 §2.3 建 `synova-product-lead`（转正触发器） |

## 考虑过的其他方案

**方案 B：按"工作性质"再拆线**（如"DSH 借鉴线"＋"参考自研线"）。
**否决理由**：① **四类清单（必须自建 37／用 DSH 14／参考自研 11／可裁剪 16）已按性质分类，但落到三线是按能力域**——
若按性质立线，"借鉴"会**穿在所有条目上**（参考自研 11 项分布在 A 线客户端／B 线数据／C 线部署），
等于**每个域再切两半**，跨线协调从 3 条变 6 条；② **"照范式自研"是常态**（我方运行时自建、守 G1）⇒
该线**永不退休**；③ CTO 上下文 ∝ 线数 ⇒ 增加常驻节点是最贵的一种改法。

**方案 C：按架构层（L1–L5）拆线。**
**否决理由**：① L1–L5 是**代码依赖方向**（铁律 39，pre-commit 已在查），**不是交付单元**；② **铁律 1「垂直切片交付」反对按层横切**——
一个功能（如加一个专家）要穿 L3+L4+L5 ⇒ **5 个线各占一段，跨线协调爆炸**；③ 同样使线数增到 5+。

**方案 D：CTO 继续兼做线内操作（现状）。**
**否决理由**：正是本决策要治的病 —— CTO 上下文 ∝ **任务数**（不可封顶），而三级制的设计前提是 ∝ **线数**（可封顶）。
实证：2026-10-02 当日，CTO 因逐 PR 解冲突／补写集声明／改号而**耗掉整轮上下文**，主线零推进。

## 影响

- **各线按各自锚自拆自派**；CTO 退回四件事；
- **PR 下放**从治理线开始试点（先决条件：`merge_group` 落地 + 存量红清偿 + 缺陷 B）；
- **不影响已有派生形态**：`coordination/` 下既有 248 件**维持原状**（见下"待办"）；
- 本决策**不改任何门禁实现**，仅定职责边界。
