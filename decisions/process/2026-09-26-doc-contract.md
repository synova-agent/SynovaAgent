# 决策: 建立文档契约（痕迹不入库，思考必须入库）

状态: implemented
日期: 2026-09-26

## 一句话

以前我们每做一件事就写一份文档并提交，现在改为「只把为什么写进仓库，做过的过程留在 PR 里」。

## 问题

我们是一个**无技术背景的创始人 + 几个 AI 助手**的团队。仓库是我们**唯一的记忆**。
过去几个月，团队每完成一件事就产出一份文档（任务卡、brief、报告、分类、派单、纪要、验收记录），
并且**每一份都提交进仓库、每一份都开一个 PR、每一个 PR 都跑一次全量 CI（10–13 个 job × 双操作系统）**。

实测后果（2026-09-26）：

| 症状 | 实测值 |
|---|---|
| open PR 中「文档/治理」类占比 | **59 / 90 = 65%** |
| CI run 中 doc/chore/audit 类占比 | **52%–83%** |
| `docs/**` 下 `.md` 总数 | **2,169**，其中「过程类」约 **83%**（brief 711 / coordination 601 / plans 335 / notes 151） |
| 同一件事的文档份数 | 存在 **2 份「文档管理规范」** + **1 份 957 行且中文已乱码的文档清单** |

由此形成**自增强循环**：
```
治理以文档为产物 → 每份文档一个 PR → 每个 PR 跑全量 CI → 合并变慢
   → 积压 → 「找不到真相」→ 再写文档澄清 → 回到起点
```

**⇒ 根因不是「文档多」，而是「什么都提交」** —— 我们缺少「什么才配进版本库」的判据。

## 决定

建立 **《SynovaAgent 文档契约 v1.0》**（`docs/synova/DOC-CONTRACT.md`），核心三条：

1. **唯一判据**：*「3 个月后一个新人，是否必须靠它才能理解我们为什么这样做？」*
   答「是」⇒ 入决策层；答「否」⇒ **不入库**（写 PR 正文 / commit / 卡 note）
2. **五层归属**：A 入口（README/AGENTS/CLAUDE/STATE）｜B 决策（`decisions/`）｜C 长期（`docs/`）｜
   **D 过程（不入库）**｜E 生成（不入库或标注 + `--check` 对账）
3. **三闸**：格式闸（决策五段强制）｜**取代闸**（新增决策必须判取代）｜**入库闸**（新增 `.md` 必须命中白名单，否则阻断）

**与 DSH 的关系**：借鉴其「四态 + 类别闭集 + 路径即元数据 + 格式门禁 + 取代链 + 禁中央索引」的**形状**；
**不采纳**其「过程完全不入库」的**前提** —— 因为它有 20 人团队与平台可见性，我们只有仓库。

**独立于实现的约束**：创始人无技术背景 ⇒ **每条决策强制 `## 一句话`（≤50 字，禁未解释术语）**。

## 考虑过的其他方案

**① 照抄 DSH（过程完全不入库，只保留代码/配置/测试作为治理载体）**
否决：DSH 有 20 人团队和 PR/issue 平台可见性，过程留在平台有人读；我们的创始人不会翻 PR 列表，
AI 助手没有「人的记忆」沉淀，新人加入只能自己读仓库。**若过程不入库，三个月后没人知道我们为什么这样决定。**

**② 继续增加文档规范（在既有 DOCUMENT-CONVENTIONS 上补规则）**
否决：那正是病根 —— 我们已经有两份「文档管理规范」互相不知道对方存在。
再加一份规范 = 再增一份文档 = 循环加强。

**③ 只做归档，不改产出（把旧文档搬进 archive/）**
否决：归档只是搬家。实测归档区已有 725 份，但**产出速度 > 归档速度**，
活跃 brief 仍有 711 份。不切断产出，存量永远降不下来。

**④ 全面 git rm 所有过程文档（一次性清空）**
否决：会丢失「思考」（不是所有过程文档都是痕迹；其中含真实决策）。
且违反「删历史」的稳妥原则 —— 正确做法是**分流**：决策抽出入库，痕迹出库（内容留在 git 历史与 PR）。

## 后果

**好的**：
- 从机制上切断「每做一件事多一个 PR」的来源（预计砍掉 65% 的 PR 来源、52–83% 的 CI 负载）
- 新人有了明确的 30 分钟入口路径（README → AGENTS → STATE → decisions → architecture）
- 决策可查、有取代链 ⇒ 不再「同一决定 5 份文档各说各话」
- 创始人有了 30 秒可读的 `## 一句话`

**坏的 / 要长期承担的**：
- **CTO 每阶段必须重写 `STATE.md`**（重写式维护有持续成本）
- **决策由「做决定的人」自己写**，CTO 不代笔 ⇒ 短期会变慢
- **存量迁移是长期工程**（711 brief + 601 coordination + 335 plans 需分流），不是一次做完
- **闸 3 会挡住一些「顺手加一份 md」的便利** ⇒ 有人会感到不便（这正是目的）

**要警惕的**：
- ⚠️ **不要学 DSH 的双语 + 1743 个 i18n sidecar**（我们单语内部项目，抄它自增 3 倍文件量）
- ⚠️ **不要用「数量/年龄/配额」决定归档**（照 DSH 原话：改用「是否仍有未来指导价值」）
- ⚠️ **不要新建第二个进度文件**（`STATE.md` 是唯一答案；禁止再建索引/台账/看板 md）
