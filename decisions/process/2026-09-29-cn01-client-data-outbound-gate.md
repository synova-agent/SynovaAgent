# 决策: 客户机密名入库扫描门禁（加盐哈希清单 + 文本/二进制双分流 + CT-34 分支内接线）

状态: implemented
日期: 2026-09-29
理由: 客户机密数据被公开仓库以文件名与内容两种形态发布（基线 9608fba7：文件名 25 件 ｜ 内容命中 167 件＝仅 CN-01 / 172 件＝CN-01∪CN-02 ｜ 并集 177 件 ｜ 另一件路径干净的 docx 二进制内含名 ⇒ 实际待清 178 件；口径见正文表），根因是「无任何门禁能拦把客户数据写进仓库这个动作」；补门禁必须同时补「纯文档提交走 CT-34 早退分支」这条绕过路径。

## 一句话

以后任何提交（含纯文档提交）都会被一道「客户机密名」扫描门禁检查：清单只存加盐 SHA-256（不存明文），命中即阻断；二进制不做内容扫描但**未登记就阻断**，绝不静默放行。

## 问题

本仓库 `private: false`（公开）。**实测**（2026-09-29，基线 `9608fba7`）：

| 症状 | 实测值 | 实测方法 |
|---|---|---|
| 当前树**文件名**含客户名（代号 CN-01） | **25 件** | `scan-client-names.py --scan-filenames` |
| 当前树**内容**含 CN-01（**仅 CN-01 条目**） | **167 件** | `--scan-all-tree`（数据文件仅 CN-01 时；独立复算，见下） |
| 当前树**内容**含 CN-01 **或** CN-02（部分名，见「决定」末段） | **172 件** | `--scan-all-tree`（数据文件 CN-01∪CN-02 时） |
| 并集（**名 ∪ 内容**，CN-01∪CN-02） | **177 件** | 25 ∪ 172 |
| 其中二进制内含（路径却干净，**不属上述任何集合**） | **1 件** | OOXML 逐 member 文本抽取（`--review-binary`） |
| ⇒ **实际待清合计** | **178 件** | 177 ∪ 1（两者不重叠：该件路径干净且二进制不做内容扫描） |
| 形态分布（**CN-01 口径并集 172 件内**） | `.md` 98 / `.html` 45 / `.txt` 12 / `.ts` 6 / `.docx` 2 / `.pdf` 2 / `.py` 2 / `.bak(.bak3)` 3 / `.json` 1 / `.yaml` 1 | 扩展名聚合 |

> 🔴 **口径纪律（本表订正过一次，写在这里防再漂）**：同一棵树在不同**条目集**下的命中数不同 ——
> `167` 的**唯一正确归属**是「数据文件仅含 CN-01 时的内容命中」；一旦登记了 CN-02（部分名），
> 内容命中即变 `172`、并集变 `177`。**报数必须带口径**（哪套 entries / 哪种扫描维度），
> 否则「167」与「172」会被混读成本卡的工具错误（本卡实际发生过：登记 CN-02 后未回填注释）。

**根因不是「删得不够快」，是三道缺口同时存在**：

1. **无任何门禁**能拦「把客户数据写进仓库」这一动作（46+ 条铁律与 13 组门禁全都在管代码质量）。
2. **CT-34 纯文档草退分支**（`scripts/pre-commit-check.sh:319-352`）只保留 Secrets 扫描、豁免其余 12 组。
   而**本次泄露正是文档形态**（CN-01 口径并集 172 件中，`.md/.html/.txt` 占 155 件）：实测 `docs/synova/business/<客户方案>.html`
   在 `DOC_PREFIX_RE` 白名单内 → 非文档计数 0 → 走早退分支。**若新门禁只接在 13 组里，它会整段绕过。**
3. **二进制是文本扫描的盲区**：实测 `docs/plans/codex/20260815-<主题>.docx` 路径**不含** CN-01，
   但其 `word/document.xml` 含 3 处、`docProps/thumbnail.wmf` 含 2 处（UTF-16LE）——
   任何基于文件名或 `git grep` 的清点都会漏掉它（它**不在** 162 件删除集内）。

## 决定

新增「客户机密名扫描门禁」，三合一落地：

1. **数据文件 `scripts/control-tower/client-name-patterns.json`**：只存 `{id, len, sha256}`
   （`sha256 = SHA-256(salt_bytes ‖ 名称 UTF-8)`）+ `binaryPolicy{allowlist, refused, default:"block"}`。
   清单不写死进脚本（新增客户 = 改数据文件，不改代码）；**文件内不含任何明文**。
2. **扫描器 `scripts/control-tower/scan-client-names.py`**：三态退出码
   `0 通过 / 1 命中 / 2 自身失败或降级`（D328，绝不与通过混同）。
   文件名按**路径各段**滑窗；内容按**新增/修改行**滑窗（剥 UTF-8 BOM、兼容 CRLF）；
   二进制不做内容扫描 ⇒ **未登记二进制 = 阻断**（变更集 fail-closed exit 1；全树清点 exit 2），
   并显式打印「未内容扫描（binary）」。
3. **接线两处（缺一即不达标）**：13 组主路径（`soft_check`，本地软提示 / CI `SYNO_CI=1` 转硬 ❌）
   **+ CT-34 早退分支内**（与 Secrets 同级，命中即 `exit 1`，不看 `SYNO_CI`）。
   不并入 13 组编号（改组数会连锁打破「✅ 全部 13 组通过」自声明链，同 D782/D734 判定）。

补充：`binaryPolicy.allowlist` 的条目**必须**以 `--review-binary` 逐件复核后才登记 ——
实测「按扫描器是否命中自动生成 allowlist」会把上表那件含名 docx **误登记成干净**（掩盖泄露），
故数据文件另设 `refused` 字段记录复核命中被拒的路径，并对 `allowlist ∩ refused` 做自洽性校验（矛盾即 exit 2）。

## 考虑过的其他方案

**① 明文清单（把 CN-01 及后续客户名直接写进数据文件或脚本常量）**
否决：本文件/脚本本身入库。**明文清单 = 把要清除的东西再写进仓库一次** —— 与本次任务目标自相矛盾。
而且门禁文件会随仓库被 clone/fork，等于把泄露面扩大一份。

**② 哈希清单 + 倒排索引 / Aho-Corasick 自动机（换取 O(n) 扫描速度）**
否决（本轮）：多模式匹配要**持有明文才能建自动机**，落盘或常驻内存都会把明文重新引入。
替代是「逐窗口算加盐 SHA-256」，代价是逐窗口 CPU —— 用两个手段压住：
① 门禁只扫**暂存增量**（不扫全树）；② 条目带 `nonAscii` 提示位 ⇒ 纯 ASCII 窗口直接跳过
（`str.isascii()` 是 C 级实现，比 `sha256` 便宜约 8 倍）。实测门禁增量路径 <1s，
全树清点 5076 件约 10s（清点是审计动作，不在提交路径上）。

**③ 库外清单（清单放仓库外的机器路径 / 环境变量 / 私有仓，不随公开仓发布）**
否决：门禁必须在 **CI**（`.github/workflows/ci.yml` 注入 `SYNO_CI=1`）上生效，CI runner 只有仓库内容；
库外清单 = CI 拿不到清单 = 门禁在权威端**静默失效**（正是 M1「检查未执行 == 检查通过」）。
且新机器/新 clone 开工即失去防线，与本项目「仓库是唯一记忆」的前提冲突。

**④ 只做一次清（按口径删除 178 件），不加门禁**
否决：无门禁 ⇒ 三周后重新长回来。本次泄露的内容命中件里（**仅 CN-01 口径 167 件** / CN-01∪CN-02 口径 172 件），
大量是**日常文档写作**顺手带进去的，不是一次性事故；不加防线的清理等于定期重做。

**⑤ 把门禁只接在 13 组主路径（不接 CT-34 早退分支内）**
否决：实测纯文档提交在 `:319` 就早退，永远到不了主路径 ⇒ 占 CN-01 口径并集 172 件中 155 件的文本形态**整段绕过**。
这是本卡与 D472（Notes 迁移门禁被 CT-34 绕过）同型的缺陷，必须两处都接。

## 后果

- **正向**：新增/修改内容里出现已登记客户名 ⇒ 阻断，且**纯文档提交不再豁免**（判别性测试证明：
  含名 `.md/.html` 走 CT-34 路径 `exit 1`；同一夹具去掉客户名后 `exit 0` —— 非恒红假门禁）。
- **代价（如实声明，不假称全知）**：窗口不跨行、不跨路径分隔符 ⇒ 名称被换行或 `/` 拆开时漏检；
  PDF 正文可能以字体子集 CID 编码 ⇒ 靠「未登记二进制即阻断」兜；加盐哈希不可枚举 ⇒ 无「列出所有已知名」能力。
- **运行成本**：`binaryPolicy.default = "block"` ⇒ **任何未登记二进制入库都会被阻断**
  （含新增截图/模板）。这是有意为之的 fail-closed：二进制无法内容扫描，只能靠「显式登记 = 人工审过」放行。
  代价是新增二进制需先登记，属可接受摩擦；若成为高频负担，应改数据文件（加 allowlist 条目），**不得**关掉默认阻断。
- **遗留（本卡范围外，已上报队长）**：`docs/plans/codex/20260815-<主题>.docx` 内含 CN-01 但路径干净，
  且**不在** 162 件删除集内 ⇒ 即使三张 PR 全部落地，C2「内容清零」仍不为 0。
  本门禁把它留在 `binaryPolicy.refused`（**不登记**）⇒ 只要它还在树里，扫描就持续报缺口（留红不掩盖）。
