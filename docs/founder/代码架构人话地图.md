# 代码架构人话地图（给创始人的「软件平面图」· v2 修订版）

> ⚠️ **本版重要修正**：上一版把「代码分层 L1–L5」当成了产品的整体架构来讲，这是**错的**。《产品宪章 v8.3》§4.8.2 明确说有**两套完全不同的「层」，不许混**：
> - **架构层 ⓪–⑥** ＝ 产品该长什么样（宪章定义，向客户交付的东西）
> - **代码分层 L1–L5** ＝ 管代码 `import` 方向的工程纪律（只是内部整洁度要求）
>
> 下面**先讲产品真正长什么样（⓪–⑥）**，再单独讲 L1–L5 是什么、为什么不是一回事。

---

## 一、产品真正的架构：宪章 ⓪–⑥（产品长什么样）

把 Synova 想成**「装进一家企业的智能操作系统」**——由 7 个功能块组成，外加 1 个底层引擎。这是《产品宪章》定义的「产品该长什么样」。

| 块 | 名字（英文） | 管什么（人话） | 类比 | 东西放哪（内容载体） |
|----|------|--------------|------|-------------------|
| ⓪ | 连接器 Connector | 把企业的**数据**和**人**接进系统（两类输入：数据侧描述/观测；人侧是谁、什么岗位、能看什么） | 前台 / 总机接线员 | `extensions/adapters/`（数据）、`extensions/presets/`（角色预设）+ `extensions/onboarding/`（建档） |
| ① | 循环层 Cycles | 企业**怎么运转**：钱和事怎么流动、一个投入多久以什么幅度溢出 | 业务节拍器 | `cycles/*.cycle.json` |
| ② | 本体层 Ontology | 把企业画成**知识地图**（谁连着谁、什么导致什么）；**只管「结构」** | 企业档案室 | `extensions/ontology/` |
| ③ | 哨兵层 Sentinels | **24h 巡逻**：报异常 / 报正向 / 留取值时序 / 存决策结果（四职责） | 巡逻保安 | `extensions/sentinels/`、`extensions/industries/`（阈值）、`extensions/rules/` |
| ④ | 参数层 Parameters | 把「什么判断准、什么不准」**沉淀下来**（护城河所在〖待验证〗） | 经验金库 | `extensions/evolution/`（标定参数/阈值）+ 客户实测值 |
| ⑤ | 导航层 Navigation | 企业目标**全生命周期**：设定、对齐、执行 | 目标驾驶舱 | `expert/`（专家域）、`extensions/frameworks/`、`extensions/reports/` |
| ⑥ | 进化回环 Evolution | 对比「我们说的」和「实际发生的」，**回写改进**前面的块 | 复盘学习 | `extensions/evolution/`（模式；铁律：范式可沉淀、数据不可搬） |
| −1 | 运行时 Runtime | 让上面所有块能跑起来的**底层引擎**（调度/工具/会话/沙箱/审批/压缩/编排），我们自己造 | 发动机 | `src/` + `packages/`（DSH 是借鉴对象，**不是依赖**） |

**数据怎么流**：企业数据/人 → ⓪连接器 → ①循环 → ②本体 → ③哨兵 → ④参数 → ⑤导航；**⑥进化**从「系统输出 vs 实际结果」的差异里学习，回写改进 ①②③④⑤。−1 运行时是提供动力的底层引擎。

**关键边界（宪章 §4.8.1）**：② 本体层**只负责结构**（这张地图长啥样）；「什么导致什么」的因果归 ① 循环，参数值归 ④，观测归 ③。各块分工不能乱——这正是你担心的「跑偏」最容易发生的位置。

## 二、那 L1–L5 到底是什么？（代码分层，不是产品架构）

L1–L5 是**写在 `src/` 代码里的「分层纪律」**：规定代码模块之间的 `import`（引用）只能「上层依赖下层」，不能反过来。例如宪章原话：`src/l4 → src/cycles` 命中即红（代码层 L4 不该去引用 cycles）。它管的是**代码整洁度**，不是产品功能。

| 代码层 | 大致管什么（仅作参考，别和产品块一一对应） |
|--------|------|
| L1 | 交互 / 路由（接待外部请求） |
| L2 | 编排（决定跑哪个流程） |
| L3 | 洞察（诊断、专家） |
| L4 | 本体 / 证据（知识图、证据） |
| L5 | 存储（数据落地） |

⚠️ **最容易混的点（宪章 §4.8.2 原话）**：`src/l4` 是**代码层 L4**，**不是**架构层 ② 本体；架构层 ② 的载体是 `extensions/ontology/`。二者**不是同一张图**。同理 `src/l1` ≠ 架构层 ⓪。所以「L1–L5」和「⓪–⑥」是**两个互相垂直的坐标系**，别用同一套数字去套两套东西。

## 三、两套层怎么对照（避免再混）

| 维度 | 架构层 ⓪–⑥ | 代码分层 L1–L5 |
|------|------------|---------------|
| 回答的问题 | 产品该长什么样 | 代码怎么分层才不乱 |
| 定义出处 | 宪章 §0.4 / §4.1 | `src/` 的 import 规则（工程门禁体系） |
| 载体 | **内容文件**：`extensions/`、`cycles/*.cycle.json`、`expert/`… | **代码模块**：`src/l1` ~ `src/l5` |
| 谁说了算 | 产品 / 创始人裁定 | 工程门禁（铁律 39） |
| 违反的后果 | 产品做歪 | 代码判红、需重构 |

一句话：**⓪–⑥ 是「向客户交付的产品」，L1–L5 是「我们内部写代码的规矩」**。

## 四、一次「诊断请求」的真实旅程（按宪章流）

```
客户触发诊断
   ↓
⓪ 连接器：接入客户数据 / 身份权限
   ↓
① 循环层：按业务节拍跑「投入 → 溢出」模型
   ↓
② 本体层：从企业知识图取结构、印证因果
   ↓
③ 哨兵层：观测指标、报异常/正向、留时序、记决策
   ↓
④ 参数层：存测量值、记决策台账
   ↓
⑤ 导航层：结合企业目标给出建议
   ↓
⑥ 进化回环（事后）：对比实际结果，回写改进 ①②③④⑤
（全程由 −1 运行时引擎驱动）
   ↓
结果回到客户界面
```

## 五、东西放哪（按宪章的 6 个内容根）

宪章实测「内容面」有 6 个物理根（这些是「加文件即可、不改代码」的内容，不是代码）：

| 你想找…… | 去哪看 |
|--------|------|
| 接入企业的适配器 | `extensions/adapters/` |
| 业务循环配置 | `cycles/*.cycle.json` |
| 企业知识图谱 / 本体 | `extensions/ontology/` |
| 哨兵 / 阈值 / 规则 | `extensions/sentinels/`、`extensions/industries/`、`extensions/rules/` |
| 专家域内容 | `expert/` |
| 方法论 / 技能 | `knowledge/`、`skills/` |
| 客户专属配置 | `customer-config/`（目前完全为空） |
| 底层引擎代码 | `src/`、`packages/`（−1 运行时） |
| 开发规矩 / 门禁 | `docs/authority/` + handbook 仓库《工程纪律》 |

## 六、出事怎么初步定位

| 现象 | 大概率在 | 对应块 |
|------|---------|--------|
| 数据接不进来、身份/权限错 | 接入 | ⓪ 连接器 |
| 业务流程算错、投入溢出不对 | 循环模型 | ① 循环 |
| 企业关系图错乱、取不到证据 | 知识图 | ② 本体 |
| 没报警 / 报警不准 / 没留时序 | 巡检 | ③ 哨兵 |
| 经验没沉淀、判断无来源 | 参数 | ④ 参数 |
| 目标/建议不贴合企业方向 | 导航 | ⑤ 导航 |
| 系统整体跑不起来 | 引擎 | −1 运行时（`src/`） |

> 真正的「仪表盘」在 `dsh/` 插件和 sentinel 报告里（`GET /api/sentinel/reports`），是工程师盯系统健康度的地方。

## 七、给你的一句总结

记住**两句话**就够了：
1. **产品由 ⓪–⑥ 七个块组成**（连接器/循环/本体/哨兵/参数/导航 + 进化回环），底层有 −1 运行时引擎——这是《产品宪章》定义的「产品长什么样」。
2. **L1–L5 是写代码的内部纪律，不是产品架构**——别用同一套数字套两套东西。
