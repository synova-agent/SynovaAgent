# 术语表（活字典 · 含 TypeScript 专业英语）

> 给非技术创始人看的「人话词典」。每遇到一个专业词就补一条，越积越多。
> 类比尽量用生活 / 生意里的东西，不假设你有技术背景。
> **英文标注**：你说过英文不好、要顺带学专业英语，所以每条都带英文术语（加粗），方便你边看边记。

## A. 基础概念（先搞懂这几个，后面都靠它们）

**1. AI Agent（智能体 / 代理）— AI Agent**
一个能自己「感知→思考→行动」的 AI 程序，不是你问一句它答一句的聊天机器人，而是会主动干活、调用工具、连续完成任务。本项目整个产品就是一个 Agent。
类比：雇佣了一个不会累、24 小时在线的员工。

**2. LLM / 大模型 — Large Language Model**
大语言模型，就是 ChatGPT、DeepSeek 这类「能理解和生成文字的 AI 大脑」。本项目需要接一个大模型当「大脑」才能诊断企业。
类比：Agent 的身体装了个什么牌子的脑子。

**3. API Key / 密钥 — API Key / Secret**
一串密码一样的字符，用来让软件「登录」大模型服务并花钱调用它。本项目配置好 Key 就能用。
类比：你给员工配的门禁卡 + 消费卡。⚠️ 这串字符很敏感，绝不能公开出去。

**4. 进程 — Process**
软件运行时在电脑里「活着的那个实例」。本项目是个「独立进程」——意思是它自己单独跑，不依赖别的前置软件。
类比：开了一家独立门店，不挂靠在别人工位上。

**5. 数字孪生 — Digital Twin**
用数据和模型在电脑里造一个「企业的虚拟替身」，可以拿来反复观察、推演。本项目说自己是「组织数字孪生」，就是给企业建了个虚拟模型来诊断。
类比：给公司拍了个会动的 X 光片。

## B. 产品与功能相关

**6. 诊断 — Diagnosis**
本项目核心动作：分析一家企业，找出增长卡点和根因，给建议。
类比：医生给病人看病。

**7. GA 按需诊断 — Growth Advisor（增长顾问）**
「按需」＝你什么时候想查，就触发一次完整诊断。
类比：你哪天不舒服，主动挂个号做全身体检。

**8. 哨兵 / Sentinel — Sentinel**
「定时哨兵」：按时间表（比如每天/每周）自动巡检企业健康，不用你触发。发现问题就报警、开「工单」。
类比：家里装的烟雾报警器，平时不动，有异常就响。

**9. 工单 — Ticket**
哨兵发现问题时生成的一张「待办提醒单」，记录「哪里不对、严重不严重、建议干嘛」。
类比：物业贴的检修单。

**10. 本体层 / 知识图谱 — Ontology Layer / Knowledge Graph**
本项目把企业知识（部门、人、钱、流程、因果）存成一张「关系网」。节点＝事物，边＝关系。
类比：把公司画成一张「谁连着谁、什么导致什么」的地铁线路图。

**11. 节点 / 边 — Node / Edge**
图里的两个基本元素：节点是「点」（一个人、一个部门），边是「连线」（A 导致 B）。
类比：地铁图里的车站和线路。

**12. 因果边 — Causal Edge**
一种特殊的边，表示「A 导致 B」的关系。本项目用它描述企业运转规律。
类比：线路图上标了「下雨→地面湿」这种因果箭头。

**13. 测量器 / compute — Measurer / Metric**
一组纯数学计算函数，输入企业数据，输出某个指标（如人效、现金流健康度）。它们不碰数据库，只算数。
类比：体检里的多项化验指标（血压、血糖……），每项单独测。

**14. 专家体系 — Expert System**
本项目内置几位「领域专家」AI（如组织能力专家、客户增长专家），分别审阅自己领域的诊断结果。
类比：医院里不同科室的主任医师联合会诊。

**15. ReAct 推理 — ReAct (Reason + Act)**
一种 AI 思考方式：推理（Reason）和行动（Act）交替进行，边想边查边干。
类比：侦探边推理边搜证，不是一次性想完。

**16. 信号聚合 — Signal Aggregation**
把各处零散的「异常信号」汇总、关联、判断严重程度，再决定要不要升级报警。
类比：把各处的火警探头信号汇总到消防控制室。

## C. 工程纪律与质量（CTO 用来盯代码守不守规矩）

**17. 工程纪律 — Engineering Discipline**
一套「写代码必须遵守的规则」。本项目最新版是《工程纪律·命中判据 Q1–Q15》，共 15 条（参数校验、密钥脱敏、统一错误处理……）。
类比：公司的员工守则。

**18. 门禁 / 铁律 — Gate / Iron Law**
提交代码前的自动检查（pre-commit），不达标就拦下，防止 AI 写出带病代码。铁律是规则编号（铁律 1、铁律 38……）。
类比：出厂前的质检流水线，不合格不让发货。

**19. 命中判据 — Hit Criterion**
判断「一条纪律到底守没守住」的具体标准。比如 Q-1 判定「参数校验要出现在工具接收用户输入的地方」。
类比：守则里「什么叫做到」的评分标准。

**20. 基线 — Baseline**
在某个时点、对代码实跑统计得到的「起点数字」，用来比较「改前 / 改后」。文档里基线锚 `f8b481e78`（2026-10-24 实跑）。
类比：体检时的「初始指标」，以后复查对比用。

**21. 改坏必红 — Break-it-must-go-red（突变测试思想 / Mutation Test）**
验证一条纪律「真生效」的办法：故意把代码改坏，看对应测试会不会变红（报错）。会变红＝纪律真在被守护。
类比：故意拔掉一根线，看警报会不会响；不响说明监控是假的。

**22. 两段式判定 — Two-stage Judgment**
判定纪律命中必须过两关：① 机制出现在**正确的位置**；② 有行为测试证明它生效（改坏必红）。只过一关不算。
类比：考核员工既要「活儿干在正确的事上」，又要「出成果能被验证」。

**23. fail-closed / fail-loud（失败即拒 / 失败即报错）**
两种「出错时的态度」：fail-closed＝遇到未知就**拒绝**（不降级放行）；fail-loud＝缺能力就**大声报错**（不悄悄给个兜底值）。
类比：门禁遇到刷不出身份的卡——fail-closed 是「不放行」，fail-loud 是「立刻响铃」，都不是「假装放行」。

**24. 快照测试 — Snapshot Test**
把某次运行的输出「拍照」存下来，以后每次跑都和这张照片比对，不一样就报错。用来防「不知不觉改坏了」。
类比：每天给文件柜拍张照，明天发现照片对不上就知道被人动过。

**25. 行为测试 — Behavioral Test**
测「软件行为对不对」（传非法参数就该报错），而不是只测「代码长什么样」。
类比：考驾照考「会不会开」，不是考「车漆颜色对不对」。

**26. 契约测试 / 后端契约 — Contract Test / Backend Conformance**
验证「存储后端（数据库实现）都遵守同一套规矩」。新写一个假后端，共享测试套件应该变红，说明契约在被人遵守。
类比：不管谁来供货，都得过同一套验货标准。

**27. 静默降级 — Silent Degradation（⚠️ 禁止）**
出错时一声不响地「带病运行」，既不报错也不标记。本项目明令禁止——必须 log + 返回 degraded 标记。
类比：车胎瘪了仪表盘却不亮灯，最危险。

**28. 反例必红 — Negative-case-must-red**
测试里必须包含「故意给错误输入」的例子，且它必须报错（红）。用来证明校验真的在起作用。
类比：测烟雾报警器必须真放烟，看它响不响。

**29. 假复用 / 假收口 — Fake Reuse / Fake Closure**
「代码写出来了（骨架在）」但没真接上、没真跑通（实证在）。项目反复栽在这上面。
类比：说「装好空调了」，其实只把外机摆着、没接管线——看着像，吹不出冷气。

**30. 骨架在 ≠ 实证在 — Skeleton ≠ Evidence**
上面的另一种说法：有代码结构 ≠ 功能真被验证过。

**31. 漂移 / 跑偏 — Drift**
文档说的和代码实际做的对不上，或不同文档互相矛盾。
类比：施工图改了，但贴在墙上的旧图没撕，工人按错图干活。

**32. 降级 — Degradation / Degraded**
某个功能失败时，系统不崩溃，而是「带病运行」并返回「我这边降级了」的标记，让上层知道。
类比：发动机一个缸坏了，车还能开但动力减弱，仪表盘亮黄灯。

**33. 契约优先 — Contract-first**
写代码前先定清楚「输入什么、输出什么、失败了怎么降级」，再动手。本项目铁律 47。
类比：先定好「你交什么材料、我给你出什么结果、出不了怎么办」，再开工。

**34. 控制塔 — Control Tower**
管理整个开发流程的「总调度台」，负责任务分配、状态跟踪、同步。
类比：工地上的指挥塔，看着所有吊车进度。

**35. 审计线（K3）— Audit Line**
独立于写代码的那条线，专门有人（Kimi K3，也是 AI）复查代码质量，防止写代码的人自己糊弄自己。
类比：工程监理，和施工队不是一拨人。

**36. 仪表盘 — Dashboard**
把关键指标（测试通过率、门禁状态、任务进度）集中显示在一个页面，一眼看清健康度。
类比：汽车仪表盘，速度/油量/故障灯一处看全。

## D. TypeScript 专业英语（你点名要学的，重点记）

> 本项目代码用 **TypeScript（TS）** 写。TS 是 JavaScript 的「严格版」——给变量加了「类型」这层约束，能在写代码时就拦住大量错误。下面都是 TS 里的高频词。

**37. 类型 / 类型系统 — Type / Type System**
「类型」就是给数据贴标签：这是数字、那是文字、那是「用户对象」。类型系统负责检查标签有没有用错。
类比：仓库里给每箱货贴「食品/易燃/易碎」标签，搬错就报警。

**38. 类型安全 — Type Safety**
代码被类型系统管住，不容易出现「把文字当数字算」这种低级错。本项目把它当铁律。
类比：有标签系统的仓库，出错概率低。

**39. 类型断言 — Type Assertion（`as`）**
程序员对某值「强行声明它的类型」。`x as User` 意思是「我保证 x 就是 User」。
类比：你指着箱子说「这里面就是食品」——是你担保，系统不再查。

**40. `as any` — `as any`（⚠️ 零容忍，禁用）**
一种「放弃类型检查」的写法。`x as any`＝「别管它是什么，全放开」。本项目铁律 38 严禁，因为等于拆掉护栏。
类比：把「食品」标签撕了说「随便啥都行」——最危险，47 次事故教训。

**41. `as never` / `as unknown as` — `as never` / `as unknown as`（⚠️ 同样禁用）**
和 `as any` 一类的「绕过类型检查」写法，本项目同样零容忍。
类比：换了个花样的「撕标签」，本质一样危险。

**42. 类型守卫 — Type Guard**
一小段代码，运行时判断「这个值到底是不是某种类型」，帮 TS 缩小范围。常见 `typeof` / `instanceof` 判断。
类比：入库前先拿仪器测一下「这箱到底是不是食品」。

**43. 类型收窄 — Type Narrowing**
经类型守卫判断后，TS 自动「知道」后面这段代码里变量就是某类型，不再让你重复判断。
类比：测完贴好标签，后面环节直接信标签。

**44. 联合类型 — Union Type（`A | B`）**
一个值「可能是 A，也可能是 B」。如 `string | number`。
类比：这箱货「可能是食品，也可能是日用品」。

**45. 交叉类型 — Intersection Type（`A & B`）**
一个值「同时是 A 和 B」。如「用户 & 会员」。
类比：这箱货「既是食品又是冷藏品」，两个标签都要满足。

**46. 泛型 — Generics（`<T>`）**
写函数/类时先不固定类型，留个「占位符 T」，用的时候再填。如 `list<T>` 表示「任意类型的列表」。
类比：做模具时先不规定尺寸，浇筑时再决定做小杯还是大杯。

**47. 接口 — Interface**
给「对象长什么样」定一份模板：有哪些字段、各是什么类型。别人按模板造数据。
类比：入职登记表模板：姓名(文字)、年龄(数字)……照着填。

**48. 类型别名 — Type Alias（`type`）**
给一个复杂类型起个短名字。如 `type ID = string | number`。
类比：把「食品或日用品」简称为「杂货」。

**49. 类型推断 — Type Inference**
TS 能根据你赋的值自动猜出类型，不必每次手写。如 `const n = 1` 自动知道 n 是数字。
类比：你放了个「1」进去，系统自动贴上「数字」标签。

**50. `unknown` 类型 — `unknown`（推荐用）**
「我不知道是什么类型，但先收着」。比 `any` 安全：用之前必须先用类型守卫查清。
类比：收到一个不明箱子，先放隔离区，验明身份前不许拆。

**51. `never` 类型 — `never`**
「永远不会出现的值 / 这条路永远走不到」。常用于「所有情况都处理完后的兜底」。
类比：传送带尽头有个「不该有任何东西到这里」的回收口。

**52. `Record` 类型 — `Record<K, V>`**
「键值对集合」的写法，`Record<string, number>`＝「键是文字、值是数字的对象」。
类比：花名册：名字(文字)→ 工号(数字)。

**53. 穷尽 switch / 穷尽性检查 — Exhaustive Switch**
写 `switch` 时把所有情况都列全，并用 `never` 兜底，确保「将来加新情况会编译报错提醒你」。本项目 Q-4 命中判据就查这个。
类比：排班表把周一到周日全排满，漏一天系统就报警。

**54. 可选 / 可空 — Optional / Nullable（`?` / `| null`）**
`age?: number`＝「年龄可有可无」。`| null`＝「可能是空」。
类比：登记表上「邮箱(选填)」。

**55. 模块 / 命名空间 — Module / Namespace**
把代码按功能分装成「一个个盒子（模块）」，互不污染。`import` 引入，`export` 导出。
类比：公司按部门分办公室，需要时用内线呼叫别的部门。

**56. 装饰器 — Decorator（`@xxx`）**
一种「贴在类/方法上的标注」，给它们附加额外能力（如标记这是个路由）。
类比：门上挂个「会议室」牌子，大家一看就知道用途。

**57. 枚举 — Enum**
把一组相关常量起好名字列出来，如 `enum Role { Admin, User }`，避免到处写魔法数字。
类比：把「1=管理员,2=用户」写成看得懂的名字。

**58. Promise / async / await — 异步（Asynchronous）**
「先发请求、不干等、好了再回来处理」的写法。`async/await` 让异步代码读起来像顺序执行。
类比：点外卖后先去忙别的，手机响了（await）再下楼取。

**59. 重载 — Overload**
同一个函数名支持「不同参数组合」，TS 按你传的参数选对应版本。
类比：同一个窗口，「寄信」和「寄包裹」走不同流程，但都叫「寄件」。

**60. 编译 / 转译 — Compile / Transpile（`tsc`）**
把 TS 代码「翻译」成浏览器/Node 能跑的 JS。`tsc` 是 TypeScript 编译器（同时做类型检查）。
类比：把中文稿译成英文稿，翻译时顺手把错别字（类型错）挑出来。

**61. 运行时 vs 编译时 — Runtime vs Compile-time**
编译时＝写/翻译代码的阶段（类型检查在这拦错）；运行时＝真正跑起来的阶段。
类比：彩排(编译时)发现台词错能改；正式演出(运行时)出错就真砸了。

## E. 架构与代码组织（为「代码地图」铺垫）

**62. 架构层 ⓪–⑥ vs 代码分层 L1–L5 — Architecture Layers vs Code Layering（两回事，宪章明令不许混）**
本项目里有**两套完全不同的「层」，不能混为一谈**（宪章 v8.3 §4.8.2 原话「两套层不许混」）：
- **架构层 ⓪–⑥** ＝ 《产品宪章》定义的「产品长什么样」：⓪连接器 → ①循环 → ②本体 → ③哨兵 → ④参数 → ⑤导航，外加 ⑥进化回环 和 −1 运行时引擎。这是**向客户交付的东西**，详见《代码架构人话地图》。
- **代码分层 L1–L5** ＝ 管 `src/` 代码里 `import`（引用）方向的工程纪律（上层只能依赖下层），只是**代码整洁度要求，不是产品架构**。
⚠️ 易混点（宪章原话）：`src/l4`（代码层）**不等于**架构层②本体（其载体是 `extensions/ontology/`），二者不是同一张图。一句话记死：**⓪–⑥ 是产品，L1–L5 是写代码的内部规矩。**

**63. 调用链 / 接线 — Call Chain / Wiring**
一个功能从「用户点一下」到「结果出来」，中间经过哪些函数调用。本项目铁律要求「新功能必须有完整调用链，不能写了代码没接上」。
类比：快递从下单到送达的全程路由，断一环就送不到。

**64. 依赖方向 — Dependency Direction**
谁允许「认识」谁。本项目规定只能「上层依赖下层」，禁止反过来（铁律 39）。
类比：仓库可以听调度安排，但调度不能绕过科长直接翻仓库箱子。

**65. 入口 — Entry Point**
程序「从哪开始跑」的文件。`server.ts`（HTTP 服务）、`electron-main.ts`（桌面端）、`cli.ts`（命令行）、`index.ts`（主入口）。
类比：门店的大门 / 公司的前台接待处。

**66. 路由 — Route**
把「不同的网址请求」分配到「对应的处理函数」。如 `GET /api/diagnose` 交给诊断函数。
类比：总机接线员，按分机号转给对应部门。

**67. 中间件 — Middleware**
请求在处理前/后「经过的一道工序」，如身份验证、日志记录。
类比：进门先过安检、再登记，一道道工序。

**68. 适配器 — Adapter**
把「外部系统的接口」转成「本项目能懂的格式」。如把不同大模型 API 统一成一套调用方式。
类比：万能转换插头，不管什么插座都能接上。

**69. 插件 — Plugin**
可插拔的功能扩展模块。本项目 `dsh/` 目录就是 DSH 的插件代码。
类比：手机外接镜头，装上就有新功能。

**70. 分支 / 主干 — Branch / Trunk (main)**
代码的一条「平行时间线」，可以单独开发新功能而不影响主线（main）。开发完再合并回主干。
类比：先画个草图稿（分支），定稿了再贴回正稿（主干）。

**71. 提交 — Commit (git)**
把改好的代码「存档并留记录」一步。每次提交有个说明，记录「这次改了啥」。
类比：每次改动盖个章、写个日记。

**72. worktree（工作树）— Worktree**
让多个 AI 同时在不同「副本」上改代码、互不打架的机制。
类比：同一栋楼里隔出几间独立办公室，各干各的，最后再合并。

## F. 数据与运维

**73. SQLite — SQLite**
一种「轻量、单文件」的数据库，本项目用它存会话等数据。
类比：一个 Excel 文件就能当数据库用，不用另开服务器。

**74. schema 版本 — Schema Version**
数据库「表结构」的版本号。本项目 Q-8 要求：版本对不上就拒绝启动（防旧数据被新代码读坏）。
类比：文件柜的目录体系版本，版本不符就不让你乱翻。

**75. 键值存储 — Key-Value Store (Kv)**
「名字→值」最简单的数据存储，如 `getUser('张三')→用户对象`。本项目有 Kv 后端契约测试（Q-9）。
类比：字典：查词(键)→释义(值)。

**76. 持久化 — Persistence**
把内存里的数据「存到硬盘」，关掉程序再开还在。
类比：下班前把活儿存进文件，第二天接着干。

**77. 凭证 — Credential**
登录凭据（密码、Token）。本项目 Q-13 要求「读到的凭证不能露出具体值」，只能显示「已配置」。
类比：工牌里存着你的身份，但别人不能偷看工牌里的照片。

**78. 脱敏 / 擦除 — Redaction / Scrub (PII)**
把敏感信息（手机号、密钥）在日志/上报里抹掉。PII＝个人可识别信息（Personally Identifiable Info）。
类比：发朋友圈前给身份证号打码。

**79. 加密 — Encryption**
把数据变成只有钥匙能解的乱码，防泄露。
类比：把信锁进保险箱，只有钥匙能开。

**80. 运行时 — Runtime**
程序「正在跑」的那个环境（Node.js 等）。和「编译时」相对。
类比：正式演出的舞台。

**81. 构建 / 打包 — Build / Bundle**
把源码「编译 + 拼装」成可发布的成品。桌面端要打包成 exe/app。
类比：把散件组装成一台能卖的整机。

**82. 容器 — Container（如 Docker）**
把程序连同它的运行环境「打包成一个标准箱子」，到哪都能一模一样地跑。
类比：集装箱运输，港口不同但箱子一样好卸。

**83. 端口 — Port**
程序对外「开门营业」的编号（本项目默认 3000）。别的程序通过这个端口找它说话。
类比：大楼的哪个门（3000 号门）能进。

**84. 环境变量 — Environment Variable**
不写死在代码里、运行时从外部注入的配置（如密钥、端口）。`.env` 文件存放。
类比：便签贴在显示器边，程序启动时自己看，不在代码里写死。

**85. 日志 / 审计 — Log / Audit**
程序运行时留下的「流水账记录」，出事时用来查「刚才发生了啥」。
类比：飞机黑匣子。

**86. OTel / 遥测 — OpenTelemetry (Telemetry)**
一套「把程序运行数据上报出去」的标准。本项目 Q-14 要求上报前先脱敏、未知字段要拒收。
类比：给设备装传感器，数据回传监控中心（但先打码）。

**87. 并发 / 锁 — Concurrency / Lock**
「多个任务同时跑」时的协调。本项目 Q-12 要求超并发上限要报错并给可执行指引。
类比：多个窗口同时办业务，限流叫号，挤爆了就提示「请稍后」。

**88. CI / CD — 持续集成 / 持续部署（Continuous Integration / Deployment）**
CI＝频繁把大家的代码合到一起自动测试；CD＝测试过了自动发布。本项目门禁就在 CI 里跑。
类比：每天收工把各工地的活拼一起先试装一遍（CI），试通了再发货（CD）。

**89. pre-commit / pre-push — 提交前 / 推送前钩子**
代码「提交 / 推送到仓库前」自动跑的检查脚本，不过就拦下。本项目 13 组门禁在 pre-commit。
类比：出厂前（提交）/ 发货前（推送）的质检。

## G. 本周新增术语（2026-10-27）

**90. 裁定 / 裁决 — Ruling / Adjudication（常用「裁 XXX」）**
CTO 拍板定下的正式决定，带编号（如「裁 421」）。在本项目里是"最终裁判"，后面的活都得照它办。
类比：法官的判决书，编号存档，全员按它执行。

**91. 缺口 — Gap**
该有却没有、或该做却没做实的地方。本周 M7 就查出"七卡缺口"。
类比：墙看着完整，其实有几个没补的洞——不补，一推就塌。

**92. 收口 — Closeout**
把一个模块"彻底做完 + 验证通过 + 关单"的全过程。本周「853 模块收口」就是把积压工单清账。
类比：装修完最后一验、交钥匙、销账——不是"写得差不多"，是"验完签字"。

**93. 形态 — Form / Mode**
软件"以哪种姿势运行"：开发模式（dev，程序员自己跑）、打包形态（bundle，发给客户）、客户形态（真实部署）、桌面形态（Electron 装成软件）。同一种功能在不同形态下可能表现不同。
类比：同一个人，穿便装(d)、穿工服(bundle)、穿正装(客户)——看着是一个人，能干的活可能不一样。⚠️ 项目反复强调：在 dev 下跑通 ≠ 客户形态下跑通。

**94. 在飞 / 在飞 PR — In-flight (Pull Request)**
已经写好、正在走审查、但**还没合进主线**的代码改动。
类比：已经发货、还在路上的快递——没签收就不算你仓库里的货。本周大量真活在"在飞"状态，主线(main)是空的。

**95. 亲验 — Direct / Personal Verification**
不轻信"宣称已做完"，自己跑一遍、看原始输出。本周 M7 就是靠"三处亲验"推翻了旧结论。
类比：不看法条说"合格"，自己上手试一下才知道真不真。

**96. 复审 — Re-review**
标"做完"之后，再回头查一遍有没有"假收口"。
类比：二次质检——头道过了，再抽一道，专抓"看着过其实没过"。

**97. 派单 — Dispatch / Ticket Assignment**
把一项任务正式派给某个 AI（Codex/DSH/Claude Code）去写代码，附规格与判据。
类比：工头把施工图和验收标准派给班组。

**98. declared-only（只宣不做）— Declared-only**
一种"假收口"：数据文件在、探针报绿、文档写"已实现"，但**生产代码压根没真正用上它**。本周 M7 就是典型。
类比：说"空调装好了"，其实只把外机摆着、管线没接——看着像，吹不出冷气，还骗过了检测仪。

## E 组 · 安全与失败处理（2026-10-28 今日提交解读时补）

**99. 失效开放 / 失效关闭 — fail-open / fail-closed**
出岔子那一刻，系统是"放你过去"还是"把你拦下"。涉及数据权限必须 fail-closed。
类比：门禁坏了，是大开（open）还是锁死（closed）。

**100. 降级 — degraded / degradation**
没全坏但打了折，并且**明确告诉你打折了**（代码写 `degraded: true` + `code`）。
类比：餐厅说"鱼没了给您换菜"叫降级；**不说**偷偷换叫"静默降级"（违规）。

**101. 静默兜底 — silent fallback**
出错不报错，自己猜一个值继续跑。**危险：调用方以为在查 A，实际拿到全量。**
类比：客户填"数量：abc"，你不回电，自作主张发 7 件。

**102. 判错对象 — wrong target**
检查通过了，但**检查的不是你那份东西**（自动 fallback 找到别人的 brief 来判）。
假绿比红灯更危险——红灯你会修，假绿你不知道有问题。

**103. 失败要出声 — fail-loud**
出错必须打日志/报警，不许闷声。项目铁律 11/24/31 都在管这个。

**104. 类型断言 — type assertion（as any / as never / as unknown as）**
对编译器喊"别管了，我说它是什么就是什么"＝关掉类型检查。项目铁律 38 **零容忍**。
替代：内联类型 `as { field?: string }` / `Record<string, unknown>` / `unknown` + 类型守卫。
类比：过安检说"别查了，肯定没违禁品"。

**105. 类型守卫 / 类型收窄 — type guard / narrowing**
用 `typeof x === 'string'` 这类**运行时**判断，把不确定类型一步步缩成确定类型。类型断言的正确替代品。

## F 组 · 测试与门禁（2026-10-28 补）

**106. 夹具 — fixture**
测试时临时造的假环境/假数据，让测试能稳定复现。类比：驾校练车场，不是真马路但能考侧方停车。

**107. 死码 / 死分支 — dead code / dead branch / no-op**
写了但**永远执行不到**的代码。危险在"让人误以为有保护"。铁律 37：死码进仓库即违规。
类比：墙上的假消防栓——看着有，着火没水。

**108. 垫片 — shim**
为兼容/过渡加的一小层代码，本身不干正事。

**109. 变异测试 — mutation testing**
**故意把代码改坏**，看测试会不会变红。会红＝测试真有用。项目行话叫**「改坏必红」**。
类比：验钞机好不好？塞张假钞，它叫才算合格。

**110. 判别力 — discriminating power**
一个检查能不能分清"对"和"错"。永远绿灯的检查，判别力为零。
类比：体温计永远 36.5℃，测不出你发烧。

**111. 接线 — wiring**
代码写好了 ≠ 用上了。接线＝真正接进系统被调用。类比：灯泡买了但没接电线，永远不会亮。

**112. 认领 / 写集 — claim / writeset**
改代码前先登记"我这次要动哪几个文件"。动了清单外＝越界被拦。
类比：施工报批"只改 3 楼两间房"，结果去拆承重墙，监理叫停。

**113. 退出码 — exit code / return code (rc)**
命令跑完用数字报告结果：**0＝成功，非 0＝出问题**。

**114. 门禁 / 闸 — gate / pre-commit hook**
代码进仓库前要过的自动检查关卡。项目里"闸①闸②闸③"是三道不同质检站。

**115. 指纹缓存 — fingerprint cache**
用"文件最后修改时间 + 文件大小"当指纹判断文件变没变，变了才重读，省性能。

**116. 回退 / 回滚 — revert / rollback**
把刚做的改动撤回来。`git revert` 是生成一个"反向提交"，不删历史。

**117. 空跑 / 空绿 — skipped / vacuous green**
显示成功，但**关键那一步根本没跑**（被判跳过）。比红灯更骗人。

**118. 审查疲劳 / 噪音 — review fatigue / noise**
改动太大（如一次 2049 行），审查者看不出真改了什么，真风险被淹没。
项目自己写过："噪音会导致整条门禁链被绕过"。

**119. 原子提交 — atomic commit**
一个提交只做一件事。格式化单独提交，功能改动单独提交。

**120. 逃生舱 / 豁免清单 — escape hatch / exclusion list / allowlist**
规则允许显式豁免（如跳过 `tests/**`），比"偷偷扭曲代码绕过检查"健康得多。

## G 组 · 门禁治理（2026-10-28 门禁膨胀专题补）

**121. 门禁膨胀 — gate sprawl**
检查越加越多、只加不减。本项目实测：检查器 8月 0 → 9月 8 → 10月 18 → 现在 32；
近 30 天新增 74 个脚本、删除 3 个（**25:1**）。
类比：公司制度越写越厚，最后没人看得完，也没人执行。

**122. 门禁退役 — gate retirement**
把过时/没用的检查撤掉。仓库里有退役规则（`GATE-INVENTORY.yaml` 的 keep/replace/retire/pairing），
但实测**没电**：判据依赖的 `gate-hits.log` 被 .gitignore 忽略 ⇒ 数据拿不到 ⇒ 实际退役 0 个。
类比：制度写了"过期作废"，但从没人真的去清理。

**123. 孤儿检查器 — orphan checker**
写了但没有任何地方调用的检查脚本。机器复算出 6 个孤儿，最后只判 2 个退役候选，实际退役 0。

**124. 零命中退役 — zero-hit retirement**
一道门禁如果连续 90 天没拦住过任何东西，说明它没用 ⇒ 自动进退役候选，无需讨论。
类比：装了三年没响过的报警器，该拆了。

**125. 门禁预算 — gate budget**
给检查总耗时设硬上限（建议 pre-commit ≤ 90 秒、PR 的 CI ≤ 15 分钟），超了必须砍门禁。
类比：部门预算，花超了就得减项目——不能无限加。

**126. 一进一出 — one-in-one-out**
加一道新检查，必须退役或合并掉一道旧的。用来把现在 25:1 的比例扭到 ≤ 2:1。

**127. 豁免债 — exemption debt**
累积的"这次先不查我"条数。本项目 **86 份豁免，含到期日的仅 1 份、含责任人的 0 份**
⇒ 等于"一次豁免 = 永久豁免"。类比：欠债，越积越多迟早要还。

**128. 日落条款 — sunset clause**
规定"到某天自动失效"，逼人回来复查。豁免和门禁都该有。

**129. 举证责任 — burden of proof**
谁负责拿出证据。健康的设计是"做了的人举证"，不是"没做的人自证清白"。
本项目 §7.4 写的「不适用也要举证」把责任反转了 ⇒ 成本放大器。

**130. 判据重叠 — overlapping criteria**
两条检查其实在查同一件事，却要证明两次。实证：
品味 2「typed error 带 code」＝ 纪律 Q-3；品味 3「fail loud」＝ 纪律 Q-7 ＋ Q-15 ⇒ 23 格里至少 3 格重复计价。

**131. 管理开销 — overhead**
为了管理而付出的成本，不直接产生客户价值。写门禁脚本（3150 行/日）、
豁免（86 份）、认领文件（48 个文件次）都属于 overhead。

**132. 自动化门禁 vs 规范 — automated gate vs standard**
**标准**＝代码应该写成什么样（目标，写进规范让 AI 照做）；
**门禁**＝机器自动拦住不合规的（手段，跑一次就完事）。
现在的错误是把每条标准都做成"每次交付必须人工举证的格子"。

**133. 抽检 — spot check**
不每次都查，随机抽一部分查。适合纯文书类标准（头部契约、README 骨架）。
类比：质检抽验，不是全检。
