**6.8 建议的结构（`proposal_only` 的产物，五段缺一不可）**

> **为什么单列**：本阶段**只给建议、不做执行**（创始人 2026-10-20 令）。"建议"若不结构化，就无法判质量、无法记录、无法校正——会退化成"评论"。

| # | 段 | 字段 | 为什么必须 | 判据（机器可判） |
|---|---|---|---|---|
| **1** | **动作** | `suggestedActionType`（∈ `action-types/` 的 `$id`） | 人要知道"做什么" | 值 ∈ 已声明的 action `$id` 集合 |
| **2** | **参数** | `suggestedActionParams`（对象/数值/目标） | 不能让执行者猜 | 每个参数能对到 ② 的属性或 ④ 的测量值 |
| **3** | **预期效果** | `expectedEffect`（哪个指标、变多少、**置信区间**） | 人才能判"值不值得做" | 含指标名 + 方向 + 幅度 + 区间；**无区间的判红**（是承诺不是预测） |
| **4** | **前置条件** | `preconditions`（依赖/审批/时机） | 防止做错时机 | 至少 1 条；空 = 假设"随时可做"，须显式写"无" |
| **5** | **回滚方式** | `rollback`（怎么撤） | 可逆判据（§4.7.2 判据 1） | 非空；写"不可撤"即触发 🔴 判红 |

**建议的最小形态（示例，非规范条文）**：

```
suggestedActionType: action/close_channel
suggestedActionParams: { channel: 抖音, from: 2026-11 }
expectedEffect: { metric: 毛利率, direction: +, magnitude: 2.5pp, ci: [1.2, 3.8] }
preconditions: [该渠道近 3 月贡献 < 5%, 客户确认关停不影响存量]
rollback: 重新开启该渠道 + 恢复预算（可逆）
```

**6.9 可执行性判据（四条，全过才算"可用建议"）**

| # | 判据 | 怎么判 | 不过的样子 |
|---|---|---|---|
| **1 可执行** | 人照做能完成 | 含 **≥3 步**操作序列，不需要再问 | "提高转化率"——没步骤 |
| **2 可验证** | 做完能验 | `expectedEffect` 有可测指标 + 观察期 | "效果会更好"——无指标 |
| **3 可逆** | 做错能撤 | `rollback` 非空 | "不可撤" |
| **4 有责任** | 谁做谁负责 | `owner`（执行人）+ `approver`（确认人）两字段 | 只有"建议方"没有执行方 |

**反馈用途**：`decision` + `result_ref` 回校建议质量（采纳率、采纳后有效率）；**没有这条链，建议永远不知道对错**。

**状态机（`proposal_only` 下）**：

```
**状态机（以 18:119 为准，`execution_status` 字段）**：

```
none → proposed → approved → executed / failed / rolled_back
```

- **今天只走到 `approved`**（客户拍板）；`executed/failed/rolled_back` 是预留（18:119）。
- **`viewed/adopted/rejected/deferred` 不是 `execution_status`**——它们是"建议决策"的独立字段（§6.10 的 `decision`），两者不许混用同一字段。
- **`executed_by` 在 `proposal_only` 下只能是 `human`**；出现 `system` ⇒ 判红（越权执行）。

**建议→结果的回流**：`decision` → `executed_at`（人执行）→ `result_ref`（④c）。
```

> **系统不执行**：`execution_status` 在 `proposal_only` 下**只能停到 `executed`（人执行）**；系统侧不写 `executed_by=system`。若出现 `executed_by=system` 而 `executionMode=proposal_only` ⇒ **判红**（越权执行）。

**反例（什么会证明本章写错）**：若 `expectedEffect` 的置信区间在 SME 场景下无法给出（数据太少），则"无区间判红"会让大部分建议不可用——此时应改为"区间可空，但必须标 `ci_unavailable` 并降级置信度"，**不许沉默**。

**反例（什么会证明本章写错）**：若 12 个月内 `writableProps`/`actionRefs` 零消费者，按 18:198 精简（预留变死字段）。若 `execute` 开启但无适配器，`execution_status` 停在 `proposed`——此时"契约有效"仍成立，但"执行"是假的，须在台账如实标 `execution_ref=null`，不许补假 ID。

### 11.9 决策-结果存储（action 四件 ＋ executor 抽象）

> **为什么单列**：创始人 2026-10-20 定「哨兵的计算必须有一个地方存储」——没有存储，**行动带来什么变化、决策造成什么后果、上季度与本季度差在哪、时序与趋势怎么算、决策-结果因果怎么判**，全部无从谈起。本节规定"存什么、怎么存、怎么关联"。

#### 11.9.1 借 Palantir 的四件（不搬平台形态）

> **依据**：11 号件 `:20`「action 的运行机制里，**可搬的是四件：参数类型 → 提交条件（纯谓词）→ 单事务 → 审计行**；不可搬的是面向用户的操作面、writeback dataset、副作用编排、revert」；`:60`（H-R3）「台账写入可复用四件，不必搬 action type」。

| # | 件 | 本规范要求 |
|---|---|---|
| **1** | **参数类型** | 定义 `action-types/`：每个动作类型有 `$id`、参数 schema、前置条件、预期效果定义 |
| **2** | **提交条件** | 纯谓词（不依赖外部系统状态），写在 `preconditions` |
| **3** | **单事务** | 动作 + 结果验证**同事务**写；半写即红 |
| **4** | **审计行** | 一条记录，含谁/何时/什么/结果/裁决 |

**不搬的四件**（照搬会死）：
- ❌ **writeback dataset**：客户系统无写接口（01:411）；撞宪章 4.7
- ❌ **副作用编排**：平台级工程量，SME 场景不需要
- ❌ **revert**：我们不写客户系统，无需回滚客户数据
- ❌ **用户操作面**：我们有对话口/界面，不需要 Workshop

#### 11.9.2 `executor` 抽象（**不做"人 vs 系统"的二分**）

> **最关键的一条**：Palantir 的 action 本质上**执行者无关**（只是它默认系统执行）。**不得把本规范写成"人的决策记录"**——那样未来 agent 执行时模型就废了。

| 概念 | 今天 | 未来 | 说明 |
|---|---|---|---|
| `executor` | **`human`** | **`agent`** | **字段，不是设计前提** |
| `executionMode` | `proposal_only` | `execute` | 与 executor 是**同一件事的两面** |

**判据**：
- `executor` ∈ `{human, agent}`（可扩展，但必须先登记）
- `executionMode = proposal_only` ⇒ `executor` 只能是 `human`
- `executionMode = execute` ⇒ `executor` 可为 `agent`（仍受 §11.7 的 ④b 写入约束）
- **同一张审计行、同一套验证**——从人切到 agent **不改表结构**

#### 11.9.3 一条记录，七个字段

| # | 字段 | 语义 | 必填 | 判据 |
|---|---|---|---|---|
| **1** | `actionType` | 动作类型（`$id`，∈ `action-types/`） | ✅ | 值 ∈ 已声明 action `$id` 集合 |
| **2** | `params` | 参数（对象/数值/时间） | ✅ | 每个参数能对到 ② 属性或 ④ 测量值 |
| **3** | **`executor`** | **谁执行**（`human`/`agent`） | ✅ | ∈ `{human, agent}` |
| **4** | `preconditions` | 提交条件（纯谓词） | ✅ | 至少 1 条；空须显式写"无" |
| **5** | `expectedEffect` | 预期（指标+方向+幅度+**置信区间**） | ✅ | 无区间须标 `ci_unavailable`（不许沉默） |
| **6** | `verdict` | 裁决（`hit`/`deviation`/`reverse`） | ✅（结果回来后） | 三态；不得只写 pass/fail |
| **7** | `run_id` | 与 `metric_readings` 的关联键 | ✅ | **能 JOIN**：`decision.run_id = metric_readings.run_id` |

> **受 §10 验收线约束**：决策记录同样必须带 **`source`（来源）＋ 数据月数**——宪章 §4.3 的验收判据是「`source` ＋ 数据月数」，**不是置信度**（那个字段今天被伪造，先不认）。缺 `source` ⇒ 不出结论；缺数据月数 ⇒ 降级。

#### 11.9.4 决策-结果因果：靠 `run_id` 关联，不建因果表

> **不新建"决策台账表"**——Palantir 也没有"决策表"（它用 action 的审计行）。
> **关联方式**：决策行带 `run_id`，`metric_readings` 行也带 `run_id` ⇒ 同一决策的"预期 vs 实际"可 JOIN 查询。

**⚠️ 决策行是图边，不是 SQL 表**（`decision-capture.ts` 写 `createEdge`）——不要写 `FROM decision_ledger`。

复盘查询的形态：
1. 用 `decision-ledger-readback.ts` 的 `queryEdges` 取决策边（按 `run_id` / 时间窗）
2. 用 `metric_readings` 按同 `run_id` 取指标行
3. 在应用层 JOIN（不是 SQL JOIN）

**判据**：给定一个 `run_id`，能取到该决策的"预期"（决策边 props）与"实际"（`metric_readings` 行）两组数。

#### 11.9.5 载体：扩展现有入口，不新建第三套

> **现状**：`src/l4/decision-capture.ts`（自称"决策台账单一入口"，K12-08）已实现审计行 + `verdict` + 回流；但它**写"边"**（`createEdge`），且缺 `expectedEffect`/`run_id`。
> **规范要求**：**单一入口不得新增第二套**；`src/growth/decision-record.ts` 的裸节点路线（`DECISION_RECORD` 不在类型系统）须**并入或降级**，不得与台账并行。

**判据**：全仓写决策台账的路径**只有一处**（现状有 `DECISION_LEDGER_SCHEMA` 锚点可作反证：`grep -rn "export const DECISION_LEDGER_SCHEMA" src/` = 1（⚠️ 用 `grep -rn "decision-ledger/v1"` 会命中 **2 行**：`decision-capture.ts:41` 的定义 ＋ `:37` 的注释示例；判"定义唯一"必须排除注释） 应只命中一处定义）。

#### 11.9.6 从"给建议"到"agent 执行"的平滑演进

| 阶段 | `executionMode` | `executor` | 系统做什么 | 记录 |
|---|---|---|---|---|
| **现在** | `proposal_only` | `human` | 给建议、记录人做了什么、验证结果 | 同一张审计行 |
| **未来（客户授权后）** | `execute` | `agent` | agent 执行、同一套记录、同一套验证 | **同一张审计行** |

**判据**：从 human 切到 agent，**不改表、不改判据、不改验收**——只改 `executionMode` 与 `executor` 两个值。
