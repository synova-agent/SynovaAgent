# SynovaAgent 文档契约 v1.0

> **给非技术读者的一句话**：这份契约规定了「什么该写进仓库、写成什么样、由谁维护」。
> **它要解决的一件事**：我们把「过程」也提交进了仓库 —— 每一份卡、日报、分类、派单都变成一次提交，
> 于是仓库臃肿、CI 满载、PR 积压、新人无从下手。**文档多不是问题，什么都提交才是问题。**

---

## 0. 第一性原理：为什么我们和 DSH 不同

我们借鉴 DeepSeek Harness（国内顶级团队）的文档体系，但**不复制**。因为前提不同：

| 维度 | DSH | **我们** |
|---|---|---|
| 团队 | 20 人 + 人的记忆沉淀 | **无技术背景创始人 + 几个 AI 助手** |
| 平台层 | PR / issue 有人读 | **创始人不会去翻 PR 列表；AI 没有人的记忆** |
| 记忆载体 | 人 + 平台 + 仓库 | **只有仓库** |
| ⇒ 结论 | 过程可以不入库 | **思考必须入库；痕迹不入库** |

**⇒ 我们与 DSH 唯一根本分歧**：它可以让过程不入库；**我们不能**。
**⇒ 因此本契约的命题是：痕迹不入库，思考必须入库，且思考必须「双读者可读」。**

**学 DSH 什么（形状） / 不学什么（前提）**：

| ✅ 学 | ❌ 不学 | 原因 |
|---|---|---|
| 四态生命周期 + 类别闭集 + **路径即元数据** | 双语 + 1743 个 i18n sidecar | 内部单语项目，抄它自增 3 倍文件量 |
| **格式由门禁强制**（不靠自律） | 3539 个 note 的规模 | 我们起步，先做质量 |
| **必须写「考虑过的其他方案」** | 「过程完全不入库」 | 见上表：我们的仓库就是记忆 |
| **禁止中央索引**（用 `git grep` 检索） | 15 组 gen/verify 对账 | 先做 3 组（见 §6） |
| **取代链强制 + 归档后冻结** | 用「词数 / 年龄 / 配额」决定归档 | 同 DSH：改用「是否仍有未来指导价值」 |
| PR 三段式模板（动机/变更/证据） | — | 过程留痕的平台层载体 |

## 1. 唯一判据（写任何东西之前先问）

> **❓「3 个月后一个新人，是否必须靠它才能理解我们为什么这样做？」**
>
> **✅ 是** ⇒ 写入 **B 决策层**（`decisions/`）
> **❌ 否** ⇒ **不写进仓库**（写 PR 正文 / commit message / 卡 note）

**这一问就砍掉我们大部分 md** —— ⚠️ **具体数字不写在本契约**（本契约只定规则）；
**现行数字见 `docs/synova/STATE.md` §4（那里每值带 as_of 与取数命令）。**

## 2. 五层归属（每份文档/记录必须归属且仅归属一层）

| 层 | 位置 | 内容 | 维护者 | 维护方式 |
|---|---|---|---|---|
| **A 入口** | `README.md`、`AGENTS.md`、`CLAUDE.md`、`docs/synova/STATE.md` | 这是什么 / 规则是什么 / **现在到哪了** | 创始人 + CTO | **重写式**（不追加） |
| **B 决策** | `decisions/{lifecycle}/{class}/YYYY-MM-DD-topic.md` | **为什么这么做**、考虑过什么、放弃了什么 | **做决定的人**（不代笔） | 四态 + 取代链 |
| **C 长期** | `docs/**` | 指南 / 架构 / API / 领域知识 / 术语表 | 各域作者 | 一主题一份，禁中央索引 |
| **D 过程** | **不入库** | 做了什么、进度、分类、派单、验收、探针、日报 | 各 session | **PR 正文 + commit + 卡 note** |
| **E 生成** | 不入库或标注 | 看板 / 水位 / 清单 / 测试输出 | 生成器 | 三条同时满足方可入库 |

### 2.1 A 层：入口（新人 30 分钟路径）

| 顺序 | 文件 | 回答 | 上限 |
|---|---|---|---|
| 0–5 min | `README.md` | 这是什么；怎么跑起来 | 重写式，短 |
| 5–15 min | `AGENTS.md` | 规则是什么（铁律 / 门禁 / 流程 / 怎么提交） | 重写式 |
| 15–20 min | `docs/synova/STATE.md` | **现在到哪了**（阶段 / 在做什么 / 下一步 / 卡在哪） | **≤200 行，重写式** |
| 20–25 min | `decisions/` 最近 5 条 | 关键决策与为什么 | 见 §3 |
| 25–30 min | `docs/synova/architecture/` | 系统结构 | 见 §4 |

**三条硬规矩**：
1. **A 层是「重写式」的** —— 每次更新**重写**，不做追加（追加即变流水账 = 痕迹）
2. **`STATE.md` 是「现在到哪了」的唯一答案** —— 不允许第二个进度文件
3. **禁止新建任何索引 / 台账 / 看板 md（主仓库范围内）** —— 库外资产仓另见 §11（其 `INDEX.md` 是**库外**索引，不在本条约束内）（照 DSH：*"Do not add a centralized INDEX.md"*）—— 要检索用 `git grep`

### 2.2 B 层：决策记录（本契约核心）

**结构（路径即元数据）**：
```
decisions/{lifecycle}/{class}/YYYY-MM-DD-topic-title.md
```

**lifecycle 四态**（文件在文件夹间移动 = 状态变化）：
- `proposed/` —— 提案，评审中，尚未落地（或部分落地）
- `implemented/` —— 已落地；**并与实际交付保持一致**（改路径/改名/改默认值时同批更新事实，不改决定本身）
- `rejected/` —— 否决；**仅当其理由能阻止一个诱人的错误时才保留**，否则连同三元组删除
- `archived/` —— 冻结：已完成、理由不再指导未来、但仍有历史价值

**class 闭集（六类，门禁强制；新增类别须先改门禁与本节）**：
| class | 覆盖 |
|---|---|
| `product` | **产品方向 / 用户 / 定位 / 商业模式** ← 我们独有（DSH 没有） |
| `architecture` | 结构、分层、数据流、契约 |
| `process` | 流程、门禁、工具、协作方式 |
| `feature` | 新的用户或模型可见能力 |
| `bug-fix` | 缺陷修复及其教训 |
| `simplification` | 删除 / 简化（不新增能力） |

**文件格式（门禁强制：六段缺一不可 —— 2026-09-26 按 K3 判据③定版）**：
```markdown
# 决策: <标题>

状态: <proposed | implemented | rejected — 原因>
日期: YYYY-MM-DD

## 一句话
（**给非技术读者**：这个决定改变了什么。≤50 字，禁止未解释术语）

## 问题
（什么场景、什么痛点。必须让不懂技术的人读懂）

## 决定
（决定了什么 + 为什么这么定）

## 考虑过的其他方案        ← 强制。缺少它 = 阻断
（有哪些、为什么不选。写不出就写「未记录（pre-format）」并登记）

## 后果
（好的 / 坏的 / 要长期承担什么）

## 取代
（取代了谁 / 被谁取代 —— **相对链接**，机器可核）
```

**两条我们独有的要求**（因创始人无技术背景）：
1. **`## 一句话` 必填** —— 让你 30 秒知道「这改变了什么」
2. **`## 问题` 段禁止未解释术语** —— 术语须在 `docs/synova/GLOSSARY.md` 中可查

**取代链（强制流程）**：
```
写新决策前 ⇒ 必做三步：
  ① grep 同主题旧决策 → 列出候选
  ② 判「全部取代 / 部分取代 / 不取代」
  ③ 全取代 ⇒ 同一 PR 内归档旧的（移动 + 加 `Archived:` + 冻结）
     部分取代 ⇒ 双方互加相对链接
⇒ 未输出「候选清单 + 判定」= 阻断（可为「无候选」，但必须显式写）
⇒ 目的：根治「同一决定有 5 份文档各说各话」
```

**归档即冻结**：归档的决策文件**不得再编辑、翻译、重排、移动或删除**。

### 2.3 C 层：长期文档

- **一主题一份**；发现重复 ⇒ **合并**，不新增
- **禁止中央索引**
- 允许子目录：`architecture/`、`implementation/`、`runbooks/`、`setup/`、`research/` 等
- 现有 `docs/synova/**` 按 §7 迁移（**数量不写在此** —— 见 `STATE.md` §4 或跑枚举命令）

### 2.4 D 层：过程（**不入库**）

**PR 三段式**（唯一过程载体）：
```markdown
## 为什么（Motivation）
（一句话：解决什么问题 / 给谁 / 不改会怎样）

## 改了什么（Changes）
（命令 / 配置 / 接口 / 行为变化；用户可观察的变化优先）

## 怎么证明（Testing）
- 方法：
  <details><summary>证据</summary>
  （原始输出 / 截图 / 日志）
  </details>
```

**其余过程痕迹**：`commit message` + 卡 note（`task-state/<D>.json` 的 `note` 字段，一卡一文件，**不派生 md**）。

### 2.5 E 层：生成物

**三条同时满足才可入库**：① 文件头标 `GENERATED` ② `.gitattributes` 标 `linguist-generated` ③ **配 `--check` 对账**
**缺任一 ⇒ 不得入库**。现状缺口：`DASHBOARD-CN.md`、`tests/output/**`、`.claude/reference-map.md`。

**阻断条目的覆盖语义（D1203 修 K3 X1a / X2，两条均已实测复现）**：

- `X/**` 覆盖 `X` 本身、`X/` 子树，**以及同名前缀文件 `X.<ext>`**（例：`docs/plans/**` 同时拦 `docs/plans.md`）

- **不**覆盖命名不同的近邻（`docs/plans-archive/`、`docs/synova/coordinationX/` 不在自动覆盖内）：
  新增「语义同类但命名不同」的目录时，**必须显式登记进上面的阻断清单**，不得依赖匹配器猜名字
  （猜名字会误拦合法目录 ⇒ 噪音 ⇒ 门禁被绕过，V3.9 教训）；
- **搬移不可绕过**：`git mv <允许路径> <阻断路径>` 必须被拦。执行体统一带 `--no-renames`，
  于是 rename 被拆成「删除 + 新增」，新路径必然进入新增清单（K3 实测首版此处三闸 PASS ⇒ 已修，
  并有回归断言 `J rename 进阻断区`）。

**逃生舱（铁律 11：显式降级 + 落盘，不静默）**：`SYNO_DOC_CONTRACT_ACK=1`（须同时给

### 3.1 三闸的执行体（D1107 建 · D1193 修判据 + 接线）

> 契约 §3 自述「机器可核」，但 D1107 实测**全仓零执行体**（`grep -rn "DOC-CONTRACT" scripts/ .github/` = 0，
> 阳性对照 `pre-commit-check` = 45）。D1107 补了执行体但**不接线**；D1193 修判据并接线。

| 闸 | 执行体 | 触发点 | 现状 |
|---|---|---|---|
| 格式闸 / 取代闸 / 入库闸 | `bash scripts/control-tower/check-doc-contract.sh`<br>（`--staged` / `--base` / `--files` / `--baseline` / `--all-decisions` / `--json`；内核 `validate_doc_contract.py`） | pre-commit（**位于纯文档早退之前**）+ CI（`SYNO_CI=1` 转硬阻断） | 🟢 **已接线（D1193）** |

**D1193 修的三处（均为 D1107 首版实测缺口）**：

1. **阻断优先于白名单** —— 首版先匹配白名单前缀，`docs/**` 一击中即放行 ⇒ 阻断清单成死代码，
   §3 ❌ 点名的 coordination/、plans/ **永不触发**（实测这两条路径判 pass）。现改为：阻断 → 过渡例外 → 白名单。
2. **闸 3 扩到 `.md` + `.html`** —— 首版只认 md，HTML 成侧门（实测漏网 `docs/synova/coordination/四问-64格.html`）。
3. **判据全部解析自 §3 的三个机器可读块** —— 不再硬编码；块缺失 ⇒ degraded exit 2（不静默放行）。

**为什么必须接在「纯文档早退」之前**：pre-commit 的 CT-34/D387「纯文档提交豁免 12 组」会在组 1 之前
`exit 0`，而闸 3 的对象**恰恰是文档提交** ⇒ 接在其后等于永不点火（D1193 实测）。代价：纯路径判定，<1s。

**独立性声明（红线 R-6）**：执行体由 D1107/D1193 作者新增与修改 ⇒ **判据正确性须 K3 独立复核**；
作者侧附红/绿夹具与生产接线断言，但**夹具自测 ≠ 独立验证**。

## 5. 与门禁 / CI 的同批关系（三合一）

| 动作 | 直接效果 |

## 6. 验收（可机器核 —— ③④⑥ 按本表定义生效）

```
① 入口四份齐备：README / AGENTS / CLAUDE / STATE（STATE ≤200 行）
② 新增 md 全部命中白名单（闸 3）⇒ 连续两周「新增过程 md = 0」

## 11. 库外资产规范（2026-09-27 生效）

> 创始人 2026-09-26：**"审计报告不入仓库，我们已经确定的。那么不入仓库的那些文档，如何处理，也要有个规矩。
> 所有 agent、所有人统一规范。这样以后才能完整复盘。同时这个过程，也是我们自己犯过的错、做过的事情，完整的记录。
> **但是不推到主仓库，但是也要规范起来**。"**
>
> **⇒ §10 说"哪些不入库"；§11 说"不入库的怎么管"。两者互补。**

### 11.1 一句话

**不入库 ≠ 不管。** 过程资产要有**统一落点 + 统一命名 + 一份索引**，否则**复盘做不到**。

### 11.2 落点：**独立档案仓**

```
一个独立 git 仓库（与 K3 独立审计仓同级），当前路径：`~/Synova-过程档案/`

为什么是独立仓（四条）：
 ① **有版本控制** ⇒ 可追溯、可 diff（"完整复盘"必须有历史，不能只有一个快照）
 ② **不占主仓库** ✓（创始人硬要求）
 ③ **一个落点** ⇒ 规范简单（"所有库外产物都在这"）
 ④ **可搜**（`git grep`）✓
```

### 11.3 命名（强制）

```
<日期>-<线>-<类型>-<主题>.md

· 日期 = YYYY-MM-DD
· **线 ∈ 固定值集**：cto / k3 / 门禁线 / 积压线 / 文档线 / mac小队 / win侧 / 研究院
· **类型 ∈ 固定值集**：回执 / 交付 / 审计报告 / 通告 / 记录 / 规格 / 证据
· 主题 = 非空，用 `-` 连接，不含空格

例：2026-09-27-k3-审计报告-文档契约-R3.md
```

### 11.4 索引（**"完整复盘"的关键**）

```
档案仓根目录 `INDEX.md`，时间倒序，每行：
  日期 ｜ 线 ｜ 类型 ｜ 主题 ｜ **一句话** ｜ 关联卡/PR

⇒ 复盘时**看一页就够**；"一句话"栏目强制写清"这条记录讲了什么"
```

### 11.5 🔴 复核：**轻复核，不设严格门禁**（创始人 2026-09-26 明令）

**只查规范三行，全过即入**：
```
✅ ① **命名合规**（§11.3 的格式 + 线/类型在固定值集内）
✅ ② **索引同步**（INDEX.md 里有对应一行）
✅ ③ **front-matter 三行**（日期 / 线 / 类型，与文件名一致）
```

**❌ 明确不做（本仓一概不上）**：
```
· ❌ 不跑 CI
· ❌ 不做 lint / tsc / 测试 / 架构检查
· ❌ **不查内容对错**（那是 K3 的事，不是这个仓的事）
· ❌ **不查"该不该入库"**（那是主仓契约的事）
```

**形式（先不上脚本，符合"不臃肿"）**：
```
① **模板兜底**：仓根 `TEMPLATE.md`，新建文件复制它 ⇒ 命名/结构自动对
② **提交时自查**（三行，见上）

⇒ **两边都能查到，但内容只有一份**
