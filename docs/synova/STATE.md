## 1. 我们在做什么（30 秒）

**SynovaAgent** = 组织数字孪生诊断 + 持续增长导航系统。
**核心问题**：这家企业的增长卡在哪里？现在该做什么？
**形态**：独立 Agent 进程（HTTP + MCP），驻扎企业，持续观测 → 主动发现 → 自动诊断 → 行动建议 → 跟踪执行。
**不是** ChatBot。

> 产品细节见 `README.md`；规则见 `AGENTS.md`；关键决策见 `decisions/`。

## 2. 当前主线（三条，都必须做完）

| # | 主线 | 为什么现在做 | 状态 |
|---|---|---|---|
| **①** | **治理体系最小充分形态**（六阶段） | 门禁已从「防错」滑向「制造阻塞」：一次提交要等 25–37 分钟；号会撞；账本假冲突 | 阶段 0/1 ✅；阶段 2 部分 ✅；2③/3/4/5/6 ⏳ |
| **②** | **CI 与分支积压清理** | 实测：**89 个 open PR / 469 分支 / 3,761 提交**；下降速度追不上产出速度 | 分类 ✅；**合并刚起步** |
| **③** | **文档契约**（本文件所在体系） | **65% 的积压 PR 是治理文档**；我们把「过程」也提交进了仓库 | **v1.0 已立**（见 `docs/synova/DOC-CONTRACT.md`） |

**三条的因果关系（一句话）**：
> 治理以文档为产物 ⇒ 每份文档一个 PR ⇒ 每个 PR 跑全量 CI ⇒ 合并变慢 ⇒ 积压 ⇒ 再写文档澄清 ⇒ 循环加强。
> **⇒ 三条必须同批解决，分开治必复发。**

**做完之后的验收（唯一硬闸）**：
- **连续两周「治理类提交 < 主线类提交」**
- **`src/` 交付速度回升**
- 若做完后主线还是慢 ⇒ **说明我们治错了方向**
