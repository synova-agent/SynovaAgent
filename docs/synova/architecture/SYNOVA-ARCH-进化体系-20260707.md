# 进化体系架构

> 进化体系是 Synova "越用越好"的机制。它从用户反馈、GA纠错、跨客户数据中持续学习，
> 让哨兵阈值更精准、诊断更可靠、行业基线从无到有。

---

## 一、三层进化结构

进化引擎（`packages/evolution`）按学习范围和持久性分为三层：

| 层 | 范围 | 持久化 | 代码 |
|----|------|--------|------|
| 第一层：会话内学习 | 单次诊断会话 | 仅内存 | `session-learner.ts` |
| 第二层：组织自适应 | 单个客户企业内 | AgentMemoryStore | `org-adapter.ts`, `feedback-collector.ts` |
| 第三层：全局进化 | 跨客户行业 | 中心知识基座 | `global-analyzer.ts`, `rule-version-manager.ts` |

**L0 定位**：进化引擎是横向切面，不改变五层架构。
它读 L1（用户反馈）、L3（哨兵结果/专家报告）、L4（本体数据），
写回 L3（阈值调整）和 L4（事实/基线）。

---

## 二、当前代码状态

### 2.1 第一层：会话内学习（✅ 已实现）

`session-learner.ts`：在单次诊断对话中，根据用户反馈动态调整诊断方向。
例如用户在对话中说"这个分析不对，我们现金流实际是500万"，
会话学习器调整后续假设的权重，让诊断更聚焦于用户关心的维度。

不持久化——会话结束即清空。目的是让这次对话越聊越准。此外，第一层还负责系统提示词的渐进优化：Synova在和企业的持续对话中，学习怎么和这家企业沟通最有效——老板的沟通风格、中层的汇报习惯、哪些术语需要解释。系统提示词根据对话历史自动调整。调整提案进入进化提案池，GA审批后生效。

### 2.2 第二层：组织自适应（✅ 已实现）

| 组件 | 功能 | 状态 |
|------|------|------|
| `feedback-collector.ts` | 采集用户对诊断建议/哨兵告警的确认/修改/拒绝 | ✅ |
| `org-adapter.ts` | 分析纠错模式，生成阈值调整建议、提取可复用事实 | ✅ |
| `routes/ga-corrections.ts` | GA 提交对诊断结果的修正 | ✅ |
| `l4/agent-memory-store.ts` | 持久化存储纠错、事实、企业特征 | ✅ |

**GA纠错链路（完整）**：
```
GA 审查诊断报告 → POST /api/ga/corrections
  → agent-memory-store.remember(type='ga_correction')
  → org-adapter 定期扫描 → 同类纠错 ≥ 3 条 → 生成 ThresholdAdjustment
  → 写入进化提案池 → GA 审批 → 生效
```

### 2.3 第三层：全局进化（⚠️ 部分实现）

| 组件 | 功能 | 状态 |
|------|------|------|
| `global-analyzer.ts` | 跨组织行业聚合分析 | ⚠️ 框架存在，数据源未接入 |
| `rule-version-manager.ts` | 规则版本管理 | ✅ |
| 行业知识基座 | 跨客户统计特征汇聚 | ❌ 未实现（已在Loop Engineering中设计） |
| 行业知识基座上传接口 | `adapters/federal-adapter.ts` | ⚠️ 文件存在但需改造——当前名称为历史遗留，实际方向为行业知识基座 |

**待补充**：全局进化的数据源——行业知识基座的本地提取和中心汇聚。

### 2.4 进化提案管理（✅ 已实现）

`routes/evolution.ts` 提供完整的提案生命周期：
- `GET /api/evolution/proposals` — 列出提案（可按状态过滤）
- `POST /api/evolution/proposals/:id/approve` — 审批通过
- `POST /api/evolution/proposals/:id/reject` — 拒绝
- `GET /api/evolution/status` — 进化引擎运行状态

`routes/ga-evolution.ts` 提供 GA 管理面板（HTML界面）。

## 三、三层的数据流

```
用户反馈（对话中的纠正/确认/拒绝）
  → feedback-collector.ts
  → 第一层：会话内学习（仅内存，调整本次诊断权重）
  → 第二层：持久化到 AgentMemoryStore
    → org-adapter 定期分析 → 阈值调整建议 → 提案池 → GA审批

GA 纠错（审查诊断报告后的修正）
  → routes/ga-corrections.ts
  → AgentMemoryStore (type='ga_correction')
  → org-adapter 扫描同类纠错 → 阈值调整 + 事实提取

跨客户数据（行业知识基座）
  → 本地提取统计特征（自动）
  → 中心汇聚（自动，无需审批）
  → global-analyzer 生成行业基线
  → 新客户自动下载行业基线
```

## 四、和 Loop Engineering 的关系

进化体系和 Loop Engineering 是 Synova 的两个独立维度：

- **Loop Engineering** 回答"Synova 怎么在企业里工作"——四个循环是产品运行方式
- **进化体系** 回答"Synova 怎么越用越好"——三层结构是系统学习机制

两者有数据交叉，但不是"谁实现谁"的层级关系：

| 数据来源 | 进化体系的消费方式 |
|---------|-----------------|
| 企业循环的诊断结果 | 第二层（org-adapter）从中提取企业专属知识 |
| 部门循环的中层反馈 | 第一层（session-learner）在对话中实时调整 |
| GA 循环的纠错标注 | 第二层（feedback-collector）采集并持久化 |
| 进化循环的跨客户统计 | 第三层（global-analyzer + 行业知识基座）汇聚 |

进化体系不"实现"Loop Engineering——它从 Loop Engineering 的运转中采集学习素材。
反过来，进化体系的产出（更准的阈值、行业基线）又反哺回 Loop Engineering，
让企业循环的诊断更准、部门循环的建议更可靠。

同样的，企业内部进化（进化循环——Synova越来越懂客户A）靠的是
Loop Engineering 的持续驻扎 + AgentMemoryStore，不是靠跨客户统计。
跨客户的学习才是三层进化体系的能力范围。

## 五、关键设计决策

### 5.1 两层审批线

| 操作 | 审批 | 原因 |
|------|------|------|
| 行业统计特征汇聚 | 无需审批，全自动 | 纯数学汇聚 |
| 行业基线更新 | 无需审批，全自动 | 同上 |
| 哨兵阈值调整建议 | GA 审批 | 有业务影响 |
| 规则版本更新 | GA 审批 | 影响诊断逻辑 |

### 5.2 触发条件（防误调）

| 进化操作 | 最小触发条件 |
|---------|------------|
| 阈值调整提案 | 同类纠错 ≥ 3 条 |
| 行业基线生成 | 同行业组织 ≥ 5 个 |
| 行业特征上传 | 同行业样本 ≥ 3 个 |

### 5.3 数据不出企业

- 会话学习：纯内存，进程退出即清空
- 组织自适应：存储在客户本地 SQLite
- 全局进化：只上传统计特征（均值/方差/分位数），不上传原始数据

---

## 六、结论

**进化体系的三层结构清晰，第一层（会话）和第二层（组织）基本完整。
第三层（全局）的关键缺口是行业知识基座——数据提取和中心汇聚逻辑。**

- 第一层：完整，正确
- 第二层：完整，GA纠错→阈值调整的链路通畅
- 第三层：框架存在，数据源缺失
- 行业知识基座：已设计，待实现（属于第三层的子模块）

### 7.1 五种进化信号

当前文档已覆盖三层结构（会话/组织/全局）和行业知识基座概念，以下补充 5 个进化信号来源的完整列表：

| # | 来源 | 信号类型 | 审核级别 | 当前代码状态 |
|---|------|---------|---------|------------|
| 1 | **GA 结构化反馈** | 诊断报告评审（方向正确/错误）、Signal驳回/确认、行业模板参数更新、新型沉默模式标记 | 自动（模板参数更新）/ 自动检测+人工审核（沉默模式标记） | ✅ 部分实现（markApplied/markDismissed） |
| 2 | **企业用户日常行为** | 财务采纳/忽略建议、销售查询后的策略变化、产品经理反复查询的方向聚类、CEO对话中反复提及的方向 | 自动 | ❌ 零实现——需新增 detectBehavioralValidation |
| 3 | **外部数据自动聚合** | 行业当前值自动更新、基础设施渗透率更新、竞争对手配置权重变化、理论成本下限被实际成本突破 | 自动 / 自动检测+人工审核（阈值校准） | ❌ 零实现——需新增 aggregateExternalData |
| 4 | **哨兵-诊断矛盾检测** | NCI高非共识 vs 三阶推理引擎保守建议、企业实际行为 vs 诊断建议方向、哨兵得分趋势与行业基准矛盾 | 自动检测+人工审核 | ❌ 零实现——需新增 detectDiagnosisContradiction |
| 5 | **跨企业统计量聚合** | 行业哨兵阈值自动校准、NCI全局模式识别、新型沉默模式跨企业出现、NCI计算公式权重调整建议 | 严格人工审核 | ❌ 零实现——需新增 global-analyzer |

### 7.2 三种审核级别

| 级别 | 定义 | 适用场景 |
|------|------|---------|
| **自动** | 无需人工介入，系统自动执行更新 | 行业当前值自动聚合、企业行为反向验证、GA在企业内的反馈导致的本地校准 |
| **自动检测+人工审核** | 系统自动检测异常并生成建议，人工审核后才能生效 | 跨企业的阈值调整建议、成本模板过期检测、沉默模式新分类创建 |
| **严格人工审核** | 系统生成建议，人工审核+灰度发布+可回滚 | 全局规则变更（修改哨兵阈值、修改NCI权重、修改专家提示词） |

### 7.3 进化信号来源的 NCI 专属挂载点

| NCI进化需求 | 信号来源 | 挂载层 | 审核级别 |
|-----------|---------|--------|---------|
| 信号确认/驳回自动学习 | 来源一+二 | 第二层（组织自适应） | 自动 |
| 企业行为反向验证NCI判断 | 来源二 | 第二层（组织自适应） | 自动 |
| 成本模板过期检测 | 来源三 | 第二层（组织自适应） | 自动检测+人工审核 |
| 沉默模式异常检测 | 来源一+四 | 第三层（全局进化） | 自动检测+人工审核 |

### 7.4 与 Loop Engineering 的关系

进化体系中的信号来源与 Loop Engineering 的四个循环形成对应关系：

| 进化信号来源 | Loop Engineering 中的消费场景 |
|------------|---------------------------|
| GA结构化反馈 | GA循环——GA审查诊断报告后进行修正，修正数据进入进化体系 |
| 企业用户日常行为 | 部门循环——中层管理者与Synova的日常互动产生隐式反馈 |
| 外部数据自动聚合 | 企业循环——每轮诊断中使用的行业基线保持更新 |
| 哨兵-诊断矛盾检测 | 企业循环——诊断结果与哨兵监控结果对比发现问题 |
| 跨企业统计量聚合 | 进化循环——跨客户统计特征的自动汇聚和学习 |

进化体系不"实现" Loop Engineering——它从 Loop Engineering 的运转中采集学习素材。反过来，进化体系的产出（更准的阈值、行业基线）又反哺回 Loop Engineering，让企业循环的诊断更准、部门循环的建议更可靠。
