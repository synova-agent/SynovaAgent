## 〇、核实基础：我读到的物理事实

### 0.1 已核实为真的研究结论

| 研究声称 | 我的物理核实 |
|---|---|
| Harness 约 200 包、纯底座 | ✅ 194 个 `@deepseek-ai/*` 包，全部通用基建，**零领域包** |
| 事件溯源 session log | ✅ 且比研究写的更深：append-only 事件流是唯一真相源，LLM 消息历史是**派生投影**（`dsh-session` README: "the LLM message history is *derived* from it"）；持久化格式是 zstd 帧 + 校验和 + 崩溃截断恢复（`dsh-session-persistence-jsonl` README "Durability and crash semantics" 整节）；`dsh-invariants` 会在 reload 时**重放已有 session** 校验单调 seq/turn 闭合/工具调用配对 |
| capability seam 三角色 | ✅ 每个能力拆 Definition/Provider/Consumer 三包（compaction README 表格为证），spill/skill/sandbox/subagent 同构 |
| guard/超时/循环卫生 | ✅ `dsh-timeout`（纯计时库，**明确不拥有终止权**："share the timing/classification, keep the hard kill local"）；`repeat-tool-reminder`（同参连调 3/5/8 次递进提醒，**advisory 永不否决**）；`dsh-invariants`（运行时关系断言，fail-closed） |
| Cordis 时空可组合 | ✅ 插件卸载即撤销其注册的一切（effect/disposer 模式），scope 分层注册 |

### 0.2 对研究的三处修正（影响任务定义）

**修正 1：Agent Notes 不是产品记忆机制，是开发组织的决策记录约定。**
物理证据：DSH 全库 grep 到的路径是 `.agents/notes/{implemented(引用396处), proposed(16), archived(16)}`，全部出现在 README 的设计决策引用中（如 "The project-session directory **decision** records this tradeoff"）。它是"每个非平凡设计决策留一份带状态的文档"的**工程纪律**，不是运行时记忆系统。D395 任务卡写"补 S5-3 知识沉淀"——那是产品侧需求，二者不是一个东西。直接后果：D395 必须拆成两个任务（见 §4.2）。

**修正 2（经附录交叉佐证后软化）："subagent 多后端"在 npm 发布物中未见外部后端，但源码仓库证据为强。**
物理证据：npm 安装物中只有 `subagent-fork-in-process` / `subagent-spawn-in-process` / `subagent-in-process-driver`；`dsh-subagent` README 原话是 "in another process, or through a **future** transport"。**但研究附录 H-07 标注强证据**（源码仓库 `packages/subagent/` 含 acp/claude-code/codex 包族，研究在 Win 机 `D:\deepseek-harness` 全源码上核对）——差异是"npm 发布物 vs 源码仓库"的口径，不是研究失实。处置：涉及 subagent 外部后端的排期决策时，以源码仓库为准再核实一次（D9/B8 排多客户后，届时核实成本很低）。战略判断不受影响。

**修正 3：npm 发布物中的 "snapshot" 指持久化数据的深冻结无损快照（数据完整性纪律），不是黄金测试基建。**
DSH 的 keyless 回放测试在 GitHub 仓库的工程体系里，不在本地代码中。D396 的素材需要读仓库测试设施而非本地包。同时物理事实：Synova 已有 `scripts/ci/golden-case-checker.ts`（pre-push D300 门禁，pre-push-check.sh:220-221）——D396 是**扩展现有门禁**，不是新建。

### 0.3 我发现的、研究没强调的一个关键事实

**Synova 的哨兵 findings 不持久化——进程重启即丢。**
物理证据：K3 08-14 全链路审计（FAIL 报告 §2.1 L1 行）："findings 来自 runner **内存** records（进程重启即丢）"；我复核 `src/store/` 与 `src/l5/` 无 findings 表（grep `CREATE TABLE.*finding` 零命中；只有 `sentinel_baselines`、`sentinel_tickets`、`cron_jobs` 三张相关表）。对照 Harness `dsh-schedule` 的设计："The Session event log **owns** reminder state; timers, tool values, and model follow-ups are **disposable projections** of that log."

**这改变了 D394 的切入点。** 事件溯源对 Synova 的第一价值不是"会话回放信任叙事"（那是 S3-5/S0 的故事），而是先治"产品核心输出重启即丢"这个真实缺陷。详见 §4.1。

## 一、创始人视角：此时点的大局判断

如果我是创始人，我在 2026-08-16 这个时点看到的世界是这样的：

### 1.1 三个已经发生的时代性事实

**事实一：通用 Agent 工程的商品化已经完成，且不可逆。**
DeepSeek 把 194 个包的成熟底座 MIT 开源了。事件溯源、能力接缝、沙箱、子 agent 编排——这些上周还是"自研资产"，这周已经是"公共水电"。在公共水电上继续自建发电厂，不是坚持，是浪费。战略三铁律①（不再自研通用 Agent 工程）是对这个事实的正确回应。**这一条没有任何可犹豫的。**

**事实二：底座越成熟，领域知识越贵。**
经济学很简单：当任何人都能免费获得"会循环、会调度、会记忆的 agent"，稀缺的就只剩"知道拿这个 agent 干什么"。42 边因果本体、诊断方法论、专家体系、GA 闭环——这些不是"功能"，是**对一个领域（组织增长）的建模权利**。Harness 越成功，这个权利越值钱。所以铁律②（预算压到 8 项独有）不仅正确，而且是唯一正确的资本配置。

**事实三：Synova 的真实瓶颈不是工程范式，是数据闭环没转起来。**
物理事实：26 条产品线 3% 完成度；三循环端到端断裂（K3 08-14：L5 无 CRM/财务/HR 连接器、L4 类型契约 Market≠Client、camelCase≠snake_case 属性断裂）；哨兵 findings 重启即丢；8/20 演示、9 月客户A部署在即。这个处境下，**任何不能回答"它让哪个验收点前进了"的工程投入都是奢侈品**——包括借鉴 Harness。这是我对全部借鉴任务的第一道闸门。

### 1.2 此时点我作为创始人的三个判断

**判断一：路径 B 正确，但 B 的任务卡目前全部按"借形"写法立项，照此执行必败。**
"事件溯源 session log（1-3 天）"这种写法，交付出来的一定是"多了一个 JSONL 日志文件，读路径没切，双写不一致没人发现"——这就是形似神不似，而且比不做更糟（多了一个需要维护的伪资产）。本备忘 §4 逐项给出"神"的定义和验收。

**判断二：借鉴顺序应该由"Synova 哪里在流血"决定，不是由"Harness 什么最强"决定。**
研究的借鉴清单是按 Harness 的能力图谱排的（B1-B8）。正确的排法是按 Synova 的伤口排：
- 伤口 1（在流血）：P0 修复的场景验收（FOUNDER-OPERATING-MODE Phase 1，GS-02~05 转绿）是**一次性的**，未固化为可重复回归门禁 → **D396 提到 P0 同批**；
- 伤口 2（在流血）：findings 重启即丢 + 无冷恢复 → **D394 的第一刀切这里**，不切会话回放；
- 伤口 3（M4 三次复发）：执行证据链 → 控制塔**稳定优先于通用化**，D397 现定义砍掉；
- 伤口 4（9 月后才会疼）：知识沉淀/组织记忆 → D398 排最后，且需要先看到部署数据。

**判断三：这是最后一次战略调整，所以它必须包含"不再调整"的机制。**
"最后一次"的真正含义不是"这次定完永远对"，而是**把未来的调整判据现在也写死**：路径 A 的触发 rubric（§7）、借鉴项的 invariant 验收制（§5）、防跑偏的三问闸门。有了判据，未来 Q4 的评估是执行而不是又一次战略摇摆。

## 二、Synova 的最终形态（目光长远部分）

创始人问"这会决定产品的最终形态"。我把 24 个月后的终局画出来：

### 2.1 终局定义

**Synova 最终不是一个 Agent，而是"组织诊断知识的可执行载体"——一套领域知识系统，运行在可替换的通用底座上。**

```
┌─────────────────────────────────────────────────┐
│  领域知识层（Synova 的全部价值，全部插件化）        │
│  · 42 边本体 = 企业的 schema（边是语义，点是状态）   │
│  · 专家/哨兵 = 可装卸的领域插件（文件驱动→运行时热装卸）│
│  · 诊断方法论 = 6 阶段管道（领域流程编排）           │
│  · 行业模板 = 本体的行业变体包                     │
├─────────────────────────────────────────────────┤
│  信任层（事件溯源 + 黄金数据集 + invariant 守护）    │
│  · 全事件流可回放：任何诊断结论可重建               │
│  · model-visible ⟺ logged：进模型的必可审计        │
├─────────────────────────────────────────────────┤
│  底座层（可替换：自研残片 → Harness → 未来的更好底座）│
│  · session/loop/调度/沙箱/subagent —— seam 隔离     │
│  · 换底座不动领域层                                │
└─────────────────────────────────────────────────┘
```

### 2.2 关于插件化——你认可的方向，我要给它精确的定义

你说"非常认可一切插件化的产品思维"。物理事实是 Synova 已经有**两种**插件化，Harness 是第三种，最终形态是三者合一：

| 层级 | Synova 现状 | Harness 对照 | 终局形态 |
|---|---|---|---|
| **知识插件化**（改行为不改代码） | ✅ 已强：48 个哨兵目录（manifest.json + computes/ + aggregate.ts）、7 专家目录、55 边类型 JSON、行业模板——文件驱动自动注册 | Harness 的 skill-filesystem 同构（文件驱动 skill） | **保持，这是对的** |
| **运行时服务插件化**（seam 三角色：接口/实现/消费分离，实现可换） | ⚠️ 雏形：providers/ 有 registry；其余是静态 import | 全部能力 seam 化，卸载即撤销（Cordis effect/disposer） | **渐进吸收**（D6/B2，Q4 后） |
| **进程/生态插件化**（第三方可分发） | ❌ 无 | Harness 插件市场 | 路径 C，多客户后再说 |

**关键判断：Synova 的知识插件化已经比 Harness 的 skill 体系走得更远**（哨兵 manifest 带阈值/调度/数据权限声明，比 dsh-skill 的 invocation policy 更领域化）。所以插件化上 Synova 要借的不是"文件驱动"（自己已强），而是 **seam 的"实现可换"纪律**——它服务的是"底座可替换"，不是"知识可扩展"。两者别混。

### 2.3 终局的胜负手

Harness 越成功对 Synova 越有利——底座越便宜，领域知识越贵。**唯一会输的剧本**：有人用同样的免费底座 + 更快的领域知识积累速度超车。所以防御指标不是"我们有多少边/专家"，而是：

> **本体被真实数据验证的速率**——每月 GA 确认的边数、被确认/否决的记忆条目数、部署企业回流的校准事件数。

这个指标从今天起就该被追踪（客户A是第一个数据源）。D398 的成功标准应该直接定义为这个指标，不是"记忆条目数"。

**研究第三章给这一节补了一块证据**："公司大脑"模板层也在商品化——Sylph（YC X25，README 全文证据）把"8 个 AI 员工 + cadence + self-improving skill"做成了纯 markdown 模板，但它**停留在"流程自动化 + 知识库"层，无诊断因果深度**。含义：Synova 不能退守"企业知识库模板"这一层（那层也在被开源填平），护城河的精确位置是**因果诊断深度 × 数据验证速率**——Sylph 的 "diff 重写 skill 文本"和 Synova N13 的"因果规则调权"是同构思想，但后者挂在 42 边本体上，这是深度差。

## 三、借鉴总目录：三类借法，三种防歪

把研究和转交文档的 B1-B8/D1-D9 重新归成三类——**三类的东西，借法完全不同，混在一起是形似神不似的总根源**：

| 类 | 内容 | 借法 | 神是什么 | 主要失败模式 |
|---|---|---|---|---|
| **A. 架构纪律类** | 事件溯源（B1/D394）、seam 三角色（B2）、model-visible⟺logged | 借**不变量**：先定义可验证性质，实现围绕性质 | 一条可物理验证的系统性质（如"杀进程后能从事件流重建等价状态"） | 交付了工件（日志文件/接口层）但性质不成立，且无人检查性质 |
| **B. 机制类** | spill（B6）、schedule 冷恢复、timeout/repeat-reminder（B5/D397）、三层加载（D398/OpenViking） | 借**机制设计**：读对方的决策记录（Agent Note/论文），理解 tradeoff，按自己的约束重新实现 | 机制解决的原始问题在 Synova 场景真实存在且被解决 | 机制抄过来了，但它解决的问题在 Synova 不存在（为借而借） |
| **C. 工程流程类** | Agent Notes 四态（B4/D395 开发组织版）、snapshot 测试（B3/D396）、README 决策锚点纪律 | 借**纪律**：直接改造 Synova 开发流程，成本极低 | 开发组织的知识/决策可沉淀、可检索、不腐化 | 流程建了没人用（M3 未接线的流程版） |

**规则：A 类必须过 invariant 验收（最严），B 类必须先证明"问题在 Synova 存在"，C 类随手做但要有使用门禁。**

## 四、逐项深度方案

### 4.1 D394 事件溯源（B1）——最重要，也最容易做歪

**Harness 的物理事实**（我核实过）：
- append-only `SessionEvent` 流是唯一真相源；消息历史 `deriveMessages()` 派生，不单独存（dsh-session README）
- 持久化：zstd 帧 + 每帧校验和 + 崩溃时截断到最近完整帧 + 合成闭合事件（dsh-session-persistence-jsonl "Crash recovery"）
- `ctx.sessions.flush(session)` 是持久化屏障——所有读决策前 await flush，持久化不确定时返回 `persistence_uncertain` 而不是猜（dsh-schedule README）
- invariants 在 reload 时重放全部已有日志校验（dsh-invariants README）

**神（invariant）是什么**：三条可验证性质——
1. **I1 可重建**：任意时刻 kill -9，重启后从事件流重建的会话状态与崩溃前等价（消息序列、诊断阶段、findings）
2. **I2 单源**：消息/状态只有事件流一个写入口；所有读路径从事件流（或其物化投影）派生——**读路径切换是检验单源的唯一标准**
3. **I3 可审计**：任何一次诊断结论（报告、finding）能从事件流回答"它由哪些输入事件产生"

**形似神不似长什么样**（这是对 D394 任务卡的直接预警）：
> 新增 `session_events` 表，写入时双写 messages + events；读路径不动（还读 messages 表）；events 表沦为没人读的日志副本；三个月后两处数据漂移，没人发现；审计时声称"已事件溯源"。**工件在，性质全不成立。**

**怎么借（我的具体方案，分三片，每片独立验收）**：

- **片 1（先做，治流血）：哨兵 findings + 信号事件化**
  - 落点：`src/sentinel/runner.ts`（findings 目前只在内存 records，K3 08-14 审计实证）→ 新增 `sentinel_events` append-only 表（L5），finding/signal/ticket 状态迁移全部作为事件写入；runner 内存态变成事件流的物化投影，启动时重放重建（这就是 Harness schedule 的 "durable state in log, timers are projections" 模式）
  - 同时修掉 `src/agent/sentinel-service.ts` 把 durationMs 当时间戳的 bug（`checkedAt: new Date(run.result.durationMs)`，当前 :97，K3 08-14 审计记录为 :101，文件已微移；恒输出 1970-01-01）
  - 验收（物理）：`npm run dev` 启动 → 触发哨兵 → kill -9 → 重启 → `GET /api/sentinel/findings` 输出与 kill 前一致；事件表 `seq` 单调无洞（grep/SQL 可验）
  - 工时实估：2-3 天（表设计 0.5 + 写入 0.5 + 重放重建 1 + 验收测试 0.5-1）

- **片 2（部署后做，信任叙事）：诊断会话（FDE 六阶段）事件化**
  - 落点：`src/store/session-store.ts`（314 行，messages 表 + FTS5）+ `src/agent/conversation-engine.ts`（845 行）+ `src/orchestrator/phase-state-machine.ts`
  - 做法：新增 session_events 流；**agent_messages 表降级为只读物化投影**（写路径切到事件流，读路径切到投影——SQLite 不扔，它变成查询层，这正是 `dsh-session-query-sqlite` 的模式：事件流是真相源，SQLite FTS5 是可重建的查询索引）
  - model-visible⟺logged 落地为一条 pre-commit 级检查：进 LLM 请求的上下文组装点（`prompt-assembler.ts`）必须有对应事件类型
  - **采纳 Harness feedback 的 log-only 纪律**（研究第一章 §1.6 标记的 Synova 缺口，交叉佐证补入）：GA/人类反馈一律先作为事件入流（可审计），**进不进模型上下文是显式决策而非默认**——`dsh-message-feedback` 同构（sidecar 存储 + 生命周期绑定 + 不进遥测）。这直接补强 N13：反馈先入流，才有"纠错→规则回流"的可追溯源
  - **数据安全边界（本备忘初版遗漏，补上——这是 append-only 的固有权衡，不设计就是事故）**：事件不可变 ⟹ PII 必须在 append **前**过 `security/PIIScrubber`，事后无法擦除；事件流继承现有数据安全四层（L0 公开摘要/L1 聚合信号/L2 脱敏证据/L3 原始数据仅客户企业内部可见）——事件流本身按 L3 处理，脱敏投影按 L2 派生；删除权诉求（企业主"忘了这条"）的答案是 per-org 事件流物理隔离 + 整流销毁，不做单事件删除。Harness 自己也承认同一权衡（dsh-session README："可回放提高可审计性**也扩大数据面**"）——我们面对的是企业数据，比它更敏感，必须在 schema 设计时把这一层焊死，不能事后补
  - 验收：I1 杀进程重建测试 + I3 "这份诊断报告由哪些输入产生"可查询 + 既有会话一次性迁移脚本 + 事件流 PII 抽查（append 后事件中零明文 PII）
  - 工时实估：**6-8 天，不是任务卡上的 1-3 天**（事件 schema 1 + 写入 1 + PII 前置接线 1 + 派生读路径 1.5 + 重放工具 1 + 迁移 0.5 + invariant 测试 1）

- **片 3（Q4 后，路径 A 的预备）：fork/resume + 完整回放视图**
  - 只有当片 1+2 的性质稳定后才做；做了它，路径 A 迁移成本降一半

**与 P0 的关系**：片 1 与 D355-D360 无冲突（不同表、不同代码路径），且为它们提供事件级观测；片 2 **硬依赖 D355-D360 的 L4/L5 契约先稳定**——在断裂的契约上叠事件流 = 把断点冻进事件 schema，事件 schema 上线后有迁移成本，比改代码贵。**顺序：D355-D360 → D394 片 2。**

### 4.4 D397 guard（B5）——现定义砍掉，重新定义后降级

**问题**：任务卡写"通用化控制塔"。三个反对理由：

## 五、防"形似神不似"的元机制（制度，不是口号）

逐项防歪写在 §4 了。这里是**制度层**的五条——它们保证未来任何借鉴任务（不限于 D394-D398）自动带上防歪：

**M-1 任务卡强制两字段。** 借鉴类 task brief 增加两个 pre-commit 物理检查字段：
- `## 借的 Invariant:` ——一条可物理验证的系统性质（写不出来 → 不准开工。写不出 invariant 的借鉴 = 观光）
- `## 做歪了长什么样:` ——一段具体的反例描述（强迫任务作者在写代码前见过失败形态。这是从 Synova 自己的铁律传统学的：每条铁律都附历史事故）

**M-2 验收只验性质，不验工件。** 借鉴任务的 Done 标准禁止出现"XX 表已建/XX 文件已创建"这类工件陈述；必须是"杀进程→重建→输出一致"这类性质陈述 + 可执行命令。K3 审计时按命令复跑（claim-verifier 既有纪律的自然延伸，不新增机制类）。

**M-3 读路径切换才算数。** 凡涉及"新存储/新索引/新投影"的借鉴，读路径不切换 = 双写 = 形似。审计检查方式：grep 旧读路径调用点必须归零（铁律 47"拆完了由 grep 物理证明"的泛化）。

**M-4 神对照表回填。** 每个借鉴任务交付时回填一张三行表：Harness 原文怎么说的（README/Note 锚点）→ 我们的实现 → 偏离及理由。偏离不禁止，**不记录的偏离禁止**（M2/M7 防线的既有原则）。

**M-5 一道固定的 K3 审计问句。** 借鉴任务进审计时固定回答："这个任务的 invariant 是什么？给我看证据。"——写进 synova-audit skill 的检查清单（这是改审计预设，归因 audit，符合错误归因闭环）。
