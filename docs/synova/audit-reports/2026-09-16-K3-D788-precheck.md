## 4. 前置审发现（派单层 + 实现约束）

### F2（P1，实现硬约束）口径必须 fail-closed，且排除清单不能写成否定结构

派单 §二-1 原文：**"不计入：`docs/**` · `task-state/**` · `.claude/**` · `memory/**` · `synova_worker/**` 之外的纯文档/治理产物"**——句式含"之外"，语义可被反向理解（可读作"…之内不计入"或"…之外不计入"）。且"纯文档/治理产物"是**语义描述**，bash 无法判定。

**要求（验收时会逐条验）**：
1. 实现必须落成**显式前缀白名单**（计哪些 / 不计入哪些各一张表），不允许"除……之外"这类否定式判定；
2. **未列入任何表 → 默认计入审查面**（fail-closed）——否则任何新目录（如未来的 `newdir/**`）自动逃出预算，等于给夹带开后门；
3. 白名单须排除"可执行/可影响 CI 的"文件类型混入治理目录（例如治理目录下的 `*.sh`/`*.yml`），或在文档中显式声明该选择。

### F3（P1，实现硬约束）`N_FILES` 语义迁移会撞旧分支，禁静默

`check-pr-budget.sh:122` 现有分支：`if [ "$N_FILES" -eq 0 ]; then echo "  ✅ ② 无变更文件 → 域校验跳过"`。
新口径下 `N_FILES` 变"审查面件数"：**审查面 0 件 + 治理产物 51 件**会命中该分支 → 输出"无变更文件"，与实际不符（**铁律 11 静默/失真**）。

**要求**：该分支须改为区分「真·空变更」与「治理产物 M 件、审查面 0 件」，且两类件数**显性打印**（派单 §二-3 已要求：`审查面 N 件（上限 12）／治理产物 M 件（不计入）`——验收时会做字面检查）。

### F4（P2）派单锚点语义未文档化（我首轮误判为"幻影 sha"，已自纠）

派单头：`依据计划: v1.2@4e46603f（当前 main）｜ v1.3@eef38a85（PR #584 带入后）`。
`git cat-file -t 4e46603f` → **Not a valid object name**；GitHub API `/commits/4e46603f` → **HTTP 422**（本地 + 远端双核验均不可解析）。

**但我没有就此判失实**——先对照同族惯例：`派单-D760-D769…:3` 写 `v1.2@8d331729`，同样不可解析 ⇒ 说明"@sha"**不是 git 对象**。进一步实测（计划文件 = `docs/synova/coordination/整体推进计划-主线-20260913.md` 的 blob 内容哈希）：

```bash
$ git cat-file blob 5feb36b8 | shasum -a 256 | cut -c1-8     # v1.2（2026-09-15 时点）
  8d331729        # ← 与 D760 派单锚点一致 ✅
$ git cat-file blob 8078f15b | shasum -a 256 | cut -c1-8     # main 当前版
  4e46603f        # ← 与 D788 派单「v1.2@4e46603f（当前 main）」一致 ✅
$ git cat-file blob 33f4214a | shasum -a 256 | cut -c1-8     # PR #584 分支版（v1.3）
  eef38a85        # ← 与 D788 派单「v1.3@eef38a85」一致 ✅
```

**判定：D788 派单锚点属实且可核验**（语义 = 计划文档**内容 sha256 前 8 位**）。
**但语义未文档化**（`pre-dispatch-check.sh` 只做格式匹配：输出 `✅ 派单已锚定计划 v1.2@4e46603f`，不校验可解析性）→ 第三方核验成本高、极易误判为幻影（本审计首轮即经历）。
**建议（P2，属派单模板/门禁小改，不新增机制）**：把"锚点 = `sha256(计划文件内容)[:8]`"写入派单模板与 `pre-dispatch-check.sh` 注释，或改用 git 原生的 `blob sha`；并让门禁能机械复算。

### F5（P2）D788 brief 的 Done 标准在当前交付路径下不可达（门禁时序假设 vs 交付现实）

brief Done 标准第 1 条：`bash scripts/control-tower/pre-dispatch-check.sh <派单文档>` → 末行「✅ 机械项全通过」。
实测（main 树，2026-09-16）：

```
── ① 任务号真实性 ──
  ⚠️ D788 无 task-state（新建须走 alloc-task-id.sh）      ← 唯一触发项
  ❌ 机械项发现问题——修正后再派单            exit = 1（实测）
```

**根因 = 环境依赖，非派单缺陷**：`task-state/D788.json` 与派单**同批**位于 `origin/docs/d788-budget-scope`，尚未合 main；在 main 树上该文件必然不存在。
**含义（比这条本身更重要）**：这与 D788 要修的 D734 问题**同族**——**门禁的时序/形态假设与现实交付形态错配，摩擦成本落在治理/审计线上**（D734 假设"代码 PR 形态"；pre-dispatch-check 假设"task-state 已先落地"）。
**建议（P2）**：CTO 统一约定时序（先合 task-state 或门禁显式豁免"同批交付"），并把该约定写进派单模板——**不要再为它加新脚本**。

### F6（P2）与 D515 docs-only 白名单口径相反，需登记差异（不在本单扩范围）

`ci.yml:24` 的 docs-only 正则把**所有 `*.json`（含根级 `package.json`）**视为"文档"→ 只改 `package.json` 的 PR 会被当 docs-only，跳过 TS/Iron Laws/verify-parallel/D708。
而 D788 §二-1 明确"根级配置文件（`package.json` 等）**计入**审查面"。两处口径**方向相反**（既有事实，非 D788 引入）。
**建议**：本单不扩范围（保持写集纯度），但请 CTO 在台账登记该差异；若未来统一，应一次改动两处。

### F7（P2）验收必须双模式 + 真分支

`check-pr-budget.sh` 有两套取变更集路径：`--files` 注入（`:71-73`，不涉 git）与真 git 模式（`:74-97`，含基线解析/落后计数）。
D788 派单 §四 只写"对 #572 跑 → PASS"，未区分模式。**要求**：两种模式都要跑（新口径的过滤逻辑若只接在 `--files` 分支，真 git 模式下 `BEHIND`/域判定会带出不一致）。
