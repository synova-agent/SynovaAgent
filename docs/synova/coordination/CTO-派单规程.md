# CTO 派单规程（dispatch gate）★ 每张卡逐条过

> 建立 2026-09-28 ｜ 起因：创始人问「如何保证每一次派单都与权威研究一致、与产品完成度一致」
> **前提承认**：靠"CTO 认真"不可行（2026-09-28 单日实证 5 类错：per_page 截断 / 口径陈旧 /
>   假绿件提交 / 报告遗漏 / 把自述当事实）。**只能靠"把规矩变成物理检查"。**
> **设计原则**（V3.9 教训）：**能机器判的机器判；机器判不了的，必须"写出来"——写出来才能被审。**
> **硬阻断 100% 有效，软提醒 0% 有效** ⇒ 本规程的终点是**脚本化**（见 §四）。

## 一、派单七问（**每张卡逐条答，答案写进派单件 §〇 归属与依据**）

| # | 问 | 怎么答（**必须给命令/出处，不许凭记忆**） |
|---|---|---|
| 1 | **归属**：这张卡挂哪条线的哪个验收点？ | 写 **线 id + 点 id**（如"线25 · 25-8/25-9"）。**不挂点的卡不得派出**——除非显式标为「前提清单 3 项」或「线外工作项 12 项」（总纲 §2.2/§2.3） |
| 2 | **格子现状**：该点当前是五态里的哪一态？ | **现场跑命令**取（`product-progress.json` 或 calc-progress），带实测时间；**引用前四查**照做 |
| 3 | **依据**：读了哪几份权威件？ | 研究院件写**全名 + 版本/日期**；过「引用四规则」（数字查未核实册 / file:line 查取码登记 / 取舍查权威索引 / 判据穿生产入口） |
| 4 | **DSH 边界**：这块自建还是用 DSH？ | 查 `CTO-DSH派单台账.md` §一 四类清单（自建 35 / 用 DSH 14 / 参考自研 11 / 可裁剪 16）；写**结论 + 类目** |
| 5 | **架构合规**：过不过三类否决？三问能否机器判定？ | 查台账 §二；写"加了吗/接上了吗/生效了吗"**各自怎么判** |
| 6 | **红线**：三红线 + 不该做 8 + 禁做 8（G1）逐条对照 | 写**逐条结论**（含 G1：`@deepseek-ai` 零命中） |
| 7 | **判据**：完成判据是什么？ | = **穿生产入口的用例**（不是 grep）；四件套（verify 命令 / .json 证据附实跑数 / 真实入口 / 改坏即红）逐条写出 |

## 一-b、🔴 闸门的分域裁剪（**约束的定位：保主线不跑偏，不堵治理线**）

> 创始人 2026-09-28 指正：三道闸**不能什么都拦**——遗留的文档治理/门禁治理/CI 处置
> **不挂产品格子**，若强行要求"挂线+点 id"会把它们全堵死。
> ⇒ **闸门按域裁剪作用域：主线严、治理宽，但两条全域强制不许裁。**

### 三类卡 × 七问适用矩阵

| 问 | 主线卡（产品线切片） | 治理卡（文档/门禁/CI/控制塔/审计/流程） | 前提卡（总纲 §2.2 三项） |
|---|---|---|---|
| ① 归属 | **线 id + 点 id（必须）** | **治理域 + 服务的阻塞**（必答句："本卡解除哪条线/哪个格子的什么阻塞"） | 前提清单第 n 项 |
| ② 现状 | 五态**实测** | **阻塞状态实测**（如"门禁误红 N 个 PR"/"删除侧零覆盖"） | 前提项状态 |
| ③ 依据 | 权威件回执 | **该域权威源**（契约 §3 ／ 门禁必要性审计 ／ CI 成本裁决 ／ 控制塔模式库） | 总纲 §2.2 |
| ④ DSH 边界 | 查四类清单 | **仅当涉及 DSH 时**（多数治理卡不涉及 ⇒ 标"不适用"即可） | 同左 |
| ⑤ 架构合规 | 三类否决 + 三问 | **仅当涉及 `src/` 架构时**；治理卡改为：**该域模式库**（改控制塔⇒`ctrl-tower-change`；跨平台⇒`windows-compat`；新模块⇒`contract-template`）+ **改坏即红** | — |
| ⑥ 红线 | 三红线 + 不该做 8 + G1 | **同左（全域强制）** | **同左** |
| ⑦ 判据 | 穿生产入口 + 四件套 | **该域判据**（门禁卡：改坏即红；文档卡：引用零悬挂 + 承接 sha256 对账；CI 卡：成本/覆盖率**实测**） | 前提项判据 |

### 两条**全域强制**（任何域都不许裁）
```
③ 权威件回执 —— 治理卡也要写"读了哪几份权威件"（治理域有自己的权威源，见矩阵③）
⑥ 红线（三红线/8 禁做/G1/不碰 audit 域/不用 --no-verify）
```

### 可裁剪的三种情形（要显式标"不适用 + 理由"）
```
① 挂点要求：治理卡不挂产品点，但**必须**答"服务哪条主线阻塞"
② 格子口径：治理卡用"阻塞状态"替代"五态"
④⑤：与 DSH/架构无关时标"不适用"
```

### 🔴 治理卡的核心要求：「目的声明」（防自娱自乐）
> **每张治理卡必须写：本卡解除哪条线/哪个格子的什么阻塞。**
> 写不出 ⇒ 该卡的优先级降为 P3 批处理（不是禁止，是**排在主线之后**）。
> 依据（2026-09-28 实证）：治理线是**为解除主线阻塞而存在**的 ——
> B1/B2 出库解除"文档债务"、门禁凑批解除"开发被误拦"、CI 处置解除"合并积压"，
> 每一条都能指回它解锁的主线能力（这条正是"治理不跑偏"的判据）。

## 二、派单件必须含的三样（缺一 = 不得发出）

```
① 「§〇 归属与依据」段 = 上述七问的答案（模板 v3 增补段）
② 「权威件回执」= 读了哪几份 + 版本/日期 + 逐条结论（引用纪律硬要求）
③ 「DSH 借鉴核查」三步 = 四色定位 / 借鉴边界 / 源码参考（含行号现查，§〇b）
```

## 三、抽验闭环（防我系统性跑偏）

```
每批卡发出后：K3 或独立复核员抽 ≥1 张，核三件事是否一致：
  ① 派单件 §〇 ↔ 权威件（研究院文件）② 派单件 ↔ 格子现状（仪表盘实测）
  ③ 派单写集 ↔ 该点的 modules（防跨线夹带）
发现不一致 ⇒ 记教训库 + **加固闸门**（不是"下次注意"）
```

## 四、物理闸门（**这是终点：让机器替我记规矩**）—— 待立卡

```
在 `scripts/control-tower/pre-dispatch-check.sh` 现有 8+2 项之上增补 3 项：
  ① **点 id 存在性**：派单件声明的 `线id · 点id` 必须能在 product-lines.yaml 命中（防臆造/防过期）
  ② **归属字段必填**：无「归属」段 ⇒ 阻断（除非带「前提清单/线外工作项」显式标记）
  ③ **权威件回执必填**：无回执段 ⇒ 阻断
⇒ 立卡（P1，归门禁线）；未落地前，本规程由我逐条手跑（**但手跑 ≠ 机制，落地前不允许自称"已保证"**）
```
