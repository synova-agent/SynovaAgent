## 3. 机制：`simulate-ci.test.sh` 在测试内**递归跑全表**（file:line）

```bash
# tests/control-tower/simulate-ci.test.sh（3 次调用同一个 SIM）
GREEN_STUB=…; OUT=$(SYNO_SIM_PRECOMMIT="$GREEN_STUB" bash "$SIM" 2>&1); rc=$?      # 第 1 次
RED_STUB=…;   OUT=$(SYNO_SIM_PRECOMMIT="$RED_STUB"   bash "$SIM" 2>&1); rc=$?      # 第 2 次
OUT2=$(SYNO_SIM_PRECOMMIT="$TMPD/missing.sh" bash "$SIM" 2>&1); rc=$?              # 第 3 次
```
```bash
# scripts/control-tower/simulate-ci.sh:49（从 ci.yml 抽全表，仅排除自己）
TESTS=$(grep -oE 'tests/control-tower/[a-z0-9-]+\.test\.sh' "$ROOT/.github/workflows/ci.yml" 2>/dev/null \
        | grep -v 'simulate-ci\.test\.sh' | sort -u || true)
# :53  while IFS= read -r t; do … bash "$t" … done
```
**放大链**：`simulate-ci.test.sh` → `simulate-ci.sh` → 其余 **49 个测试 ×（最多）3 轮** ≈ **150 次测试执行**；其中还包含 `platform-checklist.test.sh`（**再**跑 `pre-commit-check.sh` 4 次）与 `gate-failopen-net.test.sh`（31s）等重项 ⇒ 组合爆炸。
**为什么"看起来像挂"**：该 step **无 per-test timeout、无 step `timeout-minutes`**，Windows 上单是这一项就 ~20–25 min；任何一轮更慢（runner 抖动）就会把总时长推到 30 min+，在 PR 页面上表现为"必需检查迟迟不报告"。

**递归护栏**：`simulate-ci.sh:49` 的 `grep -v` **只挡住"自己"**，挡不住"N 层重入"（例如 `platform-checklist.test.sh` 里跑 `pre-commit-check.sh`，而 `pre-commit-check.sh` 会经 `ct-test-gate.sh` 运行**配对测试**——两者叠加使工作量随测试数近似平方增长：50 项测试时 ≈ 50×49×3）。

### 4.1 ★ 本地已复现的**挂起机制**（本卡最强证据，升级为第 1 嫌疑）

**链路（file:line）**：`tests/control-tower/alloc-task-id-lock.test.sh:97-100` → 启 **20 个并发** `alloc-task-id.sh` → 每个都会走到
`scripts/control-tower/alloc-task-id.sh:152-159`：
```bash
_LSR_TO="$(command -v timeout || command -v gtimeout || true)"
if [ -n "$_LSR_TO" ]; then
  _LSR_OUT="$("$_LSR_TO" "${SYNO_ALLOC_LSREMOTE_TIMEOUT:-20}" git -C "$TS_TOP" ls-remote --heads origin 2>/dev/null)"
else
  _LSR_OUT="$(git -C "$TS_TOP" ls-remote --heads origin 2>/dev/null)" || _LSR_RC=$?   # ← 无超时兜底！
fi
```
- **macOS 上 `timeout`/`gtimeout` 均不存在**（本机实测 `(no timeout/gtimeout)`）⇒ 走 **else 分支 = 裸 `git ls-remote`，无任何超时**。本 session 网络反复 443 超时 / `HTTP2 framing layer` 错误 ⇒ 该调用可**长时间阻塞**。
- 该测试的并发段**未设 `SYNO_ALLOC_NO_REMOTE=1`**（对比 `alloc-task-id.test.sh` 的并发段显式设了）⇒ 20 个进程**并发打真实 origin**；随后是**裸 `wait`**（`:100`，无 pid、无超时）⇒ 任一个不返回 ⇒ **测试永不结束**。
- **本地复现**：我以 90s 上限 kill 掉该测试的父进程后，**其 20 个子进程仍存活并继续阻塞在 `git ls-remote` 上 20+ 分钟**（`pgrep` 实测：`alloc-task-id-lock.test.sh` + `alloc-task-id.sh 缝探针 --dry-run` 共 7 个孤儿），并占用锁目录；**已由我清理**（本 worktree 内、我创建的进程与锁）。
- **Windows 面**：Git Bash 同样**没有 `timeout`** ⇒ 同一无超时兜底；Windows runner 上 `git ls-remote` 若撞上 **凭证管理器（GCM）提示 / 限流**，即可能**阻塞在交互提示**上 ⇒ 与"step 3 永不完结"的观测一致。
- **反证/边界**：ubuntu 上该测试仅 **6.9s**（不挂）⇒ 说明该路径在快网络+无 GCM 时正常；**挂起风险来自"无超时兜底 + 并发 + 平台凭证"三者叠加**，不是每次必挂（与"有的 run 完成、有的长跑"一致）。

## 5. 独立真故障：`*` 文件名让 Windows checkout 直接失败（128）

```console
$（run 36184156096 / 36182865555 的 windows job 日志）
##[error]error: invalid path '.claude/task-briefs/2026-09-26-D1015-阶段1-A-check-*-计数口径定版.md'
##[error]The process 'C:\Program Files\Git\bin\git.exe' failed with exit code 128
```
- 起因：某分支把 `*` 写进了**文件名**（`…check-*-计数口径定版.md`）。`*` 在 NTFS 是保留字符 ⇒ Windows 上 `git checkout` 无法落盘 ⇒ job 0.2 min 即失败（`step3` 显示 `completed/skipped`）。
- 与"慢"无关，但**同为 Windows 专属阻塞**；任何含该文件的分支必红（ubuntu 无此限制）。

## 6. 建议（**不自行修改**，交 CTO/编码线）

**最可疑 1–3 项（按证据强度）**
1. ★ **`tests/control-tower/alloc-task-id-lock.test.sh`（+ `alloc-task-id.sh:152-159` 无超时兜底）** —— **唯一有本地"挂起"复现**的项（孤儿进程阻塞在 `git ls-remote` 20+ min）；且并发段未关远端 ⇒ 20 路真实网络调用 + 裸 `wait`。
   **最小验证法**（Windows runner，不改语义）：给该 step 加 `timeout-minutes` 并**只跑这一项**；或在该测试外挂 `GIT_TERMINAL_PROMPT=0`/`GCM_INTERACTIVE=never` **仅作观测**（若为 GCM 提示阻塞，加上即立刻转成失败而非挂起）。
2. **`tests/control-tower/simulate-ci.test.sh`（+ `simulate-ci.sh:49/53`）** —— **慢**而非挂：占 ubuntu 该 step 69%、Windows 估算 ~20–25 min（所以 §2.2 的正常区间是 25–36 min）。
   **最小验证法**：只跑这一项 + `timeout-minutes: 20`；20 min 内不结束即坐实其为时长支配项。
