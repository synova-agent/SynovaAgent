## 一、六项待裁（逐条：事实 → 选项 → 我倾向 → 代价）

### ① P3 的 R1 口径 —— **`Closes` 还是「关联」？**
**事实（复核用执行结果证明）**：`closingIssuesReferences` **只含会自动关闭的引用**。
拿它跑它自己那 PR ⇒ 判「关联 Issue = 0」；而 GitHub 自己记着 #1164 的交叉引用里有它。
抽样 25 个已合并 PR：CIR 非空 **1/25**、正文含 `Refs #N` **14/25**。
**⇒「关联」被窄化成「关闭」⇒ 本仓现状 ≥14/25 系统性假红（D734 同型：越守规矩越红）。**
| 选项 | 含义 | 代价 |
|---|---|---|
| **A** | 判据改「必须 `Closes`」 | 需**连全队约定一起改**（所有人改写法）；且 `Closes` 语义更强 |
| **B** | `CIR ∪ issue 侧 CrossReferencedEvent` | 用**权威口**（非正则扫正文，守得住 S-04）；不改变全队现有写法 |
**我倾向 B。** 需你裁 Z：**A / B / 其它**。

### ② 聚合 job 的「必需集」来源
**事实**：`all-checks-passed` 的必需集读的是 `ci.yml` 里**硬编码的 `needs`（10 个 job id）**，
**不读** `required-checks-baseline.txt`（**9** 条 = 唯一真值源）。
多出的两个是 `audit`（npm audit）与 `gate-integrity`。
**⇒ 一旦把 `all-checks-passed` 加进必需集，这两个会被隐性升格为「阻断合并」**（超出 W3 声明范围）。
| 选项 | 含义 |
|---|---|
| **A** | 保持硬编码 needs；**在其进必需集时明示**"audit/gate-integrity 随之阻断" |
| **B** | 改成**读 baseline 文件**（单一真值源），needs 只作依赖声明 |
**我倾向 B**（与 W9「口径统一到基线」同向）。需你裁 Z。

### ③ 堆叠 PR（stacked PR）—— **建议禁止或改触发条件**
**事实**：`ci.yml` 的 `on.pull_request.branches: [main]` **按 base 过滤** ⇒ base ≠ main 的 PR **零 CI run**。
实测：#1187 / #1188（堆叠件）= **0 run** ⇒ **合并条件①「CI 全绿」结构性不可满足**。
**另一个后果（本轮新观察到）**：#1188 因下游 base（D2 分支）更新而**转 DIRTY（冲突）**。
| 选项 | 含义 | 代价 |
|---|---|---|
| **A** | **禁止堆叠**，每个 PR 都从 main 起 | 拆卡更细；本线 D 组现在就是堆叠的，需重做 |
| **B** | 改触发条件（去掉 `branches:[main]` 过滤，或加 base 白名单） | 会让**所有** PR 触发全量 CI ⇒ **队列成本上升**（与 D1014/D1039 的"队列放大器"顾虑相反） |
| **C** | 保持现状，但**堆叠件一律不判「可合」**（明确不满足条件①） | D2/D3 现在就在这个状态 |
**我倾向 C 短期 + A 长期**（C 零成本且诚实；A 需重做 D2/D3 的 base）。需你裁 Z。
