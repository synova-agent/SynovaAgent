## 一、先量两条前提（**不靠转述**）

### 前提①「本地 <10s」——**已成立**
```
SYNO_GATEKEEPER_ACK=1 SYNO_DIFF_BASE=origin/main bash scripts/pre-commit-check.sh
  第1次: 1938ms exit=0 ｜ 第2次: 1890ms ｜ 第3次: 1877ms
```
⇒ **~1.9s**，距 10s 上限有 **5 倍余量**。

⚠️ **一条测量陷阱（我自己踩了）**：**不带 `SYNO_GATEKEEPER_ACK=1` 时只有 68ms + exit 1** —— 因为
GATEKEEPER 在 pre-commit 的**前段**就退出了。**若只看那 68ms 会得出"本地极快"的错误结论**。
⇒ 凡报"本地耗时"，**必须报"跑完全部 13 组"的那个数**（本提案报 1.9s）。

### 前提②「CI 不跳」——**不成立，且缺口很大**
```
ci.yml: step 数 38 ｜ 带 if: 的 step 数 37 ｜ 其中与 skip/docs-only/ctsignal 相关: 34
```
⇒ **34/37 个 step 带条件**，最常见的三种: `steps.docsonly.outputs.docs_only != 'true'`、
`steps.ctsignal.outputs.run`、`github.event_name == 'schedule'`。
⇒ 这正是「**跳过 = 成功**」病的量化面。

## 二、分工线的**现状**（谁在守什么）

| 面 | 守在哪 | 能不能被跳过 |
|---|---|---|
| **机械/契约类**（13 组: 类型安全 / 测试配对 / secrets / 接线 / 架构边界 / brief 字段 / plan-integrity …） | **本地 pre-commit（1.9s）** | **不能**（本地跑，无 `if:`） |
| **重活类**（tsc / vitest / hermetic 套件 / golden-case / 集成契约） | **CI** | **能**（34/37 带 `if:`） |
| **push 事件** | CI | W2 之前**全跳**；W2 之后 push 不再走 docs-only |
| **job 级缺失** | CI | W3 的聚合 job（skipped ⇒ FAIL）覆盖 |
| **step 级缺失** | CI | 🔴 **仍是洞** —— 见 W5 提案（#1180） |

## 三、我的判断：**W11 的大部分已被 W2 / W3 / W5 覆盖，剩下的是一条"政策声明"**

| W11 想守的 | 已被谁覆盖 | 状态 |
|---|---|---|
| push 不得走 docs-only 早退 | **W2**（#1168，含 HARD step + 10 块行为验证） | ✅ 已交付 |
| 「skipped」不得被当成成功（**job 级**） | **W3**（聚合 job，复核在真实 CI 上验证过 `cancelled` 被判红） | ✅ 已交付 |
| 核心 hermetic step 不得 skip（**step 级**） | **W5 提案**（#1180） | 🟡 待裁 |
| 本地要快（<10s） | **已经成立**（1.9s） | ✅ 无需动作 |

⇒ **本提案要你裁的，不是"再修什么"，而是"把哪几条写成不可跳过的红线"**（政策层）。
**我建议写死三条**：
```
R1  任何承载**必需 context** 的 job，**不得**带 job 级 `if:`/`paths:`（缺失 ⇒ context 永不报告）
R2  **push 事件**不得走 docs-only 早退（已由 W2 实现）
R3  注册进通用 `for t` 清单的夹具**必须默认硬**（不得以"未设某个环境变量 = SOFT"为前提）
    —— 这一条来自 W2 复核的实测：同一登记面下，W3 夹具默认硬=真门禁、
       W2 夹具默认软=**纸老虎**，而登记闸对"登记即阻断"**零校验**。
```

### R3 为什么最该写死（它是最便宜的防复发）
W2 的两个阻塞点**都是同一个根因**：
> **`for t` 登记面只判 exit code，而夹具可以默认 SOFT（恒 exit 0）⇒ 登记 ≠ 阻断。**

⇒ 一条登记面规则（**注册进清单的夹具必须默认硬**）即可防住这一整类，
**比给每个夹具单独补 HARD step 更省**（后者是"逐例打补丁"，前者是"堵住入口"）。

## 四、代价（写全）

| 选项 | 代价 |
|---|---|
| 写死 R1 | 未来若真有 job 需要 `paths:` 过滤，必须走 K3+CTO 例外 ⇒ **加了一道手续** |
| 写死 R2 | 已由 W2 实现 ⇒ **零额外代价**（只是把它写成红线） |
| 写死 R3 | 需给**既有** SOFT 夹具补 `SYNO_CI:"1"`（或改默认）⇒ **一次性工作量**；但**不改存量则审计面继续是纸老虎** |
| 提高本地覆盖面（把更多检查从 CI 挪到本地） | **本地时间上升** ⇒ 逼近 10s 上限；且**本地可被 `--no-verify` 绕过**（W11 若把重活挪本地，等于把门禁交给"可绕"的一侧） |

🔴 **我明确不建议**："把 CI 的检查挪到本地" —— 因为**本地是可绕的**（本线今天就用了 23 次 `SYNO_GATEKEEPER_ACK`），
而 **CI 不可绕**。正确的分工是：**本地求快（<10s，抓机械错）＋ CI 求全（不可绕，抓重活）**，
**而不是把全量挪到快的那一侧**。
