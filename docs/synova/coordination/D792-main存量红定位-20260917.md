## 3. 归因一：CI 棘轮口径缺口（决定性）

### 3.1 代码事实（`origin/main` = `6a06e853`，`.github/workflows/ci.yml`）

```yaml
126:          BASE=$(git merge-base refs/remotes/origin/main HEAD 2>/dev/null || git merge-base origin/main HEAD 2>/dev/null || echo "")
127:          if [ -n "$BASE" ]; then
128:            CHANGED=$(git diff --name-only "$BASE"..HEAD 2>/dev/null || echo "")
...
134:          OUTPUT=$(npx vitest run --shard=${{ matrix.shard }} --reporter=verbose 2>&1; echo "EXIT:$?")
136:          EXIT_CODE=$(echo "$OUTPUT" | grep "EXIT:" | sed 's/.*EXIT://')
137:          if [ "$EXIT_CODE" = "0" ]; then exit 0; fi
140:          FAILED_TESTS=$(echo "$CLEAN_OUTPUT" | grep " FAIL " | grep -oP 'tests/\S+\.test\.ts' || true)
141:          if [ -n "$FAILED_TESTS" ] && [ -n "$CHANGED" ]; then     # ← main push 时恒为假
...
149:            if [ -z "$NEW_FAILURES" ]; then
152:              echo "::warning::Vitest 存量红放行（非本 PR 改动文件引入，main 上同样红）: ..."
156:              exit 0
...
161:          exit 1
```

### 3.2 物理复现：main push 时 `CHANGED` 恒为空

在 `6a06e853` 上原样执行 CI 的取基准命令：

```bash
$ cd <worktree @ 6a06e853>
$ BASE=$(git merge-base refs/remotes/origin/main HEAD)
$ CHANGED=$(git diff --name-only "$BASE"..HEAD)
BASE=6a06e85357214fe9cf2c11522e4f7173a5a00419
HEAD=6a06e85357214fe9cf2c11522e4f7173a5a00419
origin/main=6a06e85357214fe9cf2c11522e4f7173a5a00419
CHANGED=''
CHANGED line count: 0
```

**因果链闭合**：

```
main push → HEAD == origin/main
  → merge-base(origin/main, HEAD) == HEAD
  → CHANGED = ''                      （ci.yml:128）
  → EXIT_CODE = 1（存量红真实存在）    （ci.yml:136-137，不走 exit 0）
  → [ -n "$FAILED_TESTS" ] && [ -n "$CHANGED" ]  ⇒ true && false = FALSE   （ci.yml:141）
  → 整个「存量红放行」分支被跳过
  → 直落 ci.yml:161 exit 1
```

**即：main 的红与失败集大小无关——只要 shard 2/2 存在任何失败，main 就必然 `exit 1`。棘轮在 main 上从未参与判定。**

### 3.3 历史因果：D721 把「假绿」换成了「永红」

| 提交 | 时间 | 作用 |
|---|---|---|
| `ee773d57` | — | 引入 `CHANGED` 门控（"只阻断本次修改引入的失败"） |
| `22225c28`（**D721**） | 2026-09-13 | 基准由 `HEAD~1..HEAD` 改为 **merge-base 三点差** + 放行可见化（#520） |

两者均为 `63b0ad74` 的祖先（`git merge-base --is-ancestor` 已验证）。

- **D721 之前**：main push 时 `CHANGED = HEAD~1..HEAD` = 该提交的文件集（**非空**）→ 棘轮生效 → main 可能被**放行成 success**。
  实证：`board-backlog[38]` 记录 main `021897a0` 的 `Vitest(2/2)` 打出 `Pre-existing test failures from unchanged files — not blocking` 且**作业 conclusion = success**。
- **D721 之后**：main push 时 `CHANGED` 恒为空 → 棘轮永不生效 → **恒 exit 1**。

> **结论**：D721 修好了 PR 侧「合并提交误判存量红为新增红」的永红（#513），但把 main 侧从「静默假绿」翻转为「无条件永红」。两者都是错的，方向相反。

### 3.4 A/B 对照（同一失败集，两种结论）

| | PR run #3642 | main push run #3643 |
|---|---|---|
| sha | `17961b68` | `6a06e853` |


> ① **测试 mock 陈旧** —— 未按真实 `GraphStore.createNode(type, props, graph)` 契约转发 `props`（同文件兄弟用例是对的）；

## 6. 二阶缺口：PR 侧存在**反向**漏放行（同源，一并登记）

`ci.yml:144` 的「测试文件 → 源文件」映射是朴素字符串替换：


对本次两个红文件的实测结果：

| 测试文件 | 映射出的「源文件」 | 存在？ |
|---|---|---|
| `tests/agent/expert-file-loader.integration.test.ts` | `src/agent/expert-file-loader.integration.ts` | **NO** |

`.integration.test.ts` 后缀未被吃掉（`\.test\.ts` 不匹配 `.integration.test.ts` 的前半段），且 `graphbridge-wiring` 的真实实现在 `src/l4/graph-bridge.ts`（名字都对不上）。

## 7. 修复建议（二选一 + 推荐）

> 派单要求「二选一：进棘轮基线 / 单独修复」。**结论：两者都要做，但先后与归属不同——A 先行（恢复 main 信号有效性），B 挂编码线（把红真烧掉）。** 只做其一会留坑（见下表）。

### 方案 A — 进棘轮基线（**推荐先行**，域: CI/控制塔）

**为何必须做**：只要 `ci.yml:141` 的这个门控不改，**main 会永久红，与失败集是否修完无关**。红常态化即信号失效（`check-ci-stale-red.sh` CT-39 的立论：「红常态化让『红=有问题』的信号钝化」；`board-backlog[38]` 已把该状态定性为 P1「仓库级假绿/信号失效」）。

**建议设计（不改语义，只补 main 侧判据）**：

1. 新增 CI 口径基线文件（例：`tests/baselines/vitest-preexisting-red.txt`），内容为**当前 6 条**的 `file > case` 或 file 粒度清单。
2. `ci.yml` 判定改为三分支：
   - `CHANGED` **非空**（PR）：维持现有 merge-base 判据不变；
   - `CHANGED` **为空**（main push）：以**基线文件**替代 `CHANGED` 做放行判据 —— `FAILED_TESTS ⊆ 基线` → `::warning::` + `exit 0`；**出现基线外的失败 → `exit 1`**（main 上的真新增红仍被阻断）；
   - 无失败：`exit 0`（现状不变）。
3. **棘轮纪律**：基线**只减不增**；每烧掉一条就从基线删除，并加一条 check 断言基线不增长（否则棘轮退化）。
4. **必须同时修 §6 的映射缺口**，且基线按 **`CI=1` 口径**登记（否则会登记进 CI 永不执行的条目，见 §4.4）。
5. `fail-fast` 建议显式设 `false`（`ci.yml:109-111`），否则 shard 1/2 永远被 cancelled —— 现在 main 的 `(1/2)` **从未真正跑完过**，等于半个测试面是盲区。

> 与仓库既有棘轮模式一致（TypeScript job / `SYNO_CI=1` strict「棘轮基线内不阻断，新增才阻断」、`tests/control-tower/ci-ratchet-base.test.sh`）。本方案等于把 vitest job 对齐到同一口径。

### 方案 B — 单独修复（**推荐并行**，域: 编码线）

**为何也要做**：只做 A 会把存量红**永久固化**进基线，`board-backlog[38]` 的「须烧掉，勿长期依赖放行」正是这个意思。

成本极低：**6 个用例 / 2 个文件**，且根因已收窄到具体行（§5）。

| 项 | 归属与动作 | 备注 |
|---|---|---|
| 红 #1（5 用例） | `tests/agent/expert-file-loader.integration.test.ts:25-31` 对齐 registry v3.0（6 位 + 问题域命名） | 证据倾向「6 是意图、测试是漂移」；即与 `PLAN-expert-count-drift` 合并处理 |
| 红 #2（1 用例） | 二选一（需编码线判）：① 修 mock 转发 `props`（照抄同文件 `:22-24` 的正确写法）；② 修产品守卫 `src/l4/graph-bridge.ts:90` | 建议**同时**做②（无守卫解引用是真实健壮性缺口） |
| 红 #2 附加 | 断言 `BridgeResult.degraded/errors`（铁律 31 降级信号传播） | 否则同类失败仍会以「节点数不对」间接暴露 |

### 为什么不选「只做其一」

| 选择 | 后果 |
|---|---|
| 只做 A | 6 条真红永久写进基线，`PLAN-main-vitest-preexisting-red` 从 P1 变永久豁免 → 棘轮名存实亡 |
| 只做 B | 修复落地前 main 持续红 → 信号持续失效（CT-39 定性）；且 §6 的 PR 漏放行仍潜伏；且 shard 1/2 仍被 cancelled，测试面半盲 |
