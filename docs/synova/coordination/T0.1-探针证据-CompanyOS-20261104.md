### 2.8.1 🔴 「流式」是错的——ACP 的 `agent_message_chunk` 是**块级**，不是 token 增量

独立核验实测 + 源码双向确认：

- 实测：1260 字符的答复 → `chunkCount=1`（一整块），在 prompt 发出后 **5726ms** 到达，与 `stopReason` 响应 settle **同一毫秒**（5728ms）；41 字符答复同样 `chunkCount=1`。
- 源码：`dsh-acp/lib/index.js:554-586` 的 `updates` 由「**已提交的 assistant message**」按 content block 派生 ⇒ 每条消息提交时才产出一条 update。

⇒ **不得**把 `agent_message_chunk` 当作 token/逐字流用于"打字机"式 UI 或进度判定；要做逐字效果必须另建通道或改 DSH（本册不主张）。

### 2.8.2 适配器三条硬约束（核验后确认）

1. **无 token 级流式** ⇒ Hub 只能按"回合完成"事件推进状态，不能靠流式块做超时/进度判断。
2. **`cwd` 就是会话身份** ⇒ 适配器必须持久化「`sessionId` ↔ 物理 `cwd`」配对（`resume` 必填且须 `sameDirectory`）；这正好与 §2.3 的 headless 结论（session 绑定 cwd）同源。
3. **预设不在 ACP 里** ⇒ `acp` 模板只有 `base + acp-app`，不含任何 Synova 预设；`desktop`（唯一装着全部预设的 profile）被 Electron 独占 ⇒ 想"按角色起会话"，只能**自建 profile 装 preset bundles** 或走 `--patch`，二者都改 DSH 运行配置（越过只读探针边界）。

### 2.8.3 文档坑（核验者补）

`dsh --help` 的示例仍写 `dsh tui …`（`lib/bin.js:45-48`），而 `tui` 模板**不存在**（`dsh --profile tui` → exit 1，且不建 profile 目录）⇒ 任何"照官方帮助敲命令"的人都会撞墙，写 RUNBOOK 时必须绕开。

### 2.9 反证（复核者补测，我复核确认）：唯一带 Synova 预设的 profile 无法被程序启动

```
$ dsh --profile desktop --dump-config
error: profile "desktop" is managed exclusively by the Electron application
RC=1
```

⇒ 结论合并为两条：
- **会话生命周期（启动/恢复/关闭/列出）在 ACP 面全部可用**，且是**唯一**同时具备 `close`（=停止）、`list`（=状态）、`resume`（=接回）的入口；
- **「按预设启动」在 ACP / headless / CLI 三面都没有现成入口**：`session/new` 的 `configOptions` 只有 model 与 reasoning_effort；headless 无 `--preset`；desktop 由 Electron 独占（`exit=1`）。
