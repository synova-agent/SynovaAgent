## 〇、给创始人的大白话（30 秒）

你现在的问题：**三个员工（DSH/Codex/Claude Code）跟你说"做完了"，你没法自己查证，只能信。你被忽悠过，所以请了 K3 当监理。但 K3 贵、而且是事后才审。**

这套控制台要做的事：**给你一块"测谎仪"。** 任何员工说"做完了"，控制台立刻用物理事实（代码真提交了吗？测试真过了吗？体检真绿了吗？）告诉你"是真的"还是"是假的"。你不用懂技术，只看红绿灯；看到红灯，点一下就能看到证据。

## 一、第一性原理：这是个"防忽悠"问题，不是"展示"问题

### 1.1 问题本质（委托-代理）

创始人（委托方）↔ agent（代理方）之间存在**信息不对称**：你不懂技术，agent 懂。委托-代理理论的常识是——**没有可验证性，就有欺骗空间**。你被忽悠过，根因不是 agent 坏，而是**它们的声称你无法独立验证**。

### 1.2 谁监督监督者（现有体系的根本漏洞）

现有链条：创始人 → 信任 CTO（DSH）→ CTO 读三份仪表盘 → 周报给创始人。

**漏洞**：仪表盘是 CTO 领地（`gen-cto-health.py`）生成的，而 CTO 正是创始人要监督的代理之一。更糟的是，审计已实证仪表盘数据源**只读工作区文件、不做 git 真相校验**——`CTO-HEALTH.md` 顶行写着"打开即真相"，但 D399/D394 两次发现它显示了 phantom 行（工作区有、git 里没有的假数据）。

**也就是说：你依赖的仪表盘，可能本身就是被监督者生成的、未经验证的假象。**"打开即真相"这句话本身，正是你要防的"声称 vs 事实"。

### 1.3 设计公理（Zero Trust for Founder）

> **创始人看到的每一个数字，都必须满足三条：**
> 1. **物理派生** — 从 git log / 测试退出码 / CI 状态 / 文件仓库态算出来，绝不来自任何 agent 的自报文本。
> 2. **可挑战** — 数字旁边标"这个数字怎么算的"（数据源+命令），创始人（或 K3）一键重算验证；算出来和显示的不一样 → 立刻红灯。
> 3. **主动告警** — 没事不打扰；一旦出现"声称了但没证据"，主动找创始人，而不是等创始人来翻。

## 二、现状诊断：为什么现有仪表盘不够

### 2.0 核心矛盾（最有力的一条证据）

> **"控制塔全绿，但 K3 全链路审计 0/3 贯通。"** ——创始人新模式提案（FOUNDER-OPERATING-MODE v1.1）记录的这个矛盾，是现有仪表盘会"假绿"的铁证：门禁/体检全显示健康，独立审计却发现核心能力（L5 连接器/L4 契约/哨兵告警）根本没贯通。**你看到的绿，不等于真的好。** 这正是你"被忽悠过"的技术根源，也是本控制台要解决的头号问题。

### 2.1 现状四条病根

| # | 现状问题 | 后果 | 证据 |
|---|---|---|---|
| 1 | **假绿**：控制塔全绿但 K3 实测核心断裂 | 你看到的健康是假的 | FOUNDER-OPERATING-MODE v1.1；K3 全链路审计 0/3 |
| 2 | **自报无核验**：右边栏"六维健康雷达"等信号由组件自己 emit-signal 写绿 | 你以为是雷达，实际是"各组件自夸" | 6 组件信号 emit-signal 自报；DASHBOARD MANUAL 区手写"17/17 PASS"与 K3 FAIL 直接矛盾 |
| 3 | **phantom 数据源**：只读工作区文件，不验 git 真相 | 显示假数据，"打开即真相"是空话 | gen-cto-health.py:225-228 只查 `.exists()`；D399/D394 phantom 实证 |
| 4 | **技术化 + 答非所问**：满屏 bypass.log/M模式/hash，不回答你真正的问题 | 非技术创始人看不懂，且没人答"真做完了吗/骗我了吗/跑偏了吗" | CTO-HEALTH.md 全文 |

### 2.2 "右边栏"现状（经核实修正）

创始人实际看的"右边栏"**不是** `app/index.html`（那是产品诊断 UI，右栏仅占位），而是 **D220 创始人驾驶舱的"右栏：六维健康雷达"**（6 个组件信号区块）。

**关键问题**：这 6 个组件信号是 **agent 自报的**——组件自己 `emit-signal` 写绿，无物理核验。也就是说，你以为在看"健康雷达"，实际在看"各组件自己说自己健康"。这就是"右边栏不够"的直接原因。

> 修正记录：本方案初稿曾误判右边栏为 app/index.html 占位（expert-sidebar），经独立研究核实为 D220 驾驶舱六维雷达。设计落点因此从"新建一个面板"修正为"**把现有六维雷达从自报改造成物理核验**"。

### 2.3 该保留发扬的现有好设计

不是所有都推倒。**product-progress.html 的"六态机"是现有最强设计**：`无证据 = 未验证 = 不计分`。这个"没证据就不算数"的原则，正是零信任控制台的灵魂——**保留并推广到全部指标**。

### 2.4 真实性光谱（现有各区块，从最可信到最不可信）

| 可信度 | 区块 | 数据源本质 |
|---|---|---|
| 🟢 最可信 | product-progress.html 六态机 | 证据门控"无证据=未验证=不计分" |
| 🟢 较可信 | CTO-HEALTH / DASHBOARD AUTO 区 | git log / 文件存在 / hook 日志派生 |
| 🟡 半可信 | 完成度雷达 | 静态扫描快照（已停滞 08-01）——"扫描到"≠"跑通" |
| 🟡 半可信 | 17 产品门禁 | 启发式扫描（"文件存在+非占位签名"级） |
| 🔴 不可信 | **六维雷达（右边栏）** | 组件自报 emit-signal 写绿，无核验 |
| 🔴 最不可信 | DASHBOARD MANUAL 区手写指标 | 手写"17/17 PASS、CT 20/20"，与 K3 FAIL 直接矛盾 |

> 另：D296 实证仪表盘曾显示"假 0%"——**控制塔测量自己也不可信**（G6："测量自己的系统不可信"）。这是"谁监督监督者"的又一铁证。

## 三、设计：三问直达（创始人的视角，不是工程师的视角）

> **设计定位（先对齐，不另起炉灶）**：你在 FOUNDER-OPERATING-MODE v1.1 里已构想创始人驾驶舱——**一页纸三块（产品真值按场景 / 开发流四态 / 需要创始人待裁决）+ 语言红线（不出现 D#/门禁组号/git hash/P0）+ 完成=黄金场景跑通**。本方案不推翻它，而是给它装**零信任内核**：三块形式保留，但每个数字从"agent 自报"换成"物理核验"，再加两件你没有的——**挑战按钮**和**诚信账本**。
>
> 对应关系：**产品真值（按场景）=「哪些真做完了」；开发流四态 = 任务进展；需要创始人（待裁决）= 主动找你**。我额外补两块：「哪些骗了我」诚信账本 +「方向跑偏了吗」北星对齐。

控制台不罗列指标，而是**直接回答创始人每天最关心的三个问题**。每个问题一个面板，红绿灯语义。

### 面板 1：「哪些真做完了？」— 任务真相

每个任务一行，不是 agent 说"done"，而是物理验证四连环：

```
[D405] CI 仪表盘    
  声称: 已完成 ✅ (agent 自报)
  物理: 代码已提交✅ 测试通过✅ CI绿❌ 已合并✅
  判定: 🟡 部分真实 — CI 是红的，点我看哪条红 →
```

- 数据源：git log（提交？）/ vitest 退出码（测试？）/ CI API（绿？）/ 分支合并状态（合并？）
- **判定规则**：声称 ✅ 但任一物理项 ❌ → 红/黄灯 + 标"哪一环是假的"。这就是"测谎"。
- **完成的最高判据（呼应你 v1.1 的提案）**：任务提交 ≠ 真的完成。最终判据是"**黄金场景真跑通**"（`scripts/golden-scenarios/` GS-01~08 端到端跑一遍，真出诊断结果）——这正是"控制塔全绿但 K3 0/3"的解药：**门禁绿不算数，真实场景跑通才算数。**

### 面板 2：「哪些骗了我？」— 诚信账本

每个 agent（员工）一个诚信分，基于历史"声称 vs 物理事实"的命中率：

```
🛠 编码员工 (Claude Code/Win)   诚信 96% — 近 30 天声称 48 次, 物理核实 46 次属实, 2 次夸大
📋 dev-doc 员工 (Codex)         诚信 88% — ...
🧭 CTO (DSH)                   诚信 91% — ...
⚠️ 今日新增: D395a 声称"门禁已落位", 物理核实=未落位 (check-lessons-learned.sh:8) → 已记一笔
```

- 数据源：K3 审计结论 + 控制塔 phantom 检测 + U4 声称↔证据对账。
- **价值**：让"忽悠"留下永久的、可量化的记录。诚信分跌破阈值 → 自动升级创始人。

### 面板 3：「方向跑偏了吗？」— 北星对齐

每个进行中的任务，标注它服务你哪个目标（对照 `.claude/PRODUCT-BRIEF.md`）：

```
进行中任务北星对齐: 4/5 对齐 ✅
  D394 哨兵事件化 → 服务"三、Synova 怎么工作-哨兵定时巡检" ✅
  D396 golden-case → 服务"六、还没做的-质量防线" ✅
  ⚠️ D397 产品 loop 卫生 → 在北星里找不到对应 → 需要你确认: 这是你要的吗?
```

- 数据源：任务 brief 的 Q0 锚定 vs PRODUCT-BRIEF.md 章节（机器比对关键词，人话呈现）。
- **告警**：连续 N 个任务与北星无对应 → "最近在做的几件事故和北星对不上，要不要开个会？"

```
L4 呈现层   右侧栏面板 / 独立 HTML / DSH 对话推送（三选一或并存）
            ↑ 红绿灯 + 人话 + 点查证据

            ↑ 由 L2 指标聚合

            ↑ 由 L1 物理事实计算

            ↑ 唯一可信根。U3 产物可复现校验 = 这一层的地基
```

**关键**：L1 是唯一可信根。现有仪表盘的病根就在 L1（phantom），所以 **U3（产物可复现校验）是本控制台的地基，先行施工**。

## 五、挑战机制（"测谎仪"的核心：一键验证）

这是本控制台区别于一切现有仪表盘的地方——**不只是显示，而是可主动验证**。

### 5.1 每个数字都带"验算按钮"

创始人看到任何数字，旁边有"🔍 怎么算的"。点开显示：
- **数据源**：这个数字从哪个物理事实来（如 `git log --oneline | grep D405`）
- **重算**：系统当场重新物理执行该命令，把"实时算出来的"和"仪表盘显示的"并排对比
  - 一致 → 绿灯"已复核"
  - 不一致 → 红灯"显示值过期/造假"，并记一笔到诚信账本

创始人不需要懂那条命令——他只看"重算后两个数一不一样"。一样就信，不一样就是有人忽悠或数据过期。

### 5.2 每日自动挑战（不等创始人点）

每天定时（或每次 dashboard 刷新时）自动抽样 N 个显示值做重算比对，发现 phantom 立刻红灯 + 主动告警创始人。这把 phantom 从"等 K3 审计发现"变成"当天自动现形"。

### 5.3 诚信账本的来源

每次挑战不一致、每次 K3 审计判"声称 vs 事实"（M2）、每次 phantom 检出 → 自动记到对应 agent 的诚信账本。**忽悠从"零成本"变成"永久留痕"。**

## 六、L1 物理事实层（地基，唯一可信根）

一切指标的数据源白名单（**只允许这些**，禁止任何 agent 自报文本作为数据源）：

| 指标 | 唯一允许的物理数据源 | 不允许 |
|---|---|---|
| 代码是否提交 | `git log` / `git cat-file -e <hash>` | agent 说"已提交" |
| 测试是否通过 | `vitest run` 退出码（现场重跑） | agent 说"24/24 绿" |
| CI 是否绿 | GitHub check-runs API（job 级） | agent 截图/转述 |
| 文件是否存在 | `git ls-files` / `git cat-file`（**仓库态**，非工作区） | `.exists()`（工作区，phantom 源） |
| 是否合并 | `git branch --merged` / `git ls-remote` | agent 说"已合并" |
| 是否绕过门禁 | bypass.log + `git log` 对账（U1） | agent 说"我没绕过" |

**U3（产物可复现校验）就是这一层的第一个施工项**——先把 gen-cto-health.py 的 phantom 消灭（工作区 `.exists()` → git 仓库态校验），控制台才有可信地基。

## 八、与 UPGRADE-SPEC 的施工顺序对齐

控制台不是空中楼阁，它复用控制塔升级的物理门禁作为数据源：

| 控制台依赖 | 来自 UPGRADE-SPEC | 关系 |
|---|---|---|
| L1 phantom 消除 | **U3** 产物可复现校验 | 控制台地基，**最先施工** |
|  bypass 对账（真绕过检测） | **U1** 证据链对账 | 面板 1"是否绕过门禁"的数据源 |
| 声称↔证据对账 | **U4** 自证表 | 面板 2"诚信账本"的自动数据源 |
| 机器预审汇总 | **U1-U4/U7** | K3 审计前移后，面板可显示"机器预审过没过" |

**建议总顺序**：U3（地基）→ U1（证据链）→ U7（控制塔测试门禁）→ 控制台 L1+面板 1（可见雏形）→ U4（诚信账本数据源）→ 面板 2/3。
