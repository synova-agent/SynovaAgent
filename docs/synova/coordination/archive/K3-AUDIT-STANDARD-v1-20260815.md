## 二、维度 16-20 定稿标准

> 每条判定规则按"无上下文执行者可照做"书写：给对象、给命令、给 exit 语义。
> **通用前置**：若被审对象不存在（如 `scripts/golden-scenarios/` 未建立），记 `NOT-AUDITABLE` 并在报告中显式标注——NOT-AUDITABLE ≠ PASS。

### 维度 16：场景断言质量

| 项 | 定稿 |
|----|------|
| **审什么** | `scripts/golden-scenarios/GS-*/` 全部场景的断言区（run.sh 的 assert 段 / assertions 文件） |
| **判定规则** | 执行者逐项核查：<br>① **空壳/恒真扫描**（自动）：`grep -rnE "assert[[:space:]]+true|exit 0 *$|echo .PASS" scripts/golden-scenarios/*/run.sh`——命中且该行是该场景唯一"断言"→ 记缺陷；断言区含 `TODO|FIXME|placeholder` → 记缺陷<br>② **断言数底线**：每场景断言语句（grep/diff/数值比较/状态检查）≥3 条<br>③ **物理输出对账**：每条断言的目标必须是产品真实输出（evidence 文件、产品命令 stdout、DB/文件状态），不允许只断言脚本自产中间变量。判定法：断言行含对 `evidence/`、产品二进制/脚本输出、或状态文件的引用<br>④ **负向断言存在性**：全部场景中，含 ≥1 条负向断言（非法输入被拒/异常路径被验）的场景占比 ≥25%（8 场景即 ≥2 个） |
| **怎么算过** | PASS：①-④ 全过；FAIL：任一 ①命中（存在恒真/空壳）且该场景当前声明绿；其余缺项按分级 |
| **触发频率** | git diff 触及 `scripts/golden-scenarios/` 的提交批次必审（随该 D# 任务审计走）；**每季度全量一次** |
| **分级归属** | 恒真/空壳断言 + 场景声明绿 → **P0**（假绿，对齐 P1-C2/铁律 48）；负向断言占比不达标 → **P1**；断言数 <3 或中间变量断言 → **P2** |

### 维度 17：场景转绿复核

| 项 | 定稿 |
|----|------|
| **审什么** | 每一个"转绿声明"（来源：product-lines.yaml 验收点状态变更 / 驾驶舱场景状态 / 任务完成报告）的三对照：声明 ↔ evidence ↔ K3 独立重跑 |
| **判定规则** | 三对照全部满足才算过：<br>① **声明存在**：找到明确的转绿声明位置（文件:行）<br>② **evidence 合规**：`docs/synova/product-lines/evidence/GS-XX/`（或实现方按 §五反向契约指定的路径）下存在证据文件，且机器可解析（JSON），且含**环境指纹四要素**（OS / runtime 版本 / git hash / 时间戳）与退出码<br>③ **独立重跑（T1 干净快照）**：`git archive` 或临时 clone 出干净副本 → 一行命令执行 `scripts/golden-scenarios/GS-XX/run.sh` → **exit code = 0** 且证据在干净环境再生。工作区原地重跑（T2）可作补充但不作判据 |
| **怎么算过** | PASS：三对照齐；**声明绿但 K3 重跑红 → FAIL**（该验收点判 🔴，所涉线进度回退，报告结论 FAIL）；evidence 缺失/不可解析/缺环境指纹 → CONDITIONAL PASS（证据缺陷，验收点维持 🟡 不得转 🟢） |
| **触发频率** | **逢绿必验**：转绿声明即入待验池，最近一个批次（任务审计批或双周兜底批）必验——**不设"攒够 N 个才审"的门槛**（A7 按既有节奏派发）；双周批次兜底防声明遗漏 |
| **分级归属** | 声明绿+重跑红 → **P0**；evidence 不可解析/无指纹 → **P1**；重跑耗时/资源超约定 → **P2**（记录） |

### 维度 18：驾驶舱真值复核

| 项 | 定稿 |
|----|------|
| **审什么** | `docs/synova/product-lines/product-progress.json`（及 cockpit-state / 页面数据源）与底层事实的一致性；含 A6 自动解析的正确性 |
| **判定规则** | ① **可解析**：JSON schema 有效，状态字段 ∈ 状态机四值（⚪🔴🟡🟢）<br>② **绿必有背书**：每个 🟢 验收点必须能指到：(a) K3 复核通过记录（报告 ID），或 (b) 创始人演示核验记录。无背书而绿（应 🟡 而 🟢）→ 记缺陷<br>③ **新鲜度**：`product-progress.json` 生成时间 ≥ 最近一次触及该线映射模块（`product-lines.yaml` 各线声明的模块路径）的 git merge 时间——代码已变而进度未重算 = stale（对齐 A1 失效检测是否真的执行）<br>④ **自动解析对账（A6）**：抽最近 1 份 K3 报告，比对"报告结论"与"写入状态机的判定"是否一致——解析错判（如 FAIL 被入账为 🟡）→ 记缺陷 |
| **怎么算过** | PASS：①-④ 全过；任一无背书绿 / stale / 解析错判 → 按分级 |
| **触发频率** | **每周一次**（cron 刷新后对账，成本极低——纯文件核对）；转绿复核批次联动 |
| **分级归属** | 应黄而绿（无背书绿）→ **P1**；stale 超 7 天（D-G2 停更模式）→ **P1**；A6 解析错判 → **P1**；JSON 损坏/字段缺失 → **P2** |

### 维度 19：新门禁 fault injection

| 项 | 定稿 |
|----|------|
| **审什么** | 场景回归接入 pre-push/CI 后的门禁**本身**——它是否真拦截、是否 fail-closed |
| **判定规则** | 三类注入实验（在临时 clone/worktree 中执行，不污染主工作区）：<br>① **破坏断言**：篡改一个场景断言的期望值使其必红 → 执行门禁（pre-push 或 CI 等价命令）→ **必须拦截**（exit ≠ 0 / CI 红）<br>② **断依赖**：制造依赖缺失/库不可用（如临时改名 `scripts/golden-scenarios/` 或断 DB）→ 门禁必须报 fail/degraded 且**拦截或显式 degraded 告警**——**exit 0 静默放行 = FAIL**（fail-open 即门禁形同虚设，对齐 D328 P1-1/M1）<br>③ **绕过检测**：`--no-verify` 或删除/改名门禁脚本 → 必须有旁路记录（bypass.log）或 CI 兜底拦截 |
| **怎么算过** | PASS：①②③ 全部真拦截/真告警；任一静默放行 → FAIL |
| **触发频率** | 门禁接入/变更当次必做（随该 D# 审计）；**接入后 30 天复验一次**；此后每季度一次 |
| **分级归属** | 静默放行（fail-open）→ **P0**；拦截但无任何日志/记录 → **P1**；bypass 无记录 → **P1**（对齐 M4） |

### 维度 20：进度真度审计

| 子项 | 定稿 |
|------|------|
| **20a 进度真实度（抽样）** | 按 §四抽样规则执行。判定：被抽验收点的"声称已验证"必须有 (i) evidence 合规 + (ii) K3 复核或创始人演示记录 + (iii) 需要时独立重跑通过。任一缺失 → 该点判 🟡/🔴，线进度重算。声称绿而重跑红 → **P0**；无背书绿 → **P1** |
| **20b 验收点软化** | **对象**：`product-lines.yaml` 的 git 历史。**判定**：验收点措辞变更后，该点状态必须回 🟡 重验（措辞变更即证据失效）；检出软化模式（删除量化指标 / "支持X"→"部分支持" / "完成"→"基本" / 验收标准改宽）且状态仍为 🟢 → **P0**（对齐 C线红线 2：禁止把做不到包装成不需要）。纯澄清不改语义 → PASS |
| **20c 线 100% 全量复核** | **硬触发**：任何线首次声明 100% → K3 对该线**全部验收点**（非抽样）执行 17+20a 判定；未复核或任一点不过 → 该线不得计 100%（状态机强制回 🟡）。**频率**：触发式。**分级**：声称 100% 但复核出红 → **P0**；全量复核 overdue（到 100% 后 2 周未审）→ **P1** |
| **20d 总进度一致性** | **判定**：用 `product-lines.yaml` 独立重算各线进度与总进度，与 `product-progress.json` 展示值比对（容差 ±0.5pp，容差内判一致）；同时核对 stale 标记是否按 A1 规则执行（证据失效后对应点是否已回 🟡）。**频率**：每周随 18 项执行。**分级**：加总不一致超容差 → **P1**；stale 规则未执行 → **P1** |

## 四、进度真度抽样规则（任务 3 定稿）

> 成本口径对齐创始人约束：**单批 ≤¥20**。

**单点成本基准**（实测口径，2026-08 物价）：证据文件核查 ≈ ¥0.5-1；一次场景独立重跑 ≈ ¥2-5；一次 git/yaml 对账 ≈ ¥0.5。

**每批抽点规则**（随任务审计批次或双周兜底批执行）：

| 优先级 | 池子 | 抽法 | 单批上限 |
|:---:|------|------|:---:|
| 1 | **新增绿**：自上次审计以来新转 🟢 的验收点 | **全验，不抽**（新增绿是唯一信息增量，逢绿必验） | ≤5 点 |
| 2 | **无背书绿**：标 🟢 但无 K3 复核/演示记录的状态机违规点 | 全验（本来就违规，见一个查一个） | ≤2 点 |
| 3 | **久置绿**：>90 天未复核的 🟢 点 | 每线至多 1 个，按最老优先 | ≤2 点 |
| 4 | 随机绿 | 补足批次的随机样本 | ≤1 点 |

**批次上限 8 点 / ≤¥20**——超出按优先级截断，未验点记入报告"结转清单"（下批优先）。**禁止**为压成本跳过优先级 1/2。

**全量复核时机**：① 任一线首达 100%（20c 硬触发，该线全量——**不豁免成本上限**：按 ≤¥20/批 连续分批执行，最迟 2 周内完成，与 20c overdue 判 P1 的规则自洽）；② 每季度一次全量抽检（每线 ≥2 点）。

**选点确定性**：抽点用固定种子（`seed = 报告日期 YYYYMMDD`）对候选池排序选取——保证同一批审计可被第三方复现抽点结果（防"挑软的捏"）。

| R7 | **重跑确定性**：同 git hash 同环境下重跑结果必须一致（允许白名单化的非确定项，如时间戳断言豁免清单） | 同点重跑两次结果不一致 = 场景本身 P1 |
