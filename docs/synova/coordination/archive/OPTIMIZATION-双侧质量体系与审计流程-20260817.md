## 〇、3 分钟摘要（给创始人）

**一句话**：Mac 和 Win 两边写的代码质量**都高**（审计零 P0），真正的差距不在代码，在**约束机制**和**流程**。三个最值钱的动作是：

1. **把 K3 审计前移成"机器预审 + 高风险才全量审"** —— K3 成本砍掉一半以上，还能堵住"审计跑输合并、活缺陷上线"的漏洞。
2. **把审计台账里复发 ≥2 次的问题全部做成机器门禁** —— 一次写几十行 bash，以后永不复发、永不需 K3 再审同一类问题。
3. **降门禁误伤（Win 侧）+ 补写时约束（Mac 侧）** —— 前者治"门禁反过来咬人"，后者治"Mac 全靠自觉"。

**需要你拍板的 4 个决策**见第八节（都不需要懂代码，是流程/优先级选择）。

## 一、现状：两边不是"两个体系"，是"一层物理钩子之差"

| 约束层 | Win（Claude Code） | Mac（DSH 预设） |
|---|---|---|
| 写前 PreToolUse（无 task brief 不准写） | ✅ 物理阻断 | ❌ 无 |
| 写后 PostToolUse（verify-incremental L1→L4） | ✅ 物理阻断（5-30s/次） | ❌ 无 |
| pre-commit 13 组 | ✅ | ✅（同一 repo，脚本归 DSH 管） |
| pre-push 3 项 | ✅ | ✅ |
| 铁律/SOP 自律 | ✅ | ✅（persona 注入） |

**机制事实**：DSH persona 自述——`.claude/settings.json` 的 hooks **"不会在 DSH 会话中触发，流程纪律靠自我执行 + git 门禁兜底。不要把纪律外包给 hook"**（`docs/synova/coordination/dsh-preset-draft/persona-block.yml:105`）。且该 settings.json 内全是 Windows 路径（`C:/Users/Administrator`），在 Mac 上不触发。

**结论**：两边共享同一套 pre-commit 门禁（最后一道闸完全相同）。**真实非对称只有一处：Win 写代码前后被物理卡住，Mac 写代码前后靠自觉。**

## 二、质量盘点：审计实证（都高，但失败模式相反）

### 2.1 代码质量对比（近 2-3 个编码任务逐文件核）

| 任务 | 侧 | 规模 | K3 首审判定 |
|---|---|---|---|
| D355 L4 数据契约 | Win | ~400 行 | CONDITIONAL PASS，无 P0 |
| D363 LLM failover | Win | ~301 行 | CONDITIONAL PASS，无 P0 |
| D394 哨兵 findings 事件化 | Mac | ~845 行 | spec 关卡 CP |
| D396 golden-case 快照门禁 | Mac | ~594 行 | spec 关卡 CP |

**共同优点（两边持平，均已达标）**：契约优先 JSDoc（`@input/@output/@degraded`）、`as any`=0、catch 带 log+degraded、测试非空壳（断言密度 D394=57 / D396=42 / D355=33 / D363=17 全覆盖正常+降级+边界）。

**风格差异（无优劣，是取向）**：
- **Win** = 小而紧的垂直切片，接线零遗漏（D363 每个新 export 都有生产调用方）。K3 原话：**"自我报告质量迄今最佳、交付过程质量创系列新高"**。
- **Mac** = 大而讲究的架构基建，单源纪律更强（D394 显式立 I1/I2/I3 三 invariant），但有"机制先到位、入口后补"倾向（D394 的 `transitionFindingStatus` 无生产调用方；D396 的 `findingsFnRegistry = {}` 空登记）。

### 2.2 关键判读（务必公平）

- **Mac 的代码质量本身不差。** 两次 FAIL（D391/D393）全是**过程产物问题**——声称没证据、bypass.log 没记、dev doc 没回填（M2/M4/M7），**不是代码逻辑缺陷**。
- **这恰好印证机制差异**：过程产物正是 Win 写时钩子会物理拦住、而 Mac 靠自觉就漏的那一类。
- **D395a 暴露最危险漏洞**：K3 在 spec 阶段就预测了 P1-1/P1-2，但 **impl 在审计进行中就合并进 main**（71e0620），两缺陷变成已交付活缺陷（`check-lessons-learned.sh:8,23` 仍平铺写入）。**审计跑输了合并。**

## 三、优化建议 A：Mac（DSH）侧 —— 把"自觉"拉回"物理"

> 作者领地，作者认领。按严重度排序。

| # | 问题 | 优化动作 | 验收方式 |
|---|---|---|---|
| A1 | **过程产物靠自律必漏**（M2/M4/M7 是 Mac FAIL 的全部根因） | 用 DSH 原生 `goal` 机制把 8 步 SOP 变成**带物理校验的门禁**（每步须 grep/测试证据才进下一步），替代"请自觉"的 persona 文字 | 连续 3 个任务无 M2/M4/M7 发现 |
| A2 | **bypass.log 证据链 4 次复发**（D328→D329→D383→D394/D395a） | 建 CT-17 门禁：pre-commit 加"bypass.log 有未提交行则拦截"。机器对账，不靠自觉 | `git log` vs `bypass.log` 对账脚本 exit 0 |
| A3 | **控制塔自身缺测试门禁**（CT-40）：`tests/control-tower/*.test.sh` 不跑 pre-commit/CI，D393 红灯无物理拦截 | 控制塔测试接入门禁 | 改坏的控制塔脚本在 commit 时被拦 |
| A4 | **spec 期漏 grep 消费者**（D395a P1-2 改向漏列根因） | grep-refs 三步曲从 impl 期前置到 spec 期 | spec 含"被改路径全部消费者 grep 记录" |

## 四、优化建议 B：Win（控制塔）侧 —— 降误伤

> Win 质量最好，唯一真实痛点是**门禁反噬**。脚本归 DSH 管，作者认领改造。

| # | 问题（已实证事故） | 优化动作 | 验收方式 |
|---|---|---|---|
| B1 | **CT-29 marker 并发死锁**：多 session 时误判 `--no-verify` → 硬阻断所有提交（D362 实证） | 三态化：per-session marker 或按 commit hash 对账；degraded 不硬阻断 | 双 session 并发提交互不干扰 |
| B2 | **CT-30 secrets 过拦**：gitignored 的本地 `.env` 被当违规 → 所有提交被拦（D370 已部分修） | 三态输出（pass/degraded/fail），degraded 不硬阻断 | 本地 .env 存在时提交正常 |
| B3 | **CT-28 verify-parallel 误报**：把"依赖/接力"误判并行冲突 → 硬阻断 | 判定语义修依赖顺序 | 接力任务不被误拦 |
| B4 | **pre-commit ~50s 仍慢**（V4.5.1 实测，122s 已降到 ~50s） | 增量缓存，常态 <15s | `time git commit` 实测 |
| B5 | **版本幻影/任务 ID 复用反复出现**（D355 版本幻影、D363 ID 复用） | commit-msg 门禁：消息带 `Vx.y.z` 则必须同 commit 落 VERSION.md；任务 ID 注册前查重 | 幻影版本号在 commit 时被拦 |

> **统一修法**：B1/B2/B3 的共性是把"检查没跑成"和"检查没通过"压成同一个 exit 1（M1 同型）。一律改三态输出，degraded 只告警不硬阻断。

## 五、优化建议 C：审计流程 —— 机器预审 + K3 语义终审（省钱核心）

### 5.1 问题：K3 成本高的根因是"用金贵的语义大脑干 grep 的活"

把 K3 报告的 15 项逐个拆开：

| 机器能 1 秒查的（约 7 项） | 需要 K3 语义的 |
|---|---|
| 接口真实性（grep）/ 文件路径存在（ls）/ 架构边界（已有 check-architecture.sh）/ 接线深度（grep 调用方）/ 测试覆盖（vitest）/ 控制塔执行审计（git log vs bypass.log 对账）/ 版本编排（grep VERSION.md） | T3 故障注入设计 / 声称-事实语义对账 / "形似神不似" / north-star 对齐 / dev doc 语义漂移 |

**更狠的证据**：同一类问题在反复审——M4 复发 4 次、产物不可复现复发 3 次、M7 多次。**审计发现了问题但没固化成防线，所以下次还犯、下次还审，你在为同一个问题反复付 K3 的钱。**

### 5.2 三层审计模型

```
第 0 层  机器预审（pre-commit / CI）     成本≈0，每次提交都跑
         把 7 项物理检查全前置。查不过 = 根本到不了 K3。
         （正是铁律 35：能写 check-*.sh 的不靠 review）

第 1 层  交付方自证（"声称↔证据"对照表）  成本=0
         交付必附结构化对照表：每条声称 ↔ grep行号/测试结果/diff文件。
         填不出 = 不准提交。把 K3 从侦探变法官，只抽验不重新收集。

第 2 层  K3 语义终审                     只审机器查不了的
         T3 故障注入 / 语义对账 / 形似神不似 / north-star。
```

### 5.3 风险分级（不是所有任务都配同等级审）

| 任务类型 | 例子 | 审计方式 |
|---|---|---|
| 纯文档 | memory 归档、台账 | **免 K3**（机器预审即可；CT-34 已豁免 12 组门禁，审计同理） |
| 低风险代码 | 加测试、只读 dashboard | 机器预审 + **K3 抽查**（如每 3 抽 1） |
| 高风险代码 | 改门禁/架构/数据流/schema | 机器预审 + **K3 全量**（K3 真正该花的时间） |
| spec 关卡 | 新方案 | **轻审**（很多 spec 问题如"写集有没有承载文件"机器能查） |

**预期效果**：K3 全量审任务量砍 50-60%，且因防线固化，复发问题不再返场。

## 六、效率总账：时间黑洞排序（别只盯门禁快慢）

数据显示最大的时间浪费是**返工**和**门禁死锁**，不是那 50 秒：

| 排序 | 时间黑洞 | 量级证据 | 治理动作 |
|---|---|---|---|
| 1 | **审计跑输合并 → 活缺陷返工** | D395a 两 P1 已上线；D391/D393 FAIL→fix→复审 整轮返工 | 审计入关键路径（决策 D1） |
| 2 | **门禁误伤死锁** | CT-29 全拦、CT-30 全拦、CT-28 误报，单次卡死数小时 | B1/B2/B3 三态化 |
| 3 | **M4 证据链人工追** | 4 次复发，每次 K3 手工对账 | A2/CT-17 机器化 |
| 4 | pre-commit 50s × N 次/天 | 两边共付 | B4 提速 |
| 5 | PostToolUse 5-30s/次写 | Win 每次写文件都付，20 次写≈5-10 分钟 | 增量缓存 |
