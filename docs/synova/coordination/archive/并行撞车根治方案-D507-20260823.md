# 并行撞车根治方案（D507）— session 专属 worktree 物理隔离

> 2026-08-23 | CTO (dsh-cto) | 状态: 方案待创始人批 | 触发: D506 第 4 次 M8 复发（编码 session 实证"D506 的提交一度被打进我的分支"）
> 定性: **这是我的责任**。M8 已复发 4 次（D320/D330/D331/D394→D506），PARALLEL-DISCIPLINE.md 早在 2026-08-12 就写明"D307 是物理解法"，但我一直用临时手段（/tmp worktree、补记、分支重命名）处理个案，没有推进根治。本方案是彻底解。

## 一、根因（物理事实，非纪律问题）

**所有 session（CTO / dev-doc / 编码 / K3）共享同一个 git 工作区** `/Users/wane/SynovaAgent`。git 的以下状态全部是**进程间共享单例**：

| 共享单例 | 撞车表现（已实证） |
|---|---|
| HEAD / 当前分支 | A checkout 时 B 的分支被物理切走（D506：编码 session 的 D505 提交落在了我的分支上） |
| index（暂存区） | A 的 git add 被 B 的 add/unstage 覆盖（D330/D331 拉锯） |
| 工作区文件 | A 未提交的修改被 B 的 checkout 带走/覆盖 |
| 远程分支 ref | B 在共享区 push/reset 可改写 A 已 push 的分支（D506：我的 fix 分支被重置回 main） |

**软纪律（register/暂存即提交/被拒不重试）只能减害，挡不住物理层互踩**——四次事故全部绕过了软纪律。

## 二、方案：三层防线（物理隔离 + 启动强制 + 门禁兜底）

### 第 1 层（根治）：session 专属 worktree —— D307 落地

每个 session 认领任务时，创建**独立 worktree**（git 原生机制，独立 HEAD/index/工作区文件）：

```
/Users/wane/SynovaAgent            ← 主工作区：只读基准（看仪表盘/读文档），任何 session 禁止在此写代码/提交
/Users/wane/synova-wt-D506/        ← 我的 D506 worktree（独立分支 fix/d506）
/Users/wane/synova-wt-D505/        ← 编码 session 的 D505 worktree
/Users/wane/synova-wt-k3-xxx/      ← K3 审计 worktree（已有惯例）
```

**新建 `scripts/control-tower/worktree-manager.py`**（D307 设计 §3.1 已写好，直接实现）：

```
worktree-manager create <D#>          # git worktree add ../synova-wt-<D#> -b <分支> origin/main
                                      #   + registry 登记 worktree_path/worktree_branch
worktree-manager finish <D#>          # 校验分支已 push/PR → git worktree remove + registry 清理
worktree-manager gc                   # 孤儿检测（分支已合并但 worktree 未清）→ 列出+清理
worktree-manager status               # 各 session 的 worktree 占用一览（我看板用）
```

规则：
- worktree 内提交走同一套 hooks（`git worktree` 共享 `.git/hooks`，12 组门禁天然生效）
- synova-commit 在主工作区检测到"活跃多 session + 试图提交"→ 硬阻断并提示 `worktree-manager create`（不再靠自觉）
- 完成即 `finish`（合并/PR 后清理），D461 孤儿检测接入 `gc`

### 第 2 层（启动强制）：预设注入"开工三步"

三个员工预设（synova-dsh 编码 / synova-devdoc / synova-k3-audit / synova-cto）的 persona 加一段硬规则：

> **开工第一步（任何 git 操作前）**：
> 1. `git worktree list` —— 看自己是否已在专属 worktree（cwd 含 `synova-wt-`）
> 2. 不在 → `bash scripts/control-tower/worktree-manager.py create <我的D#>`，然后**在该目录里工作**
> 3. 主工作区 `/Users/wane/SynovaAgent` 只允许：读文档/看仪表盘/跑只读命令。**禁止 checkout/add/commit/push**

### 第 3 层（门禁兜底）：synova-commit 物理检测

synova-commit 开头加检测（无法绕过，不依赖 AI 自觉）：
- 当前 cwd 是否在 `synova-wt-*` worktree 内
- 否 + registry 显示有 ≥2 活跃 session → **硬阻断**："检测到并行 session，请在专属 worktree 提交（worktree-manager create）"
- 单 session 时放行（不增加单人流程摩擦——控制塔减负原则不破）

## 三、为什么不选其他方案（决策参考 D333）

| 备选 | 否决理由 |
|---|---|
| 只加强软纪律 | 已实证 4 次失败——物理单例挡不住 |
| 每 session 独立 clone | 磁盘×4 + node_modules×4 + 门禁/hooks 不同步漂移；worktree 共享 .git 零拷贝 |
| 锁文件（串行化） | 并行变串行，dev-doc+编码同时工作时会互相等——浪费带宽 |
