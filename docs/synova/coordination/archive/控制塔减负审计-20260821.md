## 一、控制塔全景（已彻查）

### 1.1 本地 git hook 链（每次提交必跑，4 个 hook）

| hook | 调用的脚本 | 内容 | 成本 |
|---|---|---|---|
| pre-commit | `pre-commit-check.sh` | 13 组硬阻断（类型/测试/secrets/接线/架构/brief/契约/文件驱动/CP3/scope/技能） | ~50s |
| commit-msg | `commit-msg-check.sh` | 格式 + D395-a Note 引用 | <1s |

| pre-push | `pre-push-check.sh` | 同步检查 + tag 校验 + secrets 终扫 + golden-case + vitest --changed + bypass 对账 | ~5s |

### 1.2 CI（.github/workflows/ci.yml，9 个 job）

quality（tsc + **重复跑 pre-commit-check.sh**）/ test（vitest 双分片）/ architecture / control-tower-tests（5 个 canary）/ integration / checker-review / audit（豁免）/ golden-case。

**关键发现**：CI 的 `quality` job 已经 `bash scripts/pre-commit-check.sh`，但：
- 设了 `SKIP_AS_ANY=1 SKIP_EMPTY_CATCH=1`（与本地语义不一致）
- CI 是 clean checkout，`git diff --cached` 为空 → **依赖暂存区的增量检查（组 1 as-any / 组 2 测试配对 / 组 4 接线 / 组 6 brief / 组 12 scope）全部空跑跳过**，只有全仓库扫描类检查（架构边界/文件驱动）真跑。

## 二、六大时间消耗点（无谓摩擦，数据支撑）

**A. 重复执行**：本地 pre-commit 13 组 + CI 重复跑同一脚本，且 CI 上增量检查空跑（语义漂移）。

**B. 证据链维护成本**：bypass.log 390 行里 139 行（35%）是 possible-bypass/BLOCKED/DEGRADED 噪音。每次 `--no-verify`、rebase 改 hash、合并引入提交都要手动补记（我这一轮补记了 5+ 次）。

**C. 绕过检测复杂度**：post-commit 三判 + 300s 新鲜度校验，是为了治 CT-29 并发/amend 误报，但复杂度本身成了维护负担和误报源。

**D. 两机对账式同步**：D334/D335/D331 三个对账机制，每次提交都要"保持行为一致"——这正是 codex 第 1 条说的"对账式地保持行为一致"的负担。

**E. task brief 格式负担**：6 字段 + `#CRITERIA` + Q2 纯路径列表。我这一轮提交被拦 5 次，全是格式/命名/引用问题，与代码正确性无关。

**F. 状态污染**：current-brief 残留（D328 拦截）、测试写 AGENT=test 到 bypass.log、tag-bypass-wiring.test.sh 4 项存量失败（断言过时 + 环境矛盾）。

## 三、优化方案（对照 codex 4 条建议，CTO 判断）

### 方案 1：权威门禁挪 CI（治 A/C/D）——方向对，需补 gap

CI 已是权威（9 job 覆盖 tsc/铁律/vitest/架构/golden）。本地 pre-commit 降级为"秒级快速反馈"，权威验证交给 CI。

**落地前提（gap 必须先补）**：CI 上 `pre-commit-check.sh` 空暂存导致增量检查空跑。需把增量检查的 diff 语义从 `git diff --cached` 改为 `git diff origin/main..HEAD`（或 CI 注入 base），让 CI 真能查"本次 PR 的变更"。

**动铁律**：铁律 34/35/38 的本地硬阻断位置 → 需创始人拍板。

### 方案 2：状态分两类（治 B/F）——强烈认同，bypass.log 单独拎

- 证据进 git：bypass.log（但改写入时机：测试/session 态不写）、docs、dev doc、审计报告、task-state 的 impl_done/audited 交付态。
- 会话态 gitignore + 机器本地：current-brief、session-registry（identity/pid/phase）、last-precommit-success、task-state 的 claimed 进行中态。

**动 D382 状态机**（task-state 是 K3 串联点）→ 需创始人拍板。

### 方案 3：同步降频（治 D）——方向认同，防覆盖硬保障保留

D334 的"push 前 fetch + 分叉阻断"是防双机互相覆盖的物理保障（历史：D334 前双机互覆盖 11 commit），必须保留。降的是"提交前必须跟得上"这个节奏——改为"任务边界拉平一次"。

**动铁律 0-3** 的多机 PR 节奏 → 需创始人拍板。

### 方案 4：分工按线（已是现状，保留，是方案 1 的前提）
