## D527：首诊旅程端到端（验证点 1-6 — 30 分钟内从安装到可诊断，零命令行）

**目标**：企业用户双击打开桌面端，**从安装到可发起诊断 ≤ 30 分钟（零命令行）**；端到端首诊（发起 → 六阶段 → 报告呈现）在 LLM 环境跑通。

**依赖**：切片 B（桌面端能开 + 服务自启）。LLM key 可用环境（consult 真实六阶段）。

**spec 必答题**：
1. **端到端实测**（GS-01 RED 2/3 补跑）：桌面端发起 `/diagnosis` → SSE 六阶段流（以 `electron-renderer/src/hooks/useStreaming.ts` 实际 case 为准：interim_finding → community_reports → entity_resolution → judgment_card → complete）→ 报告呈现——LLM key 可用环境跑真实全链路，evidence 落盘
2. **30 分钟目标**（对齐 desc「从安装到可诊断」）：从"双击安装"到"首诊页可发起诊断"的路径实测计时（安装→启动→服务自启→首诊页可达→/diagnosis 可提交）——定义可验证的计时方法（计时脚本/日志时间戳，非模糊声称）。六阶段诊断完成是端到端目标（与 30 分钟解耦——LLM 耗时不受控）
3. **桌面端 UI 盘点补强**：Composer /diagnosis 入口 + 六阶段进度展示 + 报告页——现有接线逐项盘点（哪些已有/哪些缺），缺口补强
4. **GS-01 升级**：契约断言从 3 条扩展——全链路可跑后，加真实 consult 断言（带 LLM 的六阶段完成）
5. **降级诚实**：LLM 不可用 / 后端未就绪时，桌面端显示 degraded 提示（不静默、不白屏，铁律 24/31）

**验收**：端到端实测 evidence（LLM 环境跑通日志/截图）；**从安装到可诊断的计时记录（物理时间戳，≤30 分钟目标）**；报告在桌面端可见；GS-01 扩展断言绿（LLM 环境可用时；无 key 则如实 RED，不伪造）

## D528：升级/重装不丢数据（验证点 1-7 — 企业数据安全底线）

**目标**：升级/重装桌面端，首诊数据（SQLite）完好——企业数据安全底线。

**依赖**：切片 A（安装包升级语义）。机制已设计（main.cjs:130 userData + SYNOVA_DB_PATH），本 D 是**验证 + 补强**，非从零实现。

**spec 必答题**：
1. **升级实测**：装 v1 → 产生数据（首诊/哨兵基线）→ 升级 v2（覆盖安装）→ 数据完好断言（SQLite 内容/表/md5 前后一致）——物理可复现脚本
2. **数据目录契约**：userData 目录定位（mac `~/Library/Application Support/` / win `%APPDATA%`）+ 与安装目录的隔离——为什么升级不清数据（目录物理隔离）
3. **安装包升级语义**：electron-builder NSIS/dmg 的升级路径（覆盖安装 vs 卸载重装）——哪些会清数据哪些不会，写清楚
4. **验证脚本**：`scripts/desktop/upgrade-data-verify.sh`（装两版 → 数据断言）——可执行、可复现、幂等
5. **边界与降级**：db 损坏处理（不静默，degraded 提示）+ 多实例写同一 db 的保护

**验收**：升级实测 evidence（升级前后数据断言一致）；数据目录隔离契约文档化；验证脚本可执行
