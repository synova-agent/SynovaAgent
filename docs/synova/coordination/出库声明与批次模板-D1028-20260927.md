### 1.2 为什么它**不是** `check-pr-budget.sh` 的硬条件（本卡裁定，brief §Q2.S4）

**裁定：无 `## 出库声明` 时，豁免仍生效**（成员A 的实现须打印 ⚠️ 提示，要求在 PR 描述补声明）。

理由（**实测**，不是推测）：

1. **门禁读不到 PR 正文。** `check-pr-budget.sh` 的唯一生产调用点是 pre-commit：

```text
# scripts/pre-commit-check.sh:1515-1516
1515:if [ -x "$ROOT/scripts/control-tower/check-pr-budget.sh" ] || [ -f "$ROOT/scripts/control-tower/check-pr-budget.sh" ]; then
1516:  PRB_OUT=$(bash "$ROOT/scripts/control-tower/check-pr-budget.sh" --quiet 2>&1)
```

   而 pre-commit 只收到 `--quiet`，**没有任何 PR 正文来源**：

```text
$ git grep -n -e "PR_BODY" -e "GITHUB_EVENT" -e "pull_request" -e "pr-body" -- scripts/control-tower/check-pr-budget.sh
exit=1
--- 处数 ---
0
```

   ⇒ 0 处。若把"有声明"设成它的硬条件：本地永远报红（读不到 → 恒不满足）或永远放行（写死跳过）——两者都是**假接线**，违 **铁律 0-2（接线验收）** 与 **M3（自验独立/不得假接线）**。

2. **能读到 PR 正文的地方在别处**（→ 不在本卡写集，见 §2.5）：

```text
$ git grep -n -e "pr-body" -e "pr_body" -- scripts/control-tower/merge_writeset_gate.py
scripts/control-tower/merge_writeset_gate.py:31:           --pr-body <file>（可选；用于读取 PR 正文里的 `## 写集豁免`）
scripts/control-tower/merge_writeset_gate.py:325:def resolve_pr_body_text(arg_path: str) -> str:
scripts/control-tower/merge_writeset_gate.py:326:    """PR 正文来源: ① 显式 --pr-body <file> ② CI 的 GITHUB_EVENT_PATH（pull_request 事件体）。
scripts/control-tower/merge_writeset_gate.py:365:    ap.add_argument("--pr-body", default="")
scripts/control-tower/merge_writeset_gate.py:428:    pr_text = resolve_pr_body_text(args.pr_body)
scripts/control-tower/merge_writeset_gate.py:430:        explicit.extend(scan_exempt_section(pr_text, "pr-body"))
scripts/control-tower/merge_writeset_gate.py:432:        result["warns"].append("PR 正文不可用（--pr-body 未给且无 GITHUB_EVENT_PATH）—— 仅文件声明源生效")
```

   该 gate 在 **CI 的 PR job** 里跑（`.github/workflows/ci.yml:116-120`），**读得到** PR 正文——但它今天**只解析 `## 写集豁免`**（`:291`），且 `ci.yml:119-120` 只传了 `--base/--head/--branch`、**没传 `--pr-body`**：

```text
116:      - name: Merge write-set reconciliation (D708)
117:        if: steps.docsonly.outputs.docs_only != 'true'
118:        run: |
119:          python3 scripts/control-tower/merge_writeset_gate.py \
120:            --base origin/main --head HEAD --branch "${GITHUB_HEAD_REF:-$GITHUB_REF_NAME}"
```

   ⇒ 现状下 `:432` 会落一条 warn（"仅文件声明源生效"）。

3. **结论（冻结口径）**：`## 出库声明` 的定位是
   - **批次流程强制项**（队长在本文件的 §三 模板里逐批填写，人读 + 批次台账锚）；
   - **D708 合并级对账的承接位**：机器可读的承接**不是**新标题，而是**把同一批路径同时列进 PR 正文的 `## 写集豁免` 段**（唯一被解析的声明源，理由必填）；
   - 若要新增 `出库声明` 作为**第三个**被解析的标题（与 `写集豁免`/`引用豁免` 并列）→ 属 `merge_writeset_gate.py` 变更，**不在本卡写集**，须另立卡 + K3 复审。

### 2.7 顺带实测到的第二条缺陷：D2 门禁对**非 ASCII 新文档 fail-open**（只登记，不改）

"docs/synova/coordination/\346\226\260\346\226\207\346\241\243\344\270\255\346\226\207\345\220\215.md"

  ✅ 登记门禁通过          ← exit 0：**静默放过，无 ⚠️ 无 degraded**

**根因**：`core.quotepath=true`（git 默认）时 `git ls-files` 把非 ASCII 路径输出为 `"…\346…md"`（带八进制转义 + 尾部双引号），而 `doc-registry-gate.sh:43` 的过滤是**行尾锚定** `grep -E '\.(md|yaml)$'` ⇒ 锚点不匹配 ⇒ 该类文件**从不进入检查集**。

```text

$ git config --show-origin --get core.quotepath
file:/Users/wane/SynovaAgent/.git/config	false
```

⇒ 本仓 `.git/config`（**未被 git 追踪**）恰好置了 `false`，故本仓内逃逸不发生；但 `.git/config` **不随 clone 传播**，默认配置下（未设该键）上述 fail-open 成立。

**旁证（本地软提示是瞬时的）**：在**本工作树**跑门禁，新文档被点名（`❌ 未登记: docs/synova/coordination/出库声明与批次模板-D1028-20260927.md`，exit 1），但门禁只查 `untracked + staged-新增`（`:43`）——**文件 commit 后二者皆空 → 复跑 0 个文档 → exit 0**（探针实测：`── 汇总: 检查 0 个文档，0 个未登记 ──  ✅ 登记门禁通过`）。故它**不阻断本卡**（本地软提示；CI 无 tracked-new 输入）。

**精确定位（避免误读为"门禁没用"）**：它的**设计工作点** = 本地 `pre-commit` 那一刻，文件正处于 **staged-新增** ⇒ 会拦（`docs/authority/GOVERNANCE.md:12` 记载 2026-08-20「已接线 pre-commit …测试 8/8」）。失效的是**二段复核**：
- CI 复跑时新文件已是 **tracked** ⇒ `ls-files --others` 与 `--diff-filter=A` 皆空 ⇒ D2 在 `SYNO_CI=1` 下**无输入可判** ⇒ 本地软提示的"CI 转硬"承诺**实际落空**；
- 且默认 `core.quotepath=true` 时非 ASCII 名在**本地工作点也逃逸**（探针 B）。

⇒ 一句话：**D2 只对「ASCII 名 + 本地 staged」这一种状态有效**。

**处置**：只登记，不改（`scripts/**` 不在本卡写集）。与 brief 提到的 **CT-69**（`--files` 注入模式对非 ASCII 路径误判跨域，`docs/synova/coordination/AUDIT-FINDINGS-LEDGER.md:107`）**同源**——都是「非 ASCII 路径 + 行/字段边界解析」的 fail-open。→ 遗留清单第 ⑥ 项。
