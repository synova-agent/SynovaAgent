## §3 要做什么（四步）

### 步 1｜把 392 条按渲染面归类
每条债的键是 `(path, rule, normalizeText(text))`。对每条判定它属于哪一类：

| 类别 | 含义 |
|---|---|
| **真·客户面** | 值会直接渲染给客户看到的文本（含 `{…}` 插值的最终值） |
| **值域/类型声明** | 字符串是类型联合、常量表、枚举定义，本身不上屏 |
| **逻辑比较** | 用于 `===` / `switch` / 数组查找等，不上屏 |
| **测试夹具/注释** | 非产品面 |
| **数据驱动** | 值是运行时数据（如服务端返回），静态无法判定 |

**判定必须有据**：给出该 `path:line` 的**父级 JSX 位置**（是否在 JSX 文本节点 / 属性值 / 普通表达式里）。

### 步 2｜对"真·客户面"逐条给整改建议
按《词典》§2 映射表给出**客户说法**：
- 映射表有的 ⇒ 直接给替换词
- 映射表**没有的** ⇒ 写「需 CTO 定」，**不许自己编**
- 涉及 ID（`node-*`/`run_*`/UUID）⇒ 按《词典》§3 规则给"隐藏 或 进技术详情"
- 涉及 JSON 原文 ⇒ 给"人话化 + 技术详情折叠"

### 步 3｜与 DEV DOC §2.1 的现状审计对账
DEV DOC §2.1 的 C1–C8 已列了一批已知泄漏点（带 `path:line`）。核：
- C1–C8 里列的点，是否**都在**债单里？不在的说明什么（被规则漏了？还是当时判断有误？）
- 债单里有、但 C1–C8 没列的**客户面**条目，单独列出（这是 §2.1 的漏项）

### 步 4｜给出 T4 的执行清单
按「同一渲染位置可一次改完」聚合，输出**可派单的 checklist**：
- 每条：`path:line` ｜ 当前渲染值 ｜ 客户应看到 ｜ 对应债条目键 ｜ 是否需"技术详情"
- 按"一屏一处"排序（同一组件的条目相邻）
