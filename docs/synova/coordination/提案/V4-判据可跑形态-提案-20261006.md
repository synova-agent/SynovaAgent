## 一、现行判据（**不合格**，要换掉的那条）

计划 v2 的 V4 行「验收判据」列逐字写：

```
git cat-file -e origin/main:<判据件>   ⇒   46/46
```

**实测：7/46。**（`registry-owner` 在 task-1 实测 7/46；本件 §三 给出逐项复跑命令。）

**为什么不合格（判例 P-03 断言不变性：先问"这条断言会在什么情况下必然失败"）**：

该判据要求"每项的判据件都在 main 上存在"。但 46 项里有 **7 项**的 acceptance **直接读
gitignored 的运行时库** `data/synova.db`：

```
$ git check-ignore -v data/synova.db
.gitignore:3:data/	data/synova.db
$ sqlite3 data/synova.db "SELECT COUNT(*) FROM loop_runs WHERE created_at > datetime('now','-1 hour')"
Error: in prepare, no such table: loop_runs
```

⇒ `data/` 在 `.gitignore:3` 被忽略 ⇒ **干净检出 / CI 姿态下该路径结构性不存在**
⇒ 那 7 项**无论谁做多久、做得多好都不可能满足**。这不是执行方的过失，是**判据本身的缺陷**。

## 二、提案判据（**待裁**）

### 2.1 新判据形态：三条机器可判（缺一即不合格）

每条 `acceptance` 必须同时满足：

| # | 形态要求 | 机器判据（可复跑） |
|---|---|---|
| ① | **判据件在真相源** | `git cat-file -e origin/main:<判据件>` ⇒ exit 0（**保留现行口径，不放松**）|
| ② | **不依赖 gitignored 运行时状态** | 该 `run` 命令里出现的每个路径 `p`，`git check-ignore -q "$p"` ⇒ exit 1（即**未被忽略**）|
| ③ | **有区分力**（修复前必红） | 提供两段原始输出：修复前 `exit≠0`（**断言失败**，非"文件不存在"的平凡红）+ 修复后 `exit=0` |

> ② 是本提案的**新增量**：它是把"7 项不可达"从**事故**变成**门禁能报的具名违规**。
> 建议由执法体 INV-3 承载（`docs/synova/coordination/tools/check-construction-registry.ts`，
> 已在 main 的 CI 上运行）。**本件不预实现** —— 它是判据变更，须先裁。

### 2.2 那 7 项怎么改：**fixture 化**（CTO 已准方向）

判据改为**穿生产入口 + 自建临时库**，形态：

```
判据件 = 该卡自产的测试文件（fixture 形态）
  · 建临时库（mktemp）→ 建表 → 走**生产写入路径**喂入
  · 断言读计数（expectRowsGt / expectRowsEq）
  · 结束即删临时库；**全程不碰 data/synova.db**
```

**可行性已实测**（本件落 main 前先跑通，命令见 §三.3）：
- 现行形态：`sqlite3 data/synova.db …` ⇒ `Error: … no such table: loop_runs`（**结构性不可跑**）
- 提案形态：自建临时库 ⇒ `1`，`exit=0`
- **负对照**（没有修复的空库）⇒ 同一断言得 `0` ⇒ **有区分力**（不是"存在即可"的永远真断言）

### 2.3 落点与写集（避免又一次越槽界）

判据件落点 = **该卡自己的写集内**（例：`tests/<域>/<item>-fixture.test.ts`）。
依据：执法体 INV-3③ 的既有语义就是"**引用的文件须在 main 存在，或在自身写集内**"——
把这 7 项的判据改成"引用本卡将要产出的 fixture 测试"，**既满足 INV-3③，又不越槽界**。

⚠️ 已知边界：`tests/**` 不在产品线（B 槽）写集 ⇒ 这些 fixture 的**落地**需 A 槽或另开卡
（与 CTO 裁 2「接线归 A 槽」同因：路径所有权）。

### 2.4 其余 39 项

继续补判据件到 main（当前 7/46 ⇒ 目标逐项推进）。
**不建议**为凑 46/46 而把判据降级成"存在即可"（判例 P-03 / V-02）。
