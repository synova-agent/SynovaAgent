## 一、现行判据（**不合格**，要换掉的那条）

计划 v2 的 V4 行「验收判据」列逐字写：

```
git cat-file -e origin/main:<判据件>   ⇒   46/46
```

**实测：7/46**（`registry-owner` 实测，K3 复现一致）。

该判据要求"每项的判据件都在 main 上存在"。而 46 项里有 **7 项**的 acceptance 读**运行时数据库**，
那 7 项**结构性不可达**。但——**真因不是 v1 说的 gitignore**：

### 1.1 被点名的 7 项（自证）

```
$ node --experimental-strip-types --input-type=module -e "…扫 acceptance 含 data/synova.db 的 todo 项…"
命中项数 = 7  ⇒  0-1 0-2 0-9bis 1-4 2-1b 2-3 3-5
```

| 项 | 标题（截断） | 分量 | 断言的表 |
|---|---|---|---|
| **0-1** | 六个业务循环的 cron 是死路 | **总闸** | `loop_runs` |
| **0-2** | 进化回写 applied 恒 0 | **总闸** | `agent_memory` |
| **2-1b** | 测量值时序 · 写入侧 | **承重件 W1** | `metric_readings` |
| 0-9bis | 知识审计不可归属 | — | `knowledge_audit` |
| 1-4 | 目标"传导到每个人" | — | `graph_nodes` |
| 2-3 | 反馈两通道分裂 | — | `feedback_log` |
| 3-5 | 作业单元缺两件 | — | `graph_nodes` |

🔴 **2 项总闸 + 1 项承重件 W1** ⇒ 全系统最关键的"完成标准"**恰好都落在这 7 项里**。
⇒ 我据此推**「总闸的 Done 判据从来没真正成立过」**。K3 判：该推论**成立**。

### 1.2 🔴 真因（v2 更正）：**不是 gitignore，是表没有生产者**

```
$ git grep -cE "CREATE TABLE[^;]*\b<T>\b" origin/main              # 全仓
loop_runs        : 0        metric_readings : 0        knowledge_audit : 0
feedback_log     : 0        agent_memory    : 0        graph_nodes     : 0
$ git grep -c "loop_runs" origin/main
（零命中 —— 这个字符串在 main 上**任何地方都不存在**）
$ git grep -c "metric_readings" origin/main
只在 3 份文档里出现（evidence/*.md），**代码里零定义**
```

⇒ **`loop_runs` / `metric_readings` 等表在 main 上没有任何代码会创建它**。
这两个判据断言的**不是"某个已存在的表里的数据不对"，而是"一个还不存在的表"**。

所以 7 项应**按有无生产者分两类**，两类处置不同：

| 类 | 判 | 例 | 处置 |
|---|---|---|---|
| **A · 表无生产者**（`CREATE TABLE` 全仓 0） | 判据是**前瞻性验收**——它断言的表正是**该卡自己的交付物** | 0-1 / 2-1b / 0-9bis / 1-4 / 2-3 / 3-5 | 判据**必须锚到"生产写入模块"**，否则 fixture 自造数据 = 恒绿（见 §2.1 ④）。表建成后判据才可能成立 ⇒ **不得**记为"未完成"以外的状态 |
| **B · 本机有、CI 无**（库被 gitignore 但表有生产者） | 判据在**本机可跑**，仅在**出货姿态**不可达 | **0-2**（K3 实测：本机可跑，CI 姿态不可达） | 用**CI 姿态可复现的最小库**（fixture 建库 → 走生产写入 → 断言）|

**A 类的意义（比"不可达"更重）**：这 6 项的判据**今天无论谁做、做多久都不成立**，
且不是环境问题 —— 是**判据断言的客体尚不存在**。⇒ 它们只能在"该卡交付完成"的那一刻才可判。
**V4 的 46/46 在 A 类项上不是"难"，是"顺序上还不到"。**

## 二、提案判据（**待裁**）

### 2.1 新判据形态：**四条**机器可判（缺一即不合格）

| # | 形态要求 | 机器判据（可复跑） |
|---|---|---|
| ① | **判据件在真相源** | `git cat-file -e origin/main:<判据件>` ⇒ exit 0（**保留现行口径，不放松**）|
| ② | **不依赖 gitignored 运行时状态** | 该 `run` 里出现的每个**仓内相对路径** `p`：`git check-ignore -q "$p"` ⇒ exit 1（未被忽略）。<br>🔴 **仓外路径（例 `$(mktemp)` 出来的绝对路径）⇒ 本条件「不适用」**：实测 `git check-ignore` 对仓外路径返回 **exit 128**（fatal: outside repository）**而非 1**。<br>⇒ 判据器必须把 `128` 当**"不适用"**处理，**不得当违规、也不得当合规**。（v1 缺这条 ⇒ 提案自己的 fixture 形态会踩中自己的规则。）|
| ③ | **有区分力**（修复前必红） | 两段原始输出：修复前 `exit≠0`（**断言失败**，非"文件不存在/表不存在"的平凡红）+ 修复后 `exit=0` |
| **④** | 🔴 **v2 新增 · 数据来源必须锚到生产写入路径** | 两条同时满足：<br>(a) **负对照必备** —— 在"**未走生产写入路径**"的同一 fixture 上跑**同一断言**，必须得到**失败值**（例 `count>0` 得 `0`）；<br>(b) fixture **不得对被告表裸 `INSERT`**（可扫：fixture 内该表名不得出现在 `INSERT INTO` 后）。<br>**理由**：K3 构造的反例——fixture 自己 `INSERT` 再断言 `count>0` ⇒ **恒绿**，而 ①②③ 全过。**(a) 是硬要求，(b) 是可扫的辅助锚**（能挡常见绕过，不是证明）。|

> ② 与 ④ 是本提案的**新增量**。
> ② 建议由执法体 INV-3 扩展承载（`docs/synova/coordination/tools/check-construction-registry.ts`，已在 CI 上跑）。
> ④ 因其含"负对照"这种**成对证据**，宜由**卡自己的验收件**承载 + 执法体只扫 (b)。
> **本件不预实现** —— 判据变更，须先裁。

### 2.2 那 7 项怎么改：**fixture 化**（CTO 已准方向）+ ④ 兜底

```
判据件 = 该卡自产的测试文件（fixture 形态）
  · 建临时库（mktemp）→ **走生产写入路径**把数据写进去（不是裸 INSERT）
  · 断言读计数（expectRowsGt / expectRowsEq）
  · **负对照**：不走生产写入 ⇒ 同一断言必须给出失败值
  · 结束即删临时库；全程不碰 data/synova.db
```

**可行性已实测**（基线上先跑通，命令见 §三.3）：
- 现行形态：`sqlite3 data/synova.db …` ⇒ 表不存在（**不可跑**）
- 提案形态：自建库 ⇒ `1` / `exit=0`
- **负对照**（没走写入路径）⇒ 同一断言得 `0` ⇒ **有区分力**

### 2.3 落点与写集（v2 按实装收紧表述）

判据件落点 = **该卡自己的写集内**（例 `tests/<域>/<item>-fixture.test.ts`）。

⚠️ v1 在这里说得太满。**按实装逐字**：执法体 INV-3③ 的判据是
「`fileRefs(a.run)` 里的每个文件 `f`，要么 `existsInMain(f)`，要么 `inOwnWriteSet(f, it.paths)`」——
即「**引用的文件须在 origin/main 存在，或落在本项 `paths` 内**」。
把判据改成引用"本卡将要产出的 fixture 测试"**能过 INV-3③**，但**这不等于它已可跑** ——
`paths` 内的文件**在卡片交付前并不存在**。⇒ 这是"**顺序**"而非"**合规**"问题，
**不能拿 INV-3③ 当作"越槽界已解决"的挡箭牌**（K3 对 §2.3 的质疑成立，此处更正）。

已知边界（不变）：`tests/**` 不在产品线写集 ⇒ 这些 fixture 的**落地**需 A 槽或另开卡。

### 2.4 其余 39 项

继续补判据件到 main（当前 7/46）。**不建议**为凑 46/46 把判据降级成"存在即可"（判例 P-03 / V-02）。

### 3.3 fixture 形态可行、且**有区分力**（v2 加了生产者维度）

```
$ git check-ignore -v data/synova.db
.gitignore:3:data/	data/synova.db                         ← 现行判据的客体：CI 下不存在

$ sqlite3 data/synova.db "SELECT COUNT(*) FROM loop_runs WHERE created_at > datetime('now','-1 hour')"
Error: in prepare, no such table: loop_runs         ← 现行判据：平凡红（连断言都没到）

$ TMPDB=$(mktemp -t synova-fixture-XXXXXX.db); rm -f "$TMPDB"
$ sqlite3 "$TMPDB" "CREATE TABLE loop_runs(id INTEGER, created_at TEXT);
                    INSERT INTO loop_runs VALUES (1, datetime('now','-10 minutes'));
                    SELECT COUNT(*) FROM loop_runs WHERE created_at > datetime('now','-1 hour');"
1                                                   ← 提案形态：可跑

$ TMPDB2=$(mktemp); rm -f "$TMPDB2"
$ sqlite3 "$TMPDB2" "CREATE TABLE loop_runs(id INTEGER, created_at TEXT);
                     SELECT COUNT(*) FROM loop_runs WHERE created_at > datetime('now','-1 hour');"
0                                                   ← 负对照：没写入 ⇒ 0 ⇒ 断言 `>0` 会红
```
⚠️ **上面这段本身只是"形态示意"，不是合格判据** —— 它的第 2 段是**裸 INSERT**，
正是 K3 反例指出的恒绿路径。合规范例须把第 2 段换成**调用生产写入模块**，
并保留第 3 段作负对照。（见 §2.1 ④）

### 3.4 ② 的仓外路径语义（v2 新增，实测）

```
$ T=$(mktemp -t outside-XXXXXX.db); rm -f "$T"
$ git check-ignore -q "$T"; echo $?
128          ← fatal: outside repository。**不是 1**
$ git check-ignore -q src/…;  echo $?   ⇒ 1   （仓内未忽略）
$ git check-ignore -q data/synova.db; echo $?   ⇒ 0   （仓内已忽略）
```
⇒ 判据器**必须**显式处理 128（不适用），否则提案推荐的 fixture 形态会被自己的规则误杀。
