## 3 · 目标行为

### 3.1 正常 PR

```text
研发开 PR 到 main
→ Gitea 以已证实可信的 base 工作流触发 core-gates / core
→ 在独立工作区检出实际 github.sha，并核对 HEAD
→ 检查核心工作流／命令／配置／基础测试是否被 PR 改写
→ npm ci → 安装后工具预检 → 类型 → 构建 → Secrets
→ workflow 配对反例 → 基础契约测试＋受影响测试
→ 全部满足后核心结果为绿，G2 后只凭该必需 context 允许合并
```

### 3.2 失败与人工接管

| 情况 | 用户必须看到的结果 |
|---|---|
| 类型、构建、测试或 Secrets 业务失败 | 核心门红；原始文件、错误／断言和退出码可见，不得只剩 `exit status 1`。 |
| 工具、git、HEAD、base、runner 或结果解析故障 | 红并标为 `cannot judge / exit 2`，写一行降级 JSON，不得当业务失败或通过。 |
| PR 改写受信核心输入 | 红并标为 `CORE-TRUSTED-INPUT-CHANGED / exit 2`，不得产生可用于合并的通过 context；进入 §5.3 核心变更停点。 |
| 基础契约测试无对象、全 skipped、零 passed 或 JSON 不可判 | `exit 2`，不是通过。 |
| 有相关代码变化但受影响测试零 passed、全 skipped或空壳 | `exit 1`，不是合法跳过。 |
| 仅 CI-excluded／E2E 测试变化 | 基础契约测试仍执行；受影响测试输出 `SKIP reason=ci-excluded-only`，由 GitHub／发版执行该面。 |
| 无相关代码变化 | 基础契约测试仍执行；受影响测试输出 `SKIP reason=no-relevant-change`。 |
| 分支保护权限不足或平台工作流来源不可信 | 停在当前阶段，旧阻断保持，不猜、不绕权限。 |

### 3.3 旧门与 GitHub

- G2 严格“加新 → 用新开放 PR 隔离验证 → 移旧”；验证失败先移除刚加的新 context、恢复旧清单，再修新门。

### 5.1 工作流与 context

- `name: core-gates`；job id `core`；`runs-on: win-ci`；`timeout-minutes: 15`；显式 `permissions: contents: read`。
- 触发：`pull_request` 到 `main`、`push` 到 `main`、`workflow_dispatch`。
- 禁止 `continue-on-error`、核心失败的 `|| true`、旧报告覆盖核心结果。
- context 以真实 Gitea 设置为准；预期形如 `core-gates / core (pull_request)`，不得猜写。

### 5.2 平台可信来源预证（G2 前置）

T1 不得以“新 workflow 在自己的 PR 上运行”冒充可信验收。必须按实际运行区分：

1. T1 使用草案 PR 和无害标记观察新 workflow 是否执行、定义来自 PR head 还是 base；记录 workflow 内容标记、run URL、head/base SHA。
2. T1 合并后，再用一个后续 PR 修改 head 中 workflow 标记：若运行内容跟随 head，或同名通过 context 可由 head 自定义，则平台模式不满足本方案，**立即停止，不得 G2**。
3. 只有实证 `pull_request` 使用 base／其他受信 ref 的工作流，且 head 无法自定义同名通过 context，才能继续影子验收。
4. 若平台需要 `pull_request_target` 或其他受信事件才能达到该语义，CLI 不得自行更换事件或扩大 token 权限；退回 CTO 修订并直接定夺，不自动追加复审。

### 5.3 受信核心输入

runner 必须在 `npm ci` 和任何核心命令之前比较 `base...HEAD` 的下列输入；有变化即 `exit 2`，不得执行“按 PR 改后定义／工具判自己”的通过：

- `.gitea/workflows/core-gates.yml`
- `scripts/ci/core-tests.sh`
- `tests/control-tower/core-tests.test.sh`
- `tests/control-tower/core-gates-workflow.test.sh`
- `scripts/check-secrets.sh`
- `scripts/desktop/build-backend.sh`
- `tsconfig.json`、`tsconfig.*.json`
- `vitest.config.ts`
- `tests/contract/**`
- `package.json` 全文件（scripts、dependencies、devDependencies、postinstall 等）
- `package-lock.json`
- `patches/**`
- `.npmrc` 及其他会改变 npm 安装源、脚本或依赖解析的仓库内 npm 配置

**核心定义／依赖变更流程**：此类 PR 不得夹带产品行为变化，也不得作为正常 PR 验收证据；包括新增或修改 contract 测试、依赖、lock、patch、npm 配置。G2 前走旧门＋本件过渡审批；G2 后须由 CTO／管理员走专门的核心变更 PR、独立代码审查和受控合并，合并后以 main 的受信工作流复验，红则立即 revert。普通 coding 无权自行选择该路径。T1 harness 必须证明 patched Vitest、假 tsc／esbuild 或依赖篡改会在安装前以 `2` 红，不能产生通过 context。

### 5.4 取树、凭据、依赖与环境映射

1. 每次运行使用 `$RUNNER_TEMP` 下独立工作区；`always()` 清理临时凭据和工作区。
2. remote 使用无凭据标准 URL。用权限为 `700` 的临时 `GIT_ASKPASS` helper 从工作流令牌环境变量取密码；脚本本身不含 token，`set +x`。不得把 token 写入 remote、`.git/config` 或命令行。
3. `GIT_TERMINAL_PROMPT=0`，显式 refspec；缺 `${{ github.sha }}`、checkout 失败、HEAD 不一致均 `exit 2`，禁止回退 `FETCH_HEAD`／main。
4. 克隆失败和正常日志均不得泄露令牌；配对测试检查 `.git/config` 无 token、失败日志脱敏、收尾无 helper 残留。
5. **安装前**先完成 §5.3 受信输入检查，再预检 Node／npm／git／bash、HEAD、测试源对象并打印版本；通过后才执行 `npm ci`。
6. **安装后**直接检查 `node_modules/.bin/vitest`、`tsc`、`esbuild`，禁止 npx 自动下载。用 `npm ls vitest typescript esbuild patch-package --json` 和直接二进制版本输出，对照受信 base 的 `package-lock.json` 验证精确版本／依赖完整性；缺失、版本不符、invalid／extraneous 均 `exit 2`。可沿用 `ELECTRON_MIRROR`，不得改版本或 lock 完整性校验。
7. job 级显式设置 `CI=1`、`SYNO_CI=1`；每个调用检查入口的 shell 步骤先执行 `export SYNO_GATE_DEGRADED_LOG="${RUNNER_TEMP:?}/core-gates-degraded.jsonl"` 并创建父目录，不依赖未核实的表达式展开。本地 harness 各自设置 `$TMP` 内独立日志并隔离外层值。变量缺失时 stderr 报 `cannot judge: SYNO_GATE_DEGRADED_LOG missing` 并 `exit 2`，不得假写日志或转 0。
8. 事件只按以下映射，空值、未知值或缺必需 env 均 `exit 2`，不得猜测或回退 manual：

| 真实 Gitea 输入 | runner 输入 | base 规则 |
|---|---|---|
| `GITHUB_EVENT_NAME=pull_request` | `--event pull-request` | `GITHUB_BASE_REF` 必填；base=`merge-base(origin/$GITHUB_BASE_REF,HEAD)` |
| `GITHUB_EVENT_NAME=push` | `--event push` | 将 `${{ github.event.before }}` 显式注入 `CORE_EVENT_BEFORE`；必须有效且非全零 |
| `GITHUB_EVENT_NAME=workflow_dispatch` | `--event manual` | 无 base，允许显式 `SKIP reason=manual-no-base` |

不得假定存在默认 `GITHUB_EVENT_BEFORE`，也不得依赖旧门已证明不可靠的表达式回退。T1 必须在真实 run 核对上述 env 与 payload；不一致即停。harness 覆盖未知 event、缺 `GITHUB_BASE_REF`、缺／坏 `CORE_EVENT_BEFORE`、缺 `CI`、缺日志变量和 E2E-only 在 `CI=1` 下的实际排除。

### 5.5 核心命令与三态

| 顺序 | 真实入口 | 通过判据 | 失败 |
|---|---|---|---|
| 类型 | 受信 `package.json` 对应的 `npm run lint` | `tsc --noEmit` 返回 0 | 类型错误 `1`；工具故障 `2` |
| 构建 | 受信入口 `npm run build` | 返回 0 且 `dist/backend.mjs` 存在 | 构建／产物失败 `1`；工具故障 `2` |
| Secrets | 受信 `scripts/check-secrets.sh`，经 `npm run check:secrets` | 原样返回 0 | 违规 `1`；判不了 `2` |
| workflow 复现 | `CI=1 SYNO_CI=1 SYNO_GATE_DEGRADED_LOG="${RUNNER_TEMP:?}/core-gates-degraded.jsonl" bash tests/control-tower/core-gates-workflow.test.sh` | 正常与变异场景全过 | 业务反例失败 `1`；harness 故障 `2` |
| runner 配对 | `CI=1 SYNO_GATE_DEGRADED_LOG="${RUNNER_TEMP:?}/core-gates-degraded.jsonl" bash tests/control-tower/core-tests.test.sh` | 配对场景全过 | 失败 `1`；harness 故障 `2` |
| 实际测试 | `CI=1 bash scripts/ci/core-tests.sh --event <...> --base <...>` | 满足 §5.6 | 业务失败 `1`；判不了 `2` |

每步显式保存并返回 rc，不依赖 runner 的 `set -e`。捕获输出用 `set +e`／恢复 `set -e` 或等价写法，先打印原始输出再判定；workflow 复现必须在 `bash -e`／runner 等价环境验证 #338 日志行为。

除日志变量本身缺失外，所有新 shell 检查入口在 `exit 2` 时，stderr 给出具体原因，并向 `$SYNO_GATE_DEGRADED_LOG` 追加**恰好一行** JSON：`time/component/code/phase/retryable`。成功和业务失败 `1` 不写 degraded；配对测试验证 JSON 可解析、字段齐全和行数。

### 5.6 `core-tests.sh` 契约

**显式输入**：`--event pull-request|push|manual` 必填，映射见 §5.4。PR／push 缺 base、坏 base、diff 失败均 `exit 2`；只有 `manual` 可省略 base。HEAD 不符合事件 payload 或真实 env 缺失均 `exit 2`，不得把故障伪装成 manual。

**基础契约测试**：使用默认人读 reporter＋JSON reporter，执行 `node_modules/.bin/vitest run tests/contract/`。JSON 来自当次运行，必须可解析且 `numPassedTests > 0`；总数、passed、skipped 均打印。无文件、全 skipped、零 passed、JSON 缺失／矛盾均 `exit 2`。

**运行时零断言判据**：runner 在 `$RUNNER_TEMP` 生成一个合并受信 Vitest 配置的临时 config 和 setup 文件，保持原 include／exclude／alias，并在每个执行测试的 `beforeEach`／`afterEach` 比较 `expect.getState().assertionCalls`。该字段在当前锁版 `@vitest/expect/dist/index.d.ts` 已核实存在。任一已执行测试的断言计数未增加，返回 `1` 并输出 `CORE_ZERO_ASSERTIONS` 与测试名；计数 API 缺失或不可读返回 `2`。禁止用文本搜索 `expect` 代替运行时判据，注释、字符串、`if (false)`、未调用 helper 中的 expect 均不算断言。此规则同时作用于 contract 和 source 变更带入的既有 affected 测试。

**受影响测试**：

- 用同一受信 Vitest 配置的实际 collection／list 结果派生可收集面与 CI 排除面，不手抄 exclude 列表；collection 功能不可用或输出不可解析 `exit 2`。
- 有真实相关变化时执行 `node_modules/.bin/vitest run --changed "$BASE"`，同样要求 JSON `numPassedTests > 0` 和上述运行时断言计数；失败、全 skipped、零 passed、零断言均 `exit 1`。
- 仅 CI-excluded／E2E 变化：`SKIP reason=ci-excluded-only`，不误红、不称 affected 通过；生产代码变化＋只有 excluded 测试仍属零有效回归，`exit 1`。
- 无相关变化：`SKIP reason=no-relevant-change`；manual 无 base：`SKIP reason=manual-no-base`。

日志末尾输出 `CORE-TESTS RESULT rc=<0|1|2> contract_passed=<N> affected=<ran|skipped> affected_passed=<N|0> reason=<...>`，数值从 JSON reporter 得出，不写死。

### 5.7 用户可见行为 A／B 回归

- 每个研发任务卡写 B、A、真实入口、期望来源和完成证据；内部函数测试、CI 字符串、fixture 自推导或“文件存在”不算完成。
- 本批 B＝新核心门统一执行真实命令；A＝#338 所保护的行为不退化：Vitest 失败时 Gitea 原始日志仍含具体失败文件／断言，不被 `set -e` 吞掉。
- 后续产品任务的快速关键回归由受影响测试接入；完整 API／UI／E2E 由 GitHub／发版执行，不塞进 15 分钟核心 job，也不得删除或空跑。

### 5.8 G2 切换与回退

1. 有权限者保存变更前必需 context、分支保护和原生 protected-file 设置（脱敏）。
2. 确认实际新 context；先新增新必需 context，旧 context 全部保留。
3. **新开的正常 PR**同时显示旧、新 context 均绿且 mergeable；T1 已合并，不得拿 T1 冒充本步开放 PR。
4. **构建入口专用红 PR**必须显示旧 contexts 全绿、新门在受信输入检查以 `2` 红且不可合并，才能证明阻断来自新门。实际构建失败与产物缺失另由 T1 harness 验证，二者不得互相冒充。若旧门也红，本步不算，返回 CTO 选择其他不触旧门的探针。
5. 核心入口恒绿反例不得产生通过 context；保存 base／head 和实际 workflow 证据。
6. 任一步失败：先移除刚加的新 context、恢复变更前旧清单，确认正常 PR 恢复可合并，再修新门。
7. 全部通过后移除旧必需 context，再次读取设置并证明新在、旧不在。之后缺陷回退到已验证的新核心门版本，不默认恢复整套旧治理。
