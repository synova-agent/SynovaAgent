## §3 五件必做

### ① 扫描根扩展
- 从 `electron-renderer/src` 扩到 **`electron-renderer/src` ＋ `electron/**` ＋ `app/**`**（`app/**` 含 `app/login.html`、`app/js/*.js`）。
- 保留 `UI_REDO_SCAN_ROOT` 覆盖点（T1-D 靠它做"看不见当红"）。

### ② R2-18 大小写不敏感
- 现判据是 `normalizeText` 后**全等**；改为**大小写折叠后全等**（`Admin`/`LIAISON`/`Ga` 都要命中）。
- ⚠️ **不要**改成包含匹配（会误伤 `administrator` 这类词）。

### ③ R2-07 大小写不敏感
- `HTTP 500`/`http 500` 都要命中。

### ④ R2-05 收字段名
- 追加 `email`、`phone`、`wechatId`（客户面出现字段名即泄漏）。

### ⑤ `P0` 单列规则（新 R2-20）
- 判据：客户可见字符串中出现独立 `P0`（词边界）。
- 理由：`P0` 是内部严重度代号，客户看到的是"紧急"。审计 A 在 `Synova P0 Alert` 命中。

### ⑥ 按审计 B 的 179 条重分 `why`，并重冻结基线
- 依据：审计 B §3 全表（179 条客户面）＋§2 五类分档。
- `why` 前缀保持三档：`【客户面】`／`【非客户面】`／`【复核】`；分档依据写在 `why` 文本里（一句话，可追溯）。
- **重冻结基线**：文件数、候选总数、allowlist 条目数、按规则分布，**全部自测并写死**，命令＋原始输出进回执。
- **不得**沿用 43/1743 作为新基线（它们必然变）。

## §4 关键契约

1. **判据语义只加不减**：规则可以加严；**不得**为了降噪而放宽（如把 R2-16 的 `critical` 移出）。
2. **`normalizeText` 本体不改**（键的语义不能变）；大小写折叠只发生在**比对时**。
3. **allowlist 键仍是 `(path, rule, normalizeText(text))`**；`lineHint` 仍只作展示。
4. **四条硬断言全部保留**，另加第 ⑤ 条：**扫描根必须真的覆盖到 `electron/` 与 `app/`**（用两个已知点自检：`app/login.html` 的 `GA`、`electron/main.cjs` 的 `critical` 必须出现在债单里；把它们删掉必须红）。

## §5 验收（九项之⑤）

### 期望值来源（独立于被测对象）
- 新增命中点的期望来自**审计 A/B 的实测落位**（`app/login.html:34`、`electron/main.cjs:305` 等），不是"跑一遍看输出"。
- 大小写的期望来自《词典》§1.2 的规则文字（`Admin` 与 `admin` 是同一个客户面词）。

### A1 判别力（必给红证据）
1. 删掉 allowlist 里 `app/login.html` 的 `R1-01` 条目 ⇒ **必红**并点名该行。
2. 把 `Admin` 写进某客户面字符串（注入 `app/login.html` 的 option 文本）⇒ **R2-18 必红**（验证大小写折叠生效），取证后还原。
3. `UI_REDO_SCAN_ROOT` 指向空目录 ⇒ **必红**（"看不见"当红，不是通过）。

### A2 覆盖（下界，冻结数值由本批自测产生）
- 断言「被扫文件数 ≥ 一个本批实测下界」且「`electron/` 与 `app/` 各自至少 1 个文件被扫到」。
- 断言「候选总数 > 1743」（扩面后必然增加；若没增加说明扩面没生效）。

### A3 债单自洽
- 每条的 `why` 前缀 ∈ {`【客户面】`,`【非客户面】`,`【复核】`}，且**分档合计 == 条目总数**（脚本算，不许手写）。

### 防假绿三问（逐问作答）
1. **零对象**：扫描根写错时会不会全绿？→ 由 A1.3 拦。
2. **跳过**：扩面失败（目录不存在）会不会静默通过？→ 断言 `electron/` 与 `app/` 各 ≥1 文件。
3. **同源派生**：新基线是不是"跑一遍把输出抄下来"？→ 是，但**必须有 A1.1/A1.2 两条红证据证明判据活着**，否则基线无意义。
