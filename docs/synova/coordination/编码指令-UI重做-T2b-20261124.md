## §1 模块锚（九项之①）

- **模块**：窗口姿态（壳的物理边界）
- **服务的真实客户／用户动作**：老板**把窗口拖小**（分屏、投屏、多任务）
- **本批完成后用户能做什么**：窗口缩到最小也不会把三栏压成不可用；拖小后仍能看清内容、点得到按钮
- **与闭环的关系**：B1 修完"白盒"后，若窗口一缩就塌，客户仍读不了 ⇒ 这是 B1 的可达性补全
- **长期边界**：只改窗口参数，**不动任何组件与样式**
- **写集（文件级）**：`electron/main.cjs`（仅 `BrowserWindow` 的 `minWidth`/`minHeight` 两个参数）
- **明确不做**：不改 `global.css`、不改 `.tsx`/`.ts`、不改 `frame`/`titleBarStyle`/`webPreferences`、不做响应式断点（那是 T5）
- **验收入口**：拖窗口到最小，三栏仍可用
- **尚未确认**：无

## §3 取值（**CTO 已钉死，不许改**）

```
中栏最小宽度 = 400px（内容可读下限，本批取此值）
minWidth  = 左(240) + 中(400) + 右(320) + 分隔与边框余量(40) = 1000
minHeight = 顶部(48) + 内容(400) + 状态栏(28) + 余量(24)     = 500
```

- **必须用 `240`/`320`**（展开态令牌），**不是** 264/300（那是 T5 的窄化夹取值，属未来批）。
- 折叠态（44/0）**不参与** `minWidth`：客户随时可展开，最小值必须容下**展开**形态。
- 若实测 1000 仍挤压，**允许上调**并在回执给依据；**不允许下调**。

## §4 关键契约

1. 只加两个选项，**不动**其它 `BrowserWindow` 参数。
2. 不引入新依赖、不改窗口结构（`frame`/`titleBarStyle`）。
3. `minWidth`/`minHeight` 必须**小于**默认 `width:1280`/`height:800`（否则窗口起不来 —— 先自检）。

## §5 验收（九项之⑤）

### 期望值来源（独立于被测对象）
- 1000/500 来自 §3 的**令牌算式**（240+400+320+40、48+400+28+24），不是"拖一下看看"。
- 三栏可用性来自既有布局契约（`global.css` 的 `--left/right-panel-expanded`），不是本批实现。

### A1 参数存在且自洽（机器可判）
```bash
git grep -nE "minWidth|minHeight" -- electron/main.cjs   # 必须命中且值 >= 1000 / >= 500
```
**改坏必红**：把 `minWidth` 改成 600 ⇒ 该断言（值 ≥ 1000）必红。

### A2 真实入口：拖到最小后三栏仍可用（**用户可见回归，必做**）
入口：后端 18790 ＋ `electron-renderer` 的 `npm run dev`(5173) ＋ `electron:dev`（沙箱需一次提权）。
动作：把窗口拖到最小 → 用 CDP 或截图读布局。
断言（逐项给数字）：
1. 窗口实际尺寸 ≥ 1000×500；
2. 左栏宽度 ≥ 240、右栏 ≥ 320、**中栏 ≥ 400**；
3. 无横向滚动条（`document.documentElement.scrollWidth <= clientWidth`）；
4. 关键按钮可点（至少「发送」与左栏「DSH 会话」在视口内，`getBoundingClientRect` 不出界）。

**改坏必红**：临时把 `minWidth` 改成 600 重跑 ⇒ 断言 2/3/4 至少一条必红（取证后还原）。

### A3 默认尺寸未受影响
默认启动时窗口仍为 1280×800（`width`/`height` 未改）；`git diff` 里只有两行新增。

### 防假绿三问
1. **零对象**：CDP 没连上会不会"读到 0 就通过"？→ 断言 1 先校验 `window.innerWidth > 0`。
2. **跳过**：起不了 Electron 时 ⇒ 标"未验证"，**不得**计通过。
3. **同源派生**：A2 的期望值来自 §3 算式与布局令牌，不是"当前渲染多宽就写多宽"。
