## §1 模块锚（九项之①）

- **模块**：登录面的唯一性（壳只应有一个登录入口）
- **服务的真实客户／用户动作**：客户**打开 Synova 后登录**
- **本批完成后有什么用**：删掉一条**从来没成功过**的登录面，消除"两个登录实现"的分裂，并去掉一个泄漏面（`GA`/`Admin` 等英文角色值）
- **与闭环的关系**：这条面不删，任何"登录失败了"的现场都可能被误判成主登录坏了；也永远会有人去"修"它，等于重建第二个登录
- **长期边界**：只剩 `DshLoginPanel` 一个登录面（renderer 侧）；不新增登录实现
- **写集（文件级，逐个列出，禁止目录级通配）**：
  ```
  删：app/login.html
  删：app/js/auth.js
  改：src/server.ts                     ← 摘掉 /login 静态挂载与重定向
  改：tests/routes/setup-guide-retired.test.ts  ← 该文件 :162-164 断言了该页存在
  改：electron/main.cjs                 ← 若有指向 /app/login.html 的回落（审计 A: main.cjs:128-140）
  改：部署/构建相关文档（若 §4 核出引用）
  ```
- **明确不做**：不改 `DshLoginPanel`（T1/T4 面）；不改 `/api/auth/login` 路由契约；不动 `app/` 下**其它**未被引用的资产（先列清单，见 §4）
- **验收入口**：起服务后 `GET /login` 与 `GET /app/login.html` 都应 404；renderer 登录仍可用
- **尚未确认**：`app/` 目录下其余文件是否只服务该页（须逐个核）

## §5 验收（九项之⑤）

### 期望值来源（独立于被测对象）
"该页应 404"来自 §3 的产品决定；"主登录仍可用"来自 `DshLoginPanel` 的既有契约（不是本批实现）。

### A1 路由不可达（机器可判）
```
起服务 → curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:18790/login            → 期望 404
                            ... http://127.0.0.1:18790/app/login.html                     → 期望 404
```
**改坏必红**：把这行断言改成期望 200 ⇒ 必红。

### A2 文件确实没了且无残留引用
```bash
test ! -f app/login.html && test ! -f app/js/auth.js   → 通过
git grep -n "app/login.html\|app/js/auth.js"           → 期望 0 命中（除历史文档/审计报告）
```
**注意**：审计报告与历史 DEV DOC 里**会有**对该路径的引用（那是历史记录，**不算残留**）⇒ 断言必须排除 `docs/synova/ui-redo/` 与审计报告。

### A3 主登录未受影响（**用户可见回归**）
- 真实入口：起后端＋Vite＋Electron，走 `DshLoginPanel` 登录一次（无模型 key 时到"凭据错误"这一层即可）。
- 断言：登录面板仍渲染、提交仍有响应（不是白屏/不是崩溃）。
- **不得**只断言"文件删了"就交差——删掉一个共享挂载可能连带弄坏别的静态资源。

### A4 构建未受影响
```bash
node build-synova.cjs   # 或仓内等价命令；确认不因缺 app/ 报错
```

### 防假绿三问
1. **零对象**：`git grep` 命中 0 是不是因为路径写错？→ 断言前先用一个**已知存在**的串（如 `DshLoginPanel`）跑一次 grep，确认 grep 本身有效。
2. **跳过**：服务起不来时 A1 会不会被跳过？→ 标"未验证"，**不得**计为通过。
3. **同源派生**：A1 的期望 404 来自产品决定，不是"跑一遍看到 404 就写 404"。
