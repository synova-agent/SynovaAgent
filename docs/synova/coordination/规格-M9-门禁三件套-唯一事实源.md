# 规格 — M9 控制塔门禁三件套（**唯一事实源**）

> 立此件原因：CTO 曾以三种口径描述 M9（"门禁三件套"／"含 B2"／"模式自检"），而 **main 上 grep `门禁三件套` = 0 命中**，导致执行方无法写出忠实的 `/plan`。本件是**唯一权威规格**；与任何口头/正文描述冲突时以本件为准。

## 一、M9 是什么

**M9 = 控制塔脚本的三件套强制**：任何 `scripts/control-tower/**` 下的检查器（新增或修改），交付必须同时具备三件，缺一不算完成。

| # | 件 | 定义 | 判据（可执行） |
|---|---|---|---|
| **① 模式自检** | 检查器必须能证明**自己的判据没坏**：非法正则／静默吞错／fail-open（管道失败被 `\|\| true` 吞）／解析到 0 个对象——一律必须是**显式降级态**（`degraded:` + 日志 + **非 0 退出码**），**绝不等同通过** | 构造"判据被破坏"的输入 → 必须 `exit≠0` 且打出 `degraded:` |
| **② 判别夹具** | 夹具必须能"**改坏即红**"：至少一条断言的失败路径被真实触发过（贴原始输出），而非只测 happy path | 变异体矩阵（改坏 N 处）→ 每条对应夹具必须红；复原后必须绿 |
| **③ CI 清单登记** | 检查器与夹具必须进 `.github/workflows/ci.yml` 的密封清单；**未登记 = 没接线** | `grep -c <夹具名> ci.yml` ≥1，且 CI 上**真跑到**（非只在本地） |

## 二、B2 的归属（一次定死，不再两说）

**B2「CI 既有红显式登记」= M9 的第③件的组成部分**，不另立卡：
- 建立 `scripts/control-tower/ci-red-baseline.txt`（既有红登记表：条目 + 证据 + owner + 到期日）；
- **允许带既有红合并，但必须登记**；**未登记的带红合并 = 违规**；
- 检查器须能对账 `check-runs` 与登记表（新增未登记红 → 红）。

> 依据：`docs/synova/coordination/派单-K3回执-批次2-20260924.md` §二 待修 #1（M9）与 #3（CI 既有红登记）。

## 三、交付形态（模板）

```
scripts/control-tower/<checker>.sh|py     # 检查器（含模式自检）
tests/control-tower/<checker>.test.sh     # 判别夹具（改坏即红）
scripts/control-tower/*-baseline.txt      # 需要 ratchet/登记时
.github/workflows/ci.yml                  # ③ 登记（夹具 + 检查器本体）
```

**并入 M9 的执行项（不再单独派）**：B2（既有红登记）｜B3（D922 夹具登记 CI）｜B4（D925 调用面接线）——三者都是"三件套"在具体检查器上的落地，按 ci.yml 单写者串行：**M9 → B3 → B4**。
