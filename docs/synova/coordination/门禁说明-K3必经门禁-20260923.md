# 门禁说明：K3 必经合并门禁（D923）

> 卡号 D923 | 域 mac | 生效 2026-09-23 | 判定器 `scripts/control-tower/k3-merge-gate.sh`
> 政策外置 [k3-gate-policy.yaml](../../../scripts/control-tower/k3-gate-policy.yaml) | 夹具 `tests/control-tower/k3-merge-gate.test.sh`
> 宿主：`.github/workflows/ci.yml` → **独立 job `k3-gate`（`name: K3 Merge Gate`）** → step 「K3 merge gate (D923)」。
> **为什么必须是 job 而不是 step**（D923 收尾任务 0.5，实测两条）：① branch protection 的 required check context 是 **job 名**，
> step 不是可注册单元 ⇒ step 形态**无法被注册为必经门禁**；② job 内某 step 失败后其余 step 全部 `skipped`
> （实测：`Iron laws check` 失败 ⇒ 其后 `Verify parallel` / D708 / K3 三步全 skipped）⇒「被 skip」= 门禁在被依赖时**静默缺席**，违反裁定 3「永远会跑」。
> 故本 job **不挂 `needs:`**、**不加 docs-only 跳过**（required check 必须在每个 PR 上都有结论）；`fetch-depth: 0`（要算 merge-base/diff）；
> 保留 `GITHUB_EVENT_PATH`（供第三路 D# 归因读 PR 正文）。调用语义与 D708 同形（`--base origin/main --head HEAD --pr <event>` + 三态 0/1/2 + diff 口径）。
> **遗留（不在本卡改）**：D708 与 `Iron laws` 仍是 `quality` job 的 step，**同样会被 skip**。

---

## 1. 门禁要解决的问题

三类高风险路径（**安全/鉴权、财务计算、数据迁移/存储**）的变更，历史上出现过「代码已合、K3 结论缺失或为有条件通过」的情形。
本门禁把「**卡内必须有通过级 K3 结论**」变成合并前的物理条件。

**原则「宁窄勿宽」**（CTO 裁定 6）：误报会诱发绕过（V3.6/V4.5.1 实证：一个被绕过的门禁 = 没有门禁）。
故类目取值一律取**实测信噪比最好**的那条，而不是语义上"更大更全"的那条。

## 2. 三态语义（CTO 裁定 3，逐字落地）

| K3 结论 | 归一类 | 门禁 |
|---|---|---|
| `PASS` / `pass` | PASS | **绿**（exit 0） |
| `CONDITIONAL PASS` / `CONDITIONAL_PASS` | CONDITIONAL_PASS | **红 + 附理由**（"有条件通过 = 未通过"，创始人 2026-09-20 纪律） |
| `FAIL` | FAIL | **红 + 附理由** |
| `NOT-AUDITABLE` | NOT_AUDITABLE | **红 + 附理由**（**不可审计 ≠ 通过**） |
| `无 K3（V5.1.3 tag 锚点闭环）` / `DONE` / `CTO 验收通过（非 K3）` | NOT_K3 | **红 + 附理由**（非 K3 结论不得充当 K3 通过；出口：补 K3 结论，或由 **CTO 具名豁免**（写入卡/PR，可核）） |
| 键缺失 / `audit:null` / `verdict:null` | NO_VERDICT | **红 + 「K3 排队中」提示**（出口同上） |
| 非三类路径 + 未抽中 | — | 绿 |
| 非三类路径 + 抽中 20% | — | **绿（永不阻断，只记录 `::notice`）** |

**退出码**：`0` 通过（绿）／`1` 拒绝（红）／`2` 检查执行失败或降级（fail-closed，**绝不等同通过**）。

**降级与三类的交叉（裁定 3 附加条件 4）**：结论源/扫描器不可用时，**三类命中场景一律非 0**——不得静默放行。
（实现：扫描器整体不可用 → exit 2；能分类但结论源读不出 → 判 NO_VERDICT → exit 1。）

## 3. D# 解析：三路来源 + 必须可归因（CTO 裁定 3）

一个 PR 变更三类路径时，门禁必须知道「查哪张卡的结论」。解析三路，**红时必须报出查过哪几路、结果分别是什么**（禁只报"无结论"）：

| 路 | 来源 | 说明 |
|---|---|---|
| ① | **分支名** 中 `[Dd][0-9]+`（大小写不敏感，归一为大写） | 主路径；对齐 D708 现有 `--branch "${GITHUB_HEAD_REF}"` 做法 |
| ② | 变更集内 `.claude/task-briefs/*-D<id>-*.md` 的**文件名** | 兜底；有些分支名不含卡号 |
| ③ | **PR 正文**里的 `D\d+`（从 `GITHUB_EVENT_PATH` 读，**不硬编码**） | 兜底第二路 |

- **多 D# → 全部检查，任一非 PASS 即红**。
- **三路皆空 → `NO_CARD_ID` → 红**（fail-closed；出口：在分支名/PR 正文写明卡号，或 CTO 具名豁免）。
- 脚本始终打印一行**归因摘要**：`D# 归因 → ①分支名(x)：[… ] ②brief 文件名：[…] ③PR 正文：[…] ⇒ 采用：[…]`。

### 3.1 报告文件 D# 派生：**配方 B（文件名首个 D#）**——口径必须钉死

> **本节的由来**：同一问题用三种配方得到三个数，这件事本身就是「口径必须钉死」的最好实证（新纪律⑥）。

统计「`audit:null` 但库内已有 K3 报告文件」的卡时：

| 配方 | 定义 | 结果 |
|---|---|---|
| A | 文件名**破折号锚定** `*-D#-*.md` / `*-D#.md` | **7** |
| **B** | 文件名中**首个** `D\d+` | **8 ← 本门禁采用** |
| C | 任意位置含 `D#`（宽松子串） | **9** |

差异根因：D850 的报告是**复合名** `docs/synova/audit-reports/2026-09-20-K3-D850D852.md`——
配方 A 锚了破折号 ⇒ 漏掉；配方 B 取首个 D# ⇒ 得 `D850`；配方 C 会把同一文件的 `D852` 也算上。
**采用 B 的理由**：与既有唯一约定 `scripts/control-tower/gen-cto-health.py:320` 的 `resolve_audit_report` **同源语义**，
且与 `#723` 证据 §六的 8 张**逐张一致**。
**若将来要改用配方 C，必须走 §7 失效条件 + 重测**，不得直接改。

## 5. 20% 抽样（非三类路径）

- **取值 0.20 来自 CTO 裁定 3（拍板参数），不是本卡推导的最优值。**
  **本仓无实测数据支持「20% 优于 10%」——此项为未实测，如实标注**（新纪律⑥）。

  依据：`D923-三类路径名单实测 §四`（窗口 `since 2026-08-24`）。
- **确定性**：`pr_number % 5 == 0`——同 PR 恒同判，任何人可复算；**不用随机**（随机不可复现，无法审计）。
- **永不阻断**：抽中只打 `::notice`，exit 0。
