### 2.3 `include-hidden-files: true` 的必要性（一手来源）

- 官方 README「Uploading Hidden Files」：**"By default, hidden files are ignored by this action…"**、
  **"Hidden files are defined as any file beginning with `.` or files within folders beginning with `.`."**
- `actions/upload-artifact@v4` 的 `action.yml`：`include-hidden-files` → `default: 'false'`
  （"If false, hidden files will be excluded from the artifact."）
- 本 PR 两条 path 全在 `.claude/`、`.codex/` 内 ⇒ 缺此项 = **artifact 为空**，而 `if-no-files-found: warn` 只出警告、job 照绿 ⇒ **判据假绿**。夹具 M1 专门抓这个（§4）。

## 8. 红线段（R2 ⑤）

### 8.1 红线段（CTO 裁定「甲」）：**只在连续第 2 次失败时**新增红路径 + 计数兜底；单次/瞬时故障不红

**实测前提**：`quality` job 的名字 `TypeScript + Lint + Iron Laws` 是 **main 的必需检查**（`GET /repos/{owner}/{repo}/branches/main/protection` 实测；独立自验员执行）⇒ 该 job 转红 = **阻塞全队所有 PR 合并**。

**为什么不是 fail-loud（取舍说明，被否方案并列）**：
- **被否方案**：upload step 不加 `continue-on-error`（原 fail-loud 设计）——好处是失败立刻红、绝无静默；**否决理由** = 上传服务**瞬时抖动**即红 main 必需检查 ⇒ **阻塞全队所有 PR 合并**，属本工程要消灭的"治理制造阻塞"形态。
- **另被否**：只加 `continue-on-error` 而不加兜底（我原提的"纯黄灯"）——**否决理由** = 归档长期坏掉也没人担责（静默失败面无限期存在），单次抖动与真故障无法区分。
- **采用（甲）**：`continue-on-error: true`（主体）+ **计数兜底**：单次失败 = 黄灯 + 计数；**连续 2 次 = 红**（连续 2 次说明是真问题，不是瞬时抖动），**且必须打印原因**。对齐蓝图 §4.2-bis「不许降级即通过，但也不得制造阻塞」。

**明文（对齐 CTO 要求）**：**本改动只在连续第 2 次失败时新增红路径（CTO 已批）**；单次失败、以及"历史取不到/不可解析"这两种情形都**不红**，但都留**可见**痕迹（`::warning`／显式 unknown，铁律 11 不静默）。逐条行为与原始输出见 **§4.3**（F1/F2/F3 + MF1）。

**CI 状态面登记（本卡未新增/未显式化任何 `permissions`）**：
- 本实现**没有**添加 `permissions:` 块、**没有**改 job 级权限 ⇒ **无 permissions 面的显式变更**（故无需 CTO 就 permissions 单独批准）。
