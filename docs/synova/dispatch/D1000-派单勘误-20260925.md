## 一、两处事实错误（已作废，均为 CTO 责任）

### E-1　「签发侧数据源已存在，不是零基础」——**在 API 面不成立**

原派单件 §三 写：`src/growth/user-store.ts` 有 `department` 字段（注册时由 `extra.department` 落库）→ 结论「签发侧数据源已存在，不是零基础」。

**实测推翻**（口径 `ref=ef5c8caa`，2026-09-25 CTO 复算）：

```
$ git grep -n createUser ef5c8caa -- src
ef5c8caa:src/routes/auth.ts:89          createUser(..., { phone, wechatId })          ← 不传 department
ef5c8caa:src/routes/enterprise.ts:116   createUser(..., { phone, wechatId })          ← 不传
ef5c8caa:src/routes/enterprise.ts:252   createUser(email, password, inv.role, orgId)  ← 不传
$ git grep -n updateUser ef5c8caa -- src
ef5c8caa:src/routes/enterprise.ts:239/303/366/632   ← 只设 orgId / role / status
ef5c8caa:src/services/anomaly-detector.ts:100/115   ← 只设 status
```

**正确表述**：`UserRecord.department` 只在**类型层**存在，**生产路径没有任何写入者**（PLAN 的 W1）。原措辞把"类型里有字段"误读成"数据会到位"。

### E-2　症状表第 3 行「打开部门工作区 → 恒无权限/空列表」——**不实**

**实测**：`src/routes/department-workspace.ts:89-98` 的页内 `fetch('/api/workspaces/mine')` 在 404 响应上仍 `await r.json()` → `:91 if(!d.workspaces.length)` 对 `undefined` **抛 TypeError** → `:96-98 catch` 只 `console.warn`、无任何 UI 呈现 ⇒ 页面**永久停在初始态「加载中…」**。

**正确表述**：用户看到的既不是"无权限"，也不是"空列表"，而是**卡在加载态**。兼带铁律 24/31 存违规（非本卡引入，已登记）。

## 二、作废声明：用户可见目标的**可达性**

原派单件 §一 承诺的验收目标「登录 → 看到本部门工作区 → 看不到别的部门」在 **W1/W2/W3 任一未解**时**不可达**：

| 墙 | 事实 | 落点 |
|---|---|---|
| **W1** | `department` 无生产写入者 | 本勘误 E-1 |
| **W2** | `GET /api/workspaces/mine` HTTP 恒 404（`/:id`@126 遮蔽 `/mine`@264；`/conflicts`@294 同病） | 另立卡 D950 |
| **W3** | 桌面端无部门工作区消费点（`useWorkspaces.ts:19-20` 明写「本地 Mock，不调用 API」） | 待产品决策 |

**D948 可证明的最远边界** = 「登录签发的 JWT 载有真实部门 + 验签后进入 RBAC 上下文 + 部门判据在同/异部门上正确」。
**D948 交付必须登记为**：**功能回退（部分恢复，未闭环）**。严禁写成"已知限制"或"部门可见性已可用"。

**正确表述**：派单件**指纹**对账 = **三条待核对坐标**（派单件分支 / 切片 base / main） × **三方值**（①派单件声明 ②`ls-remote` 远端权威 ③本地检出）。
