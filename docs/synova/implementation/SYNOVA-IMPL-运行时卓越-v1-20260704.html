Anthropic 工程原则（贯穿全文）：
1. 如果兼容层的维护成本超过重写成本，不要写兼容层。
2. 一次性切换，用自动化验证器确保切换后输出不变，切换后立即删除旧代码。
3. 不要把"一次性的切换风险"转化为"持续的维护负担"。
4. 并行化一切可以并行的工作——时间是最稀缺的资源。

1. 审计结论：当前代码库 vs 新本体

1.1 现状

模块当前状态与 v2.4 的兼容性

1.2 最关键的发现

92个compute函数全部使用 store.queryNodes('Financial') → .props.xxx 的KV读取模式。没有例外。GraphStoreReader.traverse() 已定义但从未被调用。这意味着新本体的核心要求——"compute函数沿因果边做图遍历"——需要对所有92个compute函数做数据访问层的全量重写。这不是优化，是替换数据访问范式。

2. 工程原则与策略

2.1 核心原则

原则含义否决了什么
一次性切换不存在"新旧并行"的阶段。切换后旧代码立即删除否决了 compat-layer.ts、新旧并行运行、P0/P1/P2分批渐进迁移
验证器替代兼容层用 migration-validator.ts 在切换前确认所有compute函数输出不变。切换后validator本身也被删除否决了任何形式的适配层/桥接层/兼容读取
并行化一切可并行的工作92个compute函数由3个Claude Code实例并行重写。每个实例约30个函数否决了串行分批迁移
专家提示词一次性替换新内容替换旧内容。不做"追加不删除"否决了渐进式注入

2.2 全局策略

Phase 0: 新本体JSON Schema创建（旧Schema保留不动）
    ↓
Phase 1: 图遍历能力 + migration-validator（验证器先就位）
    ↓
Phase 2: 专家提示词一次性替换 → A/B测试
    ↓
Phase 3: 92个compute函数并行重写 → 全量验证 → 一次性切换 → 删除旧代码
    ↓

4.2 migration-validator.ts — 本方案的核心安全网

这是替代compat-layer的关键组件。不是一个"长期的适配层"——是一个"一次性验证工具"。Phase 3完成后即可删除。
// src/l4/migration-validator.ts — 核心逻辑

interface ValidationReport {
  functionName: string;
  oldOutput: ComputeResult;   // 旧compute函数（读旧Financial KV）的输出
  newOutput: ComputeResult;   // 新compute函数（图遍历）的输出
  diffPercent: number;        // 数值差异百分比
  status: 'pass' | 'review' | 'block';
}

function validateMigration(
  oldCompute: Function,        // 旧compute函数引用
  newCompute: Function,        // 新compute函数引用
  testData: GraphStore         // 客户A模拟数据
): ValidationReport[] {
  // 对92个compute函数逐一执行：
  // 1. 用旧函数在旧本体数据上运行 → oldOutput
  // 2. 用新函数在新本体数据上运行 → newOutput
  // 3. 计算diffPercent = |oldOutput.value - newOutput.value| / oldOutput.value
  // 4. diffPercent < 1% → pass
  //    diffPercent 1-5% → review (人工审查)
  //    diffPercent > 5% → block (阻断合并)
}

6.4 单个compute函数的迁移示例

// 迁移前（KV模式）—— compute-kz-index.ts
export function computeKzIndex(financials: Array<{
  operatingCashFlow: number;  // ← 直接从 .props 读
  netPpe: number;
  totalDebt: number;
  equity: number;
  cash: number;
}>): KzIndexResult { ... }

// 迁移后（图遍历模式）
export function computeKzIndex(
  store: GraphStoreReader,
  traversal: GraphTraversal,
  teamId: string
): KzIndexResult {
  const money = store.queryNodes('resource/money', { teamId })[0];
  if (!money) return { ..., degraded: true };
  
  // CF = 从所有FUNDS→ACTIVITY→PRODUCES→FINANCIAL_OUTCOME汇聚
  const activities = traversal.traverse(money.id, ['edge/funds']);
  const outcomes = traversal.traverse(
    activities.map(a => a.id), ['edge/produces']
  );
  const cf = outcomes
    .filter(o => o.type === 'outcome/financial')
    .reduce((sum, o) => sum + (o.props.operating_cashflow || 0), 0);
  
  // K = MONEY子上下文中的固定资产
  const ppe = money.context?.CashPosition?.net_ppe ?? 0;
  const debt = money.context?.DebtStructure?.total_debt ?? 0;
  const cash = money.context?.CashPosition?.cash_balance ?? 0;
  
  // KZ公式不变
  const kz = -1.002 * (cf / (ppe || 1)) + 3.139 * (debt / (debt + (money.context?.EquityBase?.total_equity || 1))) - 1.315 * (cash / (ppe || 1));
  return { kzIndex: kz, ... };
}

8. 风险矩阵与缓解策略

风险严重度概率Phase缓解
migration-validator 未捕获所有差异：某些compute函数的输出差异在特定边界条件下才出现，validator没覆盖 高 中 3 validator的测试数据包含客户A全量数据，覆盖正常/边界/异常三种场景。Phase 4的端到端测试作为第二道防线
三个Claude Code实例的代码风格不一致：合并时产生大量冲突 中 中 3 在Day 1-2统一compute函数签名模板和命名规范。每个实例提交到独立分支，合并前先跑pre-commit检查
专家提示词替换后LLM输出质量劣化 中 低 2 A/B测试。劣化则回退旧提示词并人工修正新提示词
图遍历性能不满足实时诊断要求 中 中 1/4 动态锚点机制限制遍历范围。Phase 1做性能基准。不满足则增加缓存层
Sensing参数不可自动采集 低 高 2 在诚实清单和专家提示词中明确标注为GA访谈项。纯软件版不计算Sensing维度
产业时钟L2管道数据不可得 中 高 1 默认使用L1行业模板或L3 LLM推理。标注数据源层级和置信度。不声称L2级精度当数据不可得
