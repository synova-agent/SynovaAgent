## 一、为什么原问题框架是错的

原 D-1 问的是「同一件事多久内只提醒一次」（5 分钟 vs 30 分钟）——这是**工程框架**（异常检测器 + 时间窗去重），把通知当成事件流处理。

创始人指出真实场景：**企业经营问题不是代码 bug。** 代码出错改一行就好；现金流、成本超支、销售下滑这类问题**是慢变量、需要流程、需要时间、可能长期存在**。首个客户（客户A）部署后必然同时暴露财务、成本、销售多类问题，而且**这些问题不会在一两天内消失**。

在这个现实下，时间窗去重必然二选一都错：
- 窗口短 → 同一个已知问题反复轰炸老板 → **告警疲劳** → 老板不再看告警（监测功能的死法）
- 窗口长 → 把半小时内两件不同的事误合并 → 丢掉真实变化

**根因**：把「告警」（事件，一次性）和「跟踪」（订阅，有节奏）混成一个机制。

## 二、正解：问题的生命周期 + 状态驱动通知

| 问题状态 | 系统该做什么 | 通知语义 |
|---|---|---|
| 新发现 | 立刻告警：影响 + 证据 + 建议，**并询问跟踪节奏与格式** | **事件**——必须马上说 |
| 已告知待回应 | 等老板表态；未回应按契约升级 | 升级，不是重复 |
| 已认领/处理中 | **停止重复告警**，转入约定节奏 | 静默跟踪 |
| 有实质变化（恶化 / 跨档 / 新关联 / 停滞超期） | 立刻再告警 | **事件**——变化才配打扰 |
| 已解决 | 复验 + 关闭 + 复盘「这次怎么解决的」 | 归档 + 知识沉淀 |
| 老板明确选择不处理 | 记录理由，不再打扰；进「明确不管」清单定期回顾 | 沉默 ≠ 消失 |

**一句话**：不重复喊同一件事，但绝不遗忘任何一件事——靠「状态 + 节奏」，不靠「时间窗」。

### 咨询师类比（落成具体机制）

| 咨询师会怎么做 | 系统对应机制 |
|---|---|
| 不会为同一件事天天打电话 | 已认领 → 停止重复，转约定节奏 |
| 第一次发现问题时说清影响+证据+建议 | 首次告警含影响/证据/建议 |
| **然后问客户**：你希望我怎么汇报、多久一次、什么格式 | **首次告警同时请求确认节奏与格式** |
| 按约定交进展，不越界打扰 | 周期报告（默认周报、一页纸） |
| 客户一直没动作时升级关注 | 未回应/停滞 → 进周报首页 → 标停滞天数 → 给「为什么卡住」诊断 |
| 解决后复盘，把经验变成方法 | 关闭复盘 → 知识沉淀 → 复发识别 |

## 三、决策内容（创始人 2026-09-12 裁定）

1. **技术参数**：5 分钟窗口**保留但降级**为「抖动合并器」——只合并同一检查器在几十秒内的重复触发，**不承担任何产品语义**
2. **产品规则**：状态驱动（上表六态）
3. **节奏与格式由老板定**，在首次告警时询问；技术载体＝**监测契约**（每客户/每指标：阈值、渠道、节奏、格式、升级规则、责任人），**文件化**（符合「加文件不改代码」架构哲学）
4. **政策值（默认，可改）**：
   - 新发现后 **24 小时**未回应 → 提醒一次
   - **7 天**无进展 → 进周报首页
   - 老板不指定节奏时 → 默认**周报 1 次、一页纸**
   - 老板明确「不处理」的问题 → **每周回顾一次**（简短列出）

## 六、风险与兜底

1. **不重复 → 老板可能遗忘** → 兜底＝周期报告（沉默 ≠ 放弃）
2. **依赖老板至少回应一次** → 未回应则走默认节奏 + 升级规则
3. **变成「又一个没人看的看板」** → 默认低频（周报为主），只有新发现与恶化才即时
4. **跨线协作风险** → 契约文件 owner 与 loader 分属两线，须显式声明写集边界（见同步文档）
