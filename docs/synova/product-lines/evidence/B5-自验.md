### 11.2.1 值得记一笔的工程技巧：**in-place 写入（保 inode）破解自指死循环**

一轮 U5 的根因之一是**自指困境**：`writer_note` 若写"本文件 birth=…"，则该字段的**每次写入都会重置 birth**，导致它引用的值**必然过期** → 自己把自己写成 stale。

b5-c1 的解法是**就地改写（保 inode）**，我独立验证其成立：
```
原理：若 18:13 那次写入是 rename/replace（原子替换），inode 会换新、birth 会重置为 18:13；
      实测 birth=18:08 而 mtime=18:13 ⇒ 同一 inode 被就地改写 ⇒ 保 inode 成立。

  D928  birth=2026-09-24 18:08:02  mtime=2026-09-24 18:13:08  inode=19762685  → ✅
  D933  birth=2026-09-24 18:08:09  mtime=2026-09-24 18:13:08  inode=19762701  → ✅
  D934  birth=2026-09-24 18:08:04  mtime=2026-09-24 18:13:08  inode=19762693  → ✅
  D936  birth=2026-09-24 18:08:04  mtime=2026-09-24 18:13:08  inode=19762695  → ✅
```
**要点**：`birth < mtime` 是"同 inode 被就地改写"的**可判据物理证据**（替换写会让 birth == mtime）。此法把"引用自身 birth"从**必然过期**变成**在下次就地改写前长期有效**。
**边界（必须写明，防被误用为万能豁免）**：该技巧只保证 birth **在本机本 inode 上**稳定；**一旦跨机 clone / 换工作树 / 被 rename 或 checkout 重写，birth 归零重算 → 该值仍会 stale**。故它降低 stale 频率，**不消除** stale；§11.4 的"锚点声明"仍是必要的兜底。
