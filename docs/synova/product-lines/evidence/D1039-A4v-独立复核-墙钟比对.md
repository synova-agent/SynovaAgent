### 1.2 🔴 差异点名：第 5 行「总墙钟 326 s」的标签与它自己的括注**互相矛盾**

队长原文：

> | 同 run 的 ci.yml 总墙钟 | `36356959940` | `2026-09-27T22:57:00Z → 23:02:26Z` = **326 s**（windows CT job 比整条 run 还长 ⇒ 它是唯一关键路径） |

**一个 job 不可能比它所属的 run 还长**——这是物理约束，不是口径分歧。用同一份 jobs 数据把四个量分开算，矛盾就露出来了：

```
════ run 36356959940 ════
  A. run 级墙钟     (run_started_at→updated_at) = 22:55:54Z → 23:34:04Z = 2290 s  (38.2 min)
  B. 全部 job 跨度  (min started→max completed) = 22:57:00Z → 23:34:03Z = 2223 s
  C. 排除 windows CT 腿后的跨度                 = 22:57:00Z → 23:02:26Z =  326 s  ← 队长印出来的那个数
  D. windows CT 腿                              = 22:57:01Z → 23:34:03Z = 2222 s

  ⇒ 不可达性检查: D(2222) <= A(2290) ? True          （job 没超过 run，自洽）
  ⇒ C(326) 是「其余 12 个 job」的跨度，不是 run 的墙钟
  ⇒ windows CT 腿 ÷ run 墙钟 = 2222 / 2290 = 97.0%
```

**结论（事实陈述，不做归因）**：`326 s` 这个**数字**是真实的（`22:57:00Z → 23:02:26Z`），但它是「**排除 windows CT 腿之后，其余 12 个 job 的跨度**」。把它标为「ci.yml **总墙钟**」不成立：
- ci.yml 这条 run 的真实墙钟是 **2290 s (38.2 min)**；
- 仅按 job 时间戳算的跨度是 **2223 s**；
- 326 s 与 2290 s 差 **1964 s（85.8%）**。

**为什么这条必须点名（不是抠字眼）**：本批的立项理由就是「windows CT 腿 37 min 占满关键路径」。若「改前总墙钟」取 326 s，则改动后的对比会呈现「326 s → 秒级」，而真实基线是 **2290 s**——**基线被低估约十分之九**，收益会被严重低估/口径失真。本批最终判据是墙钟对比，基线口径错 = 判据错。

> 判定：**属「标签/口径错误」，不属「数字造假」**——5 个数字全部实测可复现。请队长修正第 5 行口径后再作为对比基准；建议写法：
> `| ci.yml run 级墙钟 | 36356959940 | 22:55:54Z → 23:34:04Z | 2290 s |` + 单列 `| 排除 windows CT 腿的其余 job 跨度 | 326 s |`

**✅ 队长已裁决采纳（本人消息 `team-message-517d5cce`）**：修正为「A/C/D 三分版」，对比表统一采用
`dur = updated_at − run_started_at`（= A，run 级 2290 s），并另列 D（2222 s）与占比。
队长同时指出我的纠正**让结论更强**：`D/A = 97.0%`，即 windows CT 腿几乎就是整条 run 的墙钟（仅差 68 s 排队/调度开销）。
**独立交叉核对**：另一独立成员 diagnoser-c 用同一口径（`dur = updated_at − run_started_at`）在 ci.yml 最近 8 次 run 里也取到 **2290** ⇒ 两个独立成员取到同一个数，此值可用。

## 5A. 🔴 额外独立发现：`ctsignal` step 降级分支**死代码**（已修复并复核通过）

> 保留完整记载（缺陷 + 原始输出 + 修法），因为「发现→修复→复核」链本身是证据。

**缺陷位置**：`.github/workflows/ci.yml`（coder-a 修复前版本）`Classify control-tower CI signal (D1034)` step 正文：

```bash
bash scripts/control-tower/ci-signal-classify.sh --mode github
RC=$?                                    # ← 永远执行不到
if [ "$RC" -eq 2 ]; then
  echo "::warning ... 分类器降级（exit 2）..."
  exit 0                                 # ← 死代码
fi
exit "$RC"
```

**根因**：GitHub Actions 对 `shell: bash` 使用 `bash --noprofile --norc -eo pipefail {0}`，**带 `-e`（errexit）**。
`-e` 下裸命令返回 2 会**立即中止 step** ⇒ `RC=$?` 与整个 `if` 分支**永不执行**。

**原始输出（用真实脚本，非自制替身）**：

```
===== 1) 直接跑（无 -e）= 作者写代码时假设的语义 =====
   脚本 EXIT=2
   GITHUB_OUTPUT: run=true

===== 2) 复刻 GH Actions 语义: bash --noprofile --norc -eo pipefail + ci.yml 那 6 行 step 正文 =====
   ⇒ STEP EXIT=2        ← step 红
   GITHUB_OUTPUT: run=true
   （step 自己那条 ::warning 未出现；stderr 里那两条 ::warning 是脚本内部 _degrade 打的，不是 step wrapper）
```

**⚠️ 更糟的第二层（同一根因）**：GitHub 的 step 级 `if:` 在不含状态函数时**隐式前置 `success()`**。所以 `Classify` step 一红，后续 `Run hermetic control-tower gate tests` 会被 **skip** ⇒ **不但 PR 红，重活还没跑** = 「红 + 该跑的没跑」双重失效。

**这违反脚本自己的契约**（非个人口味）。`ci-signal-classify.sh:31-33` 明文：

> `@degraded — base 不可解析或 git 不可用 ⇒ run=true（全量跑，绝不误跳）+ stderr 留痕 + exit 2。`
> `消费方据此「可见但不阻断」: 安全值（全量跑）已在效果上生效，不该把 PR 判红；铁律 11 —— 降级必须显式可见`

实现与契约相反。

**触发条件不是纯理论**——本仓库已有同源记录：`ci.yml:312` 自己的注释
`fetch-depth: 0  # D520: verify-parallel 豁免逻辑依赖 origin/main ref（depth=1 时缺失→误红）`
⇒ `origin/main` 在 CI 里**确实缺失过**，而「base ref 不可解析」正是分类器的降级条件之一。

**修法（复核员不改码，只给最小修）**：`RC=0` + `cmd || RC=$?`（或 `set +e`/`set -e` 包裹）。
**✅ coder-a 已按此修复，我已在 §5.4 用真实 step 正文复核通过（STEP EXIT=0）。**

**同类陷阱排查指引**：本仓库既有代码用 `if ! cmd; then` 是对的（`!` 豁免 errexit，见 ci.yml 的 CT for 循环）；裸 `cmd; RC=$?` 是错的。
已同步提醒 coder-b 自查其 `tests/win/vitest-log-level.test.sh`——**其自查结论：不适用**（详见 §6.6，登记为其声称，我未独立复核）。
