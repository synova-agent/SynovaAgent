## 3. 选择器新增 `--shard <i>/<n>`

- 语义：在既有「选择集」之上做分片过滤（与 `--platform` 正交）；
- 映射表声明分片总数 `shards.count`；`--shard n` 与映射表不符 ⇒ 显式 degraded + 全量回退；
- **参数校验 fail-closed**（不静默给空）：`4/3` 越界 → exit 2；`abc` 非数字 → exit 2；`1`（缺 `/n`）→ exit 2；
- 分片内 0 选中 ⇒ stderr `[D1061-SHARD] … selected_in_shard=0` + CI `::notice`（**显式可见，非静默跳过**）；
- `--list` 增列 `SHARD <id> :: <suite>` 与 `SHARDKEY count <n>`（可核派生）。

## 4. ci.yml 接线

```yaml

  os: [ubuntu-latest, windows-latest]
```

## 7. run 间计时方差声明 + 按较差 run 的**敏感性检查**（队长点名要补）

**事实**：PR-A 两次全绿 run 的 windows CT 腿 **630s（run 36528674633）/ 704s（run 36532607064）**，方差 **≈12%**
⇒ **单次 run 的逐套件表本就有噪声**，故必须声明分片表的输入取自哪一次，并给出「按较差 run 缩放是否仍达标」。

**分片表 LPT 输入**：取自 **630s 那次**（`run 36528674633`）的逐套件表（当时测得完整 43 标记 / 598s）。

**敏感性检查（按 704s 缩放全部已知成本，重算既有分配表，不含重排）**：

```
按 630s（较小者）→ 各分片 278 / 275 / 277s ｜ 最大 278s ｜ ≤300s: ✅
按 704s（较大者）→ 各分片 299 / 295 / 298s ｜ 最大 299s ｜ ≤300s: ✅（**余量仅 1s**）
对照 4 分片（同 704s 口径）→ 238 / 238 / 236 / 236s ｜ 最大 238s ｜ ≤300s: ✅（余量 62s）
```

### 7.1 ⚠️ 结论与建议（**余量 1s 是本卡要 CTO 看见的数字**）

- **3 分片在观测到的方差范围内仍达标**，但**最大分片 299s vs 判据 300s ⇒ 余量仅 1s**。
  下一次 run 若再偏慢 ~1%，即会**擦线超标** —— 这属于「达标但无鲁棒性」，不应按"已达标"归档。
- **4 分片**（同敏感性口径）最大 **238s**，余量 62s，**抗方差**。
- 代价：4 分片 ⇒ 必需检查名从 1 个变 **4 个**（CTO 需改分支保护）；`ubuntu` 面不受影响（job 名不变）。
- **建议**：若 CTO 认为"必需检查名多 3 个"可接受 → **取 4 分片**（鲁棒）；若坚持 3 个 → 3 分片可交，
  但请在裁定里**显式记录"余量 1s、抗方差能力弱"**。**本卡默认按 3 分片交付（按队长已裁的 3 分），并把 4 分片作为可选升级项呈报。**
