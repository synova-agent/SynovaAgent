## 3. 增量选项（**只提案，本卡不实施，请 CTO 裁定**）

### 选项 A — windows job 内并行跑（`xargs -P 2` / 分批）

- **做法**：把逐条 `bash "$t"` 的串行 for 循环改为 `printf '%s\n' "$TESTS" | xargs -P 2 -I{} bash -c '…'`，
  失败聚合逻辑（D956 注解）保留。
- **预估收益**：GitHub windows-latest runner 为 2–4 vCPU；按 CPU-bound 假设
  `570s / 2 ≈ 285s`、按 I/O-bound 打七折 `≈ 400s` ⇒ **≈ 285–400s（可能刚好达标）**。
- **风险（中高）**：
  1. **共享临时路径**：个别测试写固定路径（`/tmp/ct-out.log`、`/tmp/.synova-*`）⇒ 并行会互相覆盖。
     需先逐条审计 54 条测试的固定路径（**尚未做**）。
  2. **仓库内写入互斥**：多条测试写 `.claude/`、`.codex/`、`task-state/` 夹具目录 ⇒ 需确认全部在 `mktemp -d` 沙箱内。
  3. **失败聚合语义变化**：D956 注解段与 `d956-failmsg.test.sh` 夹具强耦合，改循环结构**必须同步夹具**。
  4. 8GB 本机无法预演（CI runner 与本机不同）；只能靠 CI 试。
- **性质**：**不改选择集**，不改门禁覆盖面 ⇒ 不削弱门禁。

### 选项 B — 把「非平台敏感的重套件」移出**必需** job

- **做法**：新建非必需 job（或 `continue-on-error: true` 的平行 job），承接
  `gate-failopen-net.test.sh`（120s）+ `ct-test-gate.test.sh`（15s）等**非平台敏感**重套件；
  必需 job 只留「变更相关 ∪ 平台敏感」。
- **预估收益**：windows 必需腿 `≈ 470 − 135 = 335s`；若连带迁出 `scan-fullwidth-vars`(21) 等 → **≈ 300s 附近**。
- **风险（高）**：**这就是删门禁的等价物** —— `gate-failopen-net` 是「门禁坏了能抓到」的 canary 之一，
  移出必需面 ⇒ 它红不再阻断合并。**须创始人/CTO 明确背书**；本卡红线明列「不删任何现有门禁」，故不实施。

### 选项 C — 攻三个重套件自身的耗时（最干净，但工作量在别的卡）

- **做法**：为 `alloc-task-id-lock`(99s) / `check-gate-integrity`(72s) / `gate-failopen-net`(120s)
  立独立卡，逐条做「自身耗时剖析 → 减少 sleep/轮询/重复子进程」，**不动覆盖面**。
- **预估收益**：三者合计 291s，若各砍一半 → `≈ 145s`，windows 必需腿 `≈ 325s`；配合选项 A 则稳妥达标。
- **风险（低）**：不改选择集、不改门禁语义；风险集中在"改测试自身"可能改变其判别力（需判别性夹具守住）。

### 选项 D — 把 windows 腿的「必需」定义改为 ubuntu 必需 + windows 夜间

- **做法**：windows CT 腿改为 `continue-on-error: true`（保留运行但非必需检查）。
- **风险（高）**：平台问题不再阻断合并 —— 与 D520「双平台矩阵」立项理由直接冲突。
- **本卡立场**：**不建议**，仅列出供 CTO 完整比较。

1. **先合本卡**（N1 + 选择器 + 子集）：把 65% 的确定性浪费砍掉，且**不削弱任何门禁**。

4. 选项 B / D **属门禁覆盖面决策**，不在工程侧自决范围，须 CTO/创始人裁定。
