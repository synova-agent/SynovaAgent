```
0 3 * * *    |   1 ms |     742 iterations | match

```

**退化输入规模**：

```
=== 含 '/' 或 '-' 的 cron 行数（真实 parseCronField 会退化为空集）===
rows_with_step_or_range: 383
rows_plain: 1309
```

**因果对照**：把 383 行退化输入从副本中删除（`synova-causal.db`，仓库外），同机同代码重启：

| | 实例1（原副本，1692 行 / 383 退化） | 实例2（删 383 退化行，1309 行） |
|---|---|---|
| Phase2c→2e | **143,128 ms** | **13,825 ms** |

**结论（B1）：启动阻塞 ~143 s 可归因于 `CronScheduler.restoreJobs()` × `nextCronTime()` 退化全扫——已由"删除即变快"的判别性对照实验证实。**

## 6. 遗留与复现须知

1. **日志文件是 UTF-16LE**（PowerShell `*>` 重定向所致，首 2 字节 `FF FE`）。直接按 UTF-8 读会得到 0 条记录（我首轮踩坑）。复现者请按 BOM 判编码，或改走 `cmd /c ... > log`。
2. **`npx tsx` 的父进程不是服务进程**：`tsx cli`（PID A）→ 子 node（PID B，实际服务）。清理必须用 `taskkill /PID <wrapper> /T /F` 树杀，**禁 `taskkill //IM node.exe`**。本次仅杀自起两棵进程树，残留检查 = 0，端口 18891/18892 均回落 0。
3. **临时物均在仓库外**：`%TEMP%\synova-1432\`（库副本、因果变体库、探针脚本、日志、SSE）。仓库内本次仅新增本证据文件。
4. 未做：独立自验员复跑、④参数/⑤导航段验证、哨兵定时自跑（`last_sentinel_run` 仍 degraded）、桌面端连通性。
