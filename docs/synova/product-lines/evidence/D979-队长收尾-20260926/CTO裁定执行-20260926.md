### 2.2 为什么"逐件 rebase 到 main"不等价于"每件孤立"

栈式分支里，#815 含 #809 的提交、#820 含 #815 的、依此类推。
**把 #815 rebase 到 main 并不会剥掉 #809 的提交**（#809 未合并进 main，仍是 #815 的祖先）
⇒ rebase 后 #815 相对 main 仍是 **9 文件**、#820 **18 文件**、#823 **31 文件**，**全部超出 12 文件 PR 预算**（D734 ① 会红）。

⇒ 单靠 rebase **无法**让每件拿到"孤立 diff + 自己的 CI 结论"。
唯一能让 diff 逐层收缩的机制是**按序合并**（lower PR 进 main 后，GitHub 自动 retarget 上层 base，diff 与 CI 才逐层孤立）。

### 2.3 卡在哪一条规则上（**我停手的原因，非技术困难**）

- **按序合** 需要合并权限 —— 而裁定三② 明写「门禁语义变更（D328 判定 + 归属表）未过 K3 前不得合并」，且合并属 CTO 收件闸；我无权自行合并。
- **rebase** 需要 **force push** —— 我的现行红线明文「禁 force push」，且本批 7 条分支互为父子（`#819` 基于 `#815`、`#825` 基于 `#823`），force push 任一条会连带打断下游证据分支。
- **`PATCH /pulls/N {base: main}`**（只改 PR base、不重写历史）实测**亦不达标**：diff 会膨胀为累计内容（#820 变 18 文件、#823 变 31），D734 ① 直接红。
- **`feat/*` 镜像推送**（触发 `push: [main, feat/*]` 让 CI 跑到同一 SHA）能拿到 check-run，但跑的是**累积内容**，恰是裁定三① 禁止的「栈式状态当已过闸」。
