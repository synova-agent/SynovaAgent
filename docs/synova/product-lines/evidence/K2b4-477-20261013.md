## §2 设计（CTO 裁定 ②①「定新状态/新字段」——命名与形态由实施席定并给理由）

**决定：新增一个与 `status` 正交的轴 `calibration`，而非改 `status` 取值。**

```ts
export type EdgeParamCalibration = 'formula' | 'declared_unknown' | 'other';
//  · formula           已标定：形如 `<标识符> = <非空右侧>` 的赋值式（散文公式）
//  · declared_unknown  未标定：**边文件自己声明**该值未知（串**全串**等于 `unknown`）
//  · other             上两类之外的一切（占位串 / 声明串 / P-3 值域 / 缺键 / 非法形态 …），兜底
```

**命名理由（采纳卡面 §⑥① 的建议名，补理由）**：
- `declared_unknown` —— 直译「**被声明的**未知」。卡面 §〇⑦ 给的 DSH 借鉴方向是「**按名声明、宿主满足**」：
  `transfer_function: "unknown"` 本身就是**边文件作出的声明**，loader 只是**识别声明**、不是"猜"。
- `formula` —— 正向**形态**判据（赋值式），不是"看起来像散文就发已标定证"。
- `other` —— 兜底且**不猜**：未登记形态一律落这里。

**🔴 为什么正交而不改 `status`（本卡的关键工程约束）**：`status` 是**既有消费面**——
`tests/ontology/k4-05bis-edge-vocabulary-1350.test.ts:257` 逐字断言
`expect(statuses).toEqual(['prose_formula', 'prose_formula'])`（两件 `unknown` 边）。
该文件**不在本卡写集**（卡面 Q2 边界）⇒ 改 `status` 会打破写集外消费者；
本卡属**读路径** ⇒ **只加轴、不动既有语义** ⇒ 消费面**零破坏**（§5 用 12 件回归 + tsc 双向实证）。

**两条判据边界（写死在实现里）**：
```ts
const DECLARED_UNKNOWN_RE = /^unknown$/i;                  // 全串相等 —— 不做子串匹配（防 unknown_v2 类假阳）
const FORMULA_SHAPE_RE = /^[A-Za-z_][A-Za-z0-9_]*\s*=\s*\S/; // 只判形态，不判数学/语义正确性
```

## §8 它测不出什么（逐条）

1. **只判形态，不判正确性**：`lhs = rhs` 形态即 `formula` —— **公式写得对不对、量纲/符号是否合理，一律不判**
   （M4 只证明"拆掉赋值号会掉出 formula"，不证明"留下的公式是对的"）。
2. **`declared_unknown` 只认全串 `unknown`**：`unknown(待补)` / `待定` / `n/a` 等变体落 `other`
   （`n/a` 另被占位族接走 ⇒ `placeholder`）。**变体要进 `declared_unknown` 必须显式改规则**（判据变更，非本卡）。
3. **`other` 是兜底桶**（含 `resolved` 的 P-3 值域）：**单独看 `calibration` 分不清"可注入"** ⇒ 调用方必须**同时**读 `status`。
4. **不判"还差多少条标定"的绝对真值**：可数性**只在给定登记面下**成立；登记面（`TFR_E_TO_FILE` 等）是**手写面**，
   抓不到"清单与磁盘被一起改成同一错误"（所有具名清单类判据的共性边界）。
5. **本卡不改 `extensions/**`**：真正的"边文件显式声明字段"（如 `transfer_function_status`）**未落地** ——
   本卡做的是**识别既有声明**（串 `unknown`），不是**新增声明载体**（属另卡，见 U-3）。
6. **本卡未跑全量套件** ⇒ 不声称全量绿；全量差集口径须另跑（本仓口径：两次跑交 ∩）。
7. **判据源与测试件不是互为证明**：探针读**文档逐字**、本件读 **loader 分类**；M5 只证明两者在**同一输入**上同向，
   不证明"两者都错时还能发现"。
8. **loader 判定必须经 vitest，裸 `node`/`tsx` 探针不可行**（复核席补的口径，2026-10-13）：
   `src/l4/ontology-loader.ts` 依赖 `@synova/logger`，而该别名**只在 vitest 配置里解析** ⇒ 任何"直连 loader 的裸 `node`/`tsx` 探针"
   会因模块解析失败而**测不到 loader 行为**（不是"绿"，是"跑不起来"）。⇒ 本卡一切 loader 面读数**只能**来自 vitest 运行面；
   本件 §3/§5 的读数均为 vitest 产出，**未**声称任何裸运行时验证。
