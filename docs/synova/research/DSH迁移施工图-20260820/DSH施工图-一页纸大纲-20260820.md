## 战略判断（一句话）

**终态锁定 A 形态：DSH 壳 + Synova 核心独立服务 + MCP 边界；但路径分四阶段走，种子客户部署永远优先，迁移永不阻塞部署。**

依据：8-16 研究（七章，证据充分）+ 本次代码实证。核心直觉是对的——本体、测量器、哨兵、专家才是命根子；harness 通用工程已被 DSH 底座化，继续自研是重复造轮子。

## 已验证的两个关键事实

- **DSH 许可证 = MIT（DeepSeek, 2026）**：可商用、可保留自己品牌，义务仅为保留版权声明。✅
- **DSH 版本 = v0.1.0-rc.5 开发者预览**：官方明示"将有破坏性变更"。→ 现在直接依赖它 = 把产品地基打在流沙上。**所以借鉴现在做，依赖 Q4 再建。**

## 多客户命门：客户配置包（详版 §5.4，必须读）

**引擎只有一套，每个客户一份"调校单"**：默认值 → 行业包 → 客户包 → 工作区，四层叠加；签新客户的全部技术动作 = 复制模板文件夹、填配置，**零代码改动**。这直接决定"部署第二家客户是一周还是三个月"，也是反定位咨询公司的物理实现。顺带解决：① 数据合规（客户A的校准只写进客户A的包，不串客户）；② 自进化落点（校准产出写回客户包、可回滚可审计，普适规律经创始人审核后才升格全局方法论）。借鉴 DSH profile/bundle 分层思想，在核心服务内实现，Stage 2 做雏形。

## 权限管理（详版 §5.5）

现有五角色 RBAC（admin/manager/liaison/staff/ga + 模板派生）底子完整；**DSH 无企业多用户概念 = 双缺差异化机会**，权限建在核心服务里，永远归你。部署客户A前四要素逐项实测：数据边界 / 动作权限（GA 验证·否决·仲裁）/ 审计留痕 / 跨客户隔离（含自己团队的运营访问）。

## 自进化（详版 §5.3）

分级走：E1 数据回流校准（人审）= **修好并闭环已有的 `packages/evolution` L0 引擎**（N13 断裂是其一环，客户A验收项）→ E2 低风险参数自动回流（带审批闸）→ E3 运行时自调整（DSH 实验性功能，等成熟）。红线：不宣称"越用越准"直到 E1 有数据证明。

## 四阶段序列（绞杀者模式，每阶段可交付可回退）

```
Stage 0  部署验收后  死代码清理 + AGENTS.md 漂移修正（部署前只动文档与配置）
Stage 1  9~10月    范式借鉴（不引 DSH 依赖）：事件溯源/Notes四态/snapshot/guard
Stage 2  10~11月   MCP 边界收敛：核心服务化、契约固化、混合模块拆家、客户配置包雏形
Stage 3  Q4评估后   DSH 壳试点：synova profile 影子运行，与现有部署并行
Stage 4  切换       影子验证通过 → 切流量 + 存量数据零丢失 → 旧 harness 打 tag 归档
```

Stage 3 的入场券三条件：**客户A首季度数据回收 + DSH 脱离 rc 预览 + 收益值一个额外运行时进程**。缺一不开工；第三问答案弱则 Stage 3 合法永久挂起。

## 旧 harness 三幕处置

1. **冻结**（现在起）：不再长新功能，只修部署相关 bug
2. **逐块替换验证后删除**（Stage 3-4）：遵循铁律 37（删除+grep 零引用）
3. **归档进 git tag**（`archive/pre-dsh-harness`）：**不另起工作区**——git 历史就是归档库

例外：🟡 治理层原样保留继续服役（多 Agent 开发流水线靠它运转），移植是独立节奏。

## 三条红线

1. Stage 3 之前**不引任何 DSH 代码依赖**（rc.5 破坏性变更承诺）
2. **不复制 OpenViking 代码**（AGPLv3 传染），只用 HTTP 接口或借鉴理念
3. 任何阶段验收必须含**接线审计**（历史上 4 次"组件通过测试但从未被调用"）
