## 5. 目标架构（A 形态终态）

```
┌─ 品牌层（客户可见，100% 自有）──────────────────────────┐
│  Synova 报表/仪表盘（app/）· 桌面壳（electron/）· 方法论   │
│  命名（42边/7专家/增长导航）· synova profile 皮肤          │
├─ DSH 壳（运行时，客户不可见）───────────────────────────┤
│  synova profile = dsh-base（模型/工具/持久化/沙箱/审批）    │
│                + synova-core 插件（经 mcp-client 消费 ↓）   │
│                + synova-gates（治理层移植：verify/hooks）   │
├─ MCP 边界（契约层）─────────────────────────────────────┤
│  输入：企业数据/问卷/连接器  输出：诊断报告/工单/增长方案      │
│  契约固化于 Stage 2，版本化，向后兼容                        │
├─ Synova 核心独立服务（现有代码演进而来）──────────────────┤
│  🟢 全部领域核心 + routes/mcp 表层                         │
│  保持独立可运行：不依赖 DSH 也能服务（=可逆性/反锁定）        │
└──────────────────────────────────────────────────────────┘
```

**品牌的三个锚点**：① 产品表层（app/electron/报告模板）② 方法论命名与数据（42 边、专家体系、积累的组织数据）③ profile/bundle 是 DSH 官方的品牌组合机制。**runtime 不可见，客户从头到尾只看到 Synova。**

**反锁定设计**：核心服务不 import 任何 DSH 包，只出 MCP/HTTP 契约。DSH 壳是消费者之一。将来换底座（DSH 方向变了/自建薄壳），核心不动。

### 5.1 "未来无限拓展"在终态里如何保证

"无限拓展"需求在 A 形态终态里有**三层扩展通道**，全部保留、互不阻塞：

1. **核心服务内部（主通道，不受影响）**：文件驱动体系原样保留——新增行业模板、新专家、新技能、新本体边 = 往 `extensions/`、`expert/`、`skills/` 放文件，loader 扫描即生效，**零代码改动**。DSH 壳不碰这一层。
2. **MCP 契约层**：新增诊断能力（新报告类型、新工单类型）时扩展 MCP 工具集，契约版本化、向后兼容。
3. **DSH 壳层（额外多出来的一层）**：Cordis 插件组合提供运行时扩展（新模型适配、新工具、新表面）——这是迁移后**白赚**的扩展位，不替代前两层。

一句话：**场景拓展能力（行业/专家/技能/边）长在你的核心服务里，永远归你；DSH 只提供运行时扩展，且是增量不是替代。**

### 5.3 自进化路线（分级定义 + 红线 + 正确顺序）

"自进化"必须分级谈，否则会把产品信任赌进去：

| 级 | 形态 | 机制 | 状态 |
|---|---|---|---|
| **E0** 人工迭代 | 人改文件 → 生效 | 现有文件驱动体系 | ✅ 现状 |
| **E1** 数据回流校准（半自动） | 部署数据 → 校准建议 → **人审** → 更新规则/阈值 | GA 闭环（S4）+ N13 反馈回流 + 知识沉淀（S5-3） | ⚠️ N13 断裂待修，**这是客户A部署的验收项** |
| **E2** 规则自动回流（带审批闸） | 低风险参数（阈值/权重）自动调；规则级变更仍人审 | 前置：事件溯源可回放（D1）+ snapshot 可复现（D3）+ 准确率度量（`sentinel-accuracy.ts` **已存在**） | 🔜 E1 跑通 + Stage 1 基建落地后 |
| **E3** 运行时自调整 | agent 检查/挂载自己的插件 | DSH creative 模式 / self-modification 包——**DSH 官方自己标注为实验性** | ⏸️ 等 DSH 成熟 + 多客户数据规模 |

**重要事实**：E1 不是从零开始——`packages/evolution` 已实现 L0 自我进化引擎三层结构（SessionLearner 会话内学习·内存级 / OrgAdapter 组织自适应·持久化 / GlobalAnalyzer 全局进化·行业聚合 + 规则版本管理 RuleVersionManager），且**已接线**（`routes/evolution.ts`、`routes/ga-evolution.ts`、`post-diagnosis-processor`、`sentinel/runner`、L3 诊断引擎均消费）。E1 的真实含义是**修好并闭环已有引擎**——N13 断裂（C线 S5-1）正是其中一环——而不是新建一套机制。这也让 E1 的工作量显著低于"从零构建"的直觉估计。

**三条红线（重申 8-16 研究 §7.4，一条不能松）**：

1. **不宣称"越用越准/自我进化"，直到 E1 闭环真实跑通并有数据证明。** 客户A部署期对外话术禁用此类表述。
2. **诊断结论影响企业经营决策**——一条自动回流的错误规则可能误导客户。信任（C 线 S0"让老板放下直觉相信系统"）是产品核心价值，自进化必须证据门禁化，不能为了炫技牺牲可信度。
3. **架构上现在预留接缝，但不提前启用全自动**：事件溯源（可回放审计）+ Agent Notes（结构化沉淀）+ feedback log-only（干净反馈流）三个接缝在 Stage 1 就建好，E2/E3 将来直接插上。

**正确顺序**：E1 先做扎实——它本身就是产品卖点（人机协同 GA 闭环），不是自进化的妥协版 → Stage 1 建基建（D1/D3/D4）→ E2 只放开低风险参数 → E3 等外部条件成熟。**自进化对 Synova 的正确形态不是"AI 自己改自己"，而是"每服务一个客户，方法论资产就厚一分"——这个资产沉淀在 `extensions/`、`expert/`、`knowledge/` 里，归你所有，不随任何 harness 迁移。**

### 5.4 客户配置包详解（多客户时代的命门机制）

**问题**：今天阈值、边权重、启用专家集、提示词、报告样式全是**全局一套**。服务客户A一家时无所谓；服务五家不同行业的客户时，同一条"现金流预警线"不可能同时适用于外贸母婴（账期长、季节性）和软件公司（预付年费制）。要么改全局（客户间互相打架），要么改代码（每客户分叉，死路一条）。

**机制：四层叠加，引擎不变，每客户一份"调校单"**：

```
Layer 0  全局默认    产品出厂的方法论默认（42边定义、默认阈值、全专家启用）
   ↑ 覆盖
Layer 1  行业包      extensions/industries/{制造业|外贸|母婴…} 的行业级覆盖
   ↑ 覆盖
Layer 2  客户包      customers/{客户A}/ —— 连接器凭证、校准后阈值、启用哨兵集、
                     报告品牌（logo/配色）、GA 审批人、飞书 webhook、角色模板微调
   ↑ 覆盖
Layer 3  工作区包    客户内部部门/子组织的局部覆盖（厂长看生产数据、外贸经理看客户循环）
```

运行时计算客户 X 的诊断 = `merge(L0, L1, L2, L3)`——每层只写自己与上层不同的部分。**新增一个客户的全部动作 = 复制模板文件夹、填配置，零代码改动。**这就是"边际成本趋零、反定位传统咨询公司"的物理实现。

**客户A客户包内容示例**：① 连接器凭证（ERP/飞书，存 credential-vault，按客户隔离）② 数据字段映射（他们的 ERP 字段 → 本体节点）③ 哨兵启用集 + 校准阈值 ④ 行业包引用（产销一体外贸型）⑤ 报告品牌定制 ⑥ 权限角色实例（老板=admin、对接人=liaison、中层=manager、GA 审批人=ga + 合同到期约束）

**与自进化（§5.3）的关系**：E1 校准产出**写回客户包**（版本化、可审计、可回滚），不污染全局方法论；只有被创始人审核确认具有普适性的规律，才升格进 `extensions/`/`expert/` 全局资产。**客户数据养客户的调校单，跨客户只沉淀方法论，不串数据**——这同时解决了数据边界合规问题。

**对 DSH 的借鉴点**：profile/bundle 的"有序层级、上层覆盖下层、`--dump-config` 可检查实际生效配置"三件套，原样搬到客户配置包。实现位置在核心服务内，Stage 2（MCP 边界收敛）同期做雏形。

### 5.5 企业多用户权限管理

**现状实证**（main 快照）：`middleware/rbac.ts` 已有五角色 `admin / manager / liaison / staff / ga` + `RoleTemplate`/`BUILTIN_TEMPLATES` 模板派生权限 + 工作区级 `canAccessWorkspace`/`canModifyWorkspace` + GA 角色专属约束（含合同到期 `contractExpiry`）。**底子比预想完整**，但 A 线审计标注"企业多用户仅设计未全量验证"（A5）。

**完整四要素**（部署客户A前必须逐项实测）：

| 要素 | 内容 | 现状 |
|---|---|---|
| 数据边界 | 薪酬类数据仅老板+HR 可见；部门级可见性；诊断报告分级 | ⚠️ 工作区级已有，数据类目级待验证 |
| 动作权限 | 谁能触发诊断 / 谁在 GA 里验证·否决·仲裁（C线 S5-2）/ 谁能接数据源 / 谁能邀请用户 | ⚠️ 模板有雏形，真实接线待验证 |
| 审计 | 谁在何时看了什么、改了什么、批了什么 | ✅ 事件溯源（D1/B1）落地后天然获得 |
| 凭证与跨客户隔离 | 每客户凭证独立（credential-vault）；**Synova 运营人员的支持访问也要被权限管住** | ⚠️ 待验证 |

**与 DSH 的关系**：DSH 定位单 agent 单机，**没有企业多用户概念**——这不是弱点，是 8-16 研究认定的【双缺】差异化机会（S9）。权限体系建在核心服务里（🟢 做深），DSH 壳不提供也不冲突。**对客户讲的故事：别人给你的是一个 agent，Synova 给你的是全公司分级使用、责任可追溯的诊断系统。**

**与客户配置包的衔接**：角色模板的客户级微调（比如客户A要加一个"厂长"角色）作为客户包的一部分下发，全局模板不动。
