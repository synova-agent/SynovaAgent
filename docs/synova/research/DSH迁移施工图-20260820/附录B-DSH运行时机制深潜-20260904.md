## 1. LLM 适配 seam + 重试（dsh-llm / dsh-llm-deepseek / dsh-llm-retry）

### 机制综述

DSH 的 LLM 层是三层分离：**dsh-llm** 定义 provider 无关的抽象服务 `LlmRuntime`（adapter 注册表 + 可被 `llm/stream` waterfall 拦截的流式调用 API）和抽象基类 `LlmAdapter`；**dsh-llm-deepseek** 是第一个真实适配器（直连 fetch 的 chat-completions 实现），负责把 HTTP 状态码/错误文案归类为稳定错误码；**dsh-llm-retry** 是独立插件，挂在 agent loop 的 `agent/request-error` 恢复扩展点上执行 provider 拥有的重试策略。关键设计：重试策略归 **provider（adapter）** 所有而非重试插件所有（`RetryPolicySchema` 嵌在每个 provider 配置里），重试计数器本身是**会话事件溯源投影**（`llmRetry` projection），使重试状态跨进程恢复、可回放。错误分类用"稳定机器码 vs 人类消息"二分（`HarnessError.code`，注释明确写"route on this, never by parsing message"），并用正则集合识别各家 provider 的 context-overflow/quota 文案。

### 对 Synova 的借鉴要点

Synova 的 `providers/`（DeepSeek/OpenAI/Gateway）应收敛为一个 `LlmAdapter` 式窄接口（`providerInfo/providerRetryPolicy/resolveModel/prepareCall→stream`），把 HTTP→错误码归类和 `Retry-After` 解析压进 adapter 层，编排层只 route on `code`（对齐铁律 32 的 `.code/.phase/.retryable`）。最值得抄的是 **重试计数 = 事件溯源投影**：把每次重试意图/启动写成 append-only 事件（等价于 `llm/retry`），Sentinel 长跑任务的重试就能跨进程恢复、可审计；以及 **重试策略由 provider 配置拥有** 而非重试器拥有，让不同 LLM 供应商可声明不同 `retryableCodes`。

## 2. token 计量 / 预算（dsh-token-meter）

### 机制综述

`ctx.tokenMeter` 是**单一 replay-aware 计量服务**：它把会话事件流折算成三种 O(1) 状态投影（用量 `tokenUsage`、上下文压力 `contextPressure`、构成 `contextBreakdown`），同时维护一个按节点计价的"model-visible 表面"供 `measure()` 输出。计量口径：provider 上报的四桶 `uncachedInputTokens / outputTokens / cacheReadTokens / cacheWriteTokens`（缓存读写分开计）；启发式估价按固定密度 `CHARS_PER_TOKEN=4`、每 block 结构开销 4 token 递归计价 text/reasoning/tool-call/tool-result，图片走 route 专属定价。**该包本身没有预算/上限强制机制**——它只产出 `pressureTokens/projectedTokens/contextWindow` 等数字；阈值判定和压缩动作属于 dsh-compaction-basic（见 §5）。投影状态必须 O(1)（要整包 checkpoint 持久化），因此替换范围的价格通过"影子价格协议"传递：替换前紧邻 append 一条 `compaction/summary` 或 `compaction/prune` 事件携带 `shadowedTokenCount`，折算器武装一个 claim、由紧随的 replace 事件消费。

### 对 Synova 的借鉴要点

Synova 的 Sentinel/诊断长对话需要同款"**计量即投影**"范式：token 用量和上下文压力不是临时变量，而是从会话日志折叠出的持久状态（进程重启可恢复、UI 可直读），Compaction 触发器只消费数字不做测量。优先抄三件：四桶用量（缓存读写分离，DeepSeek 缓存定价差异大）、`projectedTokens`（把样本后表面增量外推，避免"压力读数永远滞后一个请求"）、以及 `plan/commit` 两段式折算（先全量校验再变异，坏事件永不半应用——直接对齐铁律 24/31 的可审计降级）。

## 3. 定时调度与冷恢复（dsh-schedule）

### 机制综述

`dsh-schedule` 提供 agent 级的 after/at/every 三种提醒（"Agent-scoped durable after, at, and fixed-rate reminders over the session event log"）。**没有独立的 job 持久化文件**：job（reminder）定义就是 frozen 记录 `{id, kind, prompt, afterSeconds|at|everySeconds, scheduledAt}`，其 create/delete/dispatch 全部以 `schedule/change` 事件写进所属会话的事件日志；"持久化在哪"的答案是**会话 JSONL 日志本身**（经 `ctx.sessions.flush` 持久化屏障落盘）。冷恢复没有专门函数——它是**结构性的**：每次唤醒都从事件日志重折（`foldScheduleEvents`），进程重启后 `ScheduleRuntime.start()` 第一次 `driveOnce()` 就重折出全部活跃 reminder，`dueDecision` 对错过的 every 触发点**不枚举、只取最新一个到期 occurrence 批量补发**（"skip missed occurrences, and batch one latest occurrence per overdue rule"）。投递是 session-local 的：会话活着才准点触发，否则变 overdue 直到会话恢复；工具描述 `CREATE_DESCRIPTION` 原文即如此声明。`at` 规则支持 IANA 时区 + 本地日期时间 + DST 解析（`resolveLocalInstant`/`canonicalizeTimeZone`）。

## 4. 会话事件溯源（dsh-session / -persistence-jsonl / -projection / -query-sqlite）

### 机制综述

`dsh-session` 是整个系统的心脏：`Session` 持有严格 append-only 的事件日志（`seq = log.length` 连续契约），**log 是唯一事实源，"model-visible 表面"是从日志派生的投影**——`user/message / assistant/message / tool/result` 三类事件必须带 `surfaceOp` 标记（`append` 或 `replace{start,end}`）声明自己如何进入表面，非表面类型携带标记直接抛错。模型可见⟺已记录的强制点有两处：① `Session.append()` 在入口做 JSON 可序列化快照 + surface 合同校验（replace 必须完整覆盖被影子化节点、`sourceEventSeqs` 必须唯一且更早、tool/result 替换只许改 content）；② agent loop 构造请求时用 `session.deriveMessages()`（日志派生），不存在第二条内存消息通道——dsh-agent-presets 的注释原文："it is required outright by the repo's model-visible ⟺ logged rule"。JSONL 后端把日志落成 per-project/session 目录（可 zstd 压缩、torn-tail 恢复）；`dsh-session-projection` 提供带 `stateVersion` 版本化和 checkpoint 恢复的投影注册表（§1 重试计数、§2 token 计量、§5 压缩状态全部 ride 在上面）；`dsh-session-query-sqlite` 把已持久化会话索引进 SQLite FTS5 供全局搜索。

## 5. 上下文压缩（dsh-compaction / -basic / -tool-result-pruner）

### 机制综述

压缩是"**摘要替换，不删日志**"：`dsh-compaction` 定义抽象 seam（`ctx.compaction`，子类拥有触发策略/保留策略/摘要器），`dsh-compaction-basic` 是默认实现，`dsh-compaction-tool-result-pruner` 是模型无关的预处理。触发条件两条路：① **压力触发**——每步开始（`agent/pre-step` 钩子）用 token meter 测 `totalTokens`，≥ `thresholdTokens = contextWindow × thresholdRatio`（默认 0.8）则压缩；② **溢出恢复**——`agent/request-error` 钩子上 `failure.code === CONTEXT_WINDOW_EXCEEDED` 时强制压缩（绕过阈值，retain=0）并 `{kind:"retry"}` 重试请求。basic 策略：头锚定选择压缩范围，按 token 从尾往前累计保留 `retainTokens`（默认 `contextWindow × retainRatio`，0.16）的 verbatim 尾部，且绝不切开 assistant tool-call/result 配对（`toolPairingBalancedBefore/After`）。压缩执行：append `compaction/start`（兼作 durable 锁）→ 用**当前会话自己的 system prompt + tools + 被压缩区消息前缀**调 `ctx.llm.stream()`（摘要指令作为最后一条 user message 追加——这是刻意的 KV-cache 复用设计）→ append `compaction/summary`（含 `shadowedRange/shadowedSeqs/shadowedTokenCount` 影子价格）→ append 带框摘要的 `user/message`（`surfaceOp:{op:"replace",start,end}` + `sourceEventSeqs` 引用）→ append `compaction/end`；摘要必须严格小于被影子内容，否则 fail loud。回指方式：替换节点文本被 `<compacted-summary>…</compacted-summary>` 标签包裹 + 前言"This is an automatically generated checkpoint…"，且旧摘要块若存在会被指令要求合并而非照抄。tool-result-pruner：对每个超 `thresholdChars`（默认 8192）的 tool/result 文本做头 4096 + `[… middle pruned …]` + 尾 1024 的确定性裁剪，同样走 `compaction/prune` 影子价格 + `tool/result` replace 事件，"replay-safe"指替换规则是确定性的（同输入同输出），重放可重建。

## 6. 预设与人格（dsh-agent-presets / dsh-persona）

### 机制综述

**preset = 一个目录**，目录里必须有组合文件 `agent.cordis.yml`（Cordis `Include` 可加载的插件行列表），旁边可选 `preset.yml` 显示元数据（`name/description/order`，只承载显示文本——`id` 是目录名、`trust` 来自发现根，都不可在此声明，防止本地预设伪装成官方）。组合文件是插件行列表：每行 `{name, disabled?, group?}`，`name` 按 `classifyRowSpecifier` 分为 `cordis:` 内建 / `./` 相对（预设自带文件）/ `file:` 与绝对路径 / 包名四类；`disabled` 支持字面量或 `!!js` 表达式。**模型/工具/系统提示词/权限全部以"挂载对应插件行"表达**：preset 不自带 schema 字段，而是通过组合行挂 `dsh-agent-default-model`（模型）、`dsh-persona`（人格）、工具包、`dsh-permission-presets` 等实现能力差异。挂载（`mountPreset`）在 agent 的 **scope context** 下 plug 子树，`ctx.tools`/`ctx.systemPrompt` 注册随 agent 生命周期 unwind；两道护栏：未达可用状态的行被拒、向 root realm 泄漏服务的行被拒（`leakedServices` 检查）。发现根分 `.system`（随部署，只读）与 `.agent-presets`（用户可写）；authoring 只允许整目录拷贝（不收组合文本，"authoring grants no capability the copied preset did not already carry"）。**多层叠加不是字段 merge 而是作用域 layering**：全局组合（部署层）→ agent preset 子树（per-session 层）→ 会话内选择（`agent-preset/selected` 事件）；同名 service 越接近 agent 作用域越优先（Cordis 作用域语义，推断——未见显式 merge 函数）。`dsh-persona` 是 scope-only 插件行：`{text, complete, includeRuntimeContext}`，向 `ctx.systemPrompt.section()` 注册名为 `deployment:persona`（`PERSONA_SECTION`）的 section，放在 `DEPLOYMENT_PERSONA`（order 0）槽位，仅遮蔽本会话的部署人格；全局挂载会与注册表自身注册冲突并 fail loud。

## 7. 配置分层（dsh-settings / dsh-settings-file）

### 机制综述

`ctx.settings` 是抽象 settings seam：provider 存一个按 namespace 分节的原始文档；每个插件注册自己的 namespace schema（schemastery），读取时按固定顺序叠加 **schema 默认值 → 注册方组合 `base` 层 → 用户文档该 namespace 节**（`register` 的 docstring 原文："layers schema defaults, the registrant's composition `base`, and the user document section, in that order"）。合并算法 `mergeLayers`：plain object 递归合并，其余值（含数组）整值替换；写路径 `cloneJsonShaped` 剥离 `undefined` 实现 sparse-patch 不抹掉下层 key。`dsh-settings-file` 是文件 provider：默认 `<dshHome>/settings.yaml`（支持 .yaml/.yml/.json），chokidar 监视外部编辑热发布（自写抑制 = 文本缓存比对），写路径 = `withFileLock` 跨进程文件锁 → 先从磁盘 reconcile → YAML `patchNode` **注释保留的叶子级 diff**（改一个 key 不动兄弟 key 的注释/锚点/格式）→ `writeFileAtomic`（mode 0600）。**"dump-config 可检查实际生效配置"在 `dsh` CLI 包实现**：`dsh --profile <name> --dump-config`（互斥选项 `--dump-default-config`）→ `runDumpConfig(profile, defaultOnly, patches)` —— 不启动进程、不求值 `!!js`，把 profile 的 patch 层栈（每 bundle 一层 + profile 自身 patch 文件 + home patch 文件 + 每个 `--patch` 覆盖层）经 `renderConfigDump` 渲染成带来源注释的组合树打印。profile 定义为"an ordered stack of plugin-bundle patch layers under your own overrides"（`dsh` CLI 描述原文）。

### 对 Synova 的借鉴要点

## 8. 后台作业 + webhook（dsh-jobs / dsh-jobs-local / dsh-webhook / dsh-webhook-github）

### 机制综述

`dsh-jobs` 定义抽象 `ctx.jobs`（`JobRegistry`，子类实现），`dsh-jobs-local` 是进程内存实现（**作业不持久化**：进程重启即失，与 §3 schedule 的持久化形成对比——DSH 把"提醒/定时"归日志、把"伴随会话的长跑工具工作"归内存）。生命周期：`start(spec)` 校验（必须有 job controller 服务该 owner、kind/label 非空、owner 活跃作业数 < `maxConcurrentJobsPerOwner`（默认 10））→ 生成 `<kind>-N` id → 记录 `{status:"running", startedAt, reported:false, settled promise}` → 生产者的 `done` promise 结算；终态三类 `completed/killed/failed`（settlement first-wins，迟到生产者无效）；`kill()` → `cancel(reason)` + status `stopping`；teardown（owner dispose 或服务 dispose）→ cancel + await settled + 删记录，抛异常的 cancel 强制 fail 该记录并报告"可能孤儿"。owner 隔离：有 owner 的 job 只能被同 session id 的 caller 读/停（`assertAccess`，注释："Ids are predictable, so authorization — not secrecy — is the boundary"）；completion listener 和 change observer 按 scope 分层（`ScopedLayers`），只投递给 owner 作用域链上的注册者。`dsh-webhook` 是 provider 无关的 fire-and-forget 规则运行时：适配器投递 frozen delivery `{kind, source, deliveryId, receivedAt, ...}` → `dispatch` 同步启动所有匹配 kind 的规则 → 规则 `run(delivery, signal)` 返回 null 或 Session 请求 `{workspacePath, title, prompt, agentPreset, permissionPreset, model?}` → `createWebhookSession` 创建 Workspace 挂载的根 Session（失败逐级回滚：detach workspace → dispose agent）。**投递保证 = 无**：fire-and-forget，202 在内存 dispatch 后立即返回，不等待规则结算，不重试（失败仅 logger.warn）——可靠性靠 GitHub 的 webhook 重投机制兜底（推断）。`dsh-webhook-github` 是签名适配器：强制 POST + JSON content-type、Content-Length 声明校验 + 流式字节上限、`x-hub-signature-256` 用 `@octokit/webhooks` HMAC 验签（secret 走 credential seam，未配置返回 503）、三个 GitHub 头必填且唯一（`headersDistinct` 防头注入歧义）、验证通过才 parse JSON。

### 对 Synova 的借鉴要点

Synova 若做"外部事件 → Agent 任务"入口（如客户系统 webhook 触发按需诊断），DSH 的分层值得照抄：**传输适配器（验签/限长/头校验 → 统一 delivery 形状）与规则运行时（fire-and-forget dispatch → 创建带 preset 的会话）彻底分离**，每条投递进会话时带完整来源 provenance（`source:{kind:"webhook", deliveryId, ruleId}`），审计链免费获得。后台作业方面，`maxConcurrentJobsPerOwner` + owner-scoped listener 分层 + `reported` 标记是三个低成本即可抄的细节；但要注意 DSH 作业**不持久化**，Synova Sentinel 工单这类必须跨重启的作业应走 §3 的日志投影路线而非此路线。

## 附录：快速速览（各 2-3 句）

**dsh-invariants（不变量强制机制）** — `lib/index.js`（123 行）：`class InvariantRegistry extends Service` + `class InvariantError extends Error`（`code="INVARIANT"`，`packageName` 归属）。每个包在自己的 `lib/invariant.js` companion 插件（如 dsh-session 的 `session-invariant`、dsh-compaction 的 compaction invariant）里向注册表登记运行时不变量检查（如会话日志的 turn/step 配对、seq 连续性），支持 `package_allowlist`/`package_blocklist` 正则过滤与 `enabled` 开关；普通包入口保持零诊断依赖，加载 companion 才启用——"检查可选、违约必炸"（INVARIANT 码的错误会穿透普通 contain 逻辑，见 dsh-llm `emitAdaptersUpdated` 对 INVARIANT 的特判）。

**dsh-spill-policy（上下文溢出处理）** — `lib/index.js`（169 行，插件 `spill-policy`，`inject=["tools"]`）：`tools/post-execute` 结果转换器——终态结果 UTF-8 超过 `maxInlineBytes` 时，全文存入会话级 spill 产物（`ctx.spillStore`），模型侧替换为 `TextRetainer` 头尾预览 + 定位符 + 取回指引（`spillNotice`/`preview` 函数）。第二臂 `tools/ptc-dispatch-log` 给 `tool/code-dispatch` 事件的日志副本设上限（模型值不动）；`read` 工具被模型臂跳过以防 `read→spill→read again` 死循环；spill 失败永不把成功工具调用变成 error（best-effort）。

**dsh-timeout + dsh-tool-call-timeout-policy（超时分层）** — dsh-timeout（140 行，零依赖）：`TimeoutReason extends Error`（携带能力自有 code + timeoutMs）、`clampTimeout(requested, def, max)`、`deadline(upstream, timeoutMs, code)`（AbortSignal 融合 + `MAX_TIMER_DELAY_MS=2147483647` 钳制）、`idleWatchdog`（只在 iterator `next()` 在途时计时的可重臂看门狗）——"只通知，不终止"，各能力自己停工并翻译原因。dsh-tool-call-timeout-policy（144 行，插件 `timeout-policy`）：`tools/execute` 包装器按工具声明的 `timeoutMs` 武装 deadline，自己的计时器赢了才把结果替换为 `isError` + `error.code=TOOL_TIMEOUT`（`toolTimeoutResult`），用 code 作用域防止嵌套外层 deadline 被误读为本插件超时——三层超时（进程 clamp / 每调用 deadline / 流 idle watchdog）各管一段。

**dsh-message-feedback（反馈闭环）** — `lib/index.js`（420 行）：`class MessageFeedbackService`（`ctx.messageFeedback`）+ 纯 schema 层（`messageFeedbackDomainSpec`，storage-domain 声明：`message_feedback` 表，行 = `{session:{createdAt, cwd?}, items:[{messageId, rating:'positive'|'negative', note?, version(uuid), createdAt, updatedAt}]}`，messageId/version 唯一性 superRefine 强制）。反馈是**与日志生命周期绑定的 sidecar**：`messageFeedbackSessionIdentitySchema` 用会话的 `createdAt+cwd` 指纹把 sidecar 行"围栏"到一个日志生命周期，fork/重放后的新生命周期读不到旧行——反馈永不污染错误会话（对应 DSH 的 `feedback/record` 事件则是进日志的另一路）。

### 总范式清单（给写借鉴指引文档的人的一句话索引）

1. **错误码先行**：稳定机器码 + 冻结可序列化 failure 快照，永远 route on code 不 parse message（§1）。
2. **状态即投影**：重试计数、token 计量、调度规则、preset 选择全部从 append-only 日志折叠，带 stateVersion（§2/3/4/6）。
3. **表面/日志二分**：模型可见历史是日志的纯函数；人类转录走 append-origin 事件（§4）。
4. **替换而非删除**：压缩/裁剪 = append replace 事件 + 影子价格（§5/附录 spill）。
5. **能力 = 作用域挂载**：preset/persona/权限都是 scope 子树的插件行，泄漏即 fail loud（§6）。
6. **配置三层 + 可 dump**：schema 默认 → 组合 base → 用户文档；`--dump-config` 带来源分层打印（§7）。
7. **持久化分级**：提醒/会话走日志（冷恢复免费），伴随会话的长跑作业走内存（重启即失）——按"死后是否需要复活"选路线（§3/8）。
8. **超时三层 + 只通知不终止**：clamp / per-call deadline / idle watchdog（附录）。
