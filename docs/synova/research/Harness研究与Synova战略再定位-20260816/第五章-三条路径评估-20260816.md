# 第五章 三条路径评估（何去何从）

> 2026-08-16 | 三条路径：A 迁移底座 / B 范式借鉴渐进升级 / C 生态并存
> 评估四维：成本 / 收益 / 风险 / 时间冲击（对 8/20 演示、9 月客户A部署）
> 硬约束：定位与应用场景不动；演示与部署优先，重构排后

---

## 5.0 评估框架

Synova 价值 = 让老板放下直觉相信系统（C 线 S0），信任来自"诊断对不对"。引擎越可白嫖底座，越该把工程预算压到领域深度（第四章 8 项【独有】能力）。

---

## 5.1 路径 A：迁移底座（Synova 引擎重建在 Harness 上）

**做法**：用 Harness 替换 Synova 的 4 个核心通用模块——SessionStore（→事件溯源 log）、ConversationEngine（→core/agent-loop）、SubAgentCoordinator（→subagent seam）、providers（→llm seam），Synova 的领域层（42 边/专家/测量器/哨兵/诊断/GA）作为 Harness 的插件挂载。

| 维度 | 评估 |
|------|------|
| 成本 | **高**：替换 4 核心模块 = 大重构，预估 2-4 周甚至更久（含领域层插件化改造、回归测试） |
| 收益 | **大**：白嫖 Harness 全部成熟工程（事件溯源/多后端 subagent/沙箱/工程门禁），工程重心全转领域；长期可跟随 Harness 演进 |
| 风险 | **高**：Harness 是 v0.1.0-rc.5 开发者预览，官方承诺破坏性变更；迁移期若 Harness API 变动则返工 |
| 时间冲击 | **致命**：与 8/20 演示（4 天后）、9 月客户A部署直接冲突，迁移期产品不可用 |

**结论**：**现在不做**。作为"部署稳定后"的中长期战略选项（Q4 后评估）。触发条件：客户A部署跑通 + 首季度数据回收后，再评估迁移的收益是否值得成本。

---

## 5.2 路径 B：范式借鉴渐进升级（主路径）

**做法**：保留 Synova 引擎不动，局部吸收 Harness 的最强范式——事件溯源 session log、capability seam、snapshot 测试、Agent Notes 四态记忆、sandbox、guard、spill。每个借鉴项独立可排期，直接补 C 线缺口。

| 维度 | 评估 |
|------|------|
| 成本 | **低-中**：渐进、可控，每项独立（估每项 1-3 天），不动地基 |
| 收益 | **中-高**：直接补 C 线 P0/P1 缺口（S3-5 自诊断可信度、S0 信任建立、S5-1 反馈闭环、黄金数据集门禁）——借 Harness 范式等于借力补缺口 |
| 风险 | **低**：不动 Synova 架构，借鉴的是"范式"不是"代码依赖"（Harness 是 MIT，可复制理念） |
| 时间冲击 | **无**：演示与部署不受影响，借鉴项排在部署后 |

**结论**：**作为主路径，立即推进**。这是唯一同时满足"做深 + 不牺牲演示部署 + 为未来打基本功"的路径。

---

## 5.3 路径 C：生态并存（Synova 作为 Harness 生态一员）

**做法**：把 Synova 的"领域知识层"（42 边本体 + 专家 + 诊断）封装成可复用资产，二选一或并行：

- C1：Synova 作为 Harness 插件发布（打 `dsh-plugin` topic，进插件市场/排行/推荐）
- C2：Synova 保持独立产品，但"领域层"以 SDK/插件形式开放，让 Harness 用户挂载 Synova 的诊断能力

| 维度 | 评估 |
|------|------|
| 成本 | **中**：需要"领域层插件化"（与路径 A 的部分改造重叠）或薄封装 |
| 收益 | **中**：借 DSH 生态分发（现成市场/排行/推荐），获生态流量与外部验证 |
| 风险 | **中**：依赖 Harness 破坏性变更；插件治理风险（可信度）；可能稀释 Synova 独立产品定位 |
| 时间冲击 | **无**：并行，不影响演示部署 |

**结论**：**作为路径 B 完成后的增强**，或"领域知识层"的对外分发策略。短期不动，避免稀释"独立产品"定位。

---

## 5.4 综合建议（三路径关系）

```
现在 → 8/20 演示 + 9 月部署（不动引擎）
      │
      ↓ 部署稳定后
路径 B（主）：借鉴 Harness 范式补 C 线缺口（事件溯源/seam/snapshot/Agent Notes）
      │
      ↓ 首季度数据回收后
路径 A（评估）：是否迁移底座（若 Harness 生态持续健康且迁移收益 > 成本）
      │
      ↓ 领域层成熟后
路径 C（增强）：领域知识层对外分发（插件/SDK）
```

**核心原则**：无论路径怎么选，第一优先级永远是"把 8 项【独有】领域能力做深做透"。通用工程能借就借（B），底座能迁就迁（A，但要等稳定），生态能借力就借力（C）——但**Synova 之所以是 Synova，是因为 42 边、专家、诊断方法论，不是因为会循环、会调度、会记忆。**

---

## 5.5 第五章结论

1. **路径 A（迁移底座）现在不做**——与演示/部署冲突 + Harness 未稳定。
2. **路径 B（范式借鉴）是主路径**——渐进补缺口，不牺牲演示部署，为未来打基本功。
3. **路径 C（生态并存）是增强**——领域层成熟后考虑，现在不做以免稀释定位。
4. **最高优先级是领域深度**——8 项【独有】能力做深做透，通用工程能借就借。
