## 7.1 结论先行

专家的本质不是"固定角色"，而是**可组合的诊断能力单元（Expert Unit）**。专家体系 = 能力单元 + 声明式组合 + 分层适配，实现"无限组合、更改、适配不同企业"。

一句话：Synova 的专家，应该像乐高积木——能力是积木块（因果边 + compute + 领域知识），专家是拼出来的结构（声明式组合），每个企业拼出自己的诊断团队。

## 7.2 第一性原理：为什么专家必须可组合

Synova 服务 5-1000 人企业，行业千差万别：外贸（客户A）、制造、零售、SaaS、专业服务……每个行业有自己独特的诊断维度（外贸看汇率/跨境，制造看供应链/产能，零售看渠道/坪效）。固定的 5 个问题域专家，无法覆盖所有行业，更无法适配具体企业。

第一性原理推导：

```
诊断能力（原子）→ 专家单元（分子）→ 专家体系（企业诊断团队）
  因果边 + compute    一个可组合单元      声明式组合的集合
```

- 诊断能力是原子：42 边因果结构 + 25 测量器 + 哨兵 compute，是固定的领域真理
- 专家单元是分子：把若干原子组合成"一个诊断视角"（资金效率 = 现金流边 + 财务 compute + 财务知识）
- 专家体系是结构：一个企业 = 一组专家单元的组合，组合方式随行业/企业变化

结论：固定的专家列表违背了"适配不同企业"的产品本质；可组合的专家单元才符合"无限适配"的需求。

## 7.3 DSH 的可组合哲学（从源码看它的思考过程）

DSH（`D:\deepseek-harness`）的"无限组合"不是口号，是四个工程机制（源码证据）：

| 机制 | 源码证据 | 含义 |
|------|---------|------|
| 一切皆插件 | `packages/` 约 200 包，persona/tool/skill/goal/subagent 都是插件 | 能力是插件，不是硬编码 |
| 声明式组合 | `agent.cordis.yml`（minimal=persona+2工具；standard=persona+shell+fs+web+skills+plan+goal+subagent+workflow） | 一个 agent = 一组插件行的声明式组合 |
| 分层 patch | `packages/bundle/base/cordis.patch.yml`（`insert:` 配置行，patch 按 `id` 覆盖整行 config，last write wins） | 组合是分层的，任何层可改 |
| preset + 条件禁用 | `apps/cli/config/agent-presets/`（minimal/standard/code/cordis）+ `disabled: !!js 条件` | 预置组合 + 条件化 |

DSH 的思考过程（从源码反推）：它不定义"agent 应该有什么能力"，而是定义"能力是插件、组合是配置、配置是分层的、组合可条件化"——于是"无限组合"成为自然的产物，而非刻意设计。

## 7.4 Synova 专家的可组合单元（Expert Unit）

借鉴 DSH 的"插件"，定义 Synova 的专家单元（一个可组合的诊断能力原子）：

```yaml
# expert-units/fundamental-efficiency.yaml（资金效率单元）
id: fundamental-efficiency
displayName: 资金效率
edges: [E-13, E-23, E-34, E-36, E-37]
computes: [compute-cash-runway-months, compute-gross-margin, compute-receivable-overdue-rate, compute-cost-per-head]
prompt: |
  你是资金效率诊断视角。从现金流、成本、利润、融资四个维度分析企业的资金效率...
outputSchema:
  finding: string
  rootCause: string
  evidence: [{edgeId, computeId, value, baseline}]
  actions: [string]
activation: on-demand
```

一个专家单元 = 五要素（因果边 + compute + 领域知识 + 输出 schema + 激活策略）。这是"专家"的最小可组合单位。

## 7.5 组合机制：声明式组合 + 三层 + 分层 patch

借鉴 DSH 的 profile/bundle/patch，一个企业的专家体系 = 专家单元的声明式组合：

```yaml
# expert-profile.yaml（企业专家体系 = 组合声明）
profile:
  base:
    - fundamental-efficiency
    - customer-growth
    - organizational-capability
    - technology-foundation
    - competitive-strategy
  industry: foreign-trade
  industryUnits:
    - cross-border-settlement
    - export-channel
  enterpriseUnits:
    - maternity-moments-channel
```

分层组合（借鉴 DSH 的分层 patch）：

```
基础 profile（内置 5 个问题域单元）
  ↓ patch
行业 profile（外贸加跨境/渠道单元，替换某些基础单元的 prompt 注入行业知识）
  ↓ patch
企业 profile（企业特有单元 + 企业事实注入）
  ↓ patch
用户/GA 调整（超级管理员临时调整某单元的激活策略）
```

关键：每一层可以新增单元、替换单元配置、禁用单元——无限组合，且任何层可改。

## 7.6 更改机制：四类可配置对象

每个专家单元的五要素中，四类可配置（对应之前 G6 可配置）：

| 可配置对象 | 配置在哪 | 改什么 | 举例 |
|-----------|---------|--------|------|
| prompt | expert-units/{id}.yaml 的 prompt | 诊断框架、话术、专业深度 | 技术派老板 vs 直觉派老板 |
| computes | 同上 computes | 能调用哪些 compute | 数据完整度不同的企业 |
| outputSchema | 同上 outputSchema | 结论结构 | 一页纸 vs 分层 vs 对话式 |
| activation | 同上 activation | 常驻/按需/禁用 | 企业规模/行业 |

更改 = 改 yaml 配置，不改代码——这是"无限更改"的前提。

## 7.7 适配机制：行业 profile + 企业配置

不同企业 = 不同的组合 + 不同的注入：

```
外贸企业（客户A）：
  基础单元（5 个）+ 行业单元（跨境结算/海外渠道）
  + 行业提示词（汇率风险/出口合规）注入到资金效率/客户增长单元
  + 企业事实（月子中心合作模式/前3大客户/预算约束）注入到所有单元

制造企业：
  基础单元（5 个）+ 行业单元（供应链/产能/质量）
  + 行业提示词（库存周转/产能利用率）注入

SaaS 企业：
  基础单元（5 个）+ 行业单元（ARR/留存/单位经济）
  + 行业提示词（MRR/Churn/NRR）注入
```

适配 = 换行业 profile + 换企业配置，专家体系跟着变，不改代码。

## 7.8 演进路径（从现在到未来）

| 阶段 | 状态 | 特征 |
|------|------|------|
| 现在 | 固定问题域专家（5 个） | 硬编码/固定配置，无法适配行业 |
| 近期 | 可组合专家 | 专家单元 + 声明式组合 + 三层增减，适配行业/企业 |
| 中期 | 自适应专家 | 专家单元随企业数据动态调整（哪个单元激活/禁用，由诊断信号决定） |
| 远期 | 联邦进化 | 跨企业专家单元进化（某行业的诊断单元，在多家企业验证后沉淀为行业标准单元） |

这条路径对应底座研究"持续学习"的阶梯：从"可组合"到"自适应"到"联邦进化"，正是"越用越懂企业"的逐步实现。

## 7.9 落地规范（数据结构 + 配置格式）

### 专家单元目录

```
expert-units/
  base/
    fundamental-efficiency.yaml
    customer-growth.yaml
  industries/
    foreign-trade/
      cross-border-settlement.yaml
    manufacturing/
      supply-chain.yaml
  enterprise/
    {企业}/maternity-moments-channel.yaml
```

### 组合配置（expert-profile.yaml）

如上 7.5 的三层组合。加载器（对应现有 `expert-config-loader`）按"基础 → 行业 → 企业 → 用户 patch"分层合并，最后生成的专家体系 = 所有层的组合结果。

### 与现有架构的映射

| 新概念 | 现有代码 | 关系 |
|--------|---------|------|
| 专家单元 | `expert/{域}/manifest.json` + PROMPT.md | 单元 = 现有专家配置的扩展版（加 compute 映射 + 输出 schema） |
| 组合声明 | `expert/expert-registry.yaml` | registry 升级为 profile（三层组合） |
| 分层 patch | 无（新增） | 借鉴 DSH 的 bundle/patch 机制 |
| 加载器 | `expert-config-loader.ts` | 升级为分层合并加载 |

## 7.10 第七章结论

1. 专家的本质是"可组合的诊断能力单元"，不是"固定角色"。
2. 组合机制 = 声明式组合 + 三层（基础/行业/企业）+ 分层 patch，实现无限组合。
3. 更改机制 = 四类可配置对象（prompt/computes/outputSchema/activation），改配置不改代码。
4. 适配机制 = 行业 profile + 企业配置，换行业换配置，专家体系跟着变。
5. 演进路径 = 固定 → 可组合 → 自适应 → 联邦进化，对齐"持续学习"的阶梯。
6. 这套机制借鉴 DSH 的"一切皆插件 + 声明式组合 + 分层 patch"，但落在 Synova 的领域深度（因果边 + compute + 诊断知识）。
