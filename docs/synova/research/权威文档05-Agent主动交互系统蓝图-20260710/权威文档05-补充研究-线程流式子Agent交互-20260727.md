## 一、从第一性原理推导

### 推导一：为什么需要线程管理

Synova不是ChatBot——它是诊断工具。每一次诊断是一个完整的分析循环：哨兵信号→专家并行→报告合成→Goal创建。这些循环之间是独立的——2026年Q3的全企业诊断和2026年Q2的现金流专项诊断是两个不同的分析上下文。用户需要在它们之间切换，比较不同时期的诊断结论，跟踪Goal的执行进展。

如果所有对话混在一个默认session里——上下文丢失、历史无法回溯、上次的诊断结论无法被下次引用。线程是诊断的时间轴——不是聊天记录。

**线程不是"对话历史"——是"诊断会话的时间线"。** 每个线程有明确的开始（触发诊断）和结束（报告产出+Goal创建）。自动命名从诊断触发条件提取（"现金流专项诊断 2026Q3"）。手动重命名让用户赋予它组织内部的意义（"董事会汇报用 现金流诊断"）。

### 推导二：为什么需要流式响应

诊断报告有金字塔三层结构——Governing Thought（50字）→ Key Judgments（3条判断+证据链）→ Evidence Chain（每条判断的数个数据事实/专家推断/预测假设）。当前fetch等待完整响应——用户看到空白页面30秒。流式响应让Governing Thought立即出现——CEO级别的一行结论已经足够让创始人知道"问题在哪"。接下来Key Judgments逐条出现——每位专家完成后立即展示。Evidence Chain按需展开——不是所有人都需要看每条推断的数据源。

流式不是"体验优化"——是"让诊断报告的消费方式和它的金字塔结构匹配"。最重要的信息最先到达，细节按需加载。

### 推导三：为什么需要子Agent状态可视化

一次全量诊断中host调度6位专家并行工作。当前用户看不到这个过程——提交诊断请求后，等待30秒，报告一次性出现。如果某个专家超时或失败——用户不知道，只能看到最终报告没有那个维度的分析。

子Agent状态面板解决的是"用户在诊断过程中是否信任系统在工作"的问题。看到"资本循环专家: 正在分析E-05获取链...""客户循环专家: 已完成""人才循环专家: 正在分析E-38留存链..."——用户知道系统没有卡死，知道哪个维度正在被分析，知道还需要等多久。这不是炫技——是让诊断过程对用户可见，建立对系统判断的信任。

### 推导四：为什么这三个能力必须一起设计

线程管理定义了"诊断会话的生命周期"。流式响应定义了"诊断报告的消费方式"。子Agent状态定义了"诊断过程的可见性"。三者共享同一个底层概念——诊断会话。线程是会话的容器，流式是会话进行中的输出通道，子Agent状态是会话进行中的进度指示。分开设计会导致重复的数据模型和冲突的UI状态。一起设计的优势：线程的状态（in_progress/completed）直接驱动流式响应和子Agent面板的显示/隐藏。

## 二、Codex交互模式分析

Codex桌面应用的交互架构——不是盲目参照，而是分析每个设计决策背后的"为什么"：

### 2.1 线程列表（左边栏）

**Codex的做法：** 左侧固定宽度面板，滚动线程列表。每个线程显示自动生成的标题+时间戳。当前线程高亮。线程持久化——关闭应用后重新打开时恢复。可手动重命名。

**为什么有效：**
- 自动命名降低创建门槛——不需要"取个好标题"，系统从第一条消息提取关键信息
- 手动重命名让用户加入自己的组织逻辑——"这个线程是对客户A的Q3诊断"比"2026-07-27 诊断"更有用
- 持久化让线程成为工作记录——不是一次性对话

**Synova的适配：** 线程=诊断会话。自动命名从诊断触发器提取（"全企业诊断 2026Q3""现金流专项 2026-07-27"）。手动重命名让用户标注用途（"董事会汇报用""给客户A看的现金流诊断"）。

### 2.2 流式响应（对话区）

**Codex的做法：** 响应逐段出现——不是等全部生成完再显示。代码块逐行渲染。长输出自动折叠。用户可以在流式过程中滚动查看已输出的部分而不中断流式。

**为什么有效：**
- 减少感知等待时间——第一段内容在1秒内出现
- 用户可以在前半段到达时就开始阅读和思考——不用等全部完成
- 长输出的折叠防止刷屏——用户可以选择展开

**Synova的适配：** Governing Thought立即出现（<1秒）。Key Judgments逐条出现（每位专家完成时推送一条）。Evidence Chain折叠——点击展开。流式完成后自动追加报告操作按钮（"生成Goal""导出PDF""分享给GA"）。

### 2.3 子Agent状态（右侧面板）

**Codex的做法：** 右侧面板显示当前任务spawn的子Agent。每个Agent有名称+状态指示器+输出预览。Agent在后台运行时不阻塞主对话。Agent完成后结果可展开查看。

**为什么有效：**
- 让并行工作可见——用户知道系统在做什么
- 不阻塞主流程——Agent在后台运行，用户可以继续在主对话区工作
- 失败时立即发现——Agent显示红色状态，用户可以决定重试还是跳过

**Synova的适配：** 诊断会话中显示6位专家的状态——每位专家的名称、当前分析的边、进度、耗时。host调度时自动显示。诊断完成后自动收起。

## 三、设计规范

### 3.1 三面板布局

```
+------------------+------------------------+------------------+
| 左边栏(240px)    | 主对话区(flex)         | 右侧面板(280px)   |
|                  |                        |                  |
| 线程列表         | Governing Thought      | 子Agent状态      |
|  [+新建诊断]     |                        | 资本循环专家 ✓   |
|                  | Key Judgments          | 客户循环专家 ⟳   |
| 全企业诊断Q3     |   ├ 判断1 + 证据链     | 人才循环专家 ⟳   |
| 现金流专项诊断   |   ├ 判断2 + 证据链     | 技术设施专家 ⟳   |
| 组织健康诊断     |   └ 判断3 + 证据链     | 商业模式专家 ⟳   |
|                  |                        | 竞争战略专家 ⟳   |
|                  | [生成Goal] [导出]      |                  |
+------------------+------------------------+------------------+
```

### 3.2 线程数据模型（基于现有SessionStore扩展）

```
Thread {
  id: string (映射到Session.sessionId)
  title: string (自动生成/手动重命名)
  type: 'full_diagnosis' | 'scoped_diagnosis' | 'conversation'
  status: 'initiating' | 'in_progress' | 'completed' | 'failed' | 'archived'
  createdAt: ISO timestamp
  updatedAt: ISO timestamp
  triggerType: 'cron' | 'manual' | 'ga' | 'sentinel_p0'
  expertSummary: { expertId: string, status: 'running'|'completed'|'failed', edgesAnalyzed: number }
  reportUrl: string (诊断报告路径)
}
```

### 3.3 流式响应数据格式（基于现有chat.ts SSE）

```
event: diagnosis_start
data: {"sessionId": "xxx", "experts": ["capital", "customer", "talent", "tech", "finance_deep", "strategy_deep"]}

event: governing_thought
data: {"text": "客户A的增长瓶颈核心在于固定成本刚性导致经营杠杆过高...", "confidence": 0.85}

event: expert_update
data: {"expertId": "capital", "status": "completed", "edgesAnalyzed": 5, "elapsedMs": 3200}

event: key_judgment
data: {"expertId": "capital", "judgment": {"text": "固定成本占比超过65%...", "severity": "critical", "evidence": [...]}}

event: diagnosis_complete
data: {"sessionId": "xxx", "totalElapsedMs": 28000, "reportUrl": "/reports/xxx"}
```

### 3.4 线程自动命名规则

| 触发条件 | 自动命名模板 |
|---------|------------|
| Cron全量诊断 | "{季度}全企业诊断 {年份}" |
| 手动触发全量诊断 | "全企业诊断 {日期}" |
| 哨兵P0触发 | "{哨兵名称}触发的诊断 {日期}" |
| 部门级诊断 | "{部门名}诊断 {日期}" |
| 自由对话 | "{第一条消息的前30字符}..." |
