1.2 各层定义

L0：存活探针

维度内容
测试对象50 个哨兵进程 + 5 个 Loop Engineering 循环管理器
核心验证进程能否正常启动？能否消费输入？能否在规定时间(30s)内输出符合 SentinelFinding Schema 的 Finding（哪怕空内容）？
数据来源哨兵 Registry + mock 本体数据（最小可行输入）
验收标准50 个哨兵 100% 通过。静默失败（进程未死但无输出）→ 阻断
执行时机pre-commit 阶段。任何哨兵失败 → 阻断提交
责任人开发者

L1：compute 契约单元测试

维度内容
测试对象每个 compute 函数的输入 → 输出
核心验证contractId 匹配 + 正常/边界/异常路径 + 降级策略 + 时序数据处理正确
数据来源嵌入式测试蓝图——4 组 fixture：正常 / 边界 / 异常 / 时序（≥3 个时间点）
时序强制规则：消费携带时序参数的 42 边(window_3m/slope/variance)的 compute 函数，fixture 中缺少 ≥3 个时间点 = 契约不完整
验收标准P0 批次 60 个 compute ≥4 组 fixture + contractId 强制 + 时序 compute 含时序 fixture
执行时机vitest --changed（日常）+ 全量 vitest（发布前）
责任人开发者

L2a：哨兵接线测试

维度内容
测试对象哨兵 × compute × 42 边的 traversal 路径——从 DiagnosisContextNode 出发，沿因果边到 compute，产出的 Finding
核心验证traversal 路径匹配基准 YAML → Finding 非空 → Finding 中边引用在 42 边体系中存在 → Finding 严重度匹配哨兵规范中的阈值
数据来源traversal 路径 YAML 基准文件（从哨兵权威规范"可执行路径规范"字段提取，Phase 0 入库 extensions/traversal/）
验收标准50 个哨兵各 ≥1 个集成测试。路径匹配率 100%。边引用全量验证通过
前置条件Phase 0：补全 JSDoc @contract + traversal 路径 YAML 入库（代码与规范同步）
执行时机pre-push 阶段
责任人开发者

L2b：专家推理验证（新增维度）

维度内容
测试对象8 位专家 Agent 的系统提示词——给定标准化 Finding 集，验证推理输出质量
核心验证5 个维度：(1)角色对齐——只输出职责范围内的诊断，不跨界；(2)证据链一致性——引用的证据真实存在于上游推理中（证据幻觉零容忍）；(3)输出稳定性——同一输入 10 次，输出噪声度 <10%；(4)边界识别——信息不足时输出"无法判断"而非编造；(5)因果推理完整性——从 Finding 到诊断结论的因果链可追溯
故障模式覆盖死锁性偏见（只看某些边忽略其他）/ 认知嫁接（跨专家推理污染）/ 闭合循环（引用不验证）/ 角色漂移（跨界推理）
数据来源专家推理验证集——每组用例：标准化 Finding 输入 + 预期诊断结论 + 评分规则（完全匹配/部分匹配/幻觉）
验收标准每位专家 ≥5 组验证用例。角色越界率 <5%。证据幻觉率 = 0。输出稳定性噪声度 <10%
执行时机pre-push 阶段（每个 PR 合并前验证最新提示词推理质量）
责任人专家系统设计师 + 开发者

L2c：循环基础设施测试（新增维度）

维度内容
测试对象5 个 Loop Engineering 循环——企业诊断 / 部门导航 / GA 进化 / 系统自检 / 知识积累
核心验证4 个维度：(1)循环启动——Cron/事件触发能否正常启动；(2)状态机——running→completed/failed 转换正确，连续 3 次失败→断裂告警；(3)三级恢复——L1 自动重试→L2 半自动→L3 手动依次执行；(4)依赖传递——企业诊断→部门导航输出正确传递，GA 进化循环消费 GA 校准数据
数据来源mock 循环触发事件 + 循环管理器状态快照
验收标准5 个循环各 ≥1 集成测试。启动成功率 100%。状态转换正确率 100%。断裂恢复链路完整
执行时机pre-push 阶段（每周一次全量循环健康检查）
责任人开发者

L3：E2E 标准化场景测试

维度内容
测试对象完整诊断链路——从本体数据到报告产出
核心验证预设场景 → 一键运行 → 预期哨兵触发 → 报告包含预期发现。E2E 是"固定场景的可重现验证"，不是"任何用户操作都算"
数据来源3-5 个标准化测试场景（客户A / 制造企业 / SaaS 企业）——每个包含本体数据 JSON fixtures + 预期哨兵触发列表 + 预期报告结构
验收标准预期哨兵触发率 ≥90%。误报率 <10%
执行时机pre-push 阶段 + 发布前
责任人开发者 + GA

L4：因果回归测试（新增维度）

维度内容
测试对象核心诊断逻辑——代码变更后历史案例的诊断结论是否被意外推翻
核心验证每次代码变更→自动重新诊断 5 个黄金案例→对比"标准诊断结论"→度量偏差
黄金案例库客户A（真实：产品结构恶化+渠道效率）/ Netflix（经典模拟：创新转化不足+资源锁定）/ OFO（经典模拟：扩张无制动+信号衰减）/ 制造企业（标准化：成本结构+学习曲线）/ SaaS 企业（标准化：PLG→SLG 单位经济模型）
偏差阈值偏差>30% → 阻断（核心诊断逻辑退化）。偏差 10-30% → 告警（需人工审查）。偏差<10% → 通过
案例档案格式预设本体数据 JSON + 预期哨兵触发列表+严重度 + 预期根因追溯路径（DiagnosisContextNode→42边→compute→Finding）+ 上次验证快照
执行时机每次 PR 合并前（与 L3 E2E 同级）
责任人开发者 + 专家系统设计师

L5：GA 验证层

维度内容
测试对象诊断结论在真实业务场景中的正确性
核心验证GA 标注 → precision/recall/F1 → 按哨兵统计 → 质量趋势
冷启动阶段标注<50 条/哨兵：系统主动推送抽查请求（非等待 GA 主动标注）。目标每月每个 P0 哨兵 ≥5 次抽查。利用 42 边硬度测试案例为早期验证参考
成熟阶段标注 ≥50 条/哨兵：自动度量。P0 准确率>80% / P1>70% / P2>60%。准确率<60%→暂停推送。偏差>50%→标记人工。连续 2 周期下降→触发退化告警
验证周期30 天(P0) / 90 天(P1) / 180 天(P2) / 365 天(GA 进化循环整体)
责任人GA + 系统管理员
