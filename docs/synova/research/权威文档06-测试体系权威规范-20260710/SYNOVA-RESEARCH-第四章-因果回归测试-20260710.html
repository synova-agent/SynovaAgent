第四章：因果回归测试——黄金诊断案例库

5 个黄金案例 · 每次变更重新诊断 · 偏差>30%阻断 · 验证核心因果推理不退化 | 2026-07-10

4.1 核心问题

当修改了 CAPITAL_ALLOCATION 边的计算逻辑后，之前诊断出"资本配置低效"的企业，在下次诊断中是否还能被正确识别？——缺少的不是"代码没坏"的验证，而是"诊断结论没被意外推翻"的验证。这是专门针对复杂因果推理系统的回归测试。

4.3 案例档案格式

每个案例档案包含以下字段：

字段内容
本体数据 JSON fixture预设的 Node+Edge JSON 数据——模拟该案例的企业本体层。包含 42 边的参数初始值、节点池数据、时间序列
预期哨兵触发列表哪些哨兵应该触发 + 每个哨兵的预期严重度级别（如：margin-health: WARNING, cash-runway: NONE）
预期根因追溯路径DiagnosisContextNode→42 边→compute→Finding 的完整链路——作为"标准答案"
上次验证快照上一次运行此案例时的诊断结论 JSON——用于偏差对比

4.4 偏差度量与阈值

偏差类型度量方法阈值
哨兵触发差异应该触发但未触发的哨兵数 + 不应触发但触发的哨兵数 / 预期哨兵总数>30% → 阻断 / 10-30% → 告警 / <10% → 通过
严重度差异哨兵严重度级别变化的平均幅度（WARNING→CRITICAL = 2 级差异）平均差异>1 级 → 阻断
根因路径差异追溯路径中涉及的 42 边与标准答案的重叠率重叠率<50% → 阻断

4.5 执行机制

  1. 触发时机：每次 PR 合并前（pre-push 阶段）自动执行
  2. 执行方式：加载 5 个案例的 JSON fixture→运行完整诊断管线→产出诊断结论→与标准答案对比→计算偏差
  3. 联动规则：基准对比（L5 回归基准）通过 + 因果回归偏差>30% = 最高级别告警——"代码测试过了但诊断结论变了"——这是最危险的情况
