## 零、这份文档为什么是第14份

前13份权威文档是**纵向切片**——每份深挖一个技术层：42条边怎么设计（01）、50个哨兵怎么部署（03）、8位专家提示词怎么写（10）、Skill/Tool怎么编排（12）、增长导航怎么执行（13）。

但没有任何一份文档定义过**这些层次之间的接口**。一个新加入团队的工程师，拿着13份文档，不知道：

- 启动时先加载哨兵还是先加载Skill？如果Skill引用了哨兵但哨兵还没注册，会不会假阳性失败？
- 当GA报告"诊断不准确"时，问题是出在本体层（E-23参数不准确）还是专家层（推理链占位符未填充）还是数据层（GraphStore数据过期）？
- 当E-23的transfer_function从v1升级到v2时，哪些哨兵、哪些compute、哪些Skill会受影响？
- 如果只剩一周时间，用客户A数据跑通"诊断→增长导航"的最小子集是什么？
- 开发团队说的是"断裂点"，QA说的是"循环"，实施文档里的是"介入节点"——这三个是不是一个东西？

这五个缺失不是"再做一个深度研究"能补的。它是**对已有13份文档的横向重新组织**。

## 二、研究任务（5章 + 1节方法论提炼）

### 第一章：系统启动序列与热重载协议

**核心问题**：Synova从空机器到完整运行的精确加载顺序。不仅是"启动时"，还包括"运行中"——模块升级、配置变更、哨兵热重载时，系统如何保证不崩溃？

**必须包含**：

**1.1 启动阶段定义（Phase 0 ~ Phase 5）**

```
Phase 0: 基础设施 (< 2s)
  SQLite连接池 → Logger → ConfigLoader → EnvValidator
  失败策略：任何一项失败 → 终止启动，错误码 1

Phase 1: 存储层 (< 3s)
  GraphStore(建表+索引+Schema迁移) → SOG-Core枚举校验 → KnowledgeStore(检查行业基准数据)
  失败策略：Schema迁移失败 → 回滚到迁移前快照 + 终止启动
  数据预置：检查知识库行业基准数据是否存在。不存在→从预设初始数据包加载。仍不存在→系统进入"待配置"状态，HTTP服务启动但API返回503

Phase 2: 核心引擎 (< 8s)
  Phase 2a: SentinelLoader(扫描manifest.json → 50哨兵注册) < 3s
  Phase 2b: SkillLoader(扫描skills/builtin/ → 依赖校验) < 2s
  Phase 2c: PlaybookLoader(扫描playbooks/ → 优先级覆盖) < 2s
  Phase 2d: CausalChainLoader(扫描causal-chains/ → 因果链注册) < 1s
  
  子顺序逻辑：SkillLoader依赖SentinelLoader（Skill的dependencies.sentinels字段需要引用已注册哨兵ID）。PlaybookLoader依赖SkillLoader（Playbook的steps[].tool字段需要引用已注册Tool ID）。SentinelLoader和CausalChainLoader相互独立。各Loader遵循同样的依赖校验规则：依赖缺失/版本不匹配→标记degraded+写入L4事件流→不阻塞Phase。

Phase 3: 本体计算层 (< 5s)
  42条边transfer_function注册 → compute函数加载 → ToolRegistry(与Sentinel-check交叉引用) → CausalChainRegistry索引构建
  失败策略：compute函数加载失败→标记该compute为degraded→继续

Phase 4: 专家与安全 (< 5s)
  ExpertPromptLoader(扫描expert/*/manifest.json → 8位专家就绪) → PolicyEngine(D38)初始化 → DataBoundary校验
  失败策略：专家manifest缺失→跳过该专家+记录错误→主Agent路由时自动排除

Phase 5: 交互层 (< 3s)
  HTTP Server → MCP Server → TUI → CronScheduler(哨兵+诊断+导航循环的定时任务注册)
  失败策略：TUI失败不影响HTTP/MCP。CronScheduler中单个循环注册失败不影响其他循环。
```

**1.2 失败回滚协议（每Phase独立）**

- 每个Phase内任何模块失败时，回滚该Phase到上一个已知良好状态
- 不影响已成功初始化的其他Phase——Phase 2的PlaybookLoader失败不会回滚Phase 1的GraphStore
- 回滚触发：模块初始化抛出未捕获异常、health check超时（30s）、依赖校验发现error级告警

**1.3 运行中热重载协议**

- SentinelLoader热重载：文件监控检测到`extensions/sentinels/*/manifest.json`变更 → 重新加载该哨兵 → 新manifest校验通过→替换注册表条目。校验失败→保留旧版本+WARN日志+GA通知
- SkillLoader/PlaybookLoader同模式
- CausalChainLoader：新增YAML→自动注册。修改已有YAML→版本号校验。版本号递增→更新。版本号不变或回退→拒绝+WARN

**1.4 数据预置阶段（Phase 1.5，介于Phase 1和Phase 2之间）**

- 检查KnowledgeStore中是否存在行业基准数据（作为哨兵基线对比的数据源）
- 不存在→从`data/seed/industry-baselines.json`加载预设初始数据包
- 检查是否有至少一个企业的本体数据（GraphStore中是否存在Enterprise节点）
- 没有→系统进入"待配置"状态。HTTP服务正常启动，但`/api/diagnosis/start`返回503 + "企业数据未配置"。GA在面板上看到"待配置"引导流程。

### 第二章：能力→场景溯源矩阵与自助诊断

**核心问题**：GA报告"诊断不准确"时，工程师怎么排查？更进一步——系统能不能自己告诉GA问题出在哪？

**必须包含**：

**2.1 能力→场景溯源矩阵**

每行：能力定义 → 支撑用户场景 → 依赖上游 → 失效影响 → 排查路径

| 能力 | 文档 | 支撑场景 | 依赖上游 | 失效影响 | 排查路径 |
|------|------|---------|---------|---------|---------|
| E-23 OPERATIONAL_EXECUTION transfer_function | 权威01 §2 | CEO看利润下降根因 | GraphStore.Financial.fixed_cost_ratio准时性 | expert报告成本结构分析不准确 | ①查`data-health`哨兵→看数据管道是否更新 ②查fixed_cost_ratio是否在0.2-0.8正常范围 ③查computeDOL输出是否异常 |
| ExpertPromptLoader | 权威10 §2 | 8位专家推理 | expert/{name}/manifest.json存在、IDENTITY.md的analytical_lens字段完整 | 该专家推理可能出错但不阻断诊断 | ①查expert-registry.yaml中该专家是否enabled ②查expert-prompts.ts降级为Loader后是否正常加载 ③查系统日志中该专家的初始化错误 |
| profit-health哨兵 | 权威03 §1 | CEO/GA/中层告警 | SentinelLoader注册成功、compute函数可用、数据源在线 | 利润率异常无法被检测 | ①查`sentinel-registry`中profit-health是否active ②查最近一次check的时间戳 ③查compute函数`computeProfitHealth`日志 |

规模的指导原则：矩阵不需要穷举13份文档的所有能力（那会是数千行）。选取以下能力即可：P0级42边（约15条）、P0级哨兵（约15个）、8位专家核心提示词模板、启动序列中的关键Loader。

**2.2 自助诊断工具**

基于矩阵自动生成面向GA和企业管理员的诊断检查清单。当用户报告"诊断结论似乎不对"时：

- 系统运行诊断自检脚本（`check-self-diagnosis.sh`）
- 自动检查：相关数据源是否在线 → 涉及的哨兵最近一次成功扫描时间 → 底层42边参数是否在正常范围 → 专家提示词模板是否完整加载
- 输出自然语言结果："数据源正常（最近更新：2小时前），相关哨兵正常（profit-health: 3小时前扫描通过），底层参数在正常范围（fixed_cost_ratio=0.58），诊断结论可信度高。"
- 或："⚠️ 数据源`financial_baseline`中断3天，诊断结论可能滞后。建议联系GA检查数据管道。"

这个工具的目的是减少GA找工程师的频率——80%的"诊断不准确"报告是数据管道问题，不需要工程师介入。

### 第三章：集成测试契约与防误报机制

**核心问题**：当任何一份文档定义的"契约"被变更时，系统如何自动检测"什么东西会坏"——且不产生大量假阳性告警？

**必须包含**：

**3.1 集成契约矩阵**

| 契约项 | 检查方法 | 告警级别 | 失败影响 |
|--------|---------|---------|---------|
| 42边ID是否全部在50哨兵的edge引用中存在 | grep哨兵manifest的edges字段，cross-check 42边清单 | error | 哨兵找不到数据源→阻塞启动 |
| compute的contractId是否在Skill/Tool的dependencies中存在 | grep Skill manifest的dependencies.computes，cross-check compute contractId列表 | error | Skill无法执行→阻塞 |
| 专家提示词{{PLACEHOLDER}}是否在Playbook的contextRequirements中声明 | 解析提示词模板占位符列表，cross-check Playbook YAML | warning | 占位符可能无法填充→不阻塞启动，记录WARN |
| 哨兵引用了预留边（尚未正式激活） | 哨兵edges字段中出现未在42边清单中但标注为"planned"的边 | warning | 哨兵暂不可用→不阻塞，GA标记 |
| ME概念映射到42边的完整性 | 逐一检查ME规范的语义映射表中的边ID是否在42边体系中存在 | info | 兼容性提示→不阻塞，供ME规范维护者参考 |
| 增长导航Goal的measurement.sourceId存在性 | 检查Goal规范中所有measurement.sourceId是否指向存在的哨兵/compute/边参数 | error | Goal无法追踪→阻塞Goal注册 |

**3.2 告警级别定义**

- **error**：引用目标不存在，且该依赖为硬依赖。系统启动时，任何error必须全部清除才能完成启动。Phase 0-5中每个Phase结束时自动运行该Phase的集成检查。
- **warning**：引用目标可能无法正确工作，但不阻断启动。warning级别告警允许启动通过，但必须推送到GA面板（系统健康仪表盘）+ 写入系统健康日志（`system-health.log`）。warning积累时触发定期健康审查。
- **info**：兼容性提示——引用有效，但"最佳实践"可能建议使用更新版本或不同路径。不推送到GA，仅在开发者日志中记录。

假阳性控制：检查逻辑优先使用精确ID匹配（如contractId==="COMPUTE-BREAK-EVEN-v1"），避免模糊语义匹配。所有ID注册到统一的`system-registry.json`中，作为检查的权威来源。

**3.3 检查脚本分层机制（check-integration.sh）**

- L1 结构性检查（<1分钟）——文件存在性/JSON-YAML格式正确性/引用ID在已知注册表中存在。零假阳性。
- L2 交叉引用检查（<3分钟）——A引用的B是否在B的注册表中存在。可能出现假阳性（引用了一个在文档中定义了但未被L1索引的ID）。出现假阳性时需要更新统一注册表，而非调整检查逻辑。
- L3 语义检查（手动触发，不纳入自动化）——语义等价性验证（如ME概念X是否被42边体系正确覆盖）。需人工审查后标记。L3的结果作为info级别记录到文档合规报告，不阻断系统运行。

### 第四章：最小可用系统（MVS）与黄金数据集

**核心问题**：如果只剩一周时间、一台机器、一个客户（客户A），跑通"诊断→增长导航"的最小子集是什么？如何保证每次系统升级后，同一个案例的诊断结果不会无声退化？

**必须包含**：

**4.1 MVS能力清单**（从13份文档中切出的最小子集）

- 42条边：15-20条P0级边（覆盖获取/配置/转化/交付/回流五个断裂点各3-4条）
- 50哨兵：15-20个P0/P1级哨兵
- 8位专家：财务+战略+行动（3位核心）
- 61compute：20-25个核心compute
- Skill：10个核心Skill（覆盖L1感知→L7自保的"最小可行深度"）
- Playbook：3个核心Playbook（全企业诊断+利润率下降根因+现金流危机）
- 因果链：5条核心链（CC-CAPITAL-03成本驱动型利润衰减等）
- 增长导航：Goal注册→方案哨兵注册→偏离检测（轻量级再诊断暂不纳入MVS）

**4.2 MVS验收标准（拆分功能验收和性能基准）**

功能验收（不受硬件影响）：
1. 用客户A数据快照启动Synova MVS
2. 数据加载完成→哨兵扫描完成→所有P0哨兵产生Finding
3. 因果链追溯——CC-CAPITAL-03（成本驱动型利润衰减）完整追溯
4. 因果链模拟——对E-23施加"fixed_cost_ratio=0.58"变化量→计算profit_volatility
5. 因果链反查——"利润下降"→归因分析→输出贡献度排序
6. 增长导航——从诊断报告生成Goal→注册方案哨兵→检测偏离

所有功能验收必须产生预期的结构化输出。

性能基准（用于优化参考，非硬性验收）：
- 在4核8GB虚拟机上，端到端时间记录为性能基线
- 后续每次系统升级后重新跑MVS，对比性能基线的变化

**4.3 黄金数据集版本锁定**

- 客户A的数据快照作为MVS基准数据集（`data/golden/client-a-v1.json`）
- 记录MVS诊断输出的checksum（SHA-256）
- 任何系统变更后，用同一份数据重新跑MVS完整闭环
- 输出checksum变化的→必须能解释变化原因
  - "修复了E-23的参数覆盖率bug→computeDOL输出从2.1修正为2.8→checksum变化→预期内的修复"
  - "更新了专家提示词模板→诊断结论措辞变化但结论一致→checksum变化→预期内"
  - "输出checksum变化但找不到任何变更记录→非预期退化→回滚+排查"
- 黄金数据集锁定的本质是：每次升级都有"回归测试"——确保同一个问题不会因为系统升级而得到不同的答案（除非答案本身在升级中变正确了）。

## 三、研究工程方法论提炼（附录）

第14份文档完成后，13+1的文档体系不仅定义了Synova"是什么"，还隐含了一套可复用的方法论——"如何从第一性原理出发，系统性地设计一个企业级AI诊断Agent"。

**五个核心原则**：

1. **第一性原理推导**：不预设数量，不照搬行业惯例。从企业价值循环的最简不可约简模型出发，演绎推导所有可能的断裂点。推导出的数量如果和已有估计吻合，这是验证；如果不吻合，这是修正。

2. **物理现实锚定**：每一个理论定义必须在一个真实企业案例（客户A）中验证。硬度不是研究者拍脑袋——是参数覆盖率≥80%且预测偏差<15%。数据驱动的工程决策，不靠经验直觉。

3. **正交性保证**：四层分离——表达层、编排层、计算层、存储层。每层只与相邻层通信。变更频率从上往下递减。修改因果链不影响42条边，修改42条边不影响GraphStore Schema。

4. **端到端验证**：不仅验证"每个零件是否工作"（单元测试），还验证"所有零件拼起来是否工作"（MVS黄金数据集）。每次系统升级后自动回归——同一个案例的同一个问题，不能因为升级而得到不同答案。

5. **持续进化**：soft边标注"缺失什么数据、何时可重新评估"。客户A零基验证发现的NEW边候选项作为下一代本体层的演进起点。知识循环（诊断→导航→学习→再诊断）是系统的节拍器。

这套方法论在Synova之外的场景中同样适用——任何需要构建复杂因果推理系统的团队都面临同样的设计挑战。
