# 附录：研究工程方法论提炼

> 13+1份文档体系不仅定义了Synova"是什么"，还隐含了一套可复用的方法论——"如何从第一性原理出发，系统性地设计一个企业级AI诊断Agent"。
> 本附录提炼五个核心原则，每个原则配一个Synova实际应用的例子 + 一段对其他AI工程团队的参考价值。

---

## 原则一：第一性原理推导

**核心主张**：不预设数量，不照搬行业惯例。从系统的最简不可约简模型出发，演绎推导所有可能的组成部分。推导出的数量如果和已有估计吻合，这是验证；如果不吻合，这是修正。

### Synova实例：42条边的推导

在权威文档01中，Synova的本体层设计没有从"业界通常有多少条因果边"出发。起点不是"42"——起点是"一家企业如何运转"的最不可约简模型：资本和人才进入企业 -> 通过决策分配到活动 -> 转化为产品或服务 -> 交付给客户 -> 客户付费后重新进入循环。

从这个闭环模型出发，我们问了三个问题：
1. 循环在哪些位置可能断裂？——五个位置（获取/配置/转化/交付/回流）
2. 每个位置上，逻辑上存在多少种唯一的断裂方式？——38种
3. 横切所有位置但不属于任一位置的感知能力有多少种？——4种

38 + 4 = 42。推导结束时，数字"42"不是设计目标——它是推导结果。如果推导结果是35条边，我们会接受35条边。如果推导结果是55条边，我们会重新审查是否过设计。

验证：在客户A案例中，38种断裂方式中至少有11种在该企业的财务报表和诊断报告中有直接体现（成本结构硬化、客户流失、定价传导、人才流失等）。没有被客户A证伪的断裂方式保留在体系中，标注为"待数据积累后验证"。

### 对其他AI工程团队的参考价值

大多数AI Agent项目从"竞品有什么功能"出发——这种归纳法受限于竞品的认知边界。第一性原理推导要求团队在写第一行代码前先回答：这个系统在其最简形式下，逻辑上必须包含哪些部分？

对于构建推荐系统、决策引擎、知识图谱、诊断Agent的团队：先定义你的"最小不可约简模型"——推荐系统的最简模型是"用户 -> 物品 -> 场景"三元组；决策引擎的最简模型是"输入 -> 推理 -> 输出"；知识图谱的最简模型是"实体 -> 关系 -> 属性"。从这个模型演绎推导所有可能的变体和边界情况，比照搬竞品的功能清单更有机会发现对方的盲区。

## 原则二：物理现实锚定

**核心主张**：每一个理论定义必须在一个真实案例中验证。硬度不是研究者拍脑袋——是参数覆盖率>=80%且预测偏差<15%。数据驱动的工程决策，不靠经验直觉。

### Synova实例：客户A零基验证

42条边定义了每个断裂点的transfer_function、参数语义、正常范围。但理论定义到工程可用之间有一个鸿沟：这些参数在真实企业中能不能被采集到？

客户A提供了这个锚定。通过该企业的财务报表（Financial节点时间序列）、门店数据（CLIENT节点）、OEM转型记录（PROCESS节点），我们逐条边验证：

- E-05 CAPITAL_ACQUISITION：cash_runway=18个月（equity=200万/monthly_burn=11万）——参数覆盖率80%，hard。验证通过。
- E-23 OPERATIONAL_EXECUTION：fixed_cost_ratio=72%，efficiency_rate与成本结构一致——参数覆盖率85%，hard。验证通过。
- E-04 PERCEPTION_LEARNING：需要企业认知模型与外部现实的对比数据——参数覆盖率25%，heuristic。验证失败——标记为"缺失数据：需GA定义internal_model维度"。

零基验证不是一次性活动。它的持久价值在于：每次软边标注了"缺失什么数据、何时可重新评估"。E-04在客户A验证时是heuristic，但如果该企业后来配置了市场认知模型的数据采集，E-04可以重新评估并升级为soft或hard。

### 对其他AI工程团队的参考价值

AI系统的最大风险不是"算错了"——是"在数据真空里算出了看起来很合理的答案"。每一个模型输出必须有一个物理锚点——一个可验证的真实世界参照物。对于构建金融风控、医疗诊断、供应链预测的团队：在模型上线前，选取一个真实案例，逐项验证模型的输入参数是否能从该案例中获取、输出预测与该案例的实际结果偏差是否在可接受范围内。如果参数覆盖率<50%，标记该模型组件为"heuristic"——不要在用户界面上把它当作可信计算输出。

## 原则三：正交性保证

**核心主张**：四层分离——表达层、编排层、计算层、存储层。每层只与相邻层通信。变更频率从上往下递减。修改因果链不影响42条边，修改42条边不影响GraphStore Schema。

### Synova实例：因果链与42条边的正交分离

这是Synova在架构演进中最重要的决策之一。最初的方案是把因果链的传导逻辑硬编码在42条边的transfer_function中——E-23的输出直接包含"传导到E-30"的逻辑。这意味着：
- 新增一条因果链 = 修改42条边中多条边的代码 = 全量回归测试
- 两条因果链共享同一条边但传导角色不同 = 边的代码越来越复杂
- 客户A的一条因果链需要修改，但修改会影响所有企业

正交分离的解决方案：因果链是独立的YAML文件，只定义"从边A到边B再到边C的传导顺序"。42条边的transfer_function不知道自己被哪条链调用——它只负责"给定输入，计算输出"。

结果：
- 新增因果链 = 新增一个YAML文件，零代码修改
- 修改因果链 = 修改YAML文件，不影响其他链或其他企业
- 42条边稳定后可以长期不变，因果链可以随新诊断场景持续新增

### 对其他AI工程团队的参考价值

正交性设计是"长期可维护性"的工程基础。大多数AI系统在早期为了快速交付，把数据采集、特征工程、模型推理、结果展示耦合在一起——这在第1-2个月没问题，在第12个月会成为技术债务的地狱。对于构建多模型/多Pipeline的团队：画一张你的系统的"变更热力图"——哪些组件变更频率最高？哪些最低？高频变更的组件和低频变更的组件之间是否有不必要的耦合？如果高频组件的改动需要低频组件配合修改——那就是正交性缺失。

## 原则四：端到端验证

**核心主张**：不仅验证"每个零件是否工作"（单元测试），还验证"所有零件拼起来是否工作"（MVS黄金数据集）。每次系统升级后自动回归——同一个案例的同一个问题，不能因为升级而得到不同答案。

### Synova实例：黄金数据集checksum机制

Synova的测试金字塔有三层：
1. 单元测试：每个compute函数有独立测试（铁律48：测试不可为空壳）。验证的是"computeDOL在给定输入下输出是否在预期范围内"。
2. 集成测试：check-integration.sh的L1+L2。验证的是"哨兵引用的边在42边体系中存在"。
3. 端到端回归：黄金数据集checksum机制。验证的是"用客户A的同一份数据、同一个问题，系统升级后是否给出相同的答案"。

第三层是Synova最独特的测试方法。它的价值在第一次被触发时就显现了：

假设场景：工程师修复了E-23的效率计算bug——以前把variable_cost和fixed_cost搞混了，导致efficiency_rate被高估了20%。修复后，efficiency_rate从0.72降到0.60。这个修复是正确的——但哨兵Finding的checksum变化了（因为margin-health的输入参数变了）。工程师在变更记录中说明"修复了E-23效率计算bug，efficiency_rate从0.72修正到0.60" -> 预期内的checksum变化 -> 通过。

再假设场景：工程师重构了专家提示词模板，调整了措辞但结论不变。checksum变化了（因为诊断报告文本变了）。但报告的结论"利润率下降的根因是成本结构刚性"不变 -> 预期内的措辞变化 -> 通过。

再假设：checksum变化了，但找不到任何变更记录。工程师排查发现：不知道什么时候GraphStore的索引被重建了，导致Financial节点的排序变了，进而影响了时间序列的计算。这是一个非预期退化 -> 被发现 -> 回滚 -> 修复。

### 对其他AI工程团队的参考价值

AI系统的"无声退化"是最隐蔽的bug——某次模型更新、某次特征工程调整、某次数据管道变更，悄悄地改变了系统输出的分布，但没有任何告警。对于构建生产级AI系统的团队：锁定一个黄金测试集（5-10个真实案例），记录每次完整运行的输出checksum。任何变更后重新运行并对比。checksum变化的 -> 必须能解释原因。不能解释的 -> 回滚。这个机制不需要复杂的监控基础设施——它只需要一个固定的输入数据集和一个哈希函数。

## 原则五：持续进化

**核心主张**：soft边标注"缺失什么数据、何时可重新评估"。客户A零基验证发现的NEW边候选项作为下一代本体层的演进起点。知识循环（诊断->导航->学习->再诊断）是系统的节拍器。

### Synova实例：从soft到hard的升级路径

42条边中，目前约30条是hard（参数覆盖率>=80%），10条是soft（50-80%），5条是heuristic（<50%）。但这三个数字不是固定的——它们随客户数据积累而动态变化。

每条soft边都标注了：
- 缺失什么数据：如E-34 PROCUREMENT_POWER缺少supplier_reliability的量化数据
- 何时可重新评估：如"当GA配置了Tool节点分类（供应商/自有/租赁）和可靠性评分后"
- 当前默认值：如reliability_i默认0.8

这个机制确保系统的能力不会停留在初始版本。随着客户A（以及后续客户）的数据积累，soft边逐步升级为hard边——不需要修改边的定义，只需要补充数据源。

### 对其他AI工程团队的参考价值

大多数AI系统在设计时有一个隐含假设：模型的能力在初始版本就冻结了。但现实是，数据质量会随着时间改善（客户从手工录入升级到API集成）、业务逻辑会变化（新业务线需要新特征）、外部环境会变化（市场基准数据更新）。对于构建"活"的AI系统的团队：为每个模型组件标注一个"成熟度"等级。hard = 已验证且稳定。soft = 理论成立但数据不足。heuristic = 经验规则占位。每次数据升级后，重新评估soft组件的成熟度——这是一个持续向好的过程，而不是一次性的交付。

## 方法论适用场景

这五个原则构成了一个完整的方法论链条：

```
第一性原理推导 -> 定义系统的最小不可约简模型（原则一）
     |
     v
物理现实锚定 -> 用真实案例验证模型的每个组件（原则二）
     |
     v
正交性保证 -> 将系统拆分为独立演进的层次（原则三）
     |
     v
端到端验证 -> 用黄金数据集保证系统不退化（原则四）
     |
     v
持续进化 -> 标注成熟度，随数据积累升级（原则五）
```

这套方法论在Synova之外的场景中同样适用——任何需要构建复杂因果推理系统的团队都面临同样的设计挑战：如何保证系统在理论上是完备的、在工程上是可验证的、在长期是可维护的、在演进中是不退化的。13+1份文档不仅定义了Synova的工程蓝图——也提供了可复用的方法论答案。
