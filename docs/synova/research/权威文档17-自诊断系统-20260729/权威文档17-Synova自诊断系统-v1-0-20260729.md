# 权威文档 17：Synova 自诊断系统

> 2026-07-29 | 控制塔 v3 —— 从"组件健康检查"升级为"系统完成度持续测量装置"
> 核心洞察: Synova 诊断企业增长瓶颈——如果连自己的代码质量都无法持续诊断, 这个承诺是虚伪的

---

## 零、第一性原理推导

### 0.1 Synova 的自我指涉

Synova 诊断企业的增长瓶颈——42条因果边、50个哨兵、8位专家、三层记忆、联邦进化。但如果连自己的代码质量都无法持续诊断, 那它为企业诊断增长瓶颈的承诺是虚伪的。

这个推导不是哲学命题——是工程命题。Synova 已有的诊断基础设施(哨兵自动扫描、专家分析偏离、Goal追踪修复)可以直接应用于诊断自己的代码质量。42条因果边变成代码质量维度, 哨兵变成自动化检查, 专家变成验证层, host变成CI编排器。

### 0.2 为什么不是"再做一次审计"

我们刚完成了跨文档一致性审计(9轮+2专项, 发现8 P0/28 P1/6 P2)。控制塔Graph升级方案设计了工作流图+PM仪表盘+Agent链路健康。但这些都有一个共同前提: **系统的预期状态是已知的。** 如果不知道"系统应该是什么样子", 所有的偏差分析都是在模糊的地基上测量。

之前方案依赖的"预期状态模型"尚未建立。AGENTS.md和16份权威文档定义了系统的预期——但它们之间存在不一致(跨文档审计已发现), 无法直接作为自动化提取的输入。

### 0.3 这次升级解决的根本问题

几百个D#任务运行了四个月。17门禁显示17 Pass / 0 Partial / 0 Fail——一切看起来完整。但在过去一周的深度研究中, 我们零散发现了: triggerFullDiagnosis函数被附录A引用但代码中不存在; bcrypt.hash被声称在enterprise.ts中调用但实际是死导入; ProactivePush用空数组实例化; feedbackCollector只导入了类型从未被调用; 审计器Ch5定义了5个子模块但实际实现了2个。

这些发现有一个共同特征: **它们不是被系统性地发现的——是在研究其他问题时偶然暴露的。**

**这次升级的目的: 用系统性的自诊断替代偶然发现。** 不是做一次更好的审计——是让Synova拥有持续诊断自己的能力。和它诊断企业增长瓶颈用的是同一套逻辑。

## 二、"完成"的量化定义

### 2.1 六条件判定

一个任务真正完成当且仅当满足以下六个条件:

| # | 条件 | 自动验证方式 | 数据来源 |
|:---:|------|------------|---------|
| 1 | 代码存在 | 任务声明的文件已创建, 函数已定义(非空壳) | Test-Path + rg函数签名 + 空壳检测(§2.2) |
| 2 | 接线完整 | 函数已被至少一个**生产代码**调用方引用(非仅测试引用) | 依赖图入边分析——排除.test.ts文件 |
| 3 | 测试存在 | 至少一个测试文件, 包含>=3个expect()断言 | rg "expect("计数 |
| 4 | 路径可达 | 函数可以从系统入口(HTTP/MCP/TUI/启动序列)被调用 | 从入口节点反向BFS搜索依赖图 |
| 5 | 依赖可用 | 函数依赖的所有模块/库路径指向存在的文件 | import路径Test-Path验证 |
| 6 | 无已知缺陷 | 该函数没有被任何P0/P1偏差标记 | deviation-report.json中无该函数的P0/P1条目 |

**任务完成度 = 已满足条件的数量 / 6**

**系统完成度 = 所有任务完成度的加权平均值**(权重: 核心诊断链路任务权重x2, 普通任务权重x1)

### 2.2 空壳判定矩阵

条件1的"非空壳"判定——不是简单的函数体 < 20字符。使用多维判定:

| 模式 | 判定规则 | 严重度 | 已知实例 |
|------|---------|:---:|---------|
| 空构造 | `new X([])` 或 `new X(null)` | P0 | ProactivePush([]) in synova-agent.ts:90 |
| 类型导入 | `import type { X }` 无对应实例化调用 | P0 | feedbackCollector in middle-evolution-engine.ts:15 |
| 存根函数 | 函数体仅 `return {}` / `throw Error('Not implemented')` | P0 | 多个connector文件 |
| 死导入 | import了但文件中无任何调用 | P1 | bcrypt in enterprise.ts:22 |
| 假接线 | 调用了但传入关键参数为空/无效 | P0 | setX(new Y())但Y为空壳 |

### 2.3 审计脚本自身的质量保障

L1-L4审计脚本的代码也在六条件判定范围内。每个审计脚本必须附带测试用例:
- 正样本: 已知的"好代码"——审计脚本必须返回PASS(零误报)
- 负样本: 已知的"坏代码"——审计脚本必须检测出问题(零漏报)

如果审计脚本自己的测试用例不通过——该审计脚本标记为"不可信"——其产出不阻断CI, 仅作为参考信息展示。审计脚本的完成度同样用六条件评分, 显示在自诊断仪表盘中。

## 三、版本化快照系统

### 3.1 存储结构

```
.codex/snapshots/
  2026-07-29T081530Z/
    gate-status.json          # 17门禁实时状态
    dependency-graph.json     # 全量依赖图(文件×import关系)
    completion-scores.json    # 所有任务×6条件得分矩阵
    deviation-report.json     # 偏差清单(含唯一ID+严重度+修复指引)
    audit-scripts-health.json # L1-L4审计脚本的自身六条件得分
    system-summary.json       # 系统完成度+趋势
  2026-07-28T184500Z/
    ...(同上结构)
  2026-07-27T120000Z/
    ...
  latest -> 2026-07-29T081530Z/  # 符号链接指向最新
```

### 3.2 快照生命周期

| 操作 | 触发条件 | 实现 |
|------|---------|------|
| 创建 | check-gates-v2.py运行结束时 | 将全部产出写入snapshots/{ISO 8601 timestamp}/ |
| 保留 | 最近30天: 每日 | 每日首次运行时快照 |
| 保留 | 30-90天: 每周 | 每周一首次运行时快照 |
| 保留 | 90天以上: 每月 | 每月1日首次运行时快照 |
| 清理 | 自动过期 | shell脚本, cron每周执行 |
| Git | 不纳入版本控制 | 快照目录加入.gitignore |

### 3.3 趋势计算与基线漂移分离

两个快照之间的趋势不需要额外存储——直接diff两个快照目录中的同名JSON文件。基线漂移的分离:

- **基线内变化**: 与上次快照中**相同**的任务集合对比(同任务集的完成度变化)
- **基线扩展**: 新增任务带来的分母变化

仪表盘的趋势线用两根线展示: 基线内变化(实线)和包含扩展的总线(虚线)。如果两根线方向相反——总线下降但基线内上升——说明问题不在质量退化, 在任务增加了。

### 3.4 本地部署的定时补偿

客户设备可能离线(晚间关机、周末休息)。系统启动时自动检查上次诊断运行的时间戳——如果距离上次运行已超过24小时, 在启动后的第一个空闲时刻自动补跑一次诊断。确保快照连续, 不因开关机模式产生空档期。

## 四、自诊断四层验证

### 4.1 触发机制

| 触发事件 | 执行范围 | 阻断规则 |
|---------|:---:|------|
| git push | L1(物理存在性) | 阻断push——代码物理事实不满足预期 |
| 合并请求 | L1+L2(接口契约) | 阻断合并——接口契约断裂 |
| 每日定时 | L1+L2+L3(行为正确性) | 标记为"需人工审查"——行为异常可能是预期内的 |
| 发布前 | L1+L2+L3+L4(集成一致性) | 阻断发布——集成链路断裂 |

### 4.2 L1: 物理存在性验证(30秒内)

每个声称存在的文件/函数/接口是否真实存在？每个声称被引用的模块是否真的被import？每个声称被实现的函数是否有非空的函数体(空壳检测)?

产出: `layer1-existence.json`——红色标记的项直接阻断CI

### 4.3 L2: 接口契约验证(2分钟内)

每个compute函数的输入输出是否与权威文档定义的contractId一致？每个哨兵的manifest.json中声明的依赖是否在代码中存在对应实体？每条因果边的参数是否被至少一个compute函数消费？

产出: `layer2-contracts.json`——P0级契约断裂直接阻断CI

### 4.4 L3: 行为正确性验证(5分钟内)

用客户A真实数据运行每条P0级因果边的transfer_function, 检查输出是否符合经济学直觉。用已知的"坏代码"样本验证审计脚本能正确检测出问题。用已知的"好代码"样本验证审计脚本不产生误报。

产出: `layer3-behavior.json`——回归失败直接阻断CI

### 4.5 L4: 集成一致性验证(10分钟内)

启动一次完整诊断流程(Phase 0->5), 检查是否能产出有效的诊断报告。检查诊断报告中引用的证据ID是否能在GraphStore中追溯到真实数据。检查Goal创建->方案哨兵注册->偏离检测->轻量级再诊断的完整链路。

产出: `layer4-integration.json`——链路断裂直接阻断CI

### 4.6 阻断附带修复指引

每个阻断不仅仅报告"什么错了"——还报告"怎么修":
- 缺失的文件应该放在哪个目录(基于AGENTS.md的五层架构)
- 缺失的函数应该实现什么接口(指向权威文档的具体章节)
- 可以参考哪个已有的类似实现作为模板

阻断消息格式: `BLOCKED: {问题描述} | FIX: {修复路径} | REF: {参考任务ID/权威文档章节}`

## 五、偏差闭环

### 5.1 偏差→任务→验证

自诊断循环发现偏差后, 自动三步:

1. **创建偏差ID**: 基于文件路径+符号名+偏差类型做SHA256哈希的前12位
2. **写入修复队列**: 在PM仪表盘中显示为待处理项, 附带严重度+修复指引+参考实现
3. **下次运行时验证**: 同样的偏差ID如果在下次快照中不再出现->自动标记为已修复

### 5.2 偏差消失模式检测

偏差ID在下次快照中不再出现——不一定是因为修好了。为每个偏差ID增加"消失模式"检测:

| 消失模式 | 判定 | 动作 |
|---------|------|------|
| 纯修复 | 函数签名不变+文件路径不变+测试文件不变 | 自动标记为已修复 |
| 移动 | 函数签名不变但文件路径改变 | 标记为"需人工审查——可能被移动" |
| 重命名 | 文件路径不变但函数签名改变 | 标记为"需人工审查——可能被重命名" |
| 删除 | 函数和文件都不再存在 | 标记为"已移除"(非修复)——如果两个快照后重新出现, 标记为"复发" |

### 5.3 复发检测

一个偏差ID在两次快照中消失后又重新出现->自动升级严重度(P1->P0)并标记为"复发"。复发超过3次的偏差->自动生成一条Iron Law候选。

## 六、Iron Law进化

### 6.1 模式匹配

自诊断循环发现的每个偏差, 如果能匹配到AGENTS.md中已定义的48条Iron Law——自动标注铁律编号。如果**不能匹配**——在全部48条中找不到对应项——自动生成一条候选Iron Law, 推送给创始人审核。

### 6.2 候选Iron Law格式

```markdown
## Iron Law {编号}: {简述}
**首次发现**: {快照时间戳}
**复发次数**: N
**影响范围**: {受影响的任务数/文件数}
**触发条件**: {偏差ID的检测规则}
**修复方式**: {已有的成功修复案例}
**状态**: 候选——待创始人审核
```

审核通过后, 新铁律加入AGENTS.md, 后续自诊断循环自动执行这条规则。这是Synova自己的联邦进化——从自己的工程教训中持续学习。

## 七、与控制塔的集成

### 7.1 作为第四个视图

控制塔现有三个视图: 工作流图、PM仪表盘、Agent链路健康。自诊断系统是**第四个视图——系统完成度**。

| 视图 | 回答的问题 | 数据来源 |
|------|----------|---------|
| 工作流图 | 开发流程的哪个环节在卡？ | 依赖图+信号文件 |
| PM仪表盘 | 离客户部署还有多远？ | 门禁+任务状态 |
| Agent链路健康 | 三个Agent之间的协作效率？ | git log+task briefs |
| **系统完成度(新)** | 系统的每个部分处于什么状态？和上周比变好还是变差？ | **快照目录** |

### 7.2 信号发射器Schema扩展

`emit-signal.py`当前只输出: `component, status, timestamp, reason, p0_count, p1_count, p2_count`。扩展后增加:

```json
{
  "component": "gatekeeper",
  "status": "green",
  "timestamp": "...",
  "reason": "all_checks_pass",
  "p0_count": 0, "p1_count": 0, "p2_count": 0,
  "completion_score": 1.0,          // 新增: 六条件完成度(0.0-1.0)
  "deviation_list": []              // 新增: 该组件的偏差ID列表
}
```

仪表盘复用现有信号文件路径和加载逻辑——只消费的字段增加了。

### 7.3 仪表盘版本管理交互

- 默认显示最新快照(通过`latest`符号链接)
- 时间轴滑块: 可拖拽到任意历史快照
- 差异模式: 选择两个快照, 高亮显示变化
- 趋势线: 30天系统完成度变化(两根线——基线内实线+含扩展虚线)
- 偏差生命周期面板: 首次发现时间 -> 修复时间 -> 复发次数 -> 当前状态
