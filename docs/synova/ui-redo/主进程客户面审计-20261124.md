### 3.3 行为发现（不是禁词，但客户直接可见）

1. **P0 告警会弹两条系统通知。** `electron/main.cjs:306` 先 `new Notification({title, body}).show()`；紧接着 `:310` 把同一 `title/body` 推给 renderer，`electron-renderer/src/App.tsx:97-104` → `pushLocalNotification` → `electron-renderer/src/stores/app-store.ts:234` → `electron/preload.cjs:64` → `electron/main.cjs:222-227` 再构造一条 `Notification`。**同一次 P0 事件有两条独立构造**；客户可能看到两条（或平台通知中心归并成一组，取决于 OS）。证据：上述 path:line 的静态调用链；未启动应用观察。
2. **重复频率。** `checkP0Alerts` 在 `app.whenReady` 后 5 秒先跑一次（`electron/main.cjs:294`），之后每 `POLL_INTERVAL`（`config.json` 300000 ms＝5 分钟，`electron/main.cjs:26`）跑一次；只要 `redCount > 0` 就再次弹。客户在告警未清零期间会每 5 分钟收到一轮（每轮两条构造）。
3. **通知文案无内容校验。** `electron/main.cjs:223-227` 只对 title/body 做长度截断与空 title 兜底，不校验文案来源与内容；`notify:show` 是 renderer 可调通道（preload 暴露），因此任何 renderer 侧调用都把字符串原样送到 OS 通知。
4. **截断形态。** `clampText`（`electron/main.cjs:182-185`）对超过 200 字符的 title/body 取前 200＋`…`；客户看到的是截断文本，不是完整句。

### 5.5 D 项判定与关键发现

**判定**：`app/login.html` 是**第二登录实现**，但它是**旧 Web UI 的登录页 + dev 回退**，不是桌面 renderer 的并行可用登录面。它与 `DshLoginPanel` **并存于代码、互斥于窗口**；根据当前代码，它连 `/api/auth/login` 的请求体都对不上（`userId/role/orgId` vs `email/phone/wechatId/password`），提交必 400，**不能完成登录**。是否退役／收敛由 CTO 定；本审计不改。

**关键发现（供 T4/T6 与 CTO 决策）**：

1. **表单契约失配**：`app/js/auth.js:16` 发 `userId/role/orgId`，`src/routes/auth.ts:115-117` 只认 `email/phone/wechatId/password`；密码框 `disabled`（`app/login.html:25`）且未提交。⇒ 正常提交必 400，客户看到 `email/phone/wechatId 和 password 必填`（F9）。
2. **状态分支失效**：`app/login.html:82/84` 用 `err.message.includes('401'/'403'/'500')` 判断，但服务端 401/403/500 的 `message` 是中文文案、不含这些数字（`src/routes/auth.ts:128/129/135`）⇒ F3/F4 对当前服务端不可达，实际显示的是服务端原文（F10/F11/F12）。
3. **旧 Web UI 证据**：成功后跳 `/app/dashboard.html`（`app/login.html:51/76`）；`app/js/auth.js:42` 登出回 `/app/login.html`；与 renderer 的 DSH 视图无关。

### 6.4 结构性防线缺口（本审计为什么必须存在）

- **T1 的扫描根**是 `electron-renderer/src/**`（DEV DOC §5.4；任务卡 §1 明示「T1 只扫 electron-renderer/src」）。`electron/**`（托盘、通知、离线页）与 `app/**`（旧 Web UI 登录页）**结构性地不在账内**；本报告补的是这块盲区。当前没有任何门禁／测试对这两处的客户文案做 §1 检查：`tests/routes/setup-guide-retired.test.ts:162-164` 只断言 `app/login.html` 仍可访问（200＋含 `login`），不断言文案；`tests/electron/ipc-contract.test.ts:170-172` 用 `expect(main).toContain("label: '打开 Synova'")`／`expect(main).toContain("label: '打开通知中心'")` 锁住**两项**菜单文案的存在（`Quit` 未被锁），但**不是 §1 判定**——T4/T6 改菜单文案时须同步改这条断言。
- **R2-18 的大小写缝隙**：`normalizeText` 不折小写，`Admin`/`Manager`/`Liaison`/`Staff` 这类首字母大写角色标签不命中；这是规则缺口，不是本审计自创的判定。是否把 `normalizeText` 改成折小写（会改 allowlist 键，按 DEV DOC §5.4 须升版本）由 CTO 裁定。
- **主进程通知无内容校验**：`notify:show` 的 title/body 由 renderer 透传，`electron/main.cjs` 只做长度截断（§3.3），所以「主进程客户面」的文案源其实在 renderer；这解释了为什么只审 `electron/main.cjs` 字面量会漏掉 `useStreaming` 的运行时正文。
