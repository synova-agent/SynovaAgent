## 0 判据与适用范围

### 0.1 三判据（缺一不可）

一个词可以出现在客户界面，当且仅当：

1. **可行动**——老板看了能拿去做判断或行动（"增长引擎健康度下降 12%"可行动；"五循环状态"不可行动）。
2. **无协议**——不含协议名、传输层名、运行时产品名、字段名、枚举原文、原始 id、HTTP 码、错误码。
3. **不用 id/数量证明价值**——"已完成 3 项、2 项待定"可以；"x12""node-1053…""calibrationId=…"不可以。

### 0.2 适用范围（客户可见 = 下列全部）

| 计入 | 不计入 |
|---|---|
| JSX 文本节点、模板字符串字面量 | `data-*` 属性值（开发者工具可见，非客户面） |
| `placeholder`、`title`、`aria-label` | `console.warn/error` 日志 |
| `<option>` 文本、按钮文案、空态文案 | 代码注释、JSDoc |
| **状态字典函数的返回值**（如 `statusText`/`errorText`/`authText`/`ticketStatusLabel`） | 服务端返回的**业务内容**（诊断报告正文、专家报告正文） |
| 模板拼接后的字符串（含把字段插进中文句子的） | |
| 主进程托盘菜单、系统通知标题与正文（**本版未审，见 §8 U-4**） | |

> 🔴 **模板拼接是重点**：`\`状态 {item.status}\`` 这类拼接会把枚举原值带进客户面，禁止词检查必须能抓到它。

### 0.3 唯一豁免：技术详情层

客户面**允许**出现原始协议内容的唯一位置是**「技术详情」折叠层**：默认收起、标题固定为`技术详情`、展开后内容不加修饰（便于支持与复现）。除此之外任何位置都不得出现 §1 禁用词。

### 0.4 宪章文案红线（上游约束，词典不得违背）

依据**产品宪章 v8.5**（当前执行版，`docs/synova/产品宪章-v8.5-修订稿.md`）：

| 宪章条款 | 对客户文案的硬约束 |
|---|---|
| §1.3 性质二 | 必须**分别**呈现「事实 / 推断 / 未知」，并给**证据、缺口、替代解释**；**不得把关联说成根因**，**不得把时间相关说成确定因果**。UI 里出现「根因是…」「因为…所以…」必须有替代解释或缺口语，否则违宪。 |
| §8.2 五条服务纪律 | 不承诺做不到的；**不宣称「越用越准」**；每条结论带来源；交付物必须可被董事会议论；退出时数据可带走。 |
| §6.2 可见性承诺 | 客户**可随时查看**「发什么、发多少」（外发内容与范围）。UI 必须有这个可查看面。 |
| §6.3 前端 | **壳是我们的；内容可以用 DSH 的**——占插槽不 fork；四条判据（可独立升级／可摘除／不侵入宿主／失败可降级）。 |

### 1.1 可判性分级（决定 T1 的阻断口径）

> 上表混装了两种东西：**纯正则可判**，与**需要语义判断**。零上下文 coding 若被要求"全部机器可判"，只有两个结果：过匹配（清单爆炸）或静默收窄（规则形同废掉）。故此处显式分级。

| 级别 | 规则 | T1 行为 |
|---|---|---|
| **M（机器可判，阻断）** | R2-01、R2-02、R2-03、R2-04、R2-05、R2-06（**不含**`内存`）、R2-07、R2-08、R2-09、R2-10、R2-11、R2-12、R2-13、R2-14（**不含**`循环`）、**R2-15（仅 `运行编号`／`会话编号` 两个精确串；裸 `会话` 见 §1.2）**、R2-16、**R2-18（裸英文枚举）**、**R2-19（枚举值域插值直出）**、R1-01，以及 §1.2 里被操作化的精确串 | 命中即违规；清单外命中 ⇒ 红 |
| **H（需人工，仅报告）** | `内存`（作安全说明）、`循环`（作名词，非"五循环"）、`会话`（作产品名词，非 §1.2 精确串）、`暂无数据`（是否"裸用"需读上下文） | 只输出复核清单，**不计入阻断**；由人工判定后**追加**为 §1.2 精确串，下一版转 M |

### 1.2 需人工项的精确操作化（M 化的第一步）

| 原规则 | 操作化为可判精确串/形态 |
|---|---|
| `暂无数据`（裸用） | **全等即红**：客户可见字符串去空白后 `=== '暂无数据'`。原因句的存在性由人工复核（H 级）判断，不由正则猜。 |
| `会话`（作产品名词） | 命中下列**精确串**即红：`DSH 会话`、`会话编号`、`会话输入`、`发起会话`、`关闭会话`、`尚未发起会话`、`会话已关闭`。其余含「会话」的句子进 H 级复核。 |
| `循环`（作名词） | 命中 `五循环`、`五循环状态`、`暂无循环`、`加载循环` 即红。裸「循环」进 H 级复核（中文本义"循环"合法）。 |
| `内存`（作安全说明） | 命中 `只在内存`、`保存在本进程内存` 即红；其余「内存」进 H 级复核。 |
| `运行编号` / `会话编号`（R2-15） | **精确串即红**（机器可判，M 级）：`运行编号`、`会话编号`。现状真实泄漏点：`DshRunPanel.tsx:175`「运行编号：{runId}」、`:176`「会话编号：{sessionId}」。客户不需要这两个编号；追溯走「技术详情」。 |
| 裸英文枚举（R2-18） | **`normalizeText` 后全等即红**（M 级），集合：`workspace`、`conversation`、`command`、`sentinel`、`admin`、`manager`、`liaison`、`staff`、`ga`。现状真实泄漏点（T1 实施中发现）：`CommandPalette.tsx:150`「{item.type}」渲染 `workspace`/`command` 等；`ga-detail-sections.tsx:221`「当前角色（{userRole}）」渲染 `admin`/`manager`/`liaison`/`staff`。**注意**：`{…}` 是运行期插值，静态扫描只能命中"字面量本身就是枚举"的情形；数据驱动的那两处由**插值来源**判定，T4 改造（把枚举映射成中文）才是根治，T1 只登记债。 |
| **枚举值域插值直出（R2-19）** | **判据**：JSX 表达式容器 `{…}` 内的表达式，按下列规则命中即红（M 级）。<br>**① 全等**：整体去空白后全等于登记表成员。<br>**② 分支全等**（v1.1 补）：表达式的顶层 `||` / `??` 分支，**任一分支**去空白后全等于成员即命中（用于 `{item.targetType || item.targetId || '—'}` 这类复合表达式）——**不是前缀/包含匹配**，仍逐分支精确比对。<br>**登记表（13 项，CTO 维护，实施者不得自行增删）**：`userRole`｜`item.type`｜`t.status`｜`a.priority`｜`loop.lastExecution.status`｜`relation.type`｜`object.type`｜`entry.status`｜`source.evidence_status`｜`source.instance_state`｜`item.action`｜`item.targetType`｜**`props.role`**（转传后仍上屏：`RightPanel.tsx:1014 role={userRole}` → `ga-detail-sections.tsx:221 {props.role}`）。<br>**为什么要有这条**：R2-18 只认字面量，而真实的"技术字段直出"多发生在插值上；且 `admin`/`staff`/`ga` 这类短词被提取规则②排除，**R2-18 结构性看不见它们**（T1 实测：这三词候选数 = 0）。本规则打在**渲染位**上，所以 T4 把文案改成中文后，该条目会自然失效并被断言 2 逼着删掉 ⇒ **"改 UI 即销账"成立**。<br>**登记表里某项 0 命中不算失败**（是观察名单）；**新增项须 CTO 裁定**。<br>**属性值位置**（如 `role={userRole}`）**不算渲染位**，只在汇总里作为观察项打印、不登记进债单——但它**转传后的渲染位必须登记**（`props.role` 就是为此而加）。 |

> 🔴 新增 H 级条目转 M 时必须**同时**给出"现有代码里能被命中"的位置，否则该条不计入验收（防"加了条永远不命中的规则"）。

**判别力要求**：该清单必须能对**现有代码**报出违规（P3 起用于门禁/测试）。若跑出 0 命中而 §2 表里登记的现状文案仍在代码中 ⇒ 检查本身失效，按 exit 2 处理（不得当作通过）。

|---|---|
| 3.1 | **内部 id 默认不出现在客户面**。`runId`、`sessionId`、`manifest_id`、`client_request_id`、`calibrationId`、`signalId`、`findingId`、`supersedes` 一律隐藏；需可追溯时进「技术详情」。 |
| 3.2 | **业务对象必须有名字**。`node-<uuid>`、`team:delivery-a`、`businessKey` 原文都不得直接印出。后端给了名称就印名称；没给名称 ⇒ 印「未命名的业务对象」+「技术详情」里给原始 id。 |
| 3.3 | **来源引用要转人话**。`delivery_batches.csv#L3` ⇒ 「交付批次表 第 3 行」。文件名保留客户原文（那是客户的文件），行号必须转中文；`operator-statement.json` ⇒ 「人工说明（operator-statement.json）」。 |
| 3.4 | **会计式数字要有单位与量级**。`1,240` 不够 ⇒ 「1,240 万元」；`0.32` 比率 ⇒ 「32%」。单位来自服务端 `unit` 字段；缺单位 ⇒ 印「（单位未提供）」，**不许猜**。 |
| 3.5 | **时间要本地化到人可读**。完整 ISO（`2026-11-24T08:22:31.651Z`）不得直出 ⇒ 「11-24 16:22」（本地时区）。 |

## 4 三态规范（未加载 / 数据不足 / 已出结论）

> 现状最重的客户伤害不是术语，而是**三态混用**：老板分不清"没跑""没数据""跑出来是空"。

### 4.1 三态定义与强制文案

| 态 | 触发条件 | 必须显示 | 禁止 |
|---|---|---|---|
| **未加载** | 尚未请求 / 请求进行中 | ① 正在做什么（「正在读取本期指标…」）② 预计下一步 | 显示「暂无数据」；显示空列表 |
| **数据不足** | 请求成功但无内容；或内容不全；或请求失败 | ① **为什么没有**（未接入 / 未扫描 / 区间无数据 / 取不到）② **缺什么** ③ **怎么补**（一个可点的动作） | 只写「暂无数据」；把失败写成空态；把空态写成结论 |
| **已出结论** | 有可判读内容 | ① 结论 ② 依据（可回来源）③ 不确定性/边界 | 结论无依据；依据是原始 id/JSON |

### 4.2 「数据不足」四种原因必须分开（现状全部折叠成「暂无数据」）

| 原因 | 客户文案 | 可点动作 |
|---|---|---|
| 未接入数据源 | 「还没有接入企业数据」 | 「接入数据」 |
| 未做过扫描 | 「还没有做过企业扫描」 | 「开始扫描」 |
| 区间内无数据 | 「本期没有数据」+ 期间 | 「换个期间」 |
| 取不到（请求失败/降级） | 「暂时读不到数据」 | 「重试」 |

🔴 **禁止把第 4 类（取不到）显示成第 2 类（没做过）**——现状 `RightPanel.tsx:399`（报告 tab）正是这个错误：`fetchLatestReportId` 失败只 `console.warn` 就落回「请先进行一次诊断」。

### 4.3 空态禁止清单

- 裸「暂无数据」（`RightPanel.tsx:65`、`ga-detail-sections.tsx:58` 的 `Empty` 默认值）**不得**作为客户可见文案。
- 「暂无 X」句式一律补原因：`暂无哨兵报告` ⇒ 「暂无预警报告（本期尚未运行预警检查）」。
- 空态里**不得**放一张看起来像结论的卡片（四要素用占位散文填充）。

## 5 失败态规范

| # | 规则 |
|---|---|
| 5.1 | **失败必须与成功可区分**：状态词（失败/部分完成）+ 影响面（哪些内容不可信）+ 下一步（重试/联系顾问）。 |
| 5.2 | **HTTP 码与错误码只进技术详情**。主文案用：认证失效→「登录已失效，请重新登录」；403→「当前账号无权查看这项内容」；404→「这条记录已不存在」；409→「状态已变化，请刷新后重试」；5xx→「服务暂时不可用，请稍后重试」。 |
| 5.3 | **部分失败必须显式"部分"**：`K 项中有 M 项未能核对`。一轮分析里有失败环节，结论语**不得**写「已完成」，须写「已完成，但有 N 处未能核对」。 |
| 5.4 | **禁止同屏互斥结论**。现状 `DshRunPanel`：`status==='done'` 显示「运行完成」，随后「关闭会话」失败会再渲染「运行未完成」（`DshRunPanel.tsx:174` + `181`，`dsh-run-store.ts:510-524` 不改 `status`）⇒ 同屏两条互斥结论。修法：状态块只有一个来源，错误只能降级状态、不能并列。 |
| 5.5 | **「完成」不得由传输层决定**。SSE 收到 `end` 就等于「✅ 诊断完成」（`useStreaming.ts:170-175`）是假成功：普通对话、降级结果、报告未落库（`sse-contract.ts:107-117`）都会显示"诊断完成"。完成语必须依赖**业务终态**。 |
| 5.6 | **降级必须可见且带影响面**：`⚠ 部分内容未能更新（影响：报告、行动项）`，不许只 `console.warn`。 |
| 5.7 | **失败不得落到空态**。行动跟踪 tab 在 `/api/solutions` 失败时显示「无进行中的行动项」（`RightPanel.tsx:484-500`，降级条只渲染在 pattern 分支 `507`）——失败=空态，必须拆开。 |

## 6 导航与信息架构目标（P2 目标 IA）

### 6.0 宪章依据（上游，本词典不得改）

依据**产品宪章 v8.5**（当前执行版）：

- **⑤ 导航层 = 目标驱动的持续经营导航**：目标分解 · 岗位行动 · 偏差解释 · 决策变更 · 结果回验（§0.4 架构总图 L60-61）。
- **v8.5 经营回放**：⑤ **以目标和决策为索引**，沿真实引用**双向回放「目标—决策—行动—结果」**；**新决定不得覆盖旧决定及其当时依据**（§0.4 L70）。
- §1.3：解释**事实／推断／未知**，给出**证据／缺口／替代解释**。
- §6.2：客户**可随时查看**「发什么、发多少」。
- §6.3：**壳是我们的，内容可用 DSH**（占插槽不 fork）。

⇒ **IA 的第一公民是「目标」，不是「数据表」，也不是「对话」。** 本词典早前草案以「诊断/看板/行动」为三栏，**已按宪章 ⑤ 修正**（见 §6.3）。

### 6.1 主线

以「**我的目标推进到哪、卡在哪、该做什么、做到了没有**」组织界面——即宪章 ⑤ 的五件事与经营回放轴。**不按技术模块列菜单**，也**不以会话为第一公民**。

### 6.2 现状 vs 目标

| 现状（`LeftPanel.tsx:226-246`） | 目标 |
|---|---|
| 分组「产品独有能力」+ 四项（主动触达 / 五循环状态 / Action 闭环 / GA 协同） | **删除该分组**：能力不是客户概念，是内部能力清单 |
| 分组「导航」+ 五项（企业扫描 / DSH 会话 / 对话 / 工单 / 设置） | 一级导航 ≤4 项，见 §6.3 |
| 「工单」「设置」无 `onClick`（死项） | 删除或接线，**不许留着不响应** |
| 顶部 4 图标只切高亮、不切内容；「通知」图标不打开通知中心 | 图标必须有效，否则删除 |
| 「最近对话」不可点 | 合并进「增长诊断」的问题历史 |

### 6.3 目标一级导航（按宪章 ⑤ 修正）

| 序 | 一级项 | 客户问的问题 | 对应 ⑤ / 回放轴 | 内容 |
|---|---|---|---|---|
| 1 | **我的目标** | 我定了什么目标，推进到哪了 | 目标分解 | 目标树 + 进展 + 偏差；新目标不得抹掉旧目标 |
| 2 | **卡在哪**（默认首屏） | 为什么推不动，卡在哪 | 偏差解释 | 卡点结论 + 依据 + **缺口** + **替代解释** + 不确定性 |
| 3 | **该做什么** | 现在该做什么 | 岗位行动 | 建议清单 → **人拍板**（系统不自动执行） |
| 4 | **做到了什么** | 当初的判断对不对，做到了没有 | 决策变更 + 结果回验 | 决策台账（含当时依据，不许被新决定覆盖）+ 执行跟踪 + 系统输出 vs 实际结果 |
| — | **设置** | — | — | 数据接入、账号、主题、**外发可见（§6.2 承诺面）**、技术详情开关 |

**为什么这样排**：宪章 ⑤ 的五件事是「目标分解 · 岗位行动 · 偏差解释 · 决策变更 · 结果回验」。其中**决策变更与结果回验在客户视角是同一件事的两端**（我改了什么决定 → 后来的结果证明谁对），故合为第 4 项；其余三项各占一项。「卡在哪」作默认首屏，因为它回答产品核心问题，且性质一要求「不等被问」。

**缺口登记（本模块不实施，必须记账）**：宪章 §6.2 承诺的「**发什么、发多少，客户可随时查看**」在当前界面**完全没有对应面**（renderer 内无外发记录视图）。这是**承诺级缺口**，不属 UI 文案问题，应单独立项；本词典只在设置页为它留出位置。

**迁移去向**：
- 「企业扫描」⇒ 收进「我的目标 → 数据来源」子页 + 首次接入向导；**不作一级项**（客户不关心"扫描"这个动作，只关心结论可不可信）。
- 「DSH 会话」⇒ **撤出一级导航**，作为「技术详情」内的执行日志（壳自有，内容可插，见 §7）。
- 「对话」⇒ 合并为各页顶部的提问框（老板直接问，但答案落回目标/卡点/建议的结构里，不落成聊天流）。
- 「工单」⇒ 并入「做到了什么」的待办。
- 能力四项（主动触达/五循环/Action/GA）⇒ 分别落到「卡在哪（预警）」「我的目标（增长引擎健康度）」「做到了什么」「顾问协同（仅顾问角色可见）」。

### 6.4 导航硬要求

| # | 要求 |
|---|---|
| 6.4.1 | 左栏与右栏**必须有可见的收起/展开控件**（现状只有 `Ctrl+B`/`Ctrl+J`，界面无按钮：`TitleBar.tsx:50-65` 只有通知/主题/快捷件；`useKeyboard.ts:28-35`）。 |
| 6.4.2 | 收起后**必须有可见恢复入口**（现状收起后「企业扫描/DSH 会话/对话」入口全消失且无恢复按钮：`LeftPanel.tsx:310-329` 只画 4 个能力图标）。 |
| 6.4.3 | **当前视图必须高亮**（现状导航组三个可点项 className 固定为 `cap-item`，无 `active`：`LeftPanel.tsx:227/231/235`）。 |
| 6.4.4 | 键盘快捷键必须在客户可见位置告知（现状「快捷键」按钮 `onClick={() => {}}` 为空实现：`TitleBar.tsx:62`）。 |

> 标注规则：该专件里 ✅ 可直接照数值、⚠️ 只借模式须自定、❌ DSH 也没有由我们自定；**⚠️/❌ 项不得对外表述为"DSH 的做法"**。

### 7.2 不借什么（禁止照搬）

DSH 的导航结构（按技术模块分栏）、DSH 的会话模型（会话当第一公民）、DSH 的内部术语与命名、DSH 的协议层字段展示。

### 7.3 壳／内容分线（宪章 §6.3 判据）

**壳 = Synova 自有，不可让渡**：导航结构、信息架构、客户语言与词典、主题令牌、三态/失败态表达、目标与决策的呈现模型。
**内容 = 可用 DSH 的**：模型调用后的事件呈现、工具调用节点的渲染、会话内消息流。

| 宪章四条判据 | 本项目的判据落地（验收怎么证明） |
|---|---|
| **可独立升级** | 升级 DSH 版本后，壳的导航与文案零改动（改前后 `electron-renderer/src/components/**` 无 diff 且可见文案一致） |
| **可摘除** | 摘掉 DSH 内容层 ⇒ 壳仍可用，显式显示「内容不可用」，**不白屏、不崩溃、不假成功** |
| **不侵入宿主** | DSH 内容不得改写壳的导航、文案、主题令牌（内容层不得注入全局 class/样式覆盖） |
| **失败可降级** | DSH 内容失败 ⇒ 壳显式降级并给出影响面（见 §5.6） |

### 7.4 硬约束

- **占插槽不 fork**：不修改 DSH 内核或其 UI 包（停点 2）；不复制其内部实现来"自己养一份"。
- 借的是**模式与常量值**（§7.1 表），在 `electron-renderer` 内自实现壳部分；内容若用 DSH，必须走插槽且满足 §7.3 四条判据。
- 不引入 DSH 的**导航结构／会话第一公民模型／内部术语**——这三样属壳，属混用即违 §6.3。
