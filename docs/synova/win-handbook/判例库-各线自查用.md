# 判例库（**各线自查用 —— 遇到模糊先查这里，别问 CTO**）

> **为什么有它**：CTO 成为"系统尴尬的汇聚点"，根因不是各线不担事，是**系统的模糊没有归宿**。
> 建库 = 给模糊一个归宿：**先查判例 → 再按最保守解释做并显式标注 → 只有"答案会改变方案"时才上报。**
> **用法**：开工前扫一遍；遇到判不准的，按 `P-` 族找同类。
> **维护**：新增判例由 CTO 裁后入库（各线可提议，不许自入）。每条含【判据 + 出处 + 反例】。

## 一、S 族 · 来源与证据（「你说的是真的吗」）

| # | 判例 | 判据 | 出处 |
|---|---|---|---|
| **S-01** | **工具口径误读三纪律** | ① 用 totalCount 类接口，不用默认截断的（`gh project item-list` 默认 30 条）② 用真相源不用代理（`git show origin/main:` 而非工作树 `cat`）③ 数字前 `tr -d '\n\r'` | L-044 |
| **S-02** | **一切"现状"必须带 as_of** | 引用别人或自己的旧读数前，先 `git merge-base --is-ancestor <commit> origin/main`；未入 main 标 `[local]` | L-038 同型 6 次 |
| **S-03** | **"已交付"二元化** | 只许写「已推送 / 已合入(main)」；**禁用"已交付"**。判据：`git merge-base --is-ancestor <sha> origin/main` | 关键时刻件 §十四 |
| **S-04** | **grep 结论分两层** | 命中 ≠ 生效。带 `\|\| true` 的调用是 **advisory 非阻断**；`ci.yml` 里的行号要实测（我写错过 :621，实为 :673） | K3 审计 2026-10-04 |
| **S-05** | **引用他人数字前必复核** | 含【我自己的旧测值】—— 带时间戳的实测值也会过期（AGENTS.md 里 49 个目录，真值 58） | K3 审计 2026-10-04 |
| **S-06** | **自曝归因是推断，优于"拿到结论"** | `synova-sentinel` 逐行 diff 推翻自己的归因并**主动撤回** ⇒ 这是判例级行为 | 产品线升级件（我采纳） |
| **S-07** | **撤回没有奖励，所以靠纪律不靠动机** | 检出自己错时，**必须回写**受影响的所有载体（文档/卡/PR 正文），不许只在对话里说 | CTO 升格 |
| **S-08** | **实验式更正优于推理式结论** | 2×2 隔离实验把"我以为的原因"与"真因"分开（产品线用它证明了"补机器写集块"才是解阻断主因，不是"glob→精确路径"） | 治理线 W4-A 复核 |

## 二、P 族 · 派单与配方（「派单方给的配方也要核」）

| # | 判例 | 判据 | 出处 |
|---|---|---|---|
| **P-01** | **派单方的配方同样要被执行方核** | 我给的 `cron_jobs.job_name` 列**不存在** ⇒ 执行方必须核配方，核出问题要报，不许照做 | 产品线升级件 |
| **P-02** | **写形态而非目的 = 派单缺陷** | 卡里写"怎么做"会挡住正确做法；应写【边界 + 判据 + 红线 + 上报条件】 | 产品线被纠正 ④（我的错） |
| **P-03** | **断言不变性检查（发单前必问）** | 「这条断言会在什么情况下**必然失败/必然通过**？」—— 我 7 次被纠正里，第 ⑤⑥ 两条判据在设计上恒不成立 | 产品线 ⑨-b |
| **P-04** | **不为让上级安心而做假动作** | 执行方【拒绝执行】我的多余防守建议（"5 卡全量声明"实测不需要），并说明为什么 —— 这是正确姿态 | 产品线（我采纳） |
| **P-05** | **验收卡不为"证明我们没有的东西存在"而写** | 卡应验证"做出来的东西对不对"，不是"证明某个虚空的东西不存在" | 产品线（我采纳） |
| **P-06** | **机器块优先：写集只由机器块表达** | 散文 Q2 不作判定源（D749 单一事实源）；机器块在场时散文写什么都不影响判定 | 治理线 2×2 实验 |
| **P-07** | **不许无界堆积**（DSH 原则 1：上限即纪律） | 队列/在飞任务必须有显式上限；超限第一动作是**退役**（关闭/合并/拒绝），不是攒着 | dsh-decision-lens ① |
| **P-08** | **先量，不先加机制**（DSH 原则四步之 1） | 拿机械指标说话（队列长度/behind/age/CI/谁在飞），再决定加什么 | dsh-decision-lens ② |
| **P-09** | **先修瓶颈，再加负载** | 瓶颈没解，不开新车道 —— 新车道只会让合并更慢 | dsh-decision-lens ② |
| **P-10** | **诊断不污染主路径**（DSH 原则 5） | 检查/协调做成旁路派生指标；只有"不拦就会真出事"的才进主路径门禁 | dsh-decision-lens ⑤ |

## 三、V 族 · 验证与验收（「做完没有」）

| # | 判例 | 判据 | 出处 |
|---|---|---|---|
| **V-01** | **L1 ≠ L2** | 静态可达（grep 命中/文件存在）不许报成真跑通 | 铁律 0-2 |
| **V-02** | **grep 型不得作验收依据** | 权威明文：「L3 静态检测准确率实测 3/5=60%，只能当粗筛」；「禁止 grep 命中」作验收 | 引用纪律:49 / 产品完成度总纲:194 |
| **V-03** | **自验不得由编码者兼任** | 复核方必须 fresh context、非作者 | 治理线 W4-A / D1143 |
| **V-04** | **禁止把"推送了"当"CI 绿"**；禁把"本地绿"当"CI 绿" | 判据：`gh pr checks <n> --json name,bucket` | L-039/040 |
| **V-05** | 🔴 **CI 快照必须等 check-runs 全部 completed** | 我报过"3 fail/2 pending 且 windows 从未 failure" —— 那是 run 未完结的**中间态**；终态 = 9 pass/4 fail/0 pending | K3 审计 2026-10-04 |
| **V-06** | **红名单与计数必须同源** | 取自两个时刻的 counts + 名单不可同时为真（我犯过） | 第 2 轮复核对 |
| **V-07** | **假绿要用"拔掉实现照样通过"来证伪** | D1143 自查：`not.toEqual` 会被 checkedAt 冒充通过 ⇒ 复核方独立复现"去掉归一化+拔消费者，断言照样通过" | D1143 回执 |
| **V-08** | **改坏即红（夹具判别性）** | 每条新判据必须给【构造得出来的反例】；造不出来的夹具 = 无效夹具 | 治理线纪律 |
| **V-09** | **无法核实项必须显式列出** | 不许把"未核"写成"已核" | K3/各线回执通用 |

## 四、M 族 · 机制与架构（「这样改对不对」）

| # | 判例 | 判据 | 出处 |
|---|---|---|---|
| **M-01** | **写集只由机器块表达**（同 P-06，机制面） | brief 的 Q2 只写逐条裸精确路径（无装饰符/通配符）；判定源只认机器块 | 治理线 |
| **M-02** | **三态退出码** | 0=通过／1=违规／**2=检查自身失败（同样阻断）**；禁 `\|\| true` 吞崩溃 | 治理线纪律 |
| **M-03** | **棘轮台账只减不增**；条目失效/过期即红 | 修好即须删除（`ci-red-baseline` 段头原文「须烧掉，不得长期依赖放行」） | ci-red-baseline.txt |
| **M-04** | **同一事实只许一处表达** | 匹配器族现 ≥4 机制/≥9 站点（fnmatch/字面锚定/集合成员/子串 grep）⇒ 「无单一事实源」= N3 病根同型 | 第 2 轮复核 |
| **M-05** | **运行期产物不进版本控制** | append-only + 多方并发 + 受版本控制 = 结构性冲突源；即便 union 驱动也只是"把冲突自动化" | #1026/#1030 |
| **M-06** | **GitHub 不执行 .gitattributes 自定义驱动** | 本地 `merge=union` 干净 ≠ GitHub 干净；服务端会判 DIRTY（推断，未取直接证据） | 本轮实测 |
| **M-07** | **借鉴边界** | DSH 是一能力一包互不共享文件 ⇒ advisory 写集够用；我们是单仓共享文件 ⇒ 必须保留**文件级互斥 + 串行合并** | dsh-decision-lens §四 |
| **M-08** | **问一句判据** | "如果两个 agent 同时改这个文件，坏不坏？"—— 坏 ⇒ 要物理互斥；不坏 ⇒ 可照抄 advisory | dsh-decision-lens §四 |
| **M-09** | **DSH 决策六原则** | ①上限即纪律 ②归属自有+可归因 ③只协调不干活 ④机械问题与业务语义分离 ⑤诊断不污染主路径 ⑥权威账本在 Lead | dsh-decision-lens §一 |

## 五、怎么用（三档处置，**不许直接问 CTO**）

```
遇到模糊时：
  A. 查本库           —— 有同类 ⇒ 照做（并在回执里注明"依 P-xx"）
  B. 无同类 ⇒ 按【最保守解释】做，并在 PR 正文显式标注：
       「此处我按 X 解释，代价 Y，若错请纠正」
  C. 上报 CTO（仅限）—— 当且仅当【答案会改变方案】时：
       必附：我倾向 X ｜ 代价 Y ｜ 需要你裁的是 Z
🔴 禁止的形态：「这个怎么办？」（无选项、无倾向、无代价）
```
