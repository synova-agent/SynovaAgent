# D1111 · 防跑偏机制

## 病根（不是态度问题）

前任台账的实际轨迹：`CTO-工作台.md` 72KB，自述「连续三版超限 **98→136→154**」，
治法是"加硬上限 + 拆分" ⇒ 总量仍达 ~3,500 行状态文档。
**根因：把"任务级"内容（在飞 PR、逐件交付、日报）混进了 CTO 台账。**

## 决策

**判据一句话**：**凡随「任务数」增长的一律不进台账；随「线数 × 窗数」增长的才留。**

三道机制：
1. **状态唯一入口** `coordination/CTO-状态台账.md`（≤60 行 · 重写式 · 四段：本窗锚/待裁/裁决/冷启动）
2. **6 条不变量** `scripts/control-tower/cto-drift-check.sh`（I1 膨胀 / I2 四段 / I3 三线锚齐 / I4 待裁有到期 / I5 冷启动 ≤14 天 / I6 不碰 `scripts/audit/**`）
3. **外部判据**（**未接线**）：C′1 锚齐备 / C′3 派单零痕迹 / C′6 线级收口齐收 —— 归 K3 或创始人

## 为什么不把台账放进 GitHub Projects

Projects 是**任务级视图**，放进去等于**把"随任务数增长"重新引入** ⇒ 重演病根。
GitHub 的正确用法：**Issues 记派单/回执**（PR 会关、Issue 不会）、**Milestones 记"窗"**、**Saved searches 当"待裁"自动源**。

## 未完成（不声称）

- C′1/C′3/C′6 **均未接线** ⇒ 机制 3 目前靠人；
- 自查脚本**只判格式与新鲜度，判不了"我有没有跑偏"** ⇒ 真判定必须在我之外。
