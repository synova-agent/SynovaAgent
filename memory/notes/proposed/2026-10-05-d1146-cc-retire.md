# D1146 · CC 退役 — hook 层 11 登记点 → 0

## 触发场景

创始人裁定「Claude Code 可退役，一律用 DSH 执行编码」（治理线 T2/批 1）。
CC 退役后，**写前拦截层（PreToolUse / PostToolUse / SessionStart hooks）失去唯一宿主**：
只在 CC 会话里点火，DSH 会话不消费 ⇒ 那 11 个 hook 登记点在当前组织形态下是**零效果执行点**。
写前拦截不另起机制：改由**提交端硬门禁**（pre-commit 13 组 + CI 12 必需 context）+ DSH 会话指令承担。

## 决定

1. **登记点归零（11 → 0）**：`.claude/settings.json` 的 `hooks` 段整段删除（5 个登记点）；
   `.codex/hooks.json` 整件退役（6 个登记点）。两条载体是 hook 层**唯一的点火口**。
2. **零执行方脚本删除**：`scripts/hooks/hook-session-start.sh`、`scripts/workflow/hook-post-tool-use.sh`
   —— 登记点删除后经 grep 实证零执行方、零活载体引用（除历史 plan/research 文档）。
3. **其余 hook 脚本不删**（本卡核配方后拒绝照删，判例 P-01）：
   | 脚本 | 不删理由（可复跑） |
   |---|---|
   | `scripts/hooks/hook-git-detect.sh` | `scripts/control-tower/incident-loop.py:308` 真 subprocess 执行；CI 已登记夹具 `tests/control-tower/incident-loop.test.sh:106` 真跑它 |
   | `scripts/hooks/hook-check-memory.sh` | CI 已登记夹具 `tests/control-tower/grep-oP-regression.test.sh:162` 从它**真解析**模式（文件不存在 ⇒ 断言红） |
   | `scripts/hooks/hook-git-guard.sh` | 被上述两个脚本 `source`（`hook-git-detect.sh:26` / `hook-check-memory.sh:16`），删则两脚本降级为 `\|\| true` 吞错 |
   | `scripts/hooks/hook-enforce-loop.sh`、`scripts/workflow/hook-block-write.sh`、`scripts/workflow/hook-check-task-scope.sh` | 被**写集外**载体引用（`CLAUDE.md:475/411/404`、`scripts/check-plan-integrity.sh:95`、`scripts/workflow/grep-refs.sh:9`）；单独删会在写集外制造**新**幽灵宣称——与判据③"幽灵宣称清零"的目的反向 |

## 考虑过的其他方案（及否决理由）

1. **一刀切删光 `scripts/hooks/hook-*.sh`**（卡里的"写形态"）⇒ 否决：`incident-loop.test.sh`
   与 `grep-oP-regression.test.sh` 是 **CI 已登记**夹具（`gate-integrity-baseline.txt` 之外，
   真在 `ci.yml` 的 `for t in` 密封清单里），删脚本 ⇒ `EXIT=127`/断言红 ⇒ 两个必需 context 红。
   而这两个夹具与 `incident-loop.py` 都在本卡**写集外** ⇒ 不可在本卡内修复。
2. **把 5 个写集外文档的幽灵宣称一并清零**（`CLAUDE.md:404`、`WORKLOG-20260616.md:83-124`、
   `docs/archive/v3/LOOP-ENGINEERING-V3-DEPLOYMENT.md`、`docs/archive/v3/LOOP-ENGINEERING-V3.0-设计文档-20260617.md`、
   `docs/synova/research/创始人控制塔系统-20260722/SYNOVA-RESEARCH-第一章-上下文注射器-v1-0-20260722.md`）
   ⇒ 否决（本卡内）：五者全在声明写集外；且后四个是**历史存档**——删改其正文等于篡改历史记录
   （正确处置是加"已退役"注记或另立文档卡，不是抹掉）。
3. **只清 hooks 段、不删任何脚本** ⇒ 否决：`hook-session-start.sh` / `hook-post-tool-use.sh`
   在登记点删除后经 grep 实证零执行方 ⇒ 属铁律 37「dead code 入仓库即违规」。

## 后果

- 好：11 个零效果执行点归零（产能健康口径的净减）；CC 语境下的"写前拦截必然生效"幻觉消除；
  幽灵载体（两个被文档宣称、实际**不存在**的 hook 脚本 —— 逐字命令与命中清单见本卡 PR 正文）
  在其**写集内主要载体**（`.codex/hooks.json`、`.claude/settings.json`、`AGENTS.md`）上清零。
- 坏 / 要长期承担：① 判据③**本卡只能做到 AGENTS.md 面清零**，全仓 *.md 仍有 5 个写集外载体
  （逐条见取消方案 2）⇒ 需另立文档卡或扩写集才能到 0；② 4 个 hook 脚本保留为"有活夹具的测试对象"
  （不再是运行时门禁），其命名沿用 `hook-` 前缀，语义上属历史遗留——正式改名/归档建议另立卡
  （涉及 `CLAUDE.md`、`scripts/control-tower/incident-loop.py`、两个 CI 夹具）。
- **代价显式化**（判例库 §五 B 档）：本卡按「登记点归零优先 + 脚本删除只做零风险子集」解释，
  代价 = 判据③不能全仓到 0、判据⑤删除清单短于派单预期；若错请纠正。
