# D1159 · 必需 context 变更顺序检查 — 放宽允许先行 / 收紧必须等 PR 合并后

- **状态**: proposed（新件；随 D1159 送 K3 → CTO 裁）
- **日期**: 2026-10-05
- **背景**: K3 门禁治理波次审计（报告 `2026-10-05-k3-审计报告-门禁治理波次-D1145-D1149.md`）
  §三 防线缺口收割第 4 行点出：**"branch protection 先于 PR 变更"没有任何对账门禁**；
  §总判定 #1077 把 `afde93eae` 的"保护先行 PATCH 到 9 而 PR 未合并"定性为**顺序风险**——
  受审变更落地前，共享基础设施的效果已生效。反方向更贵：**加**必需 context 若先于"产出该 check-run
  的 job"进 base，则未含该 job 的**在飞 PR 永远不上报该 check-run ⇒ 永久 blocked**（D971 同型 405）。
  既有 `check-required-contexts.py --api-check` 做**双向**差集 ⇒ 报得出"不一致"，报不出"允不允许"。
- **决定**:
  1. **判据（唯一判定轴）**: live（L，gh 只读 GET）⇄ base-ref 登记表（M，默认 `origin/main`）。
     `L ⊃ M` ⇒ **收紧先行 = 违规（exit 1）**，逐条点名 + 处置（先合并，再 PATCH live）；
     `L ⊆ M` ⇒ **OK（exit 0）**，其中 `M ∖ L` 逐条点名「放宽在途（合法）」。
     候选登记表（C，工作树）只作**信息级**打印 —— 判事实（L），不判意图（C）。
  2. **不对称是刻意的**: 放宽只丢一道防线（可回滚、不卡人）；收紧紧会让在飞 PR 集体卡死（只能人工解）
     ⇒ "松可先行、紧等合并"。
  3. **复用不重造**: live 取数（含 gh 缺失/超时/形状不符的降级）、登记表解析（schema/畸形即降级）、
     差集原语，全部按路径 import 自 `check-required-contexts.py`；测试用其既有 `SYNO_REQUIRED_CONTEXTS_GH`
     注入缝（零网络）。⇒ 同数据判决差异由夹具②物理锁住（本器 0 / peer 1）。
  4. **三态 0/1/2**，降级恒 2（gh 不可用 / base-ref 不可解析 / 登记表 0 条 / 复用面缺失）。
     **刻意不提供 `--allow-degraded`**：live 是唯一判定输入，取数不可用 = 无法判定，旗标只会造免检开关
     （D1111/收件修正口径）。
  5. **只读红线**: 无 `--method`/`-X`、无 PATCH/PUT/POST/DELETE；branch protection 变更权限不在本线。
- **考虑过的其他方案**:
  - **改 peer 的双向判据为方向性判据**：不选 —— 那是**改既有门禁语义**（既有多一条判红语义被削弱），
    且 peer 的"双向一致"本身是它存在的理由（job `name:` 漂移面）。并列新增一把方向轴，两者分工写死。
  - **把本器接进 pre-commit / pre-push**：不选 —— 本线红线（改既有门禁语义须 K3+CTO）；且这两个 hook
    在无网/无 admin 权限环境下会恒降级 exit 2（噪音）。首版 = 手工/PR 期可复跑检查。
  - **纳入 ci.yml 密封 canary 清单**：不选 —— 本卡不越域改 `ci.yml`；接线靠 `ct-test-gate.sh` 配对门禁
    （提交时真跑配对测试，已实测 `SYNC-OK`）。
- **影响**:
  - 新增一支只读检查（无执行方变更、无 job 结构变更、无 CI 改动）。
  - 真实例可复跑复现：`--base-ref 'afde93eae^'` ⇒ live=9 ⊂ M=12，逐条点名 3 条（两条 windows 腿 + npm audit），exit 0。
  - 当前态实测：live=9 == origin/main 登记表=9 ⇒ OK（#1077 放宽已合并，历史风险已闭合）。
