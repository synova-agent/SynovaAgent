### ② F2 红例基线耦合可变 main 状态 —— **已用 `--reverse` 去耦合**
- 病灶：`tests/control-tower/post-commit.test.sh:352` 的 `git log --format=%H -1 -S'D1157-REC-RE'` 取的是
  **最新**改动计数的提交。复核构造的**一次完全合法的注释编辑**（在同一文件里再提一次该串）会让
  `FIX_COMMIT` 重定位到**已锚定**的提交 ⇒ `❌ F2 前提失败` ⇒ **必需 context 对所有后续 PR 恒红**。
- **这是我自己引进去的新缺陷**（我为了修 F2 而引入 `git log -S` 动态定位）。
- **处置**：加 `--reverse` ⇒ 取**最初引入**该串的提交，后续注释编辑不再影响定位。
  实测：两版现取同一提交 `9e29d88e0`（= 引入锚定判据那个提交），但**只加 `--reverse` 的那版对后续编辑稳定**。
- 判例：**V-08**（夹具必须保判别力——方向是 fail-closed 红，不是假绿，故列建议级；但会造成**恒红**，故仍修）。

  ⇒ **我原先的兜底比产品契约更弱**，而注释却声称"不漏"。
- **处置**：① 收回过强声明（写明只覆盖**直接子进程**）；② 改「先组杀、失败再单杀」，与产品契约对齐。
- 另如实登记复核指出的两点**未消除的代价**（V-09：不写成"已解决"）：
  (a) 本兜底会**掩盖测试侧泄漏卫生**（调用方漏写 `stop()` 不再有症状）——
     减轻项：`D522 teardown` 段的 `assertDead/waitDead` 仍在**产品回收契约面**保有真断言；

## 追加：我自己在追账件里又造了一个 bug（第 8 轮实测抓出）

CI run `37442371264` 的 hermetic job：
```
❌ F2 取数失败: git show 9e29d88e…  # swallow-ok: … ^:scripts/hooks/post-commit.sh 无输出
结果: 31 通过, 1 失败
```
**根因**：我上一条把 `# swallow-ok:` 注在**闭合引号之前** ——
`FIX_COMMIT="$(… 2>/dev/null)  # swallow-ok: …"` 里的**闭合引号落在注释内部** ⇒ 字符串永不闭合
⇒ bash 把**后续行吞进字符串** ⇒ `FIX_COMMIT` 变成畸形 ref ⇒ `git show` 取数失败。
**修**：注释移到闭合引号**之外**。
**判据**：`bash -n` exit 0 ｜ `bash tests/control-tower/post-commit.test.sh` ⇒ **33 通过 / 0 失败**（F2 红例成立，基线 `9e29d88e0^` 正确取到）。
**教训**：给一行加注释这件事，我连着两次做错（一次是 `$VAR（` 吸收、一次是引号吞行）。
⇒ 这两次都不是判断错误，是**机械细节**；而现有门禁**抓不到**（本地 `bash -n` 只对**语法**，这里语法是合法的）。
`bash -n` 对"引号吞掉后续行"**返回 0** —— 即：**这类错只能靠真跑抓到**。已按此在提交前跑了该夹具。
