# #991 Q-12 · 会话事件数上限＋显式拒绝（四态 Note）

## 现状（改之前；数量一律给枚举命令，不手写）

- **无任何条数闸**（锚 `a12e621aa`）：
  ```bash
  grep -nE "MAX_SESSION_EVENTS|maxEvents|COUNT\(\*\)" src/store/session-store.ts   # 改前 0 命中
  ```
  `appendEvent` 只做两件事：`SELECT MAX(seq)` 取续写点 → `INSERT`，**不看总数**（`src/store/session-store.ts` `appendEvent`）。
- **既有 typed error 面**（可复用，不新增类）：`SessionEventError{code, phase:'validate'|'read', retryable:false}` 与 `SessionEventErrorCode` 联合，均为 #964 Q-7 交付。
- **既有 clamp 模板**（裁 219）：`src/agent/tool-loop-executor.ts` 的 `Math.min(10, Math.max(1, parseInt(env)||3))`。
- **存量分布**（选默认值的依据）：
  ```bash
  sqlite3 "file:/Users/wane/SynovaAgent/data/synova.db?mode=ro" \
    "SELECT COUNT(*), MAX(c) FROM (SELECT session_id, COUNT(*) c FROM session_events GROUP BY session_id);"
  # ⇒ 0 行 / NULL（本仓无存量会话事件，无实测分布可依）
  ```
- **同批已定性但本件不做**（裁 411）：并发工具调用（入口不存在，tool loop 是串行 `for`）／文件读取大小（`knowledge-injector.ts` 硬编码＋静默截断，另一张卡）／LLM 重试次数（属 #951 搬迁面）。

## 决定

1. **判据落在入口**：`appendEvent` 在拿到 `nextSeq` 之后、`INSERT` 之前判 `nextSeq > maxSessionEvents()` ⇒ **写库前拒单条**；会话与既有事件不受影响。
2. **typed error 原样抛**：`catch` 分支加 `if (err instanceof SessionEventError) throw err;` —— 不加这一行，上限错误会被折成 `{ok:false,degraded:true}`＝静默丢事件（Q-12 要治的正是这个形态）。
3. **上限可配且 clamp（裁 219 字面模板）**：`DEFAULT_MAX_SESSION_EVENTS = 20_000`／`MAX_SESSION_EVENTS_CEILING = 1_000_000`／`maxSessionEvents()` 逐调用读 env（可测试注入），实现与 `src/agent/tool-loop-executor.ts:183` **同形**：`Math.min(CEILING, Math.max(1, Number.parseInt(env ?? '', 10) || 默认))`。语义：`未配/非数/0` ⇒ 回落默认（不误配成"全放"或"全拒"）；**负数 ⇒ 下界 1**（显式全拒，见已知限制 4）；`> CEILING` ⇒ 夹到 CEILING。
4. **默认 20000 的理由**：本仓无存量分布（见上）⇒ 取「10 事件/日 × 5 年 ≈ 1.8 万」的保守上界；同时把异常追加挡在 2 万条（≈ 单会话 ≤ ~40MB @2KB/条）。
5. **与 STRICT 闸解耦**：`SYNO_SESSION_EVENT_STRICT=0` 只回滚词表/格式版本校验，**不回滚本上限**（两条闸独立，测试 Q12-7 钉住）。
6. **回滚**：无独立开关 ⇒ 单 commit revert（与 #964 Q-7 的回滚口径一致）。

## 生效时点

- **合并即生效**（默认 20000 条/会话）。对**已超限的存量会话**立即生效（补不进）——本仓当前无此类会话（见「现状」实测 0 行）。
- **回滚**：单 commit revert；无运行时开关。

## 已知限制

1. 额度按 **seq** 计（append-only 假设）：若发生物理删行，额度**不回收**。
2. 只做**单会话**上限，不做跨会话/跨租户配额，也不做轮转/归档/压缩（另立卡）。
3. 上限是"拒绝面"不是"容量规划"：它不告诉你 20000 够不够，只保证超过就**显式失败**。
4. **负数误配 ⇒ cap=1（显式全拒面，fail loud）**：`SYNO_MAX_SESSION_EVENTS=-5` 经裁 219 模板的 `Math.max(1, …)` 夹到下界 1 ⇒ 此后该进程每一次 `appendEvent` 都被拒并给可执行指引。这是**故意的 fail loud**：配错的闸比静默放宽更容易被发现（对应测试 Q12-6 的 `-5 ⇒ 1` 断言）。
