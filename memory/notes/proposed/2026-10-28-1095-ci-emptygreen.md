# #1095 / W4：CI **step 级**空绿判据（test_count / skipped）

- **状态**: proposed（待 L1 收口 ＋ K3 审计追认为 implemented）
- **日期**: 2026-10-28
- **批次**: 门禁治理 v2.0 · W4（单件）· 分支 `feat/1095-ci-emptygreen`（base `gitea/local-main` = `0569f2d4b`）
- **依据**: Issue #1095 ｜ 创始人 2026-10-10 明令「① 少 ② 快 ③ 可解释 ④ 硬上限」＋ 2026-10-11 裁决②（空绿必须分类）
- **生效时点**: 合入 `local-main` 后生效（CI ⑤ 步开始判；本地 pre-commit **不**接本判据）

## 一、缺陷（锚上实测，不是转述）

`.gitea/workflows/local-gates.yml` 的「③ 增量测试」步在 vitest 报
`No test files found, exiting with code 0` 时**恒绿**，而「本次 job 到底跑了几个测试」在 job 结束后
**没有任何机器判据**——只能靠人翻日志。既有 `ci-emptygreen-sim.sh` 补的是**第一层**（③ 步正文的分类
逻辑：变更集空／纯文档／不可测面 ⇒ 合法跳过；含代码面却零测试 ⇒ 红），但它是**沙箱复跑正文**，
判不了**真实 step 的结果**：

```
③ 步：No test files found, exiting with code 0   →  exit 0（绿）
④ 步（复现器）：只是"正文逻辑仍对"，与本次 job 跑了几个测试无关
⇒ 一个 PR 可以整条链零测试而全绿，且没有任何一处会红。
```

同族病根（本仓红线）：`scripts/control-tower/AGENTS.md`「信号量==0 ⇒ exit 2（禁把"看不见"当"没问题"）」——
旧链上「没有测试记录」这种情况连**判不了**都不是，它被当成"通过"。

## 二、决定

| 面 | 决定 |
|---|---|
| 判据载体 | 新增 `scripts/control-tower/check-ci-empty-green.sh`（薄判据，**不重跑测试**；三态 0/1/2） |
| 数据来源 | ③ 关键 step 末尾写**两处**：`$GITHUB_OUTPUT`（`test_count=<N>`，平台表达式可消费）＋ job 级结果记录 `${RUNNER_TEMP:-/tmp}/synova-ci-emptygreen-${GITHUB_RUN_ID:-local}.env`（末尾 ⑤ 汇总 step 消费） |
| 判据（5 条，无隐含分支） | ① `test_count>0` 且 `status=ran` ⇒ 计入**通过** ② `test_count=0` 且未声明 `skipped` ⇒ 🔴 异常空绿 ③ `skipped` 但**无未运行原因**（或 <6 字）⇒ 🔴 ④ `skipped` 且有原因 ⇒ ℹ️ **正当跳过·不计入通过** ⑤ 0 条记录／缺 `test_count` ⇒ **exit 2（判不了）** |
| 接线 | 文件**末尾**追加 ⑤ 汇总 step（`#910` 盘点表的 CI-S<n> 是位置派生 id ⇒ 只追加、不重编号）；**不引入 `always()`**（保持「① 先红后续不执行」语义） |
| 三态透传 | ⑤ 步 `set +e` 捕获 ＋ `exit $_EG_RC`（禁 `|| exit 1` 折叠，禁 #338「set -e 下子命令失败即退 ⇒ 整步零输出」） |
| 可观测（B6） | ⑤ 步把判据输出写入 `$GITHUB_STEP_SUMMARY`（CTO 在 job 摘要页直接看得到红因） |
| 不重造 | `ci-emptygreen-sim.sh`（正文逻辑）原样保留、零改动；本器只判**结果记录** |

## 三、判据（命令 ＋ 原始输出进 PR 正文）

- ① 配对测试 30/30（0 失败）——含**改坏即红**：把 `test_count>0` 判据改成 `-ge 0` ⇒ 空绿夹具 `rc 1→0`（原断言失效）
- ② `--selfcheck` 9/9（正常／空绿／跳过无原因／原因过短／正当跳过／缺 test_count／零记录／多记录／缺文件）
- ③ 接线：`grep -n 'check-ci-empty-green' .gitea/workflows/local-gates.yml` 非零（调用点在 416 行）
- ④ ①d 门禁本体自检（清单＋diff 豁免）`--changed-base gitea/local-main` ⇒ 0 失败（五条豁免逐条覆盖）
- ⑤ 既有空绿复现器语义未被改坏（③ 步分类分支文本与 rc 语义保持）

## 四、已知限制（禁写"暂无"）

- **KL-A 只判记录、不判真假**：本器信任 ③ 步写进来的 `test_count`；"测试真跑了"仍由 ③ 步自身＋
  `ci-emptygreen-sim.sh` 承担。本器**不能**证明测试没被桩掉。
- **KL-B 覆盖面收缩（有意）**：只判「已登记的关键 step」（当前＝③ 增量测试）。新增关键 step 必须同时改
  workflow 写入点，否则本器**看不见它**；`--env` 仅供人工单条复现，不是自动化入口。
- **KL-C 「正当跳过」的正当性靠声明**：本器只判"有没有原因、够不够长"，不判原因是否为真（文本真假不可机器判）。
- **KL-D `docs/authority/GATE-INVENTORY.yaml` 未补盘点行**：① 该表枚举 `local-gates.yml` 全部 step（C5 要求每步一行），
  本批新增 ⑤ 步 ⇒ 表缺一行 `CI-S13`；② `check-ci-empty-green.sh` 亦缺 `checkers:` 行。② 该表校验
  `quality-baseline.py --check-inventory` **当前无 CI／pre-commit 调用**（`memory/notes/proposed/2026-10-25-p2-975-gate-inventory.md` 实测），
  故本批不会因此变红；补行属 #975/#1089 盘点线（**不在本批写集**，越界即返工）⇒ **到期条件**：盘点表接进门禁链那批一并补两行。
- **KL-E 记录文件的并发假设**：缺 `$GITHUB_RUN_ID`（本机复现）时文件名退化为 `…-local.env`；同机并行两个 job 会混写。
  本 job 的 workspace 本就是固定路径（既有设计即假定串行）⇒ 不额外加锁，已知即不改。
- **KL-F Windows 上复现器不可用（平台既有，非本批引入）**：`ci-emptygreen-sim.sh` 的 vitest 桩在 Windows 的
  `npx` 解析下不被执行 ⇒ 该 harness 判 HARNESS-BROKEN。**基准对照**：对 `gitea/local-main` 原版 workflow 跑同一 harness，
  同样 `failures=8 / HARNESS-BROKEN`（本批前后**行为恒等**）；该 harness 的战场是 macOS CI。
- **KL-G 判据不覆盖 ①j 契约测试步**：①j 直接 `npx vitest run tests/contract/` 且未捕获输出，纳进来需改其输出语义（
  属"改既有 step"，本批明令禁止）⇒ 留作后续卡。
