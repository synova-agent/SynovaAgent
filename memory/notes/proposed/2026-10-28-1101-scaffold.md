## Q3: 验收（入口 → 交互 → 结果）

- 入口：`bash scripts/dev/new-file.sh --kind …`（或 `npm run new -- …`）。
- 交互：生成两件；头注 ≤12 行、三段齐、无 TBD、纯 LF；仓内 `src/**` 落点的配对件**镜像到 `tests/**`**
  （pre-commit 组 2b 的 `src/x.ts → tests/x.test.ts` 机械映射）。
- 结果：`bash tests/control-tower/new-file.test.sh` → 22 通过 / 0 失败；删 `@degraded` ⇒ 兜底段恰 1 处违规。

## 决定与理由

1. **为什么是"兜底"而不是"主闸"**：主闸是生成器（生成即合规，成本归零）；兜底段只负责
   「绕过生成器手写新文件」这条路。它不判契约质量 —— 判质量会变成"机器判散文"（A2 明确不做）。
2. **为什么判据对象只取"新增"（`--diff-filter=A`）**：存量文件无头注是历史事实，追溯会把整仓判红；
   本闸只对新文件负责（判据纪律 ⑨-①「禁自指、禁恰好出现的状态」）。
3. **为什么取 `git show :<path>` 而不是工作树**：判的必须是"这次真要提交的内容"，
   工作树可被后续编辑污染（同 `check-quality-delta.py` 的 `git show :<path>` 口径）。
4. **为什么空变更集"不触发"而不是 exit 2**：本段是**附加检查段**（无独立退出码），
   其"看不见"的形态是「本次没有新 src 文件」—— 有判据对象才判，是本闸语义的一部分；
   真正的"判不了"（取不到暂存内容）走 fail-closed 计违规，两者不混。
5. **为什么 component 模板不引 JSX/React**：零运行时绑定 ⇒ 生成件在任意环境可编译、可测；
   要用 JSX 由作者自己加 import 并同步改契约三段（模板里写死 React 会把脚手架绑到一个版本上）。
6. **为什么测试件镜像到 `tests/**`**：仓内约定 + pre-commit 组 2b 的机械映射就是
   `src/x.ts → tests/x.test.ts`；若把配对件写在 `src/` 旁，生成即红 ⇒ 与"成本归零"背道而驰。

## 已知限制（禁读成"已判契约"）

1. 兜底段只判**三段是否存在**，不判语义质量、不判是否落在头注 12 行内（后者是生成器/模板的约束，
   由 `tests/control-tower/new-file.test.sh` 的 G1c 守着）。
2. 兜底段只覆盖 `src/**`；`tests/`、`scripts/`、`extensions/` 的新文件不在其对象内。
3. 生成器**不替作者接线**：pre-commit 组 4 仍要求"新 export 在 src/ 有非测试引用"，
   生成件默认无人调用 ⇒ 生成后仍需作者补消费点（脚手架的正常状态，不是缺陷）。
4. 模板首期只有两类（component / module）；加类别 = 加一份模板 + 在 `build_case_block()` 加分支。
5. component 模板返回字符串（不引 JSX/React/DOM）；要 JSX 请自行改返回类型并同步契约。

## 失效条件（这条判据何时可撤）

- 当"新文件必须带三段契约"升级为 **tsc/ESLint 级判据**（能静态判字段存在性）时，
  本兜底段降级为回归锁；**不得无人接管即删**（V3.9：软机制被删等于从未存在）。
- 当仓内约定从 `src/x.ts → tests/x.test.ts` 改变时，镜像规则须同批更新（组 2b 是机械映射，会一起漂）。
