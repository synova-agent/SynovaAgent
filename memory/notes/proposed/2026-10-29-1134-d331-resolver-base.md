## 一、现状（做之前）

pre-push 的 D331 对账基自带 5 级 fallback（gitea/local-main → local-main → origin/local-main → origin/main → PUSH_REMOTE/PUSH_BRANCH），trunk 由 local-main 切到 main 后第 1 位冻结旧 trunk，对账范围扩到他人已过闸提交 ⇒ #1118/#1112/#1114 三次推送被拒。另：check-bypass-log.sh 缺失时打印“对账跳过 (fail-open)”即整条跳过。

## 二、决定（做了什么）

1. 对账基一律取 `scripts/control-tower/resolve-ci-base.sh` 的 stdout（D331 段零 trunk 字面）；
2. 判定体抽到 `scripts/control-tower/d331-bypass-gate.sh`（d331_gate），缺 resolver、缺判据脚本、基不可解析、对账失败四种情形一律返回 1（fail-closed）；
3. 台账：CT-check-bypass-log class P0 → P1，附 evidence / auditable / retired_after 备注；L4-1 tag 锚点为内联段、不占配额（卡面已定性）；
4. 夹具 7 组（F1–F4 裁定夹具 + fail-closed 两态 + 改坏即红）。

## 三、依据（为什么）

- 对账基的正确性依赖“trunk 是哪一个”，那是 resolver 的单一职责；pre-push 自算必漂移（本仓已第 5 次）。
- 防绕过的门禁不能因脚本被删/改名而整条跳过，否则删脚本比 --no-verify 更省事。
- 证据源 `.claude/bypass.log` 本机自写、K3 异机不可核 ⇒ F4 夹具显式证明“手写一行即通过”，故 P0 不成立。

## 四、生效时点

随本 PR 合入 main 生效；回滚 = 取回 pre-push D331 旧块。未做项：run_by 建账补 pre-push 腿——main 上 `run_by:` 段尚不存在（依赖 #1120 合入），已在 PR 与回报中列为阻塞。
