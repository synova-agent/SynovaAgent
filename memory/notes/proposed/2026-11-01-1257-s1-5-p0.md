# #1257 S1.5 P0 快修：cron 单飞/失败终态、tool_call 配对、备份快照一致

批次：#1257（S1.5 运行时 P0 快修）｜锚 `5550eb95b`｜PR base = `main`｜写集 15 件（`tests/contract/time-injection.test.ts` 收缩不改）＋ 1 件 CTO 批准扩张（`src/agent/diagnosis-launcher.ts`）

## 1 现状与触发（三条都是**当前在跑**的缺陷）

1 **P0-3a 单 job 可重入**（`src/cron/scheduler.ts`）：`runJob` fire-and-forget（`scheduler.ts:484`，未 await）；`minNext` 用未更新的 `job.nextRun`（`:486`）⇒ 到点任务的 `delay` 恒 1000ms（`:489`）；`nextRun` 只在 handler 结束后更新（`:502`/`:511`）⇒ **handler >1s 的 job 被下一 tick 重复启动**。
2 **P0-3b 失败无分类/无终态**（同文件）：`lastError` 是纯 string（`:509`）、`nextRun = +60000` 固定（`:511`）、`cron_jobs` 无 `disabled`/`attempts`/`next_run` 列（`:253-266`）⇒ 失败既不可分类、也不会停。
3 **P0-2a 事实层不可检出悬空调用**（`src/store/session-store.ts`）：`event_type` CHECK 白名单三处真源都无 `tool_call`（`:153-160`／基础 `CREATE TABLE`／表重建内 CHECK）；`tool-loop-executor.ts` 只写 `tool_result` ⇒ 「有 call 无 result」在事实层不可见。
4 **P0-6 备份漏 WAL**（`src/services/db-encryption.ts`）：`backupDatabase` 同步函数（原 `:175`），内部 `fs.readFileSync`／`fs.copyFileSync` 读**活库** ⇒ WAL 已提交但未 checkpoint 的行不进备份（快照不一致）。

## 2 决策与理由（逐条；数字/落点可核）

### 2.1 cron 单飞 = 进程内语义（§1.1）
- 决策：`CronJob` 增 `inFlight`，tick 内 `disabled` 跳过、`inFlight` 跳过并 `log.warn`，`inFlight` 在 **`finally` 复位**（异常路径同样复位）。
- 理由：不改调度模型、不加锁、不动 `nextCronTime`/D94 事件面；**进程内**是明确边界（跨进程归 S2／§4-1）。若 `inFlight` 不在 finally 复位，一次异常会把 job 永久卡死（比原缺陷更糟）。
- 另修 delay 恒 1000ms：派发时立刻把 `nextRun` 推进到 `nextCronTime()`，成功路径不再二次写 `nextRun`，失败路径才用退避覆盖。

### 2.2 失败分类 + 有界退避 + 终态禁用（§1.2）
- 决策：失败带 `code`（复用 `@synova/error-types`）；**无码按可重试**（哨兵 handler 抛普通 Error，若「无码即不可重试」会把 7×24 哨兵一次打死）；**只有显式不可重试码**才一次失败即 `disabled=1`；可重试退避 `min(30s·2^(attempts-1), 30min)`；`attempts >= MAX_ATTEMPTS(=5)` ⇒ `disabled=1`。
- 耐久三件：`cron_jobs` 增 `last_error_code TEXT`/`attempts INTEGER DEFAULT 0`/`disabled INTEGER DEFAULT 0`（迁移复用既有 `try ALTER … catch log.warn` 范式）；`persistRun()` 落三列、`restoreJobs()` 恢复三列；**`schedule()` 按 `name` 认领既有行**（命中则 UPDATE，绝不新插）——否则重启后用新 id 新建行（默认 `disabled=0`）会把终态复活。
- `disabled` 下游语义：tick 排除、`listJobs()` 保留、**self-check 连续失败统计排除**（`src/sentinel/runner.ts:468-475` 数据源加 `.filter(j => !j.disabled)`，1 行）。

### 2.3 tool_call 是**列**不是 payload 字段（§1.3）
- 决策：① `SESSION_EVENT_TYPES`＋基础 `CREATE TABLE` CHECK＋表重建内 CHECK **三处同步**加 `'tool_call'`；② `session_events` 新增**可空列** `source_event_seq INTEGER`（**两路都做**：基础建表同列 ＋ `PRAGMA table_info` 判缺 `ALTER TABLE ADD COLUMN`，顺序在表重建之前）；③ `SESSION_EVENT_FORMAT_VERSION` 1→2；④ 表重建门 `!tpl.sql.includes('diagnosis_phase')` → `!tpl.sql.includes('tool_call')`，重建内 `CREATE` 与 `INSERT SELECT` 都带该列；⑤ 迁移 catch 改 fail-closed：**只对 CHECK/数据完整性错误 rethrow**，`SQLITE_BUSY/LOCKED` 走既有重试（否则 Phase 0 `fatal:true` 直接启动中止）；⑥ 新增只读 `listUnclosedToolCalls()`：`tool_call LEFT JOIN tool_result ON source_event_seq = call.seq`，取 `result IS NULL`。
- 理由：列是**事实**（可索引、可 JOIN、可独立于 payload 演进）；payload 字段会随投影/序列化漂移，且「悬空调用可检出」需要 JOIN 能力。`appendEvent` 保持 3 参（见 §3-实测①），来源 seq 经 payload **保留键** `SOURCE_EVENT_SEQ_KEY` 传入，落库前剥离 ⇒ `payload_json` 不残留。

### 2.4 备份快照归 SQLite、加密归应用层（§1.4）
- 决策：`backupDatabase` **保持同步签名**（调用方 `src/deploy/bootstrap.ts:1301-1310` 零改动）；快照用只读连接 ＋ `db.prepare('VACUUM INTO ?').run(tmpPath)`（`finally db.close()`）；中间件名 `.tmp-backup-<ts>.db`（**不以 `synova-backup-` 开头** ⇒ 剪枝 `startsWith('synova-backup-')` 天然不计入 `maxBackups`）；`integrity_check` 在**加密前**对中间件跑；加密分支对中间件整文件读入加密（沿用既有 `[IV:12][authTag:16][ciphertext]` 与 `scrypt(masterSecret, salt + '-backup')` 口径），**中间明文 `try/finally` 必删**；非加密分支中间件直接 rename 为最终备份名；两分支都不再读活库字节。
- 理由：`VACUUM INTO` 是单条同步语句，天然把 WAL 已提交事务纳入快照且产物自包含（`journal_mode=delete`）；`exec()` **不支持参数绑定**（实测报 `SQLITE_ERROR: non-text filename`）⇒ 必须 `prepare + run`。备份仍是「整文件进内存」加密（§4-4），不引入 async、不扩写集。
- 安全加固（本批新增）：`encryptBackups:true` 但缺 `masterSecret`/`salt` ⇒ **直接失败**（`BACKUP_ENCRYPT_FAILED`），禁静默回落明文备份——否则生产密钥缺失会把全库明文留在备份目录。

### 2.5 时间可注入：计数预算不动（§十-4）
- 决策：不新增 `Date.now()`/`new Date()` 直取，也**不改** `tests/contract/time-injection.test.ts` 的冻结清单；实现压在各文件既有计数预算内（`scheduler.ts` 6/4、`session-store.ts` 1/5、`tool-loop-executor.ts` 4/4、`db-encryption.ts` 0/1、`runner.ts` 13/15）。
- 理由：该测试是**存量债棘轮**（增⇒红、减⇒红），改值属 A 类基线动作，归 CTO；本批只复用既有直取（如 `db-encryption.ts` 既有的那一处时间戳同时用于临时件名与最终备份名）。

## 3 已知限制（规范 §4 ＋ 本批实测补充；禁读成「已解决」）

- **§4-1 单飞是进程内**：多进程共库不保证跨进程单飞（S2 处理）。
- **§4-3 格式版本 bump 的代价**：旧构建读新库会 `EVENT_FORMAT_TOO_NEW`（拒读，非静默）——**有意的 fail-closed**；回滚＝回退旧二进制且**不得**读新库。
- **§4-7 bump 的爆炸半径**：旧构建读到**任一行 v2** ⇒ `getEvents` 遇首个 v2 行即抛 ⇒ **整个会话连 `message` 行都读不了**（不只 `tool_call`）；逃生阀 `SYNO_SESSION_EVENT_STRICT=0`（旧构建同样有）。已知限制，非缺陷。
- **§4-6 迁移失败 ⇒ 启动中止**：`initSchema` 抛错 = Phase 0 `fatal:true` ⇒ 启动失败；本批只对 CHECK/数据完整性 rethrow，`SQLITE_BUSY/LOCKED` 走既有重试；处置＝回退旧二进制或手工移除迁移门后重启。
- **§4-8 `disabled` 无自动复活**：本批不提供 re-enable（S2 管理面）；生产上被 disabled 的 job 需人工解除。
- **实测①（本批新增）**：`source_event_seq` 的原型级订阅缝 `session-projection.ts:387-395` 是 **3 参**形状、生产必安装 ⇒ 不可加第 4 参；采用「payload 保留键传输 → 落列 → 落盘前剥离」。若日后批准扩写集（改缝），可改回显式第 4 参。
- **实测②（本批新增）**：`src/agent/diagnosis-launcher.ts` 的 `SessionStoreLike.appendEvent` 内联联合是事件词表的**第二处字面镜像**（`type` 别名不可声明合并，`engine-context.ts:59` 使用它）⇒ 本批 CTO 批准 +`'tool_call'` 1 行；转 type-only（import `SessionEventType`）需另裁（会推翻该文件「内联以避免 L2→L5 import」的既有设计决定）。
- **本批另注**：备份仍同步阻塞调用线程（大库期间事件循环被占）；加密分支整文件进内存（§4-4，未优化）；`maxBackups` 按文件名排序，同毫秒两次备份会同名覆盖（cron 每日一次不受影响）。
