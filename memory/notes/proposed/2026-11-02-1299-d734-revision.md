## 一、为什么改：件数是代理指标，不是真问题

D721/D734 的事故共因是「**大 PR + 长存活分支 ⇒ 冲突面与验收面都无法收口**」。但「件数 > 12」只是这件事的
**代理指标**：一个 13 件的纯文档 PR 无害，一个 8 件的跨域 PR 却能把两条腿搅在一起。
把代理指标当硬闸门的结果是：**该拦的拦不住，不该拦的天天拦**（实测：一次 skills 改动 20 件被拦，
但真正的跨域改动只有 8 件反而放行）。

## 二、改法

| 判据 | 旧 | 新 | 理由 |
|---|---|---|---|
| ① 件数 MAX_FILES | 硬阻断 | **软提示**（`SOFT_HINT` 计数，不置 FAILED） | 代理指标只做提示 |
| ② 跨域 | 信息性（不阻断） | **硬阻断**（复用 `check-ownership.py`） | 跨域才是真冲突面 |
| ④ 分段计划表 | 无 | **>12 件时硬判据**：五列齐全＋件数合计=变更数＋base 为 sha | 把"能不能分段验收"变成可机器判的事 |

**跨域硬阻断与 2026-09-29「域不用于分配/阻断」的关系**（必须写清，防误读为推翻旧裁定）：
那条解的是「**按域分配任务**会把门禁拉扯散」；本条只管「**跨域合并**」这一件事，不产生域路由、不用于分配。
撤销办法：删 `check-pr-budget.sh` 的 ② 块并改契约注释（一次提案即可）。

## 三、四项实证缺陷

1. **#1289 gate 绿 ≠ 全量绿**：GATE-STANDARD §十二 新增 **10b** —— 每关交付判据＝「全量 vs 基线并集，新红=0」，
   附复跑命令；**不新增必跑面**（成本取向）。
2. **#1295 D331 记录按 worktree 隔离**：`bypass-ledger.sh` 落点改用 `git rev-parse --path-format=absolute --git-common-dir`
   的上一级（主仓根）⇒ 所有 worktree 共用 `.sessions/`，搬提交后 push 不需复制 `.sessions` 或手补继承行。
3. **铁律 47 裸词误伤**：`pre-commit-check.sh` 的「已拆/已迁移/已清理」原按裸词判"完成声称"⇒ claim 写"已拆卡"被误伤。
   现要求**同现 `engine-core` 或 `packages/`** 才算。
4. **豁免成本**：`.dsh/skills/**`、`.synova/skills/**` 改**自动豁免**（条件：提交信息含「提案」或「裁定」＋ `#<Issue>`），
   仍留痕、不再手写豁免件+排队（实测一次改动要 20–55 min 排队）。

## 四、附带修复：`check-ownership.py` 在 Windows 每次必崩

`subprocess.run(..., text=True)` 在 Windows 用本地编码（cp936）解码 UTF-8 输出 ⇒ reader 线程抛
`UnicodeDecodeError` ⇒ `p.stdout = None` ⇒ `AttributeError`。**实测本机每次调用都崩**，
于是"跨域判定"永远退化为"判不了"（静默降级，谁也没发现）。
修法：显式 `encoding="utf-8", errors="replace"`。

## 五、已知限制

1. 分段计划表的**路径覆盖**只校验"件数合计=变更数"，不校验"每段路径确实覆盖对应文件"（后者需 glob 求交，另批）。
2. `check-ownership.py` 修好后，本仓只有 **1 个** `.synova-owner`（maintainer）⇒ 跨域在本仓**永不触发**；
   拦截能力用**沙箱双域仓**验证（见验收 #2）。
3. 跨域判定依赖 python + 校验器；缺失时**判不了 ⇒ 软提示**（不当通过，也不误红）。
4. `--segment-file` 的默认查找链：`--segment-file` → `$SYNO_SEGMENT_PLAN_FILE` → `.claude/pr-segment-plan.md`。

## 七、附带（A 类·创始人 2026-11-02 当批批准）：CT-40 基线容差

**问题（实测）**：在干净 worktree `d0ad5f5e9`（未含本批任何改动）跑同一批配对测试：
- `bypass-ledger` 3 项红｜`check-ownership` 4 项红｜`check-pr-budget` 超时 rc=124（421s）＋2 项红

⇒ CT-40 没有基线容差 ⇒ **任何人对这 3 个脚本做任何修改都会被历史红挡住**（这些脚本事实上不可维护）。

**做法**：`ct-test-gate.sh` 读 `tests/control-tower/.ct40-baseline`（每行一个**精确测试名**）：
命中基线 ⇒ ⚠️ 告警不阻断；**未命中 ⇒ 新红阻断**。反绕过：不支持通配；新增条目须在 PR 正文附基线红的原始输出。

**已知限制**：基线只防"历史红挡住新改动"，不防"新红被误登记"——后者靠 PR 评审（正文须附证据）。
